# Полевой протокол v1

[Сохранённые запросы первого клиента](client-v1.json) фиксируют методы, пути, HTTP-коды и JSON на проводе. Четыре постоянные операции сохраняют форму при выпуске следующих версий. Сейчас хост обслуживает `info` и `ping`. Обработчики `join` и `refresh` поставляет MOB-02.

| Операция | Условия и смысл |
|---|---|
| `GET /api/field/info` | До ввода приглашения, без учётных данных. Клиент запоминает окончательный адрес ответа по правилам MOB-11/12 и показывает организацию до передачи кода. |
| `GET /api/field/ping` | Анонимная проверка доступности Work. Значение `ok: true` подтверждает получение ответа сервера. Контакт конкретного устройства регистрирует отдельная операция обмена. |
| `POST /api/field/join` | Одноразовый код передаётся строкой в теле JSON. Сотрудника определяет приглашение. Просроченный, неизвестный или использованный код даёт `invitation-invalid`. |
| `POST /api/field/refresh` | Строка refresh-токена в теле JSON. В ограниченном окне повтора та же сессия получает результат ротации при потере ответа. Полностью отозванное устройство получает `device-revoked`. |

Все показанные поля обязательны. `organizationName` — публичное имя организации. `logoUrl` — корневой относительный адрес изображения на том же сервере или JSON `null`, когда логотип отсутствует. `protocolVersions` — массив целых номеров поддерживаемого протокола. `minimumSenderVersionCode` — минимальный целый Android versionCode для записи отчётов, начиная с 1. Версии отправителя и протокола имеют разный смысл. Проверку версии при записи реализует MOB-03.

Ответы подключения и обновления содержат UUID устройства и сотрудника, непустые непрозрачные строки токенов и момент истечения access-токена `expiresAt` (RFC 3339, UTC). Для этих операций не нужны офисные полномочия. Полевой access-токен применяется к явно указанным операциям устройства. Секреты передаются в теле запроса или заголовке авторизации.

По решению владельца от 28.11.2026 имя для подтверждения подключения берётся из настройки названия приложения. На чистом экземпляре клиент увидит штатное имя `BHS.CRG`. Снимок содержит оба примера.

Отказ протокола содержит отдельную строку `reason`. Код HTTP и значение причины вместе определяют результат. Текст для монтажника выбирает приложение. Отсутствие сети, недоступность сервера и ошибка проверки сертификата определяются транспортом. Отказ записи устаревшему приложению имеет причину `client-outdated`; локальная очередь сохраняется.

Обмен предметными данными располагается под `/api/field/v1/`. Совместимое расширение добавляет необязательные поля запроса, поля ответа, которые старый клиент может пропустить, или новые операции. Обязательность, JSON-типы, прежние коды HTTP, значения причин и смысл прежних полей сохраняются. Несовместимый обмен получает новый версионный префикс.

Для выделенного имени полевого сервера используйте [пример внешнего nginx](../../deploy/field-proxy.conf.example). Он публикует `/api/field/` и файлы поставки под `/m/`. Настройка исходящего прокси экземпляра относится к внешним сервисам и на этот вход не влияет.

Выключенный Work отвечает под обоими префиксами API модуля HTTP 501 с `reason: "module-disabled"`, `module: "work"` и пояснением `error`. Отсутствующий файл в `/m/` даёт HTTP 404.

Сведения и логотип имеют общий для них лимит по адресу клиента. Он использует значение `RateLimits:Branding` и расходуется независимо от офисного оформления. При превышении сервер возвращает HTTP 429 с `reason: "rate-limited"`.

Для проверки внешней публикации запустите `python deploy/field-proxy.tests.py <порт-тестового-API>` с Docker. Скрипт поднимает обе конфигурации nginx, воспроизводит запросы клиента и проверяет выдачу файла. Для экземпляра с выключенным Work добавьте `--work-disabled`.
