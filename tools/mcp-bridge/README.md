# Мост MCP для BHS.CRG

Подключает MCP-клиента (Claude Desktop и т.п.) к MCP-серверу приложения.

## Зачем он нужен

MCP-сервер приложения живёт по HTTP и требует JWT, а access-токен действует **60 минут**
(`Jwt:AccessTokenMinutes`, продление задумано через refresh). Статичный заголовок `Authorization` в
конфиге клиента обновляться не умеет — токен пришлось бы перевставлять руками каждый час.

Мост логинится сам и держит токен свежим: в конфиге остаются только адрес и учётные данные.

## Настройка

`%APPDATA%\Claude\claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "bhs-crg": {
      "command": "node",
      "args": ["E:\\Development\\Office\\BHS.CRG\\tools\\mcp-bridge\\bridge.mjs"],
      "env": {
        "BHS_URL": "http://localhost:5000",
        "BHS_EMAIL": "admin@bhs.local",
        "BHS_PASSWORD": "Demo12345!"
      }
    }
  }
}
```

| Переменная | Назначение |
|---|---|
| `BHS_URL` | Адрес приложения; по умолчанию `http://localhost:5000` |
| `BHS_EMAIL` | Учётная запись, **от имени которой** работает агент |
| `BHS_PASSWORD` | Пароль этой учётной записи |

Агент получает ровно те права, что и указанный пользователь. Отдельной модели доступа для MCP нет,
поэтому для агента разумно завести собственную учётную запись, а не отдавать администраторскую.

Требуется Node 18+ (нужен встроенный `fetch`).

## Проверка без клиента

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"p","version":"1"}}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_datasets","arguments":{}}}' \
| BHS_EMAIL=admin@bhs.local BHS_PASSWORD=Demo12345! node tools/mcp-bridge/bridge.mjs
```

Диагностика идёт в stderr, протокол — в stdout (иначе клиент получил бы мусор вместо JSON-RPC).

## Поведение

- **Токен**: срок берётся из самого JWT; обновление за 5 минут до истечения, плюс один повтор входа
  при ответе `401` (токен могли отозвать досрочно).
- **Порядок**: сообщения обрабатываются строго последовательно — идентификатор сессии приходит с
  ответом на `initialize`, и при параллельной отправке следующий запрос ушёл бы без него.
- **Завершение**: при закрытии stdin мост дожидается незаконченных запросов. `process.exit()`
  намеренно не вызывается — на Windows выход прямо из обработчика закрытия роняет внутреннюю
  проверку libuv.
- **Ошибки**: недоступное приложение или ответ с ошибкой превращаются в JSON-RPC-ошибку с понятным
  текстом, а не в обрыв соединения.

## Что доступно агенту

Только чтение: `list_datasets`, `get_dataset`, `get_source`, `get_rows` плюс ресурсы
`bhs://dataset/{id}` и `bhs://source/{id}`. Инструментов записи нет.
Подробности — `src/server/BHS.CRG.Api/Mcp/README.md`.

## Перезапуск приложения

Мост переживает перезапуск BHS.CRG **сам**, без перезапуска клиента (issue #438): запоминает
рукопожатие, а получив «сессия не принята», здоровается заново и повторяет запрос один раз.

Без этого мёртвый идентификатор сессии отравлял бы мост навсегда — повторные попытки агента идут
через тот же мост и упираются в то же состояние. Для агента это выглядит так, будто инструментов не
стало вовсе: было 15, стало 0.

Повтор строго один: бесконечные попытки превратили бы недоступное приложение в зависший вызов, а
агенту полезнее быстрый внятный отказ («BHS.CRG недоступен на …»), чем «fetch failed».

Проверка:

```
BHS_EMAIL=… BHS_PASSWORD=… node tools/mcp-bridge/restart-check.mjs
```

Скрипт поднимает мост, гасит приложение, убеждается во внятности отказа, поднимает приложение обратно
и требует, чтобы ТОТ ЖЕ мост снова отдал полный список инструментов.
