# Design: индикатор состояния счёта

Общая архитектура — `../costs-invoice-screen-00-epic/design.md`: D3 (индикатор, уровни, пункт, banner), D4
(факты от сервера), D8 (компоненты MD3), D10.3 (доказательство). Требования — `specs/costs/spec.md`.

## Context

- **Источники сообщений.** У Архитектора их 34 (`architect-invoice-ux-logic.md` §5), у Дизайнера — 54 вида
  на экране (`designer-invoice-screen.md` §3).
  - Из одного ответа `GET /api/costs/invoices/{id}` собираются 1–14, 20 и 34 по Архитектору.
  - Ещё три соседних адреса форма уже читает: распознавание (`GET …/recognition`), подсказки запомненного
    (`POST /api/costs/supplier-matches/suggestions`) и вид для чтения.
  - Остальное — состояние формы: несохранённое, «изменили» своей части из `useDraftBase`, отказ
    справочника организаций.
- **Готовность** считает только сервер (`InvoiceReadiness.cs`). Клиент её не дублирует нарочно
  (`invoiceReadiness.ts:3-10`), и разметку «мешает чему» он вести не вправе: это был бы второй список
  правил. Её даёт ребёнок 02 вместе с «просрочен» и «кто и когда изменил».
- **Макет:** `mock/sheet0.js` (раздел 3.1), `mock/var-c.js` (`POP_S2` — пример перечня),
  `mock/md3x.js` (боковой лист «Состояние счёта»).
- **После 10** у сводки есть слот индикатора. Плашки стоят в прокрутке (10, D-10.9): однострочные — над
  частями, остальные — между «Кто и сколько» и «Строками».

## Goals / Non-Goals

**Goals:** одно место для сообщений; число в индикаторе равно числу пунктов; каждое расхождение — один
раз; в форме не больше одного banner.

**Non-Goals:**
- список и строки списка (чипы, ✦N, «просрочен» в строке) — не трогаются;
- снэкбары — `sharedui-md3-12`;
- окна (оплата, исправление) — их сообщения остаются в окнах;
- панель файла — её состояния («Строим вид для чтения…», «показать нечем») остаются в ней;
- носитель записи — рядом с индикатором, но это 10 и 12;
- новые правила на клиенте.

## Decisions

### D-11.1. Сборка пунктов — чистая функция

```
statusOf(input) → { level, count, phrase, items: StatusItem[] }
input  = { view, recognition, suggestions, form: { unsaved, saving, savedAt, stalePart,
           orgsFailed, rereadFailed, gone, hiddenByFilter, canEdit, canPay } }
StatusItem = { key, level, text, blocks?: ('parsed'|'pay')[], action?, place?: { part, field?, line? } }
```

- Живёт в `features/costs/invoiceStatus.ts`, unit-тест — `invoiceStatus.test.ts` по образцу
  `invoiceReadiness.test.ts`. React и запросов в ней нет: всё, что приходит, приходит аргументом.
- **Слияние одного расхождения.** Пункт готовности `total`, `payment.refusal` про ту же сумму и
  расхождение полосы сверки дают **один** пункт с `blocks: ['parsed','pay']`. Пометку `blocks` у пункта
  готовности даёт сервер (ребёнок 02). Клиент только склеивает отказ в оплате с пунктом, к которому сервер
  его привязал, и не сравнивает тексты.
- **`null` и `[]`.** `readiness == null` (разобран, отклонён, заперт) — пунктов готовности нет и фразы
  «Готов к «Разобран»» нет. `[]` у черновика — фраза «Готов к «Разобран»», тон «успех».
- **Фраза:**

  | Положение | Фраза |
  |---|---|
  | есть «Мешает работе» | имя худшего пункта: «Не распознан», «Счёт удалён» |
  | иначе, число > 0 | «N замечаний» |
  | иначе, распознаётся | «Распознаётся… 40 %» |
  | иначе | «Готов к «Разобран»» или «Просрочен», а у разобранного без пунктов — пусто, только точка |

- **Порядок пунктов:** по уровню, внутри уровня — по месту в форме (часть, затем строка).

### D-11.3. Индикатор и лист — из MD3, обёртки экрана

- **`InvoiceStatusIndicator.tsx`** — кнопка-пилюля:
  - точка 8 px роли тона и фраза `label-large`;
  - `Tooltip` из 12 MD3 — краткое: «6 замечаний — расхождение суммы, 2 строки без позиции… Щёлкните — весь
    перечень»;
  - `aria-live="polite"` на обёртке, объявляет смену `level` и фразы, а не состав.
- **`InvoiceStatusSheet.tsx`** — `SideSheet` (modal, ≤ 400 px) из 13 MD3, на узком экране — `BottomSheet`.
  - Заголовок «Состояние счёта», подзаголовок «N замечаний · по сохранённому · 12:04».
  - Группы по уровню. Пункт — ведущий знак, текст, пометки `StatusText` («мешает: оплата»), одно
    text-действие.
- **Banner** — `Banner` из 12 MD3, первым в прокрутке, над частями.
- **Переход к месту** — общий `goTo(place)` формы: раскрыть часть, прокрутить, сфокусировать. Он уже есть у
  строки готовности (`goTo`), расширяется на часть и строку. Лист закрывается, фокус уходит на место.
- **Пункты без права** — как решил владелец для готовности (`invoiceReadiness.ts:63-67`): видны, не ведут.

### D-11.4. Метка «со скана» в поле

`InvoiceFieldScan.tsx` вместо `ring-warning-border` и двухстрочной подсказки ставит в поле trailing-знак 20
px роли предупреждения с `Tooltip` «Со скана, не проверено. Правка снимает метку». Подпись поля для
диктора дополняется «(со скана, не проверено)». Высота поля не меняется — это и есть выигрыш в ~36 px на
поле.

### D-11.5. Два PR

1. **Индикатор и счёт целиком** — `statusOf`, индикатор, лист, banner, уход плашек 1–21, 35, 38, 42–44,
   47–48.
2. **Поля и сверка** — метка в поле (25), отгрузка (32), метки вне блоков (46), фраза полосы сверки (41),
   режим НДС со скана (36). Правило `notice-plaque` по `features/costs` опускается до нуля.

Первый PR без второго ничего не удваивает: сообщения у полей он не трогает, а плашки, которые убирает,
уходят целиком.

## Risks / Trade-offs

- [Сообщение «потеряется» при переносе] → таблица D-11.2 — чек-лист PR. Unit-тест перебирает все виды
  пунктов готовности сервера (`gap.kind`) и падает на неизвестном, а не молчит.
- [Индикатор начнёт врать о несохранённом] → подзаголовок «по сохранённому · время»; «Разобран» не
  включается, пока запись в пути (D3).
- [Факты 02 не слиты] → 11 зависит от 02 по зонтику. Без «мешает чему» склейка расхождения невозможна без
  второго списка правил на клиенте — это отказ начинать, а не обход.
- [Боковой лист закрывает часть формы на 1024] → лист modal, со scrim. Переход к месту закрывает его.
- [Важное спрятано за щелчком] → banner у «Мешает работе», число и тон всегда видны в сводке; «Разобран»
  и «Отметить оплату…» объясняют неактивность подсказкой.

## Migration Plan

Два PR, оба `version:minor`, порядок D-11.5. Сервер не меняется. Откат — revert PR: плашки возвращаются.
