# Design: правка строк во время их записи не теряется

## Context

Мотивация — proposal.md. Сейчас:

- `InvoiceLinesTable.save()` → `base.save(seen => replace.mutateAsync({ lines: toPayload(drafts) }))`;
  после ответа `setDrafts(toDrafts(saved.lines))`, `setDirty(false)`.
- `useInvoiceWrite.onSuccess` кладёт ответ в кэш (`setQueryData`) — вид счёта на экране сразу
  получает новую версию и новую подпись строк (`linesSignature`: id новых строк, досчитанные суммы).
- `useDraftBase` / `stepBase`: версия новая, подпись другая, `dirty` — `stale`; не `dirty` — `rebuild`.
  Повтор на 409 в `base.save` сравнивает свежую подпись с подписью основы.
- Ключ строки черновика: у лежащей — `id`, у новой — `новая-N`; после ответа ключ меняется на `id`,
  React монтирует строку заново, фокус теряется.

## Goals / Non-Goals

**Goals:** набранное во время записи не теряется; свой ответ — не чужая правка; поведение при
настоящей чужой правке прежнее.

**Non-Goals:** автосохранение строк (отложено); очередь записей; запись по строкам.

## Decisions

### D1. Запереть или слить — решение задачи 0.1

- **(а) Запереть.** На время записи ячейки только читаются, рядом — «Записываем…». Ничего не
  теряется, потому что ничего нельзя набрать; основа переезжает на ответ, как сейчас (`dirty` сброшен
  до рендера с новым видом). Минимум кода, но автосохранению не поможет: там таблица была бы заперта
  на каждой паузе.
- **(б) Слить.** При отправке запоминается снимок отправленного. После ответа: строки, не менявшиеся
  с отправки, берутся из ответа; изменённые после отправки остаются набранными, из ответа им
  достаются только id и серверные признаки (`nomenclatureLost`, `match`, `allocation`), и только если
  ключевые поля с отправки не менялись. Основа принимает ответ своим — новый шаг `adopt(view)` в
  `useDraftBase`, — а «есть несохранённое» = черновик отличается от принятого ответа. Серверное
  форматирование чисел в набранные поля не возвращается (запятая под курсором не пропадает).

Рекомендация Архитектора — (б): это ровно то, без чего не обойдётся автосохранение. Моя — тоже (б),
если автосохранение остаётся в планах; (а) — если владелец решит его не делать.

### D2. Сопоставление новой строки с её записью

- **(а) По позиции.** Ответ отдаёт строки в порядке набора; новые строки сопоставляются с отправленными
  по порядку. Без правки сервера; хрупко, если строку удалили или переставили за время записи.
- **(б) `newId` от клиента.** Новая строка несёт Guid, выданный клиентом, сервер создаёт строку с ним;
  строка с таким `newId` в этом счёте уже есть — она считается лежащей. Ключ на экране с рождения равен
  id (фокус не теряется), повтор после потерянного ответа не заводит дубликатов. `id` и `newId` — разные
  поля: неизвестный `id` остаётся отказом (защита от молчаливого возврата строки, удалённой соседом).

Рекомендация Архитектора — (б). Защищено тем же `If-Match`: нового пишущего адреса нет.

### D3. Где живёт приём

Слияние ответа и правило «что изменено с отправки» — в `features/costs` (знают строку счёта); шаг
`adopt` — в `draftBase.ts` (знает только версию и подпись). Ничего не выносить в `shared` до второго
потребителя.

## Risks / Trade-offs

- [Слияние разойдётся с сервером на строке, изменённой во время записи] → такая строка остаётся
  несохранённой целиком и уходит следующей записью; сервер — источник правды после неё.
- [Строку удалили во время записи] → её нет в черновике; ответ, принёсший её, её не возвращает;
  следующая запись удаляет её на сервере.
- [Потерянный ответ, повтор] → без `newId` повтор того же набора получает 409 (версия сдвинута) — это
  верно и не ослабляется; с `newId` повтор после перечитывания идемпотентен.
