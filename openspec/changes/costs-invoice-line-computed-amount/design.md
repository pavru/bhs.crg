# Design: посчитанная сумма строки счёта остаётся посчитанной

## Context

Мотивация — proposal.md. Сейчас:

- Сервер, `InvoiceLineValues.Completed(mode)` (`Data/InvoiceLine.cs:276`):
  `sum = paper ?? Money(quantity × price)`, НДС `= VatAmount ?? по ставке`; в строку ложится итог.
- Ответ отдаёт `amount` / `netAmount` / `vatAmount` — без признака, откуда число.
- Клиент, `toDrafts` (`invoiceLines.ts:114`) кладёт их в поля черновика; расчёт строки (около
  стр. 191) — `typed ?? quantity × price`. Пустое поле черновика значит «посчитай».

Строки поставляют три пути: набор в форме, вставка таблицы (`InvoiceLinesPaste`), распознавание скана
(`InvoiceScanLines`, `CostsRecognitionProfiles`). У вставки и распознавания сумма — с бумаги.

## Goals / Non-Goals

**Goals:** одно правило «с бумаги / посчитано», действующее после сохранения, одинаковое у клиента и
сервера, в обоих режимах НДС.

**Non-Goals:** автосохранение строк (отложено); смена правила сверки с бумагой.

## Decisions

### D1. Где жить различию — решение задачи 0.1

- **(а) Клиент по равенству расчёту.** `toDrafts` оставляет поле пустым, если число равно тому, что
  досчитал бы сервер (`Money(quantity × price)`, НДС по ставке от него). Повторная отправка пустого
  поля даёт то же значение — сервер и данные не меняются. Цена: бумажная сумма, по случайности равная
  расчёту, после сохранения начнёт пересчитываться при правке количества; при равенстве это
  неотличимо, и пересчёт там ожидаем. Копеечное расхождение бумаги с расчётом остаётся бумажным.
  Рекомендация Архитектора.
- **(б) Признак на сервере.** Строка хранит «сумма с бумаги» и «НДС с бумаги» (две колонки), ответ их
  отдаёт, тело `PUT …/lines` их принимает; вставка и распознавание ставят «с бумаги». Честнее и
  переживает любой клиент (MCP, будущая запись по строкам), но требует миграции и правила для лежащих
  строк (D2).

Рекомендация — (а): закрывает дефект без миграции и без нового поля в договоре; к (б) переходить, если
различие понадобится не форме (отчёт «откуда сумма», запись по строкам).

### D2. Лежащие строки при (б)

Признака у них нет. Заполнение миграцией по равенству расчёту (то же правило (а)) — единственное, что
можно вывести из данных; иначе все лежащие суммы станут «бумажными», и дефект останется на них.

### D3. Общие примеры

Случаи «посчитано → правка количества / цены / ставки» и «бумажная → правка цены» в обоих режимах —
в `invoiceLineCases.json`, чтобы правило проверялось с двух сторон одним набором.

## Risks / Trade-offs

- [При (а) расчёт в `toDrafts` разойдётся с серверным округлением] → тот же `Money` и тот же набор
  примеров, что у сервера; расхождение ловит общий набор.
- [Сверка «посчитано в форме» сдвинется на копейку после сохранения] → уже названо в
  `ReconciliationStrip`; правило не меняется.
