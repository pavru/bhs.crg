# Design: экран счёта — отмена вместо подтверждения

Общая архитектура — `../costs-invoice-screen-00-epic/design.md`: D6 (отмена вместо подтверждения), D8
(`useSnackbar` из `shared/ui`). Требования — `specs/costs/spec.md`.

## Context

- **Отклонение** — `InvoiceMoreMenu.tsx`: `ConfirmDialog` с тремя пунктами, затем
  `rejectInvoice(...)` (`invoiceReject.ts`) → `POST …/rejected` с `If-Match`. Обратный переход —
  `POST …/draft`. Под отбором «Разобрать» `leadOn` (`InvoicesPage.tsx:218`) ведёт к следующему счёту и
  показывает snackbar «Вернуться» (`useSnackbar`, `duration: 8000`).
- **Удаление строки** — `InvoiceLinesTable.tsx:372` (`onRemove`): строка уходит из черновика строк без вопроса.
  Сервер при записи уносит её разноску каскадом. Ветку «строка с разноской» берёт #1655.
- **Удаление счёта** — `InvoiceDeleteDialog` и `invoiceDelete.ts`: `canDelete`, `goingAway` (что уйдёт),
  `deleteRecord`. Вызывается из «⋮», из плашки сбоя распознавания («Не тот файл — удалить черновик…») и из
  двойников («Загружен дважды — удалить этот черновик…»). После 11 эти действия живут в banner и в пунктах
  перечня.
- **Сервер** (`InvoiceDeletion.cs`, разбор Архитектора «Ф», В1):
  - `DELETE` с `If-Match` удаляет запись, строки, доли и запись распознавания каскадом, а файл в Garage —
    последним;
  - журнал пишет «удалён насовсем»;
  - идущее распознавание по удалённому счёту завершается без ошибки.

  Восстанавливать не из чего, поэтому «Вернуть» возможен только до отправки.
- **Снэкбар** (`useSnackbar`, `shared/ui`, [UI-71], В9 = А): по одному, следующий — после закрытия текущего,
  видимое ничем не вытесняется, действие одно — text.
  - Порядок ожидающих: ошибки, затем со своим действием, затем по приходу.
  - Ожидающие успех и сведение старше 15 с отбрасываются, не показавшись, — и с действием тоже. При
    переполнении очереди (10) отбрасывается самый старый из наименее ценных не-ошибок — сначала без
    действия, затем с действием, затем с откликом.
  - «Закрыть» есть только у ошибки; успех и сведение закрываются сроком или смахиванием.
  - Срок по умолчанию — 4 с у успеха и сведения, 8 с у ошибки.
- **Отклик закрытия** — решение Э5 от 08.11.2026, change `sharedui-snackbar-close-reason` (код #1804, архив
  #1805; контракт — `openspec/specs/sharedui` [UI-71] и `docs/UI.md`):
  - `SnackbarOptions.onClose(reason)` зовётся ровно один раз; причины — `action` (после самого
    `action.onClick`), `timeout`, `dismissed` (смахнули, Esc), `dropped` (очередь отбросила, не показав).
  - Уведомление с `onClose` в очереди **не стареет** и без своего `duration` держится `SNACKBAR_UNDO_MS`
    (8 с). Поэтому `dropped` бывает только при переполнении (10 ожидающих): уведомление с откликом
    вытесняется последним из не-ошибок. Решает это очередь, когда закрывается видимое уведомление или
    приходит новое, — не таймер на 15-й секунде.
  - Уведомление с `onClose` не сливается с повтором: защита от двойного щелчка — у вызывающего.
  - Закрыть уведомление из кода нельзя. О закрытии вкладки снэкбар не знает: `pagehide` — у потребителя.
  - `SNACKBAR_UNDO_MS` — срок любого «Вернуть»; без отклика его передают в `duration` сами.

## Goals / Non-Goals

**Goals:** три действия без окна, и у каждого настоящая отмена. Отказ отменённого или отложенного действия
выглядит отказом.

**Non-Goals:**
- удаление строки с разноской — #1655;
- окно повтора файла и замена файла с вопросом — 14;
- серверные правки и мягкое удаление (D6 зонтика);
- отмена «Разобран»: у него и сейчас нет окна, а обратный ход — «Вернуть в черновик».

## Decisions

### D-13.1. Отклонение — запрос сразу, «Вернуть» — обратный переход

- Пункт «Отклонить» в «⋮» без многоточия: окна больше нет. Пояснение из окна («по нему не платим; вернуть
  — «Вернуть в черновик»») — `hint` пункта `RowActionsMenu`: строка под пунктом, видна и на телефоне.
- Успех → снэкбар «Счёт № … отклонён · Вернуть». Под очередью «Разобрать» этот снэкбар заменяет «Вернуться»
  `leadOn`: два снэкбара подряд — это два действия, которых человек не просил. Текст тогда прежний текст
  перехода («Счёт № 104 отклонён. Открыт следующий — № 105.»), а действие — «Вернуть».
- «Уже отклонён» (409, а свежий счёт отклонён — `rejectInvoice`) — сведение без «Вернуть»: отклонил, возможно,
  сосед, и возвращать чужое решение одной кнопкой нельзя.
- «Вернуть» → `POST …/draft` с версией из ответа отклонения, затем `switchTo(id)` к этому счёту. Отказ (409
  или иное) — `useSnackbar().apiError(e)`: слова сервера, у 500 — «Сообщить»; счёт остаётся отклонённым.
  Запрос и переход живут на странице, а не в «⋮»: форма под отбором уже показывает следующий счёт, и меню
  отклонённого размонтировано. Со страницы ушли — к счёту ведёт адрес, как у «Вернуться».
- Срок показа — `SNACKBAR_UNDO_MS` (8 с, Э5), передаётся в `duration`: отклик закрытия отклонению не нужен,
  на сервере всё уже сделано.
- **Альтернатива** — откладывать сам запрос отклонения, как у удаления. Отвергнута: отклонение обратимо на
  сервере, а задержка заставила бы соседа видеть «черновик» дольше, чем надо.

### D-13.2. Удаление строки без разноски

**Выбранная ветка (0.1, 08.11.2026): «до 12 и до #1655».** Ни `costs-invoice-screen-12-autosave`, ни
`costs-invoice-line-delete-allocation` (#1655) не начаты: в обоих все задачи открыты, PR нет. Поэтому:
- строка с сохранённой разноской удаляется **как сейчас** — сразу, без снэкбара; вопрос, называющий каскад,
  даст #1655 в своём обработчике той же кнопки;
- задача 2.2 (пометка записи после 12) здесь не делается: её условие «при слитом 12» не наступило. Она
  уходит в 12 — его удаление строки встраивается в этот обработчик (D-12.2).

- «Без разноски» — у строки нет сохранённых долей (`line.allocation.parts.length === 0`) или строка новая.
  Иначе — ветка #1655.
- Удаление убирает строку из черновика строк и запоминает `{ line, index }` в снэкбаре «Строка N удалена ·
  Вернуть» (`N` — номер в таблице, срок — `SNACKBAR_UNDO_MS` в `duration`, отклика не нужно). «Вернуть»
  вставляет строку на прежний индекс с прежними полями.
- **До автосохранения (12)** всё живёт в черновике: возврат — правка черновика, запись — кнопкой.
  Строки успели записать до «Вернуть» (кнопкой или охраной ухода) — в счёте строки с этим `id` уже нет, и
  возвращённая встаёт новой строкой, без `id`: старый сервер отверг бы. Таблица уже размонтирована (ушли со
  счёта) — «Вернуть» говорит сведением, что строка не возвращена, а не молчит.
- **После 12** удаление — цельное действие, повод записи строк (D-12.2 ребёнка 12). Чтобы «Вернуть» не
  превращался в повторное заведение, пометка `lines` после удаления ждёт закрытия снэкбара. Ушла раньше
  (другая правка строк, смена счёта) — значит, удаление записано. Тогда «Вернуть» добавляет строку заново
  с теми же полями, с новым `id`. Разноски у неё не было, так что теряется только `id`, на который ничто не
  ссылается.

### D-13.3. «Свежий» черновик

`isFresh(id)`:
- черновик заведён **из файла в этой вкладке** — «Счёт из файла» или бросок. Его `id` записывается в
  множество `createdHere` при ответе заведения;
- **с тех пор из этой вкладки в него ничего не записано**: ни реквизитов, ни строк, ни «Всё верно», ни
  разноски. Сдвиг версии распознаванием записью человека не считается;
- **на экране нет несохранённых правок** (`dirty` формы): без окна они пропали бы молча, а «Вернуть»
  вернул бы черновик, но не набранное.

Записи узнаются подпиской `onInvoiceWritten` — через неё проходит каждая запись счёта этой вкладки
(`useInvoiceWrite`), и новый пишущий хук попадёт туда сам.

Остальные черновики удаляются окном (`InvoiceDeleteDialog`): чужой черновик, черновик прошлого сеанса,
черновик с правками. Признак живёт в памяти вкладки и с перезагрузкой пропадает. Это безопасное
направление: окно спросит лишний раз.

**Альтернатива** — признак на сервере («ни одной записи, кроме заведения и распознавания»). Отвергнута:
сервер не меняется (D6 зонтика), а журнал для такого решения читать дорого и не нужно.

### D-13.4. Отложенный `DELETE` — очередь вне страницы

`features/costs/pendingDelete.ts` — модуль, не компонент: переход внутри приложения его не размонтирует.

```
schedule(id, version) → снэкбар «Черновик удалён · Вернуть»; список прячет id
undo(id)              → убрать из очереди, вернуть в список, switchTo(id)
send(id)              → DELETE …/invoices/{id} с If-Match: последняя известная версия
```

- **Когда уходит запрос** — по отклику закрытия снэкбара (Э5): `onClose(reason)` с любой причиной, кроме
  `action`, — `timeout`, `dismissed` или `dropped` — отправляет `DELETE`; `action` («Вернуть») не отправляет
  ничего. Срок — `SNACKBAR_UNDO_MS` (8 с): у уведомления с `onClose` он подставляется сам. «Закрыть» у успеха
  нет ([UI-71]): закрывают сроком или смахиванием.
- **Срок после нажатого действия** (найдено при живой проверке; решение владельца 08.11.2026 — чинить в 13).
  Radix Toast ставит срок на паузу, пока указатель или фокус в поле уведомлений, а уход оттуда слушает,
  только пока в поле есть уведомление. «Вернуть» закрывает уведомление под указателем: уход приходит, когда
  слушать некому, флаг паузы остаётся, и следующее уведомление сроком не закрывалось вовсе — а с ним до
  `pagehide` висел и `DELETE`. `SnackbarProvider` пересоздаёт провайдер и поле Radix под каждое показанное
  уведомление (`key`): новое поле паузы не помнит. Контракт [UI-71] не меняется — это его исполнение.
- **Очередь снэкбаров.** Снэкбар, стоящий в очереди за другим, держит удаление до своего показа и закрытия:
  уведомление с откликом в очереди не стареет. `dropped` бывает только при переполнении (10 ожидающих), и
  отброшенное считается закрытым — `DELETE` уходит, как по сроку: человек удаление уже выбрал, а черновик,
  скрытый навсегда без запроса, был бы хуже.
- **Повторы не сливаются** (Э5), поэтому двойной щелчок гасит сама очередь: `schedule` по `id`, который уже
  ждёт, ничего не делает. Закрыть снэкбар из кода нельзя — и не нужно: после `pagehide` или ответа запись
  помечена отправленной, и поздний отклик закрытия второго запроса не шлёт.
- **Версия.** Берётся последняя, которую клиент видел, — версия открытого счёта в миг `schedule`: пока форма
  была открыта, опрос распознавания её обновлял. После `schedule` форма закрыта, и версию не подменяет
  ничто: свежая из кэша удалила бы то, чего человек не видел. 409 значит, что после последнего чтения счёт
  сдвинулся. Тогда `useSnackbar().error` «Черновик не удалён:
  распознавание дописало счёт — удалите ещё раз», черновик снова в списке. Автоповтора нет: удалять то,
  чего человек не видел, нельзя.
- **`pagehide`** — для всех ждущих: `fetch(url, { method: 'DELETE', keepalive: true, headers: {
  Authorization, 'If-Match' } })`. Тела нет, лимит `keepalive` не мешает. `apiClient` (axios) `keepalive`
  не умеет, поэтому здесь прямой `fetch` с тем же токеном. Отказ или неотправка — черновик остаётся.
- **Список.** Пока удаление ждёт, страница отфильтровывает `id` из перечня, а открытый счёт закрывает. Под
  отбором «Разобрать» — ведёт к следующему, как после отклонения.
- **Сосед** в эти секунды черновик видит. Это приемлемо (Архитектор, В1).

### D-13.5. Где кнопка удаления какая

| Место | Свежий черновик | Иначе |
|---|---|---|
| banner сбоя распознавания: «Не тот файл — удалить» | отложенно, без многоточия | окно, «Не тот файл — удалить…» |
| пункт «тот же файл»: «Загружен дважды — удалить» | отложенно | окно |
| «⋮ → Удалить» | отложенно | окно |
| пункт дубликата «Это дубль — удалить…» | окно: дубликат определяется по сохранённым реквизитам, значит, черновик уже правили | окно |

Многоточие в подписи — по правилу «действие с окном»: где окна нет, его нет.

### D-13.6. Метка «со скана» у полей, дописанных в тип

Хвост 11 (D-11.4 архива): поля шапки метят непроверенное значение знаком `fromScan` ([UI-88]), а поле,
дописанное в тип, рисует общий с документами `PrimitiveInput`, у которого этого свойства нет, — и метка у
него прежней рамкой `ring-1 ring-warning` с подсказкой. Это вторая рамка, которую [COST-6.4] запрещает.
Владелец 08.11.2026 отдал правку в 13: отдельный change ради проброса одного свойства дороже самой правки.

- `PrimitiveInput` получает `fromScan?: boolean` и передаёт его полю `shared/ui`, которое рисует сам:
  `TextField` (в том числе `shown` у read-only), `TextAreaField`, `Select`, `DateField`. Знак, подсказку,
  приписку для диктора и снятие знака правкой дают сами поля ([UI-88]), `PrimitiveInput` своего не рисует.
- `InvoiceFormFields` вместо `frame` и `UNCONFIRMED_HINT` передаёт `fromScan={marked}`; у `ExtraField`
  свойства `frame` больше нет.
- Документы `fromScan` не задают: у реквизитов метки «со скана» нет, их поля не меняются.
- **Виды без `fromScan` у своего поля (4.2, 08.11.2026):** флажок (`boolean` — `Checkbox`) и подсказка по
  введённому (`SuggestField`; в форме счёта её нет — источник подсказок задаёт только форма документа).
  Поле под замком источника знак получает: оно рисуется `TextField`/`TextAreaField` только для чтения.
  Со скана ни флажок, ни перечисление, ни поле своего типа не приходят: распознавание кладёт в дописанное
  поле только `string`, `text`, `number` и `date` (`InvoiceScanHeader.ByType`, сервер). Способ метки для них
  не нужен; своей рамки нет ни у одного. Начни распознавание класть флажок — метку ему даёт change
  `sharedui-*` (свойство `fromScan` у `Checkbox`), а не рамка здесь.
- Число, дописанное в тип, рисует не `PrimitiveInput`, а `NumberInput` формы счёта (запятая и пробелы) —
  `fromScan` получает и он.

## Risks / Trade-offs

- [Отложенный `DELETE` не уйдёт при закрытии вкладки] → черновик остаётся черновиком (D6 зонтика), это не
  потеря.
- [Токен истёк к моменту `pagehide`] → запрос получит 401, черновик останется. То же безопасное
  направление.
- [Снэкбар ждёт в очереди, и удаление затягивается] → черновик скрыт из списка всё это время. Сосед видит
  его дольше. Приемлемо. Уведомление с откликом в очереди не стареет; отбросить его может только
  переполнение, и тогда `DELETE` уходит, как по сроку (D-13.4, Э5).
- [Отброшенное переполнением «Вернуть» человек не увидел] → удаление он выбрал сам; переполнение — десять
  ожидающих, почти одни ошибки, и черновик из файла остаётся в журнале.
- [«Вернуть» строки после записи меняет `id`] → у строки без разноски на `id` ничто не ссылается (D-13.2).
- [Пересечение с #1655 в одной кнопке удаления строки] → ветки разведены условием «есть сохранённая
  разноска». #1655 не начат (0.1): 13 сливается первым, и #1655 встраивает вопрос в обработчик 13.

## Migration Plan

Один PR, `version:minor`. Откат — revert: окна возвращаются. Сервер не меняется.
