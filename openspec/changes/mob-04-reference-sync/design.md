# Офлайн-справочники назначенных строек

## Context

Полевой API v1, ReportEntryCatalog, AssignmentGate, порты номенклатуры, перечня и поставщиков подсказок. Опоры и границы описаны в [эпике](../mob-00-epic/design.md). Условие старта — [mob-02-device-sessions](../archive/2026-11-28-mob-02-device-sessions/tasks.md).

## Goals / Non-Goals

Офлайн-форма должна предлагать реальные работы, материалы и участников смены при ограниченном объёме данных на личном телефоне. Объём и наблюдаемый результат закреплены в [дельте field](specs/field/spec.md).

## Decisions

Для каждого набора передавать свой серверный курсор, предел страницы и признак продолжения. Ограничения объёма применять без пропусков. Потерю доступа и удаление передавать как удаление локальной записи либо замену ограниченного снимка. Кэш участников относится к дате и стройке. Не очищать локальные черновики при уменьшении области.

Решение владельца от 28.11.2026: активное устройство с делегированным `work.report.own` получает узкие подсказки отпуска Costs и ресурсов сметы Plan, в том числе когда у сотрудника нет офисной записи. Сервер проверяет назначение сотрудника из сессии на стройку и дату запроса. Подсказка не включает количества, цены, документы или право доступа к офисным операциям. Офисный договор [WORK-48] действует как прежде. Режим досылки после отзыва не даёт права на синхронизацию справочников.

Work перед каждым чтением проверяет назначение и передаёт доверенный контекст `AssignedFieldSite` в специализированные методы `ReadFieldHintsAsync` существующих контрактов. Идентификаторы устройства и сотрудника берутся из сессии. Клиент выбирает только стройку и дату. Поставщики читают узкие проекции своих данных по стройке: Costs — отпущенную номенклатуру и единицу, Plan — пары позиции перечня и материала действующих редакций. Оба метода доступны только внутри сервера. `ModuleReader` остаётся контекстом офисных операций.

Решение владельца от 28.11.2026: адрес берётся из профиля стройки по метке поля `construction.address`.
Администратор в редакторе типа профиля ставит «Адрес стройки» на одно обычное поле `string` или `text`,
затем заполняет это поле в профиле стройки. Действуют эффективная схема и наследование общих данных.
Пустое, отсутствующее, неразрешимое или ненастроенное значение передаётся как `null`.
Составное или расчётное поле не используется. Поскольку у нескольких строек может быть один адрес,
метка сама по себе не отключает существующие подсказки ввода строковых полей.

MOB-04 поставляет версионный маршрут обмена состоянием устройства с контрактными примерами, проверкой сессии и привязкой к её deviceId. Наблюдение хранится в схеме work вместе с временем приёма сервера. Контакт фиксируется и на пустом успешном обмене. MOB-08 использует этот маршрут, MOB-10 читает его серверное хранилище. Постоянная проверка связи MOB-01 сохраняет исходную форму. Справочники дополнены поясом компании, эффективным поясом стройки и вариантами работ; Room сохраняет эти данные в MOB-08, а локальная модель и выбор варианта определены в MOB-06.

## Договор полевого API v1

### Справочники

`GET /api/field/v1/references/{kind}` принимает поля запроса `date`, `siteId`, `cursor` и `limit`
по таблице. `date` — дата начала смены `YYYY-MM-DD` по поясу стройки при сравнении с периодом назначения.

| `kind` | Обязательные поля | Элементы |
|---|---|---|
| `classifier` | — | Виды работ с единицей, признаками `requiresLocation`, `requiresMaterials`, `producesId`, `archived` и вариантами `id`, `workTypeId`, `name`, `archived` |
| `units` | — | Действующие единицы |
| `sites` | `date` | Назначенные стройки с `address` и эффективными `timeZoneId`. `metadata.companyTimeZoneId` присутствует и при пустой выдаче |
| `sections` | `date` | Разделы назначенных строек с `constructionId` |
| `positions` | `date` | Позиции перечня ядра с ключом `constructionId`, `workTypeId`, `sectionId`, `unitId`, в том числе при выключенном Plan |
| `materials` | — | Действующие ссылки справочника номенклатуры |
| `participants` | `siteId`, `date` | Участники с назначением на ту же стройку и дату, только `id` и `fullName` |
| `issued-materials` | `siteId`, `date` | `id` материала, `displayName` и `unit` |
| `estimated-materials` | `siteId`, `date` | `id` материала, `displayName` и `planItemId` |

Оболочка состоит из `state`, `items`, `metadata`, `limit`, `replace`, `more` и `cursor`.
По умолчанию `limit=100`, допустимо от 1 до 200. Передавать только курсор из ответа для того же
набора и области. Курсор задаёт позицию в упорядоченной сервером проекции и связан с устройством,
набором, датой и стройкой. Он действует 24 часа. Поля телефона и его часы на порядок не влияют.

Первый запрос, недействительный курсор и изменение проекции дают первую страницу с `replace: true`.
Последующий запрос с возвращённым курсором даёт следующую страницу того же снимка. При изменении
между страницами сервер начинает новый снимок с начала, учитывая действующие назначения, удаления
и архив. На неизменном снимке после последней страницы ответ содержит `items: []`, `replace: false`,
`more: false` и прежний курсор.

Например, `sections?date=2026-11-01&limit=1` и
`participants?siteId=<стройка>&date=2026-11-01&limit=1` дают независимые курсоры S и P.
После переименования раздела запрос с S начинает снимок разделов заново. Запрос с P продолжает
снимок участников, если назначения и имена этих участников сохранились.

Потребитель MOB-08 заменяет проекцию при `replace` и фиксирует полный набор по завершении страниц.
После завершения нового снимка строек удаляет справочные кэши пропавших строек для этой даты.
Для запроса по стройке, которая больше не назначена, `state: not-assigned` и пустой снимок также
очищают кэш этой пары даты и стройки. Черновики, отправленные строки и их выбранные идентификаторы
при любой замене справочника сохраняются. Для верхних ярусов предпочтение `issued` над `estimate`
над `materials` применяется к полученным снимкам при показе выбора. Список материалов сметы
индексируется по паре `planItemId` и `id`.

`ok` с пустым снимком означает отсутствие записей. `not-connected` значит, что поставщик выключен.
`not-configured` сообщает об отсутствии исходного справочника. Сетевой отказ или временная ошибка
оставляют результат неизвестным. Они не заменяют локальные данные пустым списком.
Полевой отчёт передаёт вид работы, раздел и единицу. `workPlanItemId` служит справкой.
Связь на сервере определяет ключ CORE-12, который разрешает Work при записи отчёта.

### Состояние устройства

`PUT /api/field/v1/device/observation` принимает, например,
`{"apkVersionCode":4,"pendingReports":0,"oldestPendingDate":null,"observedAt":"2026-11-01T06:12:00+10:00"}`.
Необязательный `deviceId` сверяется с сессией, подмена даёт 403 `device-mismatch`.
При положительном счётчике дата обязательна, при нуле — отсутствует или `null`.
Ответ 200 содержит `receivedAt` и `lastContactAt` по часам сервера. Доставка отчёта для вызова
не требуется. Сеанс фонового обмена передаёт свежий снимок после обработки очереди, даже если она
была пуста. MOB-08 отправляет такие снимки последовательно, при повторе измеряет текущую очередь.
Замеры сохраняются в порядке серверного приёма. Разница часов телефона не служит основанием
для отказа. Пока записи в `work.device_observations` нет, состояние очереди и контакт неизвестны.

## Risks / Trade-offs

Курсор нельзя продвигать за невыданные записи. Закрепить тестами изменение между страницами, отзыв назначения и первоначальную синхронизацию после истечения курсора.
