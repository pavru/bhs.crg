# Design: фото строки работы под изоляцией отчёта

Общая архитектура — `../work-00-epic/design.md`. Здесь только решения этого change.

## Context

- Порт фото — `work-05`: обёртка над `ImageDownscaler`
  (`src/server/BHS.CRG.Infrastructure/Generation/ImageDownscaler.cs`) с защитой от разжатия, поворотом
  по EXIF, сохранением геометки, лимитами через `IModuleSettings` и учётом места.
- Хранилище модуля — `IModuleBlobs` (`src/server/BHS.CRG.Modules/Ports/IModuleBlobs.cs`): сначала файл,
  потом ссылка у своей записи. Копия берёт файл по пути в строке (issue #1261).
- Колонки с путём файла объявляются в `IAppModule.Files` (`ModuleFile`, признак `Carried`,
  `src/server/BHS.CRG.Modules/Data/ModuleFile.cs`). Перепись — `ModuleFileInventoryTests`
  (`src/server/BHS.CRG.Tests/Configuration/ModuleFileInventoryTests.cs:28-34`). Модули там перечислены
  руками, сейчас только `CostsDbContext`: «новый модуль вписывается сюда».
- Чтение отчёта с параметром доступа — `work-07`, строки — `work-13`.

**Условие безопасности — локальный отчёт аудита, раздел 2.** Его исполняет change ядра
`core-attachment-owner` (владелец у файла хранилища); `work-17` не сливается раньше него. Фото кладутся
портом модуля с владельцем `work`.

## Goals / Non-Goals

**Goals:** фото строки с первого дня под изоляцией отчёта; носитель недогруженных фото для очереди.

**Non-Goals:**
- галерея и просмотр — `work-22`, `work-21` (согласовать с просмотрщиком #1489);
- очередь догрузки на телефоне — этап 5;
- показ координат геометки отдельным полем — не решено, вне этапа. Геометка живёт в файле.

## Decisions

### Хранение
- Таблица `work.line_photos`: `id` (клиентский), `line_id`, `state`, `blob_path`, `preview_blob_path`,
  `size`, `declared_at`, `stored_at`. Объявляется в `WorkModule.Files` двумя строками с
  `Carried: true`.
- Превью едет в копию тоже: перестраивать превью после восстановления пришлось бы отдельным путём,
  которого нет, а весит оно мало.
- Таблица изолирована по D4: `DbSet` не выставлен, чтение — методом с параметром доступа. Перепись
  `work-07` распространяется на неё сама.

### Выдача — только адресом модуля
- `GET /api/work/photos/{photoId}` и `…/preview`: сначала отчёт фото читается с параметром доступа.
  Не найден — 404. Найден — поток из `IModuleBlobs.OpenAsync`.
- Фото черновика для неавтора — 404, по `WORK-54`: содержимое черновика — после подачи.
- Альтернатива — общий адрес выдачи файлов ядра — отклонена: файлы модуля он не выдаёт
  (`core-attachment-owner`).

### Загрузка без `If-Match` — названное исключение
Фото догоняют отчёт отдельной очередью (`WORK-34`), и к их приходу версия отчёта сдвинута почти
всегда: подачей, правкой менеджера, приёмкой. С `If-Match` очередь фото падала бы 409 после каждой
чужой правки. Загрузка не перезаписывает ничего: идентификатор клиентский, повтор безопасен (`MOB-15`),
занятый чужой строкой идентификатор — 409. Удаление стирает данные, поэтому требует `If-Match`. Обе
стороны исключения перечислены в тесте адресов модуля — по образцу `WritesNothing` у
`InvoiceStaleFormTests`.

### Порядок записи
- Порт фото сжимает и проверяет лимит до `PutAsync`: сверх лимита в хранилище не пишется ничего.
- Затем файл и превью кладутся в хранилище, а ссылки и `state: stored` — у строки фото.
- Сбой между ними даёт осиротевший файл, его находит поиск осиротевших. Обратный порядок дал бы фото,
  которое не открывается.
- Удаление: сначала ссылка, потом файл.

### Объявленное и новое фото (`WORK-11`)
Строка при сохранении (`work-13`) перечисляет `photos: [{id}]`, и запись фото заводится в `pending`.
Файл объявленного фото, пришедший после подачи, — доставка. Фото, впервые объявленное после момента
подачи, — «правка после подачи» в журнал `work-14`.

### Носители (D15)
- У фото — `state`. У отчёта — `photosPending`.
- Пометка `photos-pending` очереди считается по `state = pending`: код заведён в `work-16`, этот change
  даёт ему данные.

### Состав PR (один)
- `Photos/PhotoEndpoints.cs`, `Photos/LinePhotos.cs`, миграция схемы `work`.
- `WorkModule.Files`; `WorkDbContext` вписан в `ModuleFileInventoryTests.Modules()`.
- Тесты `Work/PhotoAccessTests`, `Work/PhotoUploadTests`, `Work/PhotoBackupRoundTripTests` — образец
  `InvoiceBackupRoundTripTests`.
- `docs/ADMIN_GUIDE.md`: лимиты, место; что фото несут координаты и работодатель уведомляет
  сотрудников (`WORK-55`).

### Сторож
- `ModuleFileInventoryTests` с моделью `WorkDbContext`.
- `PhotoAccessTests`: чужой монтажник по адресу фото и превью получает 404.

### Чем ломается
- Выдача фото не адресом модуля — условие безопасности, локальный отчёт аудита, раздел 2.
- `WorkDbContext` не вписан в перепись файлов — колонка фото без объявления, и отчёт копии молчит.
- Сжатие только на клиенте — веб кладёт оригинал (сторож — у `work-05`).

### Зависимости
`work-05`, `work-13`, `work-07`; `work-16` — код пометки; `work-14` — запись «правка после подачи».
Параллельно пути, этап 3 не нужен.

## Risks / Trade-offs

- [Геометка — персональные данные] → решение владельца «хранить» (`WORK-55`). ADMIN_GUIDE и объяснение
  права говорят об этом прямо.
- [Объявленное фото не приходит никогда] → `pending` остаётся, пометка видна. Принять отчёт это не
  мешает (`WORK-34`).
- [Копия растёт с фото] → лимиты размера и числа — настройка модуля. Место показано администратору.
