# Design: организация в модулях — сокращённым названием, если оно есть

## Context

- Модуль читает организации портом `IModuleCatalog` (`BHS.CRG.Modules/Ports/IModuleCatalog.cs`):
  `ModuleCatalogEntry(Id, EntityType, DisplayName, DataJson, Archived)` и `ModuleCatalogRef(…, DisplayName,
  …)`. `DisplayName` — название записи общих данных: его вводит человек в карточке («Наименование»,
  `features/document-sets/catalog/index.tsx:618`), а при заведении из файла счёта —
  `CatalogIntakeService` кладёт туда название, прочитанное в скане (`request.Name`), то есть полное.
- Поле названия организации — тэг `org.name` (`FunctionalTag.cs:163`, `TagRegistry.cs:228`, виды
  `string` / `text` / `complex`). Составное «Полное / Сокращённое» раскладывает `CatalogIntakeLayout`:
  название ложится только в обязательные строковые части, «Сокращённое» остаётся пустым («полное на его
  месте было бы выдумкой»). Схема как у заказчика описана в `CatalogIntakeTests.cs:32`: «Полное»
  обязательно, «Сокращённое» нет.
- Тэги ролей ставятся существующим установкам правилом умолчаний `DirectoryRoleDefaults.Rules`
  (`ИНН` → `org.inn`, `Наименование` → `org.name`, #1101) — по коду поля, один раз, с поиском у
  носителя роли и выше по родителям.
- `IModuleCatalog.FieldValuesAsync(role, fieldTag, …)` читает значения поля по тэгу с разрешённым
  наследованием `_baseRef` (сопоставление поставщика по ИНН, #1077).

### Что выяснилось сверкой (22.10.2026)

- **Снимок экрана из issue недоступен** (хранится у администратора). Экран — `/invoices` с открытым
  счётом: карточка (поля «Поставщик» и «Плательщик», `features/costs/InvoiceForm.tsx:460,548`) рядом со
  списком (`InvoiceListRow.tsx:193`, `item.supplierName`). Прочтение issue — «показывать сокращённое
  название, если оно есть»; показывают сегодня полное (см. выше, почему).
- **Сокращённого названия код не знает вовсе:** ни тэга, ни поля; ключ «Сокращённое» встречается только
  в тестах и доккомментариях.
- Организацию показывает не один экран, а **около пятнадцати мест `costs`**, и все берут `DisplayName`
  порта: `OrganizationEndpoints.cs:64`, `InvoiceListEndpoint.cs:132`, `InvoiceDesk.cs:367`,
  `InvoiceEndpoints.cs:521`, `InvoiceParties.cs:197`, `InvoicePartyIntakeEndpoints.cs:107,122`,
  `InvoiceDeletion.cs:131`, `Tables/InvoiceTableRows.Prepare.cs:23` (колонка и отбор реестра),
  `SiteCostsEndpoints.cs:167`, `SupplierMatchListEndpoints.cs` (6 мест), `SupplierTermsEndpoints.cs:91,183`,
  `NomenclatureCandidateEndpoints.cs:119`. Поэтому правило — общее, в порте ядра, и change назван
  `core-…`, а не `costs-…`.
- `suggest-01-rule` (эпик подсказок) правит то же требование «Действующие тэги ядра — поля записей»
  (тэг `input.noSuggest`).

## Goals / Non-Goals

**Goals:** организация в модулях — сокращённым названием, где оно есть; без угадывания по названиям
полей; заказчику — без ручной разметки схемы.

**Non-Goals:**
- страница общих данных ядра и выбор записи каталога в документах ИД — там запись показывается своим
  названием (его ведёт человек);
- генерация документов — у шаблонов свои функции показа организации (`render_org_short` и др.);
- заполнение сокращённого из полного — выдумка, которую `CatalogIntakeLayout` нарочно не делает.

## Decisions

- **D1. Тэг `org.shortName`, а не ключ «Сокращённое».** Поле ищется по тэгу (`TYPE-2`). Тэг —
  `TagScope.Field`, виды `string` / `text`, одиночный, группа «Организации», роль `role.organization`.
  Ставится на строковое поле типа-организации или на строковую часть составного типа, который стоит
  полем `org.name`. ⚠️ Роль тэга сегодня проверяется по типу, несущему роль (`TagCatalog.cs:68`); часть
  составного лежит в другом типе. Проверка допустимости расширяется: «поле носителя роли или часть
  составного поля `org.name` носителя» — с тестом редактора и сохранения схемы.
- **D2. Умолчание ставит тэг сам, один раз.** Правило `DirectoryRoleDefaults`: у поля с `org.name`
  составного вида — часть с кодом «Сокращённое» строкового вида получает `org.shortName`, если тэга нет
  ни на одном поле. Так установка заказчика начинает показывать сокращённые названия без ручной
  разметки. Прецедент — `ИНН` и `Наименование` (#1101). Альтернатива — только ручная разметка —
  отклонена: правка видна лишь после того, как администратор узнает о тэге.
- **D3. Одна дверь — порт ядра.** Порт заполняет `DisplayName` записей роли `role.organization` по
  правилу «сокращённое, если заполнено, иначе название записи»; рядом — `FullName` (название записи) для
  мест, где нужно различать (D4). Значение сокращённого читается с наследованием `_baseRef`, как
  `FieldValuesAsync`. Альтернатива — отдать `ShortName` отдельным полем и выбирать в каждом из
  пятнадцати мест `costs` — отклонена: каждое новое место (и модули `plan`, `work`) забывало бы правило.
- **D4. Полное название — где выбирают.** В выборе поставщика и плательщика (`CostsOrganization`) —
  полное название второй строкой пункта; в карточке счёта и реестре — только сокращённое (решение
  владельца 22.10.2026, В1 — Б).
- **D5. Отбор реестра — не меньше видимого.** `InvoiceTableRows` строит отбор по словарю названий
  порта — отбор «по названию поставщика» находит то, что видно в колонке, **и по полному названию**
  (решение владельца 22.10.2026, В2 — по обоим).
- **D6. Макетов нет.** Раскладка и шаги не меняются: меняется текст в существующих местах. Вторая строка
  с полным названием в списке выбора — тот же пункт выбора, что у кандидатов #1511 (подпись второй строкой).
- **Сторож.**
  - `OrganizationShortNameTests` (ядро): тэг ставится умолчанием на «Сокращённое» и не дважды; порт
    называет запись сокращённым, пустое — названием записи, унаследованное — базовым; без тэга — названием.
  - Тесты `costs`: `GET /api/costs/organizations`, строка реестра и отбор по названию — сокращённым.
  - Перепись мест `costs`, читающих название организации, — тест, что все они идут через порт (нет
    чтения `DisplayName` мимо него).
- **Чем ломается.** Тэг стал ставиться на каждом старте — второй прогон умолчаний меняет схему (тест).
  Часть составного не принимается сохранением схемы — D2 молча не срабатывает (тест редактора). Отбор
  ищет по полному, а колонка показывает сокращённое — отбор «не находит» видимое (тест реестра).

## Risks / Trade-offs

- [У заказчика поле названия устроено иначе (строка, или часть называется не «Сокращённое»)] → до
  слияния сверить на копии базы заказчика: вид поля `org.name`, код части, сколько организаций с
  заполненным сокращённым (агрегатом, без названий); иначе D2 не сработает, и это видно сразу.
- [Две организации с одинаковым сокращённым названием неразличимы в списке] → D4: полное название в
  выборе.
- [`suggest-01-rule` и этот change правят одно требование] → второй по архивации переносит оба тэга
  (`input.noSuggest`, `org.shortName`) в перечень.

## Открытые вопросы

**Решено владельцем 22.10.2026 (рекомендации приняты): В1 — Б, В2 — по обоим.**

**В1. Где видно полное название.**
- **А.** Только сокращённое везде; полное — в карточке организации в общих данных.
- **Б.** Сокращённое везде, а в выборе поставщика и плательщика полное — второй строкой пункта
  (рекомендуется: в выборе путают похожие названия).
- **В.** Как Б, и в карточке счёта полное — подсказкой у поля.

**В2. Отбор реестра по названию поставщика** — по видимому (сокращённому) или по обоим. Рекомендация —
по обоим: человек ищет по любому слову из названия, а полное длиннее. Затрагивает только построитель
отбора `InvoiceTableRows`.
