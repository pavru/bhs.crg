# Design: подача отчёта, окно подачи и автоподача

Общая архитектура — `../work-00-epic/design.md` (D8, D12, D15). Здесь только решения этого change.

## Context

- Отчёт с колонкой `status` (пока только `draft`) и протокол изменений — `work-13`. Журнал отчёта и
  колонка `reports.submitted_at` — `work-14`.
- «Сегодня на стройке» и «дата стройки для мгновения» — порт `IModuleClock` из `work-11`. Действующий пояс
  стройки — в `ModuleConstruction` оттуда же.
- Признаки вида работы «требует места» и «требует материалов» объявлены тэгами
  (`src/server/BHS.CRG.Application/Documents/CoreRecordTypes.cs:133-136`). Модуль читает их портом вида
  работ `work-06`.
- Такт модульных заданий — `work-08`: объявление такта модулем и постановка задачи через `IModuleJobs` с
  постоянной целью. Образец такта — `src/server/BHS.CRG.Infrastructure/Backup/BackupScheduleService.cs`:
  «прошёл ли срок и не ставили ли после него».
- Общий файл примеров уже есть у счёта: `src/client/src/features/costs/invoiceLineCases.json`, его читают
  `invoiceVat.test.ts` и `src/server/BHS.CRG.Tests/Costs/InvoiceLineCasesTests.cs` через `RepoPaths`.

## Goals / Non-Goals

**Goals:**
- Статусы и подача.
- Окно мгновением.
- Автоподача с догоном.
- Предлагаемая пара «дата · смена».
- Файл примеров.

**Non-Goals:**
- Приёмка и возврат — `work-16`.
- Уведомления о поданных менеджерам сводкой за такт — `work-16` (D16). Такт этого change отдаёт им
  перечень поданных за прогон.
- Запрет закрытия периода при открытом окне — `work-19`.
- Досылка к принятому — `work-19`.
- Расчёт окна на телефоне — этап 5.

## Decisions

### Состав PR
Один PR.

### Хранение
- Колонки отчёта: `window_ends_at` (мгновение, не null), `submitted_by` (`manual` | `auto`, null у
  черновика), `required_missing` JSONB (заполняет только автоподача).
- Индекс `(status, window_ends_at)` для запроса автоподачи.
- Миграция `SubmissionWindow`. У отчётов, заведённых до миграции, окно считается в самой миграции по
  нынешнему поясу: других мгновений у них нет.

### Правило окна — одно место
- `Submission/SubmissionWindow.cs` — чистые функции без базы и часов:
  - `EndsAt(siteZone, date, shift)`;
  - `MomentOfManual(deviceTime, endsAt)` = `min(deviceTime, endsAt)`;
  - `Suggested(siteZone, now, hasNightYesterday)`.
- Пересчёт окна зовётся из пути сохранения `work-13`, когда меняется дата, смена или стройка.
- Стройка добавлена к дате и смене из `WORK-52`: окно считается по её поясу. Перенос черновика на стройку
  в другом поясе со старым окном дал бы автоподачу по чужим суткам.

### Общий файл примеров (MOB-18)
- `src/server/BHS.CRG.Modules.Work/Submission/SubmissionCases.json` — язык-нейтральный JSON. Пример: пояс
  компании, пояс стройки, дата, смена, «сейчас», есть ли ночной отчёт за вчера, время действия на
  устройстве; ожидание — `windowEndsAt`, `momentOfManual`, `suggested`.
- Лежит рядом с правилом, а не у клиента: веб-клиент правила не повторяет (D8), второй читатель — приложение
  этапа 5. Оно возьмёт файл по пути репозитория.
- `SubmissionCasesTests` прогоняет каждый пример и отдельным тестом проверяет состав:
  - есть ночная смена;
  - есть пояс стройки, отличный от пояса компании;
  - есть случай «после полуночи в ночную смену».

### Подача и названное исключение If-Match
- Подача черновика или возвращённого отчёта — с `If-Match` через `SeenVersion`.
- **Исключение:** подача уже поданного отчёта отвечает 200 `alreadySubmitted: true` без сверки версии.
  Изменения не происходит, поэтому и потерять нечего. Иначе телефон получал бы 409 на каждый повтор
  подачи, которую обогнала автоподача.

### Автоподача (D12)
- `Submission/AutoSubmitJob.cs` — `IModuleJobHandler`. Такт `work-08` ставит его с постоянной целью (одна
  задача на цель, двойной такт не дублирует).
- Запрос: `status = draft and window_ends_at <= now`, порциями.
- На каждый отчёт:
  - `status = submitted`, `submitted_at = window_ends_at`, `submitted_by = auto`;
  - `required_missing` по признакам вида работы;
  - запись журнала `auto-submitted` с автором «Система» — в одном `SaveChanges`.
- Конфликт версии (монтажник правит в ту же секунду) — отчёт пропускается и подаётся следующим тактом с
  тем же моментом.
- Одна запись в журнал ядра на прогон: «автоподача: N отчётов» через `IModuleActivityLog`.
- Параметр доступа — «система с причиной» (`work-07`), опубликованных наборов задача не читает (`CORE-24.1`).

### Предлагаемая пара (MOB-35)
- `GET /api/work/sites/mine` из `work-11` дополняется полем `suggested: { date, shift, label }`; `today`
  там уже есть.
- `label` («Ночная смена 16.11», «Отчёт 17.11») сервер строит по языку пользователя. Подпись тоже стоит в
  файле примеров, поэтому этап 5 подпишет кнопку так же. Это запрос экрана `work-22`: клиент не
  сочиняет подпись из пары.
- Ночной отчёт за вчера ищется среди своих отчётов спрашивающего методом с параметром доступа «свои».

### Подача введённого за сотрудника (WORK-31)
`POST /api/work/entry/reports/{id}/submit` — тот же переход, что у своих отчётов, через группу адресов
ввода `work-13`: право `work.report.review`, параметр доступа «стройки». Правило окна и обязательности
одно.

### Сторож и «чем ломается»
- **Сторож:**
  - `SubmissionCasesTests` с ночной сменой и поясом стройки, отличным от пояса компании;
  - `AutoSubmitTests.Простой_три_дня` на подставном `TimeProvider`;
  - тест «смена пояса задним числом окна не двигает».
- **Чем ломается:**
  - момент подачи записан временем прогона — после простоя всё «подано» в момент подъёма, тест простоя
    краснеет;
  - окно пересчитывается на чтении по нынешнему поясу — тест смены пояса краснеет.

### Зависимости
- `work-13`, `work-14`, `work-11` (часы и пояс), `work-06` (признаки вида работы), `work-08` (такт),
  `work-07` (параметр «система»).

## Risks / Trade-offs

- [Автоподача при незаполненных обязательных полях — решение сессии, а не владельца] → вариант «не
  подавать» оставил бы черновик навсегда и сдвинул бы момент подачи, который ТЗ определяет временем.
  Носитель `requiredMissing` даёт `work-16` пометку в очереди. Подтвердить у владельца в раунде Р4.
- [Доверие к времени устройства при ручной подаче] → момент не позже конца окна. Раньше заведения отчёта
  время устройства не проверяется. Расхождения показывает очередь `work-16` (`MOB-17`).
- [Пояс с переходом на летнее время] → в России переходов нет. Один пример с `Europe/Berlin` в файле
  примеров держит правило честным для суток длиной 23 и 25 часов.
