# Design: живой прогон счетов не ходит к движку распознавания

Самостоятельный change модуля `costs` по issue #1344. Change маленький: проверка файла до движка уже
построена #1343 (PR #1398); здесь — её место в запуске распознавания счёта и сам прогон.

## Context

Сверено по коду ветки `openspec/open-issues-changes` (master `c9586405`), 22.10.2026.

**Что уже сделано (#1343, PR #1398) — не планируется.**
- `Infrastructure/Recognition/RecognitionFileCheck.cs`: пустой файл и PDF, который не открывает PDFium,
  отказывают до движка; фраза — `RecognitionFileCheck.Unreadable` («файл повреждён, защищён паролем или
  это не PDF»). Комментарий класса прямо называет файл живых прогонов: признака `%PDF-` в начале мало.
- `ChainDocumentRecognizer.RecognizeAsync` зовёт проверку **первой**, до выбора движков;
  `WholeFileRecognition.RunAsync` превращает отказ в `RecognitionRefusedException(BadFile)`.
- Клиент знает причину: `features/costs/recognition.ts` — `failureNote` «Файл не распознан: сам файл не
  читается…», `shortReason` «файл не читается». Тесты — `Recognition/BadFileRecognitionTests.cs`.

**Что выяснила сверка — почему «Готово» issue ещё не достигнуто.**
- `Modules.Costs/Endpoints/InvoiceScanRecognition.cs:231-240`, `StartAsync`: до постановки задачи зовётся
  `recognition.EnsureReadyAsync(...)`. Порт (`Api/Modules/Ports/ModuleRecognitionPort.cs:29-35`) спрашивает
  `IRecognitionPreflight.CheckAsync`, и при ненастроенном движке исход записывается `NotConfigured`
  (тихая полоса) — до проверки файла дело не доходит. На CI прогон видит «не настроено», а не «файл не
  читается».
- Предполётная проверка — `RecognitionEngineSelector.CheckAsync` → `SelectAsync(probeVision: true)`: при
  неизвестном зрении модели это проба, то есть запрос к движку, ради файла, который движку не уйдёт.
- Файлы прогона: проверка 7 — один `Скан-…`, проверка 8 — два `Пакет-…`, проверка 8а — два `Повтор-…` и
  один с «другим содержимым»: шесть черновиков из `POST /api/costs/invoices/from-scan`, каждый ставит
  распознавание сам (`InvoiceRecognitionEndpoints.cs:115-118`). Это и есть «около шести запросов за
  прогон».
- Проверка 9 (`invoices-smoke.mjs:470-510`) приводит настоящую книгу Excel к PDF настоящим конвертером и
  жмёт «Распознать файл»: на стенде с движком — настоящий запрос с исправным файлом.
- Проверка 7 сверяет `/Файл не распознан: /` и `/не распознан — /` — слова, общие для любого отказа
  (комментарий у проверки, `:340-345`).

**Прочие прогоны, заводящие счета из файла, — сверены, запуска распознавания в них нет.**
- `e2e/seed-invoices.mjs:262` прикладывает PNG к счёту `СЧ-104` адресом `POST …/{id}/scan`; этот адрес
  распознавание не ставит (ставят только `from-scan` и `POST …/{id}/recognition`).
- `e2e/invoice-layout-checks.mjs:32` прикладывает книгу тем же адресом и читает `…/scan/image`.
- `e2e/limited-smoke.mjs:189` — файл в «Сообщить о проблеме», к счетам не относится.

## Goals / Non-Goals

**Goals:** ни одного запроса к внешнему движку из прогона счетов на любом стенде; прогон сторожит #1343
словами об отказе файла, и сторож не зависит от настроек стенда.

**Non-Goals:**
- уборка накопленных ошибок в колокольчике дев-стенда (issue: «не задача кода»);
- смена слов отказа о файле — они построены #1343 и здесь только сверяются;
- изображения: их проверка остаётся за движком (`RecognitionFileCheck`, комментарий класса).

## Decisions

- **D1. Файл — первым и в модуле.** `StartAsync` читает файл, который уходит движку **как есть** (вид
  `FileReading.AsIs` — PDF и изображение), и спрашивает порт ядра о нём **до** `EnsureReadyAsync`.
  Нечитаемый файл — исход `BadFile` со словами проверки, задача не ставится, предполётная проверка не
  зовётся.
  - *Уточнено при реализации:* не `InvoiceScanImage.ReadableAsync`. Для Excel и Word он **строит** образ
    конвертером (`IModuleRenditions.EnsureAsync`) — в запросе запуска это секунды ожидания и отказ
    конвертера ответом на нажатие вместо исхода. Образ — PDF, построенный нашим конвертером; его
    по-прежнему проверяет цепочка ядра в фоновой задаче. Файлы прогона (#1344) — PDF, их это не задевает.
  - *Уточнено ревью PR:* уйдёт ли файл как есть, отвечает ядро (`IModuleRenditions.FindAsync`, без записи —
    `EnsureAsync`, кроме файлов, которые приводятся к виду), а не записанный вид счёта: задача спрашивает
    ядро, и два правила судили бы разные файлы. Читается только PDF (`InvoiceScanImage.AsIsPdfAsync`):
    изображение проверка не судит, и тянуть его из хранилища незачем.
  - Порт: `IModuleRecognition.EnsureReadableAsync(profileCode, content, mimeType, ct)` — отказ
    `RecognitionRefusedException(BadFile, …)`, иначе молчит; реализация в `ModuleRecognitionPort` зовёт
    `RecognitionFileCheck.CheckAsync`. Модуль `Infrastructure` не видит (`ModuleBoundaryTests`), поэтому —
    порт, а не прямой вызов. Профиль — ради ворот: как у остальных вызовов порта, профиль выключенного
    модуля отказывает его названием раньше, чем файл судят (ревью PR).
  - Сбой окружения в проверке (`Outcome.Why = null`, `Cause` задан) — не отказ, как в цепочке: файл идёт
    дальше, событие — в журнал сервера. Так же — сбой хранилища или службы образов при чтении файла до
    постановки (ревью PR): задача ставится, как до проверки, и исход называет она.
  - Проверка в цепочке ядра остаётся: распознавание наборов данных и повтор из фоновой задачи идут мимо
    `StartAsync`.
  - *Отклонено:* проверять файл только в ветке «не настроено». Порядок тогда зависел бы от настроек, а
    проба зрения на настроенном стенде осталась бы. Цена выбранного — одно чтение файла из хранилища на
    запуск; при заведении из файла файл только что записан.
- **D2. Проверка 7 сверяет отказ о файле.** Форма — `Файл не распознан: сам файл не читается`, строка
  списка — `не распознан — файл не читается`, отбор «Не распознано» — тот же счёт; слов «не настроено» и
  «недоступно» на форме нет. Тексты берутся из одного места прогона, рядом — ссылка на
  `features/costs/recognition.ts`: меняются вместе (issue, «Чем ломается»).
- **D3. Проверки 8 и 8а слов не сверяют.** Их предмет — пачка и повтор. Достаточно D1: каждый их
  черновик получает `BadFile` без запроса к движку. Комментарии у проверок говорят об этом, чтобы
  содержимое файлов не «исправили» на настоящий PDF.
- **D4. Проверка 9 на стенде с движком не жмёт «Распознать файл».** Прогон спрашивает
  `GET /api/settings/integrations` (прогон идёт администратором) и при хоть одном включённом и
  настроенном **облачном** движке распознавания пропускает нажатие с названной строкой прогона: «движок
  настроен — запуск не проверяется, прогон к движку не ходит (#1344)». На стенде без движка (CI) проверка прежняя:
  исход есть, и он не об образе. Остальная проверка 9 (вид для чтения, оговорка, скачивание оригинала,
  панель в пределах экрана) идёт на любом стенде.
  - *Уточнено по первому прогону CI:* Ollama в счёт не идёт. В CI он включён по умолчанию и «настроен»
    (адрес задан, `missing` пуст), но не запущен — и по правилу «хоть один движок» проверка 9 пропускалась
    бы как раз там, где обязана идти. Ollama — свой движок поставки, платного внешнего запроса за ним нет;
    Goals говорят о внешнем движке. Облачные — все прочие (Gemini, Anthropic…).
  - *Отклонено:* выключать движки на время прогона — дев-стенд общий, это настройки разработчика.
  - *Отклонено:* оставить нажатие — один исправный платный запрос за прогон противоречит «Готово» issue.
  - *Отклонено:* заменить нажатие серверным тестом — «отказ не об образе» имеет смысл на настоящем
    конвертере, и на CI он остаётся.
- **Сторож.**
  - `InvoiceFromScanTests`: нечитаемый PDF при **ненастроенном** движке — `reason: BadFile`, а не
    `NotConfigured`; подставная предполётная проверка не вызвана ни разу. Без D1 тест красный.
  - `ModuleRecognitionPortTests`: `EnsureReadableAsync` — отказ `BadFile` на нечитаемом PDF, молчание на
    исправном и на изображении.
  - Прогон, проверка 7 — сверка слов о файле на CI (движка нет): без D1 там «не настроено», и проверка
    красная.
- **Чем ломается.** Вернуть `EnsureReadyAsync` перед проверкой файла — красные тест и прогон на CI; на
  стенде с движком — снова проба зрения ради битого файла.

## Risks / Trade-offs

- [Найдено первым прогоном CI: двойники пачки на форме устаревали] → `sendScan` кладёт в кэш вид черновика
  на момент заведения, и двойник, заведённый позже той же пачкой, в нём не значился. Раньше это прятало
  распознавание: оно шло фоном, форма опрашивала его и по исходу перечитывала счёт. С D1 исход `BadFile`
  готов сразу — перечитывания нет, и проверка 8а видела «к другому счёту» вместо «к другим счетам».
  Правка — в клиенте: новый черновик помечает устаревшим вид каждого своего двойника (`sendScan`), то есть
  ровно тех счетов, у которых двойник прибавился.
- [Тексты отказа о файле меняются отдельно от прогона] → тексты прогона лежат одной константой со
  ссылкой на `recognition.ts`; меняются тем же PR (issue, «Чем ломается»).
- [Проверка 9 на стенде с движком больше не сторожит запуск распознавания] → на CI сторожит; на стенде
  разработчика пропуск назван строкой прогона, а не молчит.
- [Лишнее чтение файла при запуске] → один раз на запуск, задача читает файл заново; файлы счёта —
  единицы мегабайт.
