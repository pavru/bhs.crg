# Proposal

## Why

Если на экземпляре нет классификатора видов работ (нет типа `ВидРаботы`), `GET /api/work-types` отвечает
**200 и пустым списком**. Это то же самое, что «видов работ нет», хотя состояния разные и выход из них
разный: в пустой классификатор можно завести вид работы, а в незаведённый нельзя, пока нет справочника
единиц. Так отказ выглядит результатом (issue #1936).

У ядра в остальном это различие уже есть:
- `POST /api/work-types` в том же случае отвечает 409;
- порт `IModuleWorkTypes` отвечает `null`;
- дверь сотрудников отвечает 409 `directory-missing` с причиной.

Требование [CORE-20.4] прямо говорит: «справочник не заведён» MUST отличаться от «записей нет». Чтение
двери видов работ — последнее место, где это не выполняется. Скоро у двери появится ещё один читатель —
строка отчёта о работах (`work-13`), поэтому чинить нужно сейчас.

## What Changes

- **Чтение списка** `GET /api/work-types` без типа `ВидРаботы` отвечает 409:
  `{ code: "directory-missing", reason, error }`, как у двери сотрудников. Пустой классификатор
  по-прежнему отвечает 200 и пустым списком.
- **Заведение** `POST /api/work-types` в том же случае отвечает тем же телом. Сейчас в нём только
  `error`, без `code` и `reason`, поэтому клиент не может отличить этот отказ от остальных 409 двери.
- **Причина** (`reason`):
  - `unit-missing` — нет справочника единиц, классификатору не на что ссылаться;
  - `not-created` — справочник единиц есть, но классификатор ещё не заведён; он появится при следующем
    запуске.

  Слова отказа называют эту причину и выход из неё.
- **Клиент.** В окне сопоставления сметы поле «Вид работы» показывает слова отказа как состояние, а не
  как красную ошибку «не прочитался». Действия «Новый вид работы» при незаведённом классификаторе нет:
  заведение всё равно получит отказ. Показ названий видов работ в смете и окнах принимает отказ как
  «названий нет», а не как ошибку.
- **Сторож.** Тест двери на оба состояния: без справочника единиц — 409 `directory-missing` с причиной,
  с пустым классификатором — 200 и пустой список. Тест клиента на разбор отказа.

`GET /api/work-types/{id}` без классификатора по-прежнему отвечает 404: запись не найдена, и состояние
справочника этот ответ не описывает.

## Impact

- **Сервер:**
  - `src/server/BHS.CRG.Api/Endpoints/Core/WorkTypeEndpoints.cs` — ветка списка и ветка заведения,
    общий ответ отказа;
  - `src/server/BHS.CRG.Tests/Integration/WorkTypeEndpointsTests.cs` — новые проверки.
- **Клиент:**
  - `src/client/src/shared/api/planningMatches.ts` — `useWorkTypeChoices`, разбор отказа;
  - `src/client/src/shared/api/planningEstimates.ts` — `useWorkTypeNames`;
  - `features/planning/estimates/RateChoiceFields.tsx` и `MatchDialog.tsx` — состояние поля и действие
    «Новый вид работы».
- **Документация:** `docs/DEV_NOTES.md`, листинг REST API у `/api/work-types`.
- **API:** код ответа меняется для экземпляра без классификатора: было 200 и пусто, стало 409. Читатели
  двери — только клиент этого репозитория. Модуль `work` читает виды работ портом, а не адресом.
- **Без миграций и без новых прав.** Метка PR — обычная, без `version:minor`: это исправление.
