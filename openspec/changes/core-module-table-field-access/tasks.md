# Задачи CORE для прав полей таблиц и метаданных источников

Порядок после planning-only PR — два кодовых PR, затем отдельно архив. Каждый кодовый PR начинается по поручению владельца. Следующий кодовый этап, в том числе локально, начинается после слияния предыдущего, фактического коммита бота и обновления базы. Перед возобновлением Plan-28 требуются код обоих этапов, подтверждённые бампы и слияние архива.

## 1. Кодовый PR 1 — метаданные табличных источников

- [ ] 1.1 Применить нейтральное хранение в общем пути создания, табличном мосте и обновлении метаданных [CORE-24.1] [CORE-24.2]. Интеграционный тест с издателем проверяет сохранённую схему, неизвестное число строк, отсутствие примеров и сохранение выбора колонок. Отдельные случаи используют права всей таблицы, права явной колонки и существующую изоляцию строк.
- [ ] 1.2 Подключить проверку актуального доступа и состояния к описанию источника и списка файлов в REST и MCP, снимкам описания, ответам привязок и автомаппингу [CORE-24.1] [AUTH-8]. Проверить публикацию при широком доступе, чтение другим пользователем, его чтение до и после отзыва права, актуальные примеры только из разрешённых колонок, удалённое поле, пустую схему, ноль строк, отказ, недоступность провайдера и выключенный модуль. Проверить штатные причины, отсутствие подстановки прежнего числа и прежние отказы на операциях чтения строк.
- [ ] 1.3 Обследовать совместимость старых записей на изолированных синтетических данных [CORE-24.2]. Проверить все ответы на ранее сохранённые метаданные, экспорт резервной копии и восстановление. Зафиксировать по результатам, нужна ли адресная нормализация, и согласовать её охват при необходимости. При согласованной нормализации проверить повторяемость, работу с выключенным модулем и сохранность идентификаторов, выбора, настроек, версий и связей.
- [ ] 1.4 Проверить совместимость Costs, Work и обычного файлового источника [CORE-24.1] [WORK-40]. Прогнать существующие проверки чтения и изоляции, сравнить значения и причины отказов по действующему контракту, подтвердить, что чтение не пишет данные и что список не читает провайдер повторно для одной группы.

## 2. Кодовый PR 2 — политика полей схемы

- [ ] 2.1 Закрепить выбор владельца по совпадению ключей в design.md и сценарии дельты до начала кода этой части [CORE-33]. Проверка — разрешённый вариант и ожидаемая причина отказа явно указаны.
- [ ] 2.2 Добавить типизированную политику, проверку каталога и общую проверку при открытии [CORE-33] [AUTH-8.2] [TYPE-7]. Стартовый тест проверяет пустые значения, неизвестное право, ключ модуля вместо права, отсутствие типа записи. Интеграционный тест добавляет после старта числовое поле без тэга и унаследованное поле, проверяет обе роли и согласованный сценарий совпадения ключей.
- [ ] 2.3 Проверить действующую таблицу на синтетическом табличном объявлении через настоящий хост [CORE-33]. Описание, строки, выбор колонок, фильтры, сортировка, итоги, поиск, XLSX и системный набор одинаково учитывают закрытие. Доступное поле возвращает ожидаемое значение и итоги, закрытое не влияет на производные результаты. Метаданные источника сохраняются и читаются по правилам первого этапа и для динамического поля.
- [ ] 2.4 Передать зависимость в `ColumnsByRight` и проверить настоящие входы общей печати и определения сверки [CORE-24.1] [CORE-32]. Источник с политикой полей отклоняется даже в отсутствие явных колонок под правом и до появления полей в схеме. Контрольный источник сохраняет штатное поведение.
