# Design: целостность версий шаблона

## Context

Шаблон — все строки `templates` с одним `DocumentTypeId` и одним `Name`. Так их группирует страница
(`groupTemplates.ts`, точное совпадение строки), так после #1920 считает новую версию сервер
(`Template.CreateNewVersion`), и так шаблон понимают «Недавние» (`[ID-13]`). Охраняет это понятие
только код `UpdateTemplateCommand`.

Что показала сверка с кодом (master `15e1662c`):

| Путь | Где | Что не так |
|---|---|---|
| Создание | `Handlers.cs:26–35`, `Template.Create` | название не проверяется, добавляется действующая v1 в чужой шаблон (#1924) |
| Копия | `Handlers.cs:85–95`, `Template.Duplicate` | «(копия)» без проверки занятости; вторая копия — та же поломка (#1924) |
| Новая версия | `Handlers.cs:37–64` | версии читаются без блокировки, номер считается в памяти — гонка (#1922) |
| Новая версия → документы | `Handlers.cs:57–62`, `DocumentTemplateInvalidator` | закреплённые за гаснущей версией не трогаются (#1923) |
| Генерация | `GenerateDocumentHandler.cs:50–57` | из `TemplateIds` берутся только активные; ни одного — отказ «не активен» |
| Предпросмотр | `PreviewDocument.cs:58–68` | погашенная пропускается молча, берётся шаблон по умолчанию |
| Вкладка генерации | `GenerationTab.tsx:87–117` | список только из `isActive`; закреплённая погашенная не видна |
| Восстановление копии | `BackupService.Restore.cs:227–248` | шаблоны вливаются по `Id`, состав группы не проверяется |
| Индексы | `TemplateConfiguration.cs` | только неуникальные `(DocumentTypeId, IsActive)` и `(DocumentTypeId, IsDefault)` |

Переименования шаблона в API нет, поэтому других путей, меняющих `Name`, нет. Шаблоны пишут ещё два
места: переход на адресацию Код.Имя (`MigrateToPrefixedAddressing.cs:368`, через `CreateNewVersion`)
и в будущем — шаблон по умолчанию модуля `plan` (`plan-15`, `PlanModule.InitializeAsync`).

Образец «проверка до базы + гонку ловит индекс» в проекте уже есть: внешний код стройки
(`ConstructionHandlers.cs:61–90` проверяет и бросает `ConflictException`, а 23505 по имени индекса
превращает в 409 `ConstructionEndpoints.cs:108`). Прикладной слой EF и Npgsql не видит, поэтому
различить 23505 может только адрес или инфраструктура.

## Goals / Non-Goals

**Goals:**
- название шаблона в типе не повторяется;
- одна действующая версия и номера без повторов при любой гонке и на любом пути записи;
- закреплённый документ после новой версии остаётся выпускаемым;
- накопленные дубли починены один раз, предсказуемо и до индексов.

**Non-Goals:**
- единственность «по умолчанию» на тип — её не трогает и #1401 (non-goal там же);
- переименование шаблона — его нет, и этот change его не вводит;
- правило выбора шаблона при генерации — его выносит в одну функцию #1401 (D9);
- нечувствительность названия к регистру и пробелам (отклонена владельцем, 0.2).

## Decisions

### D1. Шаблон определяется парой `(DocumentTypeId, Name)`, сравнение точное

Сравнение то же, что у страницы, `CreateNewVersion` и «Недавних»: точное совпадение строки. Входное
название обрезается по краям (`Trim`) при создании, как уже делается у копии. Это нормализация ввода,
а не смена сравнения: накопленные «Основной» и «Основной » остаются разными шаблонами, как и сейчас на
странице. **Решение владельца 13.11.2026 (0.2) — точное.** Отклонено сравнение без учёта регистра и
пробелов: оно меняет группировку в трёх местах и может склеить существующие шаблоны.

### D2. Занятое название — отказ в обработчике, свободное для копии подбирает сервер

`CreateTemplateCommand` и `DuplicateTemplateCommand` до записи проверяют, есть ли у типа строка с этим
`Name`. Если есть — `ConflictException` «Шаблон с таким названием уже есть: «…»». Копия без названия
перебирает «<название> (копия)», «(копия 2)», «(копия 3)», … до первого свободного. Клиент уже копирует
без названия (`TemplatesPage.tsx:263–269`), поэтому для него отказ копии возможен только в гонке.

### D3. Целостность охраняют два уникальных индекса базы

- `UX_templates_one_active` — `(DocumentTypeId, Name) WHERE "IsActive"`: прямо выражает инвариант;
- `UX_templates_version` — `(DocumentTypeId, Name, Version)`: номер не повторяется.

Оба ловят обе гонки:
- две новые версии считают один номер — второй вставке мешают оба индекса;
- два создания под одним новым названием — оба v1 и оба действующие.

Индекс охраняет и пути мимо обработчиков: восстановление, переход на Код.Имя, `plan-15`.

Отклонено:
- **`SELECT … FOR UPDATE` по группе** (вариант из #1922). Блокировать при создании под новым названием
  нечего, строк ещё нет, поэтому гонку #1924 он не закрывает. Ещё он требует сырого SQL в обобщённом
  репозитории, а пути мимо обработчика остаются без охраны.
- **Advisory lock по хешу пары.** Сериализует запросы, и оба проходят: вторая версия становится v6.
  Но охраняет только тех, кто взял замок, а восстановление и миграции замок не берут.
- **Маркер конкурентности у `Template`.** Он сторожит строку, а не группу: две новые версии от разных
  исходных строк его не заметят.

Проигравший получает 409, а не успешную v6. Его содержимое не теряется: окно новой версии остаётся
открытым с введённым текстом, и запрос можно повторить. Одновременная правка одного шаблона двумя
администраторами — редкость. Тот же ответ проект даёт любой гонке записи («тем временем изменили»).

### D4. Порядок записи в новой версии: сначала погасить, потом вставить

Частичный индекс проверяется на каждом операторе, а не в конце транзакции. Если EF отправит `INSERT`
новой действующей раньше `UPDATE`, который гасит прежнюю, запрос упадёт и без всякой гонки. Порядок
команд внутри одного `SaveChanges` для фильтрованного индекса EF не гарантирует. Поэтому
`UpdateTemplateCommand` пишет в две записи под одной транзакцией: сначала погашение, потом вставка.
Если обобщённый репозиторий транзакции не даёт, нужен узкий метод инфраструктуры для этой записи.

Отклонено: ограничение исключения `EXCLUDE … WHERE ("IsActive") DEFERRABLE INITIALLY DEFERRED`. Оно
снимает вопрос порядка, но EF Core его не описывает, и оно жило бы только в SQL миграции, невидимое
модели. Это запасной путь, если двухфазная запись не уложится в репозиторий. Тогда сначала правится
D4, потом пишется код.

Тот же порядок нужен восстановлению (D7) и переходу на Код.Имя. Последний читает с отслеживанием и
пишет одним `SaveChanges` (`MigrateToPrefixedAddressing.cs:228–234`). Сторож — тест этого перехода на
базе с индексами.

### D5. 23505 по имени индекса становится 409 на адресе

Как у стройки: `TemplateEndpoints` ловит `DbUpdateException` с `SqlState` 23505 и `ConstraintName` из
двух наших индексов. Чужие 23505 пробрасываются как есть. Текст отказа зависит от адреса:
- `POST /{id}/versions` — «Шаблон тем временем изменили — откройте его заново»;
- `POST /` и `POST /{id}/duplicate` — «Шаблон с таким названием уже есть».

Хелпер `DbFailure.IsUniqueViolation` уже есть, к нему добавляется сверка имени индекса.

### D6. Вариант А для #1923: закрепление означает «этот шаблон», а не «эта строка»

**Решение владельца 13.11.2026 (0.1) — А.** Доводы, по коду:
- Интерфейс закрепить историческую версию не даёт: вкладка генерации перечисляет только действующие
  (`GenerationTab.tsx:87`, `GenerationTemplateRows templates={activeTemplates}`). Все закрепления
  ставились на действующую версию, то есть человек выбирал шаблон. Погашенной она становится без
  его ведома.
- Новую версию администратор делает, чтобы документы печатались по-новому. При Б исправление шаблона
  не доходит до закреплённых документов, и молча.
- Пересадку уже однажды пришлось написать (`MigrateToPrefixedAddressing`: «так упали все девять
  документов комплекта»). А превращает её из разовой заплатки в правило.
- Б вводит понятие «выбранная историческая версия», которого нет в интерфейсе. Понадобятся показ на
  вкладке генерации, правки генерации, предпросмотра и отладочного пакета, и правило #1401 («все
  выбранные неактивны — отказ») пришлось бы менять. В оставляет поломку.

Как устроено при А:
- **Общая доменная операция** `DomainObject.RepinTemplates(IReadOnlyDictionary<Guid, Guid> replacedBy)`.
  Она меняет одиночный `TemplateId`, элементы `TemplateIds` (на месте, порядок сохраняется, повтор
  после замены убирается) и ключи `TemplateParams`. Сейчас это делают частные `ReplaceIds` и
  `ReplaceParamKeys` в `MigrateToPrefixedAddressing.cs:239–288`. Переход переходит на операцию, его
  тесты остаются сторожем.
- **`UpdateTemplateCommand`:**
  - соответствие «каждая гаснущая версия → новая» строится по версиям, которые погасил
    `CreateNewVersion`;
  - документы типа с `PinsTemplate(гаснущая)` пересаживаются;
  - те, что не в черновике, сбрасываются (`ResetToDraft`, блобы удаляются после коммита — порядок
    `DocumentTemplateInvalidator`).

  Это одна транзакция с записью версий (D4). Сброс считается в `TemplateMutationResult.Reset` вместе
  со сбросом документов без закрепления. Тест `NewVersion_ResetsNoPinDocs_WhenVersionDefault_ButNotPinnedToOld`
  меняет ожидание: закреплённые за старой версией теперь пересажены.
- **Неизменное.** Простое сохранение (`SaveTemplateContentCommand`) ничего не пересаживает: версия та
  же. Удаление версии по-прежнему снимает закрепление (`DeleteTemplateCommand`).
- **Окно новой версии.** `newVersionPlan.pinnedToRetired` уже считает документы. Меняется только текст
  `EditorPanel.tsx:106–107`: «N документов перейдут на новую версию и вернутся в черновик» вместо «им
  нужно будет выбрать шаблон заново».
- **Генерация, предпросмотр и вкладка генерации не меняются.** Закрепление больше не указывает на
  погашенную версию, поэтому их правила верны как есть. Поэтому при А change не сталкивается с #1401
  по смыслу (D9).

Отклонённые варианты:
- **Б** — генерация, предпросмотр и вкладка печатают закреплённой погашенной версией. Это потребовало
  бы MODIFIED правила #1401 «все выбранные неактивны — отказ».
- **В** — оставить как есть.

### D7. Восстановление копии приводит шаблоны к правилам до записи

Копия, снятая до этого change, может нести дубли и не ляжет на индексы D3. Восстановление прервалось
бы на 23505, и человек увидел бы «An error occurred while saving the entity changes». Это то же
замечание, что в сессии #1570, и это отказ, переодетый в непонятное.

`RestoreTemplatesAsync` перед записью собирает группы `(DocumentTypeId, Name)` по объединению
существующих строк и строк копии и применяет к ним правило разовой починки (D8):
- гасит лишние действующие;
- перенумеровывает повторы;
- пишет погашения раньше вставок (D4).

Каждое изменение попадает в `warnings` отчёта: «Шаблон «…»: v3 (создана …) перенумерована в v6». Правило
одно и живёт в домене (`TemplateVersionRepair`). Восстановление вызывает его в C#, а миграция повторяет
в SQL. Совпадение сторожит тест: одни и те же дубли проходят через функцию и через SQL миграции, итог
сравнивается.

Закрепления документов копии, указывающие на погашенные версии, восстановление пересаживает той же
операцией D6 (решение владельца, 0.4).

### D8. Разовая починка — в миграции `AppDbContext`, до индексов

Миграция `TemplateVersionIntegrity`: SQL-починка, затем оба индекса. Приложение мигрирует при старте,
поэтому починка пройдёт у заказчика сама, при обновлении. Правила утверждены владельцем 13.11.2026
(0.4):
1. **Лишние действующие.** В группе с несколькими `IsActive` действующей остаётся версия с наибольшим
   `Version`, при равенстве — с поздним `CreatedAt`. Это то же правило, по которому «Недавние» выбирают
   текущую версию (`[ID-13]`, сценарий «Две действующие версии»). Если `IsDefault` был у любой версии
   группы, он переходит к оставшейся, как в `CreateNewVersion`.
2. **Повторные номера.** В группе строки с повторным `Version`, кроме самой ранней по `CreatedAt`,
   получают номера `max+1`, `max+2`, … в порядке `CreatedAt`. Так история сохраняет порядок появления.
   Номер, который люди видели, меняется только у строк, номер которых и так был неоднозначен.
3. **Закрепления.** Элементы `TemplateIds` и ключи `TemplateParams`, указывающие
   на погашенную версию группы с действующей, заменяются действующей. Повтор в `TemplateIds` убирается.
   Одиночный `TemplateId` на погашенной версии **не трогается**: он и сейчас генерируется (#1923), а
   пересадка молча сменила бы его PDF. Статус документа и его PDF миграция не меняет: удалять блобы
   SQL не может, а черновик без удалённых файлов оставил бы сирот в хранилище. Следующая генерация
   выпустит документ действующей версией.

Отклонено: разделить повторные v1 (след #1924) на отдельные шаблоны с новым названием «(2)». По данным
нельзя отличить «создали второй шаблон» от «завели копию нарочно в ту же группу». После PR #1921 такие
группы уже могли получить общую новую версию, то есть слиться. Угадывание хуже предсказуемого правила
(отклонено владельцем, 0.4).

Число затронутых строк миграция пишет в журнал старта: шаблонов погашено, перенумеровано, закреплений
пересажено. Счёт до слияния — по копии рабочей базы (0.3).

### D9. Соседний change `id-debug-bundle-template-choice` (#1401)

#1401 выносит выбор шаблона в `Application/Generation/TemplateChoice.cs` и переводит на него
`GenerateDocumentHandler`, `PreviewDocument` и отладочный пакет. Ещё он упорядочивает
`ListTemplatesQuery` и делает общим отказ «ни один из выбранных шаблонов не активен».

- **Порядок свободный** (вариант А, решение 0.1). Этот change правило выбора не меняет, а только
  перестаёт оставлять закрепления на погашенных версиях. Дельты добавляют разные требования, и ни одна
  не меняет чужое.
- **Общие файлы:**
  - `Templates/Handlers.cs`: #1401 трогает только `ListTemplatesQuery`, этот change — создание, копию
    и новую версию;
  - тесты генерации.

  `GenerateDocumentHandler` и `PreviewDocument` этот change не меняет. Кто сливается вторым, тот
  обновляет ветку от master; конфликт возможен только текстовый.
- **Сторож 3.4** проверяет итог: генерация и предпросмотр берут v5. Он верен при обоих порядках, до
  `TemplateChoice` и после.

Сам #1401 этот change не правит.

### D10. `plan-15-record-print` — правила не затрагиваются

`plan-15` печатает записи модулей шаблонами ядра. Что от него касается этого change:
- **Шаблон по умолчанию модуля** заводится в `PlanModule.InitializeAsync`, только если у типа нет
  шаблона. Под индексы D3 он ложится, проверка названия ему не мешает. Единственный новый отказ —
  23505 при одновременном старте двух экземпляров с пустой базой. Это вопрос самого `plan-15`
  (идемпотентный засев), записан в Risks.
- **Выбор шаблона печати** («выбранный `?templateId=`, иначе по умолчанию, иначе первый активный») —
  параметр запроса, а не закрепление в записи. Пересадка D6 его не касается. Если `plan-15` возьмёт
  `TemplateChoice` из #1401, он получит то же правило.
- **Индексы D3 общие для всех типов**, в том числе для типов записей модулей. Это и нужно: шаблон КП
  тоже версионируется в редакторе шаблонов.
- **Общие файлы:** `TemplateEndpoints.cs` (там `plan-15` меняет ворота, здесь добавляется разбор 23505)
  и `GenerateDocumentHandler.cs`, из которого `plan-15` выносит общую часть печати. Этот change
  `GenerateDocumentHandler` при варианте А не трогает.

`plan-15` этот change не правит.

### D11. Домен спецификации — `id`

По `[ID-1]` механизм шаблонов принадлежит ядру. Но понятие «шаблон = группа версий» уже записано в
`id` (`[ID-13]`), и туда же кладёт выбор шаблона #1401. Требования ложатся рядом с ними, метки —
`[ID-3]` (сценарий генерации) и `[CORE-21]` (механизм). Если владелец сочтёт, что место им в `core`,
дельта переезжает при архиве без правки текста.

## Risks / Trade-offs

- **[Тесты и фикстуры заводят два шаблона с одним названием]** → после D2 и D3 они упадут. Задача 4.3:
  прогнать весь набор (`bash scripts/backend-tests.sh`) и живые прогоны, такие фикстуры поправить
  названиями, а не ослаблением проверки.
- **[EF отправит вставку раньше погашения]** → D4: двухфазная запись. Сторож — интеграционный тест
  новой версии на базе с индексами и тест перехода на Код.Имя.
- **[Перенумерация меняет номера, которые люди видели]** → только у строк с повторным номером, по
  порядку появления. Журнал старта и отчёт восстановления называют каждую.
- **[Пересадка при новой версии сбрасывает выпущенные PDF закреплённых документов]** → это и есть смысл
  варианта А. Окно новой версии называет их число до сохранения. Документы без закрепления уже
  сбрасываются так же (issue #362).
- **[Одновременный засев шаблона по умолчанию модулем на двух экземплярах]** → 23505 на старте. Это
