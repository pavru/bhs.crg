# Design: навигация модуля `plan` и общие механизмы оболочки

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D2 — что забрано у
`work-03`, D16 — «Ход работ», D18 — макеты П0). Здесь только решения этого change. Механизмы повторяют
спроектированное в `openspec/changes/work-03-navigation/design.md`; отличия названы ниже.

## Context

Сверено по коду master `6b81e51e`.

- **Пункт навигации.** `NavItem` (`client/src/shared/ui/navConfig.ts:14-36`) несёт одно
  `permission?: string` (`:19`). Отбор и причина отказа — `shared/ui/navAccess.ts` (`allowed`,
  `missingFor`); ими пользуются `ProtectedRoute.tsx` и палитра команд `CommandPalette.tsx`.
- **Разделы рейла.** `RailId = 'constructions' | 'data' | 'costs' | 'system'` (`navConfig.ts:42`), список —
  `railSections`; основной список пунктов — `workNav` (`navConfig.ts:82`, это «рабочие пункты», не модуль `work`).
- **Вход.** Индекс-маршрут жёстко ведёт на `/document-sets` (`client/src/App.tsx:122`).
- **Карточка стройки.** Тип панели `'catalog' | 'datasets' | 'subscribers'`
  (`features/document-sets/ConstructionDetail.tsx:31`) и ручной список пунктов блока «Эта стройка»
  (`:112-118`); «Наборы данных» уже отбираются по пространству.
- **Сервер.** Политики по имени: `perm:<код>` (`BHS.CRG.Modules/AppPolicies.cs:20`) и `module:<код>`
  (`:23`). «Любого из» нет. Атрибут MCP принимает один код (`Api/Mcp/McpGates.cs:29`).

## Goals / Non-Goals

**Goals:** «любое из» на пункте и на адресе одним списком; раздел рейла `plan`; вход по доступу; механизм
панелей карточки стройки с проверкой `PLAN-20`.

**Non-Goals:**
- сами пункты и страницы модуля `plan` — `plan-09` («Сметы»), `plan-20` («График»), `plan-25` («Ход работ»);
- раздел `work` и ранг входа монтажника — `work-03`;
- закрепление разделов — `work-04`;
- пространство как граница безопасности — его нет и не будет (`AUTH-16.2`).

Пишущих адресов change не заводит, правило `If-Match` его не касается.

## Decisions

### Состав PR

- **PR 1 — «любое из» и раздел рейла.**
  - Клиент: `NavItem.permission: string | string[]`; `allowed` — «любое из»; `missingFor` возвращает
    `{ kind: 'permission', codes: string[] }`; `NoAccessPage.tsx` — «нужно одно из прав» при двух и более.
  - `RailId` += `'plan'`, строка в `railSections` с подписью по П0 (рабочая — «Планирование»).
  - Сервер: `AppPolicies.AnyPermission(params string[] codes)` — имя `perm:<a>|<b>`; провайдер разбирает
    список, каждый код проходит `Declared()`; `AnyPermissionRequirement` и обработчик; `McpPermission`
    принимает тот же список (`AUTH-12.1`).
  - Переписи `PermissionGateTests`, `EndpointGateInventoryTests`, `ReadAllWritesNothingTests`,
    `McpGateInventoryTests` читают составное имя.
- **PR 2 — вход и панели** (после выбора макета П0).
  - `NavItem.entry?: number` и `shared/ui/entryPage.ts` — чистая функция «доступ + пространство → адрес
    входа»; индекс-маршрут в `App.tsx` зовёт её вместо `Navigate to="/document-sets"`.
  - `shared/ui/constructionPanels.ts` — реестр `{ id, module | null, label, icon, permission (строка или
    список), section, render }`. `ConstructionDetail.tsx` строит пункты и содержимое по реестру; адреса
    прежних панелей не меняются.
  - Проверка `PLAN-20` — в реестре: модуль с тремя панелями — ошибка теста реестра, а не правило в голове.

### Отличия от `work-03`

- Раздел рейла — `plan`, а не `work`; переименование раздела `costs` («Учёт» → «Затраты») решается в П0,
  раз раздел модуля появляется здесь первым.
- Панель ядра «Ход работ» — первый пункт под «любым из» на клиенте: её видят носители прав колонок
  (`plan.estimate.read`, `plan.schedule.read`, `work.facts.read`, право полосы затрат — В-3). Сам пункт
  вписывает `plan-25`; здесь — тестовым пунктом в vitest.

### Почему одна политика, а не две двери

Как в `work-03`: две двери дали бы экрану два источника и переписи две записи, а пункт навигации всё
равно называл бы два права. Список в имени политики проверяется тем же `Declared()`.

### Вход: ранг у пункта, а не карта «роль → страница»

Навигация не читает названий ролей (`AUTH-14`). Ранг вычисляется из того же ответа доступа и учитывает
пространство. Ранги пунктов `plan` назначают change экранов по макету П0.

**Главная и ранг (решение владельца 22.10.2026, вариант Б вопроса В-1 `shell-08-home`).** `/` — Главная
«Продолжить работу» (#1436), но она не отменяет расчёт по рангу, а участвует в нём пунктом ядра с рангом
по умолчанию `HOME_ENTRY_RANK` (константа в `entryPage.ts`, одна шкала для всех модулей). Пункт модуля
открывается вместо Главной, только если его ранг меньше: так монтажник сразу попадает на «Мои отчёты»
(`work-03`), а у кого такого пункта нет — на Главную. Ранги пунктов `plan` по ролям («Сметчик»,
«Менеджер проекта», «Снабженец») решает П0 с вопросом «меньше Главной или нет». Пока Главной нет
(`shell-08` не слит), `HOME_ENTRY_RANK` в расчёт не входит, и порядок прежний: наименьший ранг, первый
видимый, `AUTH-15`. Пункт Главной добавляет `shell-08`, механизм не меняется.

### Сторож и «чем ломается»

- Vitest `navAccess.test.ts`: пункт виден при любом праве списка, `missingFor` называет весь список.
  `entryPage.test.ts`: ранг, пространство, пустая навигация. `constructionPanels.test.ts`: отбор по доступу
  и пространству; модуль с третьей панелью — ошибка.
- `AnyPermissionPolicyTests` — живой хост с тестовым модулем: адрес открыт носителю каждого права, закрыт
  без обоих; необъявленный код роняет сборку политики.
- Живой прогон `e2e/limited-smoke.mjs`: под каждой системной ролью видимые пункты открываются без 403, а
  `/` ведёт на видимую страницу. `e2e/rail-checks.mjs` — раздел `plan` не виден без прав модуля.
- Ломается так: «Сметчик» без `core.constructions.read` после входа видит отказ на «Стройках»; пункт под
  одним правом пропадает у носителя второго.
- Правка оболочки — весь список живых прогонов в каждом PR.

### Зависимости

- После `plan-01`: раздел `plan` осмыслен только с модулем.
- «Модуль, открытый одним правом контракта, раздела не даёт» проверяется, когда `plan-21` заведёт вид
  права; до тех пор правило держится тем, что прав контракта нет.
- `work-04` правит те же файлы навигации; кто сливается вторым, тот перебазируется.

### Макеты

Раунд П0 — три варианта в Claude Design, выбор владельца:
- раздел рейла «Планирование» и его место, переименование раздела `costs`;
- пункты стройки «Сметы», «График», «Ход работ» и их порядок;
- панели модулей в карточке стройки;
- страница входа по ролям («Сметчик», «Менеджер проекта», «Снабженец»).

## Risks / Trade-offs

- [Список в имени политики делает имена длинными] → имена строятся кодом из констант прав.
- [Ранг входа у двух модулей совпал] → порядок — порядок рейла, `entryPage.test.ts` закрепляет его.
- [Переезд панелей карточки ломает адреса закладок] → адреса прежние, проверка — `e2e/routing-smoke.mjs`.
- [Этап 4 начнёт `work-03` по старому тексту] → пометка в `work-00-epic` и в `work-03` тем же PR нарезки.
