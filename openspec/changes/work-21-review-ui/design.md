# Design: очередь приёмки и карточка отчёта

Общая архитектура — `../work-00-epic/design.md` (D11, D15, D17). Здесь только решения этого change.

## Context

Сервер готов до этого change:
- очередь с `marks: [{code, text}]` и счётчиками по кодам, действия приёмки, `acceptWouldMark` — `work-16`;
- карточка, отказ 404 по изоляции — `work-13`;
- журнал — `work-14`;
- фото и превью адресом модуля — `work-17`;
- версии и «изменение принятого» — `work-19`.

Коды пометок 16 заводит сразу. Коды «расхождение в бригаде» (`work-18`), «изменение принятого»
(`work-19`) и «не заполнены поля» (`work-24`) могут прийти позже клиента — поэтому неизвестный код
показывается текстом сервера.

## Goals / Non-Goals

**Goals:** менеджер разбирает очередь своих строек и принимает или возвращает отчёт; пометки видны
там, где решают; «Руководитель» читает без кнопок.

**Non-Goals:**
- сверка бригад — панель `work-18` (PR 2) на адресах `GET /api/work/crew-groups` и
  `POST /api/work/crew-groups/{id}/approve`. Макет её — в раунде Р4 (при перегрузе — Р4б), и он же
  решает её место: карточка, очередь или вкладка. Здесь закладывается только код `crew-mismatch` в виде
  пометок;
- поля заказчика — `work-24`;
- печать отчёта и табеля — вне этапа до решения владельца;
- ввод за сотрудника — `work-22`.

## Decisions

- **Макеты:** раунд Р4, выбор владельца — вписать сюда ссылку. Код — после выбора (D17). В том же
  раунде владельцу задаётся вопрос о печати отчёта и табеля. Ответ вписывается сюда, а печать в этот
  change не входит при любом ответе.
- **Состав PR.**
  - **PR 1 — очередь.**
    - `src/client/src/shared/api/workReview.ts` — запросы очереди и счётчиков.
    - `src/client/src/features/work/review/ReviewQueuePage.tsx` — `PageHeader`, сетка `DataGrid`;
      пометки — `StatusBadge` из `marks`; ночная смена — «☾ ночь».
    - Чипы кодов — `Chip` с `count`. Отбор стройки — `SitesFilter` (чип с `menu`), дата — `DateRange`,
      сотрудник — `EmployeePicker` (`work-12`).
    - Каталог кодов — `WORK_MARK_CODES` в `src/client/src/shared/api/work.ts` (заводит `work-16`),
      сверяет серверный `ReviewMarkCatalogTests`. Здесь к нему добавляется только вид:
      `features/work/review/reviewMarks.ts` — порядок, значок и тон по коду.
    - Маршрут — в `src/client/src/shared/ui/navConfig.ts`, в раздел рейла `work-03`. Право пункта —
      «любое из» `work.report.review`, `work.report.read.all`.
  - **PR 2 — карточка.**
    - `ReportCard.tsx` — шапка, строки на `DataGrid`, фото-превью.
    - `src/client/src/shared/ui/JournalFeed.tsx` — новая общая лента журнала (D17).
    - `AcceptDialog.tsx`, `ReturnDialog.tsx` — `Modal` 512 px, комментарий — `TextAreaField`.
    - Правка строк менеджером — `EditGrid` в режиме правки карточки, вход из `RowActionsMenu`.
    - `ReportVersionBar.tsx` — переключатель версий.
    - Строка `ОтчётМонтажника` в `RECORD_ROUTES` (`src/client/src/shared/ui/recordRoutes.ts`) ведёт на
      экран карточки. Вносит её тот из `work-20` и этого PR, кто сливается вторым: раньше нет либо
      таблицы, либо экрана.
- **Переключатель версий — свой, а не `CorrectionBar`.** `src/client/src/features/costs/CorrectionBar.tsx`
  — полоса режима исправления счёта. Она привязана к `InvoiceView` и `useCorrectInvoice`, лежит в
  `features/costs`, а импортов между `features/` в клиенте нет. От неё берётся поведение: причина до
  записи, 409 разбирается по свежему виду. Общая полоса в `shared` — только если Р4 покажет одинаковую
  форму у счёта и отчёта; тогда это разбор с Архитектором (`docs/UI.md`, шаг 1).
- **Галерея.** Полный просмотр фото — общая `PhotoGallery` из `work-22` (PR 3). Если карточка уходит
  раньше, галерея строится в PR 2 этого change, а `work-22` берёт готовую. Решение записывается в оба
  `design.md`.
- **Носители (D15).**
  - Из ответа сервера: пометки, счётчики, граница выдачи и `reason`, `acceptWouldMark`, разрешённые
    действия карточки (`actions`), состояние черновика с моментом автоподачи, число недогруженных фото,
    версии.
  - Если поля нет, производящий change дополняется до слияния PR.
  - Кнопки рисуются по `actions`, а не по праву `work.report.review`. Право без назначения на стройку
    ведёт к 403, а «Руководитель» права не имеет.
- **Адреса `work-16`.**
  - Очередь — `GET /api/work/review/queue`: отбор по стройке, датам, сотруднику и коду; `counts` по всем
    кодам, включая нули; `reason` пустой очереди — `not-assigned` | `nothing-pending` | `filtered-out`.
  - Приёмка — `POST /api/work/reports/{id}/accept`, возврат — `POST /api/work/reports/{id}/return` с
    телом `{comment}`; оба с `If-Match`.
  - Отказ по статусу — 409 с `{status}`, чужой отчёт — 404.
  - Коды `work-16`: `edited-after-submit`, `same-person`, `manager-edit`, `site-not-assigned`,
    `photos-pending`, `late-delivery`; позже — `crew-mismatch` (18), `accepted-changed` (19),
    `fields-missing` (24).
- **Граница выдачи у очереди** — поле `boundary` ответа `work-16` (требование «[CORE-24.3] [WORK-46]
  Граница выдачи очереди — поле ответа»): «отчёты ваших строек (N)» или «все стройки». N не зависит от
  отбора по стройке. Клиент строку не составляет.
- **Без новых пишущих адресов.** If-Match и ворота — у `work-16`. Здесь — отправка версии и разбор
  400/403/404/409 словами.
- **Сторож.**
  - vitest: нулевой чип не рисуется; неизвестный код показан текстом сервера; без `actions` кнопок нет
    в разметке; 404 даёт одну фразу для «нет» и «чужой».
  - Живой прогон `work-review-smoke.mjs`: менеджер принимает и возвращает, «Руководитель» видит
    карточку без кнопок, чужой менеджер по ссылке получает фразу 404.
- **Чем ломается.** Пометка «ввёл и принял один человек» вычисляется на клиенте — сравнением автора
  ввода с собой. Чип с нулём рисуется — упрёк без выхода. Кнопки по праву — 403 на чужой стройке.
- **Зависимости:** `work-16`, `work-13`, `work-14`, `work-17`, `work-03`, `work-12` (`EmployeePicker`);
  PR 2 — ещё `work-19` (версии). Этап 3 не нужен.

## Risks / Trade-offs

- [Р4 перегружен: очередь, карточка, возврат, правка, исправление, сверка бригад] → отдельный раунд Р4б
  для сверки бригад (`work-18`), как и предусмотрено нарезкой.
- [Ответ карточки с черновиком отдаёт содержимое] → это нарушение `WORK-54` на сервере. Клиентский
  тест проверяет только отрисовку, поэтому сторож отсутствия содержимого живёт в `work-16`.
