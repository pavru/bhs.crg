# Design

## Context

Мотивация — proposal.md, «Why». Что есть сейчас (снято 16.11.2026):

- **CI**: работа «OpenSpec (строгая проверка)» ставит `@fission-ai/openspec@$OPENSPEC_VERSION` (1.14.3)
  на Node из `.nvmrc` (26.13.0) и запускает `openspec validate --all --strict --no-interactive`. Пакет
  2.0.0 — то же имя и тот же `bin`, `engines.node >=22.12.0`.
- **Машина**: глобальный CLI 1.14.3, глобальная настройка `%APPDATA%\openspec\config.json` —
  `profile: core`, `delivery: commands`. В основной копии — `.claude/commands/opsx/*.md` (6 команд) и
  `.agents/skills/openspec-*` (6 навыков 1.x). Оба каталога в `.gitignore`.
- **Рабочие деревья**: приложение копирует в новое рабочее дерево `.claude/commands/` и
  `.claude/settings.local.json` само, плюс то, что названо в `.worktreeinclude` (сейчас — `dp-keys/` и
  `.claude/launch.json`). `.agents/` не копируется: в рабочем дереве этой сессии его нет.
- **Как 2.0 ставит навыки на Windows** (проверено `openspec init --tools claude` 2.0.0 в пустом
  каталоге): `.agents/skills/openspec-*` — сами навыки, `.claude/skills/openspec-*` — каталожные
  символьные ссылки (`<SYMLINKD>`) с **относительной** целью `../../.agents/skills/<навык>`. Режим
  разработчика на машине включён (`AllowDevelopmentWithoutDevLicense = 1`) — ссылки создаются без
  повышения прав. `core.symlinks` git тут ни при чём: файлы не отслеживаются.
- **Валидатор 1.15–2.0** добавил: предупреждение на сценарий без WHEN/GIVEN или без THEN (1.16.0;
  `--strict` — отказ), отказ на нечитаемый `config.yaml` (1.16.0), отказ на требование в
  неизвестном разделе дельты (1.16.1), чтение заголовков с закрывающими `#`. Строгая проверка 2.0.0 на
  master — 47/47, как на 1.14.3. `openspec instructions` на 2.0.0 отдаёт тот же `context`, те же
  `rules` и ту же подсказку `operations.apply.guidance` из нашего `config.yaml`.
- **Упоминания `/opsx:`** в отслеживаемых файлах: CLAUDE.md и AGENTS.md (по два), `docs/tz/README.md`,
  `docs/tz/90-этапы.md`, `openspec/specs/id/spec.md` (раздел «Ожидает будущих этапов», вне
  требований), а в `openspec/changes/**` — 55 файлов архива и один активный (`costs-1c-import/tasks.md`).

## Goals / Non-Goals

**Goals:**
- CI и машина разработчика проверяют планирование одной версией CLI — 2.0.0.
- Правила проекта и документация называют только то, что после перехода существует.
- Сессия в новом рабочем дереве видит навыки `openspec-*` так же, как сейчас видит `/opsx:*`.
- Переключение не ломает идущие сессии посреди change.

**Non-Goals:**
- Переписывать записи прошлого: архив change и активные change остаются со своими `/opsx:*` (D4).
- Сторож, сверяющий версию в CLAUDE.md с `ci.yml` (D6).
- Расширять профиль навыков (`openspec config profile` — new, continue, ff, verify…): остаётся `core`,
  те же шесть навыков, что сейчас команд.
- Сделать работу «OpenSpec (строгая проверка)» обязательной — решение владельца, отдельно.

## Decisions

**D1. Точная версия `2.0.0`, а не `2` или `latest`.** Причина та же, что у 1.14.3 (комментарий в
`ci.yml`, DEV_NOTES): правила валидатора растут от версии к версии, плавающая версия краснела бы без
правки в репозитории. Подъём — правкой одной строки, PR с ней прогоняет проверку новой версией.
Альтернатива — `1.17.0` (последняя 1.x, те же правила валидатора без смены навыков) отвергнута:
владелец выбрал 2.0, а 1.17 только откладывает смену имён команд.

**D2. Правила называют навыки, а не команды.** CLAUDE.md/AGENTS.md: `/opsx:propose` →
`/openspec-propose`, `/opsx:apply <change>` → `/openspec-apply-change <change>`; команда установки —
`@fission-ai/openspec@2.0.0`. Полная таблица соответствий (все шесть навыков профиля `core` и шесть
дополнительных) — в DEV_NOTES, не в CLAUDE.md: файл читается каждой сессией, таблица нужна редко.
Тем же PR — `docs/tz/README.md`, `docs/tz/90-этапы.md`.

**D3. Спека `id` правится напрямую, без дельты; `skip_specs: true`.** Фраза «заводятся через
`/opsx:propose`» стоит в разделе «Ожидает будущих этапов» — это пояснение, а не требование: дельта
(ADDED/MODIFIED) такой текст не адресует, архив его не трогает. Требований change не меняет вовсе —
поведение системы прежнее, меняется инструмент планирования. Придумывать требование ради дельты
(«версия CLI одна») — значит записать в спеку системы свойство инструмента, которое система не
проверяет. Прецедент дельты у `infra-node26` ([UI-85]) другой: там версия Node — свойство сборки
клиента и сверяется тестом.

**D4. `openspec/changes/**` не трогаем.** Архив — запись своего времени: на дату архивации команда
называлась `/opsx:*`, переписывать историю незачем, и 55 файлов архива раздули бы PR. Активные change
(сейчас — один, `costs-1c-import`) ведут свои сессии; правка чужого change из этой ветки — конфликт с
ними и нарушение «одна сессия — один change». Агент, прочитавший `/opsx:update` в старом change,
найдёт соответствие в DEV_NOTES (D2), а навыки 2.0 сами узнают старые слова («opsx apply» в описании
навыка).

**D5. `.worktreeinclude` копирует `.agents/skills/`.** Ссылки `.claude/skills/openspec-*` относительные
(`../../.agents/skills/…`). Если приложение копирует `.claude/skills/` в рабочее дерево как ссылки, они
указывают на `.agents/skills/` рабочего дерева — без строки в `.worktreeinclude` его там нет, и навыки
пропадают молча, без ошибки. Если приложение копирует содержимое ссылок — строка лишняя, но безвредна
(копия разовая и односторонняя, как у `.claude/launch.json`). Строка добавляется заранее, в PR
реализации: в 1.x `.agents/skills/` в основной копии уже есть, копирование ничего не ломает.
Альтернатива — абсолютные ссылки или копии вместо ссылок — нам недоступна: их создаёт `openspec update`.
Что приложение делает с `.claude/skills/` на самом деле, проверяется после переключения машины
(задача 4.5); если `.claude/skills/` приложение не копирует вовсе — вторая строка `.claude/skills/` в
`.worktreeinclude` отдельным PR (комментарий файла: в `.claude/` нельзя копировать каталог целиком —
там лежат сами рабочие деревья; подкаталог `skills/` можно).

**D6. Сторожа версии CLAUDE.md ↔ `ci.yml` не заводим.** Мест два (AGENTS.md — копия, её сверяет
`AgentRulesCopyTests`), расхождение даёт разработчику другой валидатор локально, а не ложный зелёный в
CI: CI проверяет своей версией. По образцу `nodeVersion.test.ts` его можно добавить потом, если
расхождение случится.

**D7. Машинные шаги — после слияния, в паузе, основной сессией.** Порядок — «Migration Plan». Агент
сессии реализации их не делает: глобальная установка и `openspec update` меняют среду всех сессий
сразу, а сессия реализации — одна из них.

**D8. Плагин полосы узнаёт оба префикса.** `openspec-band/hooks/register.tsx` ловит вызов навыка
только по `skill.startsWith('opsx:')`. После перехода навыки зовутся `openspec-*` — проверка
расширяется на оба префикса: рабочие деревья, созданные до переключения, ещё держат копию
`.claude/commands/opsx/` и зовут старые команды. Имя change по-прежнему — первое слово аргументов;
для `openspec-propose`/`openspec-explore` с описанием вместо имени `NAME` отсечёт лишнее, как сейчас с
`opsx:propose`. Тест — второй случай в `band.test.tsx` с `skill: 'openspec-apply-change'`.

## Risks / Trade-offs

- [Окно между слиянием и переключением машины: CLAUDE.md уже называет `/openspec-*`, а у машины ещё
  `/opsx:*`] → машинные шаги сразу после слияния, в паузе (D7); навыки 2.0 и старые команды делают
  одну работу — сессия, вызвавшая старое имя, не испортит change.
- [Рабочие деревья, созданные до переключения, держат свою копию `.claude/commands/opsx/` — команды
  1.x зовут уже глобальный CLI 2.0] → подкоманды CLI, которыми пользуются навыки (`new change`,
  `status`, `instructions`, `validate`, `archive`), в 2.0 те же («workflows haven't changed», заметки
  2.0.0); всё же переключаться, когда сессий посреди change нет, а живые — довести на прежнем.
- [`openspec update` перезаписывает `.agents/skills/` без резервной копии] → перед обновлением копия
  каталога в сторону; правок в нём не ожидается (не наши), но копия дешевле догадки.
- [Навыки не доехали до рабочего дерева — тихо, без ошибки: сессия просто не видит
  `/openspec-*`] → D5 заранее и проверка новым рабочим деревом (задача 4.5) до возобновления потоков.
- [Ссылки на машине без режима разработчика] → на этой машине режим включён (проверено). На другой
  машине без него `openspec update` кладёт копии вместо ссылок — работает так же, только копии надо
  обновлять тем же `openspec update`.
- [Новые правила валидатора 1.15–2.0 закрывают то, что прежде проходило] → весь нынешний набор
  проходит; новое планирование узнает об этом в CI своего PR, как сейчас.

## Migration Plan

1. **PR реализации** (`/openspec-apply-change infra-openspec-2` или `/opsx:apply` — что есть в момент
   запуска): разделы 1–3 tasks.md. Слияние — пользователь.
2. **Пауза**: основная сессия убеждается, что нет сессий посреди change (идущие доводят шаг и
   останавливаются).
3. **Машина** (основная сессия, раздел 4 tasks.md): копия `.agents/skills/` в сторону →
   `npm install -g @fission-ai/openspec@2.0.0` → `openspec update --dry-run` → `openspec update` в
   основной копии → проверка ссылок → плагин полосы → память.
4. **Проверка**: новое рабочее дерево видит `/openspec-*`, полоса откликается на вызов навыка.
5. Потоки plan/work возобновляются с новыми именами навыков.

**Откат**: `npm install -g @fission-ai/openspec@1.14.3`, глобальная настройка `delivery: commands`,
`openspec update` в основной копии (вернёт `.claude/commands/opsx/`), PR с возвратом строки
`OPENSPEC_VERSION` и текстов. Файлы проекта (спеки, change) от версии CLI не зависят — откат их не
касается.
