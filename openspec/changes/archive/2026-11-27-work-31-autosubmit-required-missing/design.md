# Work‑31. Дизайн пометки после автоподачи

## Context

[AutoSubmitJob](../../../../src/server/BHS.CRG.Modules.Work/Submission/AutoSubmitJob.cs) вычисляет пропуски по `RequiredFields`, подаёт отчёт концом окна, сохраняет `RequiredMissing` и пишет исходный перечень в журнал. `ReportViews` возвращает это поле как снимок. Правка строк поданного отчёта сохраняет его происхождение, а `Report.Submit` при ручной повторной подаче заменяет снимок. `ResubmitAcceptedEdit` выставляет `SubmittedBy = Manual` и может оставить прежнее значение снимка.

[ReportReads.QueueAsync](../../../../src/server/BHS.CRG.Modules.Work/Data/ReportReads.cs) отбирает `Submitted` в охвате читателя и строит счётчики до отбора по пометке. `ReviewMarks` содержит общие коды, а `fields-missing` поступает из `IModuleAcceptanceFields` через отдельный расчёт. `ReviewQueuePage` уже читает `marks` и `counts`, `ReportCard` показывает текст пометок из `marks`.

## Goals / Non-Goals

Один расчёт обязательности для перехода подачи и чтения. Одна выборка для состава строк с пометкой, её счётчика и отбора. Граница изменения проходит по чтению очереди и текущей карточки приёмки [WORK-59, WORK-28]. Хранение, журнал, правила записи и архивные версии продолжают обслуживаться существующими путями.

## Decisions

### 1. Снимок события и текущие пропуски

Использовать для активной пометки пару `Status == Submitted` и `SubmittedBy == Auto`. Вынести из `RequiredFields` общий расчёт над строкой и полученными признаками вида работы. Проверка места использует `IsNullOrWhiteSpace`, проверка материалов — отсутствие элементов. Подача продолжает передавать результат в прежний контракт записи и отказа 422. Чтение оценивает действующие признаки вида и текущее сохранённое содержание строк. Так заполнение, удаление, перестановка строки, смена её вида и правки классификатора отражаются на следующем чтении.

Прямое использование `RequiredMissing` превратило бы сохранённый факт автоподачи в постоянное предупреждение даже после исправления. Обновление снимка на каждом пути записи привязало бы чтение к набору писателей и создало бы накопительное состояние при правке классификатора. Расчёт на чтении работает и для уже сохранённых автоподанных отчётов. `null` от порта видов и не найденный вид дают ту же границу известного, что при подаче. В таких случаях предупреждение относится только к подтверждённым пропускам, а запись журнала ядра о непроведённой проверке при автоподаче сохраняется.

### 2. Счётчик и отбор из общего результата

В [ReportReads](../../../../src/server/BHS.CRG.Modules.Work/Data/ReportReads.cs) использовать уже ограниченный `chosen`, включая отборы стройки, сотрудника и дат. Для автоподанных кандидатов читать идентификатор отчёта, стройку и дату, вид работы, место и признак наличия хотя бы одного материала. По одному снимку границ компании и строек оставить только строки открытого периода. Загрузить их признаки видов одним вызовом `IModuleWorkTypes.GetAsync` по различным идентификаторам. `ModuleWorkTypesPort` загружает классификатор целиком, поэтому вызов из цикла по отчётам умножил бы стоимость запроса.

В рамках нынешнего `RepeatableRead` получить карту отчётов с подтверждённым пропуском и признаком нехватки места, материалов или обоих. По этой карте сформировать счётчик, множество идентификаторов для `mark=required-missing` и текст пометки у строки. `selected.Count()`, сортировка по `SubmittedAt` и `Id` и пагинация идут после отбора по коду. `PendingEmployeeIds`, причина пустоты и охват остаются зависимыми от действующих условий очереди. У отчёта с несколькими пропусками в счётчике одна единица. Поля заказчика продолжают иметь собственный порядок расчёта и счётчик.

В [ReviewMarks](../../../../src/server/BHS.CRG.Modules.Work/Data/ReviewMarks.cs) зарегистрировать `required-missing` как вычисляемую на чтении пометку с явным источником, подобно регистрации `fields-missing`. Логику выбора текста по сочетанию пропущенных полей держать там же. В строке `ReviewQueueRowDto` достаточно действующего `marks`. В карточке построчные сведения доступны только там, где уже выдано содержимое отчёта.

### 3. Карточка и потребление результата

[ReviewCard](../../../../src/server/BHS.CRG.Modules.Work/Review/ReviewCard.cs) получает разрешённое содержимое через `ReportHistory.ReadCardAsync` и уже читает признаки тех же видов через порт. Использовать текущие строки DTO и результат этого чтения. Дополнить `report.marks` через каталог и вернуть типизированное `currentRequiredMissing` в полном ответе карточки с `line`, `lineId` и `field`. У подходящего отчёта список составлять по порядку строк DTO. Для остальных полных ответов список пустой. Краткий ответ о черновике сохраняет прежний состав. Выбор архивной версии и закрытый период исключают текущую пометку. `ReportViews`, `ReportHistory` и журнал сохраняют семантику `requiredMissing`, существующих пометок и исторического содержимого.

Синхронизировать `WORK_MARK_CODES`, тип полного ответа в `workReview.ts` и `reviewMarks.ts`. В известных клиенту кодах чип использует постоянное название категории, строки показывают точный серверный текст. `ReviewQueuePage` пользуется существующим отбором, карточка связывает позиции с `lineId`. Сохранение места из редактора приёмки уже обновляет карточку и очередь через `updateAfterWrite`. Материалы можно заполнить в существующей форме отчёта, в том числе после возврата. Положение построчной расшифровки выбирается по трём живым макетам до правки интерфейса.

## Risks / Trade-offs

- Объём расчёта растёт с числом автоподанных отчётов после отбора → читать узкую проекцию, загрузить виды одним вызовом на запрос и проверить, что чтение карточки переиспользует свой вызов порта.
- Чтение классификатора живёт за портом отдельно от транзакции Work → использовать один полученный набор признаков для всех результатов конкретного ответа. Самостоятельные запросы очереди и карточки могут увидеть разные сохранённые версии при правке между запросами.
- Повторная сборка DTO пометок может потерять `fields-missing` → проверять одновременную выдачу обеих пометок и снятие только исправленной, включая ответ карточки после перечитывания.

## Migration Plan

Обычная поставка Work. Новые поля чтения и код пометки добавляются совместимо. Старые отчёты подхватываются при чтении, а откат возвращает прежнее отображение при неизменной схеме данных.

## Варианты интерфейса

- [А · Пометка и список в карточке](http://127.0.0.1:5200/?section=mockups&project=work-31-autosubmit-required-missing&page=a) сохраняет текущий маршрут из очереди в карточку. Список пропусков виден при открытии карточки.
- [Б · Очередь и панель отчёта](http://127.0.0.1:5200/?section=mockups&project=work-31-autosubmit-required-missing&page=b) сохраняет контекст очереди рядом с карточкой на широком экране. На узком экране очередь и отчёт открываются последовательно.
- [В · Пропуски в строках](http://127.0.0.1:5200/?section=mockups&project=work-31-autosubmit-required-missing&page=c) даёт раскрытие подробностей в очереди и подсказки рядом с данными отдельных строк в карточке.

Для Work‑31 подходит вариант А. Он сохраняет действия и маршруты, а перед правкой даёт менеджеру список строк одним взглядом. В трёх макетах можно включить отбор, заполнить места и материалы в примере и отдельно проверить отбор по полям заказчика. Для просмотра доступны тёмная тема и узкий экран.

**Выбор владельца 27.11.2026 — вариант А.** В очереди используется существующая колонка пометок и чип отбора. В карточке объём исправления виден перед списком работ.
