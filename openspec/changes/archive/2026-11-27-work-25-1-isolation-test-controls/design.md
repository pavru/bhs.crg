# Work-25.1. Устройство проверки чувствительности

## Context

Основание — [#2096](https://github.com/pavru/bhs.crg/issues/2096), задачи 1.1, 1.5 и 1.6
[архива Work-25](../2026-11-25-work-25-roles-e2e-violation/tasks.md) и архивное требование
`[STG-6] Проверка нарушением срабатывает`. В действующей спецификации Work уже описаны хранение
[WORK-39] и штатное чтение [WORK-39] [WORK-40]. [AUTH-8] [AUTH-9] и [AUTH-12.1] [AUTH-12.2]
оставляют HTTP и MCP их собственные ворота. Work-30 локализовал хранение, а
`core-request-data-access-port` ввёл доступный в текущей базе `IRequestDataAccessResolver`.

`WorkIsolationViolationTests` проверяет штатные роли и хранение. `.Routes.cs` сверяет шаблоны
GET с `EndpointDataSource`, различает сигналы текста, фото и справочных путей. `.Storage.cs`
даёт независимые байты оригинала и превью. `.RequestScope.cs` использует второй хост через
`ConfigureTestServices` на текущей базе и сужает охват одного читателя для таблиц и источников.
Проверка метаданных контрольного описания и тест числового помощника сами по себе не проверяют,
что общий обход замечает отсутствие фактического ответа.

## Goals / Non-Goals

- Подтвердить 1.1, 1.5 и 1.6 по таблице ниже в отдельном change.
- Проверять только синтетические записи и запускать контролируемую конфигурацию в процессе
  интеграционных тестов. Применять действующие публичные контракты и права.
  Хранение и браузерный посев уже покрыты Work-25.

## Decisions

### Хосты и ожидаемые значения

Переиспользовать `WorkIsolationHost`, `AssignmentHost` и `ReportWorld`. У двух экземпляров
отдельные именованные тестовые БД и отдельные `FakeBlobStorage`, по одному `TestServer` и
контейнеру служб. Посев и публикация источников идут через штатную конфигурацию каждого
экземпляра с одинаковым составом данных и локальными идентификаторами. Фикстура сохраняет
словарь идентификаторов, уникальную метку, ожидаемые наборы ключей, часы и объёмы,
идентификаторы строк и файлов каждого экземпляра. Сопоставление использует смысловые
записи А и Б. Файловый эталон снимается в хранилище экземпляра до запросов обхода.
Включение отклонения ограничить чтением в управляющем сценарии, после посева. Конфигурацию
задаёт исключительно фикстура тестов при создании хоста. Хосты должны
отвечать как реальные экземпляры приложения, с обычной маршрутизацией, сериализацией,
воротами и собственными запросами к БД.

Один каталог проб и один исполнитель для штатного и контрольного обхода. По каждому
элементу фиксировать профиль, вызов, ожидание HTTP или MCP, применимый сигнал и факт
исполнения. Сверять список выполненных вызовов с обязательными пробами из инвентаря обоих хостов
и списка внешних вызовов. Проверять уникальность проб и покрытие динамических параметров. Если обязательный вызов пропущен,
вернул пустой/неподходящий результат или не подтвердил ожидаемый сигнал, сообщение называет
адрес или инструмент и ожидаемое поле. Для проверки чувствительности подавить исполнение
одной уже известной содержательной пробы и отдельно проверить отсутствие её сигнала у
аутентичного ответа с узким охватом. Действующий сторож должен отличать оба случая.

### Точки тестовой настройки и матрица

`IRequestDataAccessResolver` формирует параметр запроса для таблиц, наборов и содержательных
снимков MCP. `IModuleReaders` обслуживает прямые маршруты Work и отдельно зарегистрирован
в `ModulePorts`. Его адаптер `ModuleReadersPort` получает конкретный `DataAccessResolver`,
поэтому замена интерфейса ядра сама по себе до него не доходит. Контрольные декораторы
ограничить конкретными синтетическими читателями и вызовами чтения. Делегировать штатным
службам прочие вызовы, включая посев и фоновые задания. Выдать каждому профилю только
штатные права для соответствующего маршрута. Для менеджерских маршрутов использовать
профиль менеджера, а его охват контролировать отдельно от входных ворот. Для маршрутов
под правом руководителя сохранить штатный положительный прогон под руководителем.
Политики авторизации и выходные DTO работают штатно на обоих хостах. Замены регистрируются
в сборке тестов. В конфигурации поставки возможен только штатный охват. Посев и проверки
выполняются в локальных экземплярах приложения, подготовленных фикстурой.

Во всех содержательных строках матрицы проверяются все вызовы действующего обхода.
Текстовые совпадения сверять в конкретных полях или ячейках. Для чисел по контракту
использовать отдельные эталоны из посева и запросов, включая пустые значения. Для каждого
вызова утверждать ожидаемый статус. Внутри отдельного диагностического сценария первичным
целевым утверждением служит отсутствие сигнала Б на границе, выбранной для красного CI.

### Контрпример для чтения своих отчётов

`ReportEndpoints.ListAsync` передаёт один `Guid employeeId` в `ReportReads.SinceAsync`.
Тот фильтрует и отчёты, и удаления по равенству этому ID. `ReportEndpoints.GetAsync`
отдельно создаёт `ReportViewer.Own`. Ни `IRequestDataAccessResolver`, ни `IModuleReaders`
в этих двух цепочках не участвуют. Замена результата `IModuleEmployees` может показать
контрольный отчёт Б вместо отчёта А, но не может вернуть оба при одном посеве.

Для полного охвата на этих двух GET предусмотреть узкую внутреннюю точку формирования
`ReportViewer` только для чтения своих отчётов. Штатная реализация
должна получать того же сотрудника через `MeAsync` и возвращать тот же `Own`. Для списка
нужен явный охват запросов страниц и удалённых записей, сохранение состава и порядка
курсора, лимита, обработки удалений и версий. Продуктовая регистрация поддерживает только
текущий штатный вариант. Контролируемое значение поставляет тестовый хост. Ответы, ворота,
пишущие адреса и права берутся из действующих контрактов. Если узкая граница несовместима
с контрактом MOB-16, согласовать с владельцем до реализации этого шага. Упрощение контрольной
выдачи требует отдельного продуктового решения.

### Доказательство в GitHub CI

1. Будущий PR реализации открыть после слияния планового PR и сверки актуального `master`
   и очереди повышения версии. Держать его черновиком до получения проверок.
2. Первый коммит содержит полный тест и временно подключает контролируемую конфигурацию
   к основному тестовому хосту в целевом сценарии. В качестве диагностической пробы использовать
   штатное чтение `work.reports` под А. После успешного ответа и разбора ключей первым сравнить
   отсутствие ключа Б. Утверждение с именем таблицы применяется в обоих коммитах. Оба хоста
   должны пройти старт, посев и проверку формы ответа.
3. Дождаться завершения прогона CI первого коммита, поскольку `cancel-in-progress` отменяет
   предыдущий прогон при новом push. Проверить итог `Backend (сборка + тесты)` и лог нужной
   доли `Backend — доля`. Сохранить SHA головы PR, ссылку на запуск и долю, имя теста и
   целевое утверждение с адресом. Внешняя ошибка, посев, компиляция, Costs и Typst доказательством
   не считаются. Локальный прогон служит подготовкой.
4. Вторым коммитом убрать временную регистрацию основного хоста. Сохранить второй хост,
   тот же обход, утверждения и положительный контроль. Опубликовать вторым push в том же
   PR с сохранённой историей. Дождаться зелёного CI, включая итог Backend. Записать SHA и
   ссылку. Плановый PR содержит только OpenSpec и проходит свою строгую проверку.
5. При последующей работе несколькими PR начинать каждый после слияния предыдущего и
   подтверждённого изменения версии для слияния с изменениями кода. Для планового PR
   проверить, что повышения не требуется по `planning-only.sh`.

### Сверка исходных идей с кодом

Описания объединяли новую работу с уже слитыми посевом, браузерным прогоном и настройкой CI.
Две идеи требовали одного текстового маркера в любой выдаче. Снимок каталога MCP, служебные
справочники, байты фото и числовые итоги показывают, почему каждого формата касается свой
критерий. Одна подмена охвата не достигает двух GET своих отчётов, а регистрации для таблиц и прямых
маршрутов независимы. Для таблиц, источников и MCP в ядре уже есть порт доступа запроса.
`work-27` слит и архивирован. Ограничиться проверкой 404 и текста для
фото означало бы потерять уже имеющееся независимое сравнение оригинала и превью.
Таблица критериев сохраняет требование проверить каждый содержательный вызов и штатный
контроль остальных вызовов. Наблюдения этого плана описывают полноту проверки. Они сами
по себе не устанавливают наличие выдачи отчёта за пределами охвата в штатном приложении.

## Risks / Trade-offs

- Выход из строя общей фикстуры может скрыть целевое утверждение. Диагностика называет
  фазу, профиль и проверяемый вызов, а за доказательство принимается целевое падение в логе.
- Общие счётчики и каталоги легко принять за данные отчётов. Сверять по назначению
  конкретного поля и фиксировать независимые эталоны, включая допустимый пустой исход.
