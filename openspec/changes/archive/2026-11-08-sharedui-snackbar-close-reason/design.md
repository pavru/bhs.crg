# Design: отклик закрытия уведомления с причиной

## Context

Снэкбар ([UI-71]) устроен из трёх частей:
- `Snackbar.ts` — тип `SnackbarOptions` и хук `useSnackbar`;
- `snackbarQueue.ts` — чистый редьюсер очереди: `push`, `close`, `next`;
- `SnackbarProvider.tsx` — держит редьюсер в `useReducer` и рисует видимое уведомление через
  `@radix-ui/react-toast`.

Срок показа, паузу на наведении и фокусе, смахивание и Esc даёт Radix. Закрытие любым из этих путей
приходит одним `onOpenChange(false)`, причину оно не несёт. Отбрасывает очередь в двух местах редьюсера:
- `next` — отбрасывает ожидающих старше `PENDING_TTL_MS`, и делает это только при сдвиге, то есть когда
  закрылось видимое;
- `push` — при переполнении сверх `PENDING_MAX`.

Зачем всё это нужно, сказано в `proposal.md`, раздел Why. Требования — `specs/sharedui/spec.md`.

Чего ждут потребители:
- **13** (`pendingDelete.ts`, D-13.4) шлёт `DELETE` при закрытии, кроме «Вернуть». Ему нужно отличать
  `action` от остального, а `dropped` для него — тоже «отправить».
- **12** (D-12.2) после удаления строки ставит пометку `lines` по закрытию снэкбара. Причина ему не важна,
  важен сам факт закрытия.

## Goals / Non-Goals

**Goals:**
- отклик зовётся ровно один раз на уведомление при любом исходе, в том числе когда уведомление не
  показалось вовсе;
- редьюсер остаётся чистым — тесты очереди обходятся без Radix и таймеров.

**Non-Goals:**
- закрывать уведомление из кода (`dismiss(id)`): ни 12, ни 13 этого не просят;
- звать отклик при размонтировании провайдера. Провайдер стоит в корне `App` и живёт, пока жива вкладка.
  Закрытие вкладки потребитель ловит сам через `pagehide` (13, D-13.4), снэкбар о нём не узнаёт;
- менять сроки и правила старения очереди.

## Decisions

### D1. Причину различает провайдер, а не Radix

Radix сообщает о закрытии без причины. Поэтому провайдер ставит её в ссылку видимого уведомления раньше,
чем Radix закроет его:
- у `RT.Action` наш `onClick` выполняется до закрытия Radix, ведь `composeEventHandlers` зовёт обработчик
  свойства первым. Ставим `action`;
- `RT.Close` с `onClick`, `onSwipeEnd` и `onEscapeKeyDown` у `RT.Root` ставят `dismissed`. Esc на всём
  поле уведомлений Radix тоже проводит через `onEscapeKeyDown` у `Root`;
- `onOpenChange(false)`, перед которым причина не поставлена, означает `timeout`. Сам Radix закрывает
  только по таймеру.

Две тонкости `Action` (ревью PR #1804):
- **Смахивание, начатое на кнопке.** Щелчок, которым оно кончается, Radix гасит через `preventDefault`. Но
  обработчик свойства `composeEventHandlers` зовёт до этой проверки. Поэтому наш `onClick` сам выходит при
  `defaultPrevented`, иначе «Вернуть» сработало бы после `dismissed`.
- **Причина ставится после действия.** Упавшее действие обрывает цепочку, и Radix уведомление не закрывает.
  Поставленная заранее причина `action` пришла бы потом вместе со сроком, и 13 решил бы, что нажато
  «Вернуть».

**Альтернатива:** свой таймер вместо `duration` Radix. Отвергнута: пришлось бы повторить паузу на
наведении, фокусе и уходе окна, которую Radix уже даёт.

### D2. Отброшенные копит очередь, отклик зовёт провайдер

Звать отклик из редьюсера нельзя. Редьюсер обязан быть чистым: React в режиме `StrictMode` зовёт его
дважды, и отклик ушёл бы дважды. Поэтому у состояния очереди появляется поле `dropped`: уведомления с
откликом, которые `next` или `push` отбросили. Без отклика туда ничего не попадает, состояние не растёт
зря. Провайдер в эффекте зовёт `onClose('dropped')` у каждого и отдаёт действие `flush`, очищающее
список.

Второй вызов отклика исключает множество уже закрытых уведомлений в провайдере, общее для всех четырёх
причин. Без него двойной `onOpenChange` или повторный эффект позвали бы отклик дважды. Множество слабое
(`WeakSet` элементов очереди), так что ушедшее из очереди не копится в нём, пока жива вкладка.

Каждый отклик зовётся под `try`, а сбой уходит в `reportError`. Провайдер стоит выше корневой границы
ошибок (`App.tsx`): исключение из эффекта размонтировало бы всё приложение. Кроме того, отклики остальных
отброшенных не позвались бы вовсе. По той же причине `flush` отдаётся после цикла.

**Альтернатива:** редьюсер возвращает отброшенных вместе с состоянием, а провайдер зовёт `dispatch` сам.
Отвергнута: `useReducer` так не умеет, а свой контейнер ради этого заменил бы простой хук.

### D3. Уведомление с откликом не стареет; переполнение вытесняет его последним

Сначала уведомление с откликом старело наравне с успехом. Ревью PR #1804 показало, что так отложенное
действие выполняется, а «Вернуть» человек не видит ни разу:
- три удаления подряд по 8 с — третье ждёт 16 с и отбрасывается;
- пауза на наведении или уход из вкладки останавливают срок видимого, а ожидающие стареют по часам.

Старение заведено против стопки давних «Сохранено» от опроса и фоновой вкладки. К уведомлению о действии
человека, которое ещё можно отменить, этот довод не относится. Поэтому такое уведомление не стареет, как
и ошибка.

Переполнение вытесняет самого старого из наименее ценных не-ошибок: сведение, затем со своим действием,
затем с откликом. Раньше уходил самый старый не-ошибка без разбора, и «Вернуть» вытеснялось раньше
десятка «Сохранено». `dropped` остаётся, но приходит только тогда, когда в очереди одни ошибки и
уведомления с откликом. Решение Э5 «отброшенное считается закрытым» это не меняет: его сужает только
то, кого очередь вообще отбрасывает.

**Альтернатива** — старить от момента, когда до уведомления дошла очередь. Отвергнута: «дошла» —
это и есть показ, так что правило свелось бы к «не стареет».

### D4. Уведомление с откликом не сливается с повтором

Ключ повтора (`snackbarKey`) у такого уведомления не сверяется: `push` ставит его всегда. Слить два
уведомления значило бы либо потерять второй отклик, либо закрыть его `dropped` сразу. Тогда второе
«Строка 7 удалена · Вернуть» вернуло бы первую строку. Защита от двойного щелчка остаётся за вызывающим:
у него и так есть своё состояние (строка уже удалена, черновик уже в очереди удаления).

### D5. Срок «Вернуть» — постоянная, а не правило по тексту кнопки

`SNACKBAR_UNDO_MS = 8000` экспортируется из `Snackbar.ts`. Уведомление с `onClose` без своего `duration`
получает этот срок само: отклик и есть признак отложенного, отменяемого действия, и забытый `duration`
не должен сокращать окно отмены до 4 с (ревью PR #1804). «Вернуть» без отклика (архив, избранное)
передаёт постоянную в `duration`. Срок по умолчанию для прочих уведомлений с действием не меняется.

С 8 с ошибки (`DEFAULT_DURATION.error`) постоянная не связана. Сроки совпадают по решению, а не по
определению: продление ошибки не должно продлевать «Вернуть», и наоборот. «Вернуться», «Перейти» и «Показать все» действие
не отменяют, и решение Э5 их не касается. Узнавать «Вернуть» по тексту `label` хрупко. Три нынешних
«Вернуть» переходят на постоянную.

## Risks / Trade-offs

- [Отклик бросил исключение] → сбой уходит в `reportError` (D2): он виден и не роняет приложение.
- [Radix сменит порядок обработчиков `Action`] → причина `action` превратится в `timeout`. Тест провайдера
  нажимает действие и проверяет причину, так что обновление Radix это поймает.
- [Отклик не зовётся, если провайдер размонтирован] → провайдер стоит в корне приложения. Отложенное до
  закрытия вкладки потребитель отправляет сам (`pagehide`), см. Non-Goals.

## Migration Plan

Свойство необязательное: нынешние ~100 вызовов `useSnackbar` не меняются. «Убрано из избранного»
держится 8 с вместо 4. Откат — возврат коммита, данных нет.
