# Design: вход Typst для генерации и отладочного пакета — одним кодом

## Context

Мотив — proposal.md. Ниже то, что найдено в коде master (`40202adf`).

**Сборка контекста** написана четыре раза, одними и теми же семью шагами: `ResolveAsync` →
`DataSetResolver.InjectAsync` → `ApplyDefaults` → `ResolveEnumLabels` → `QualityLinkResolver.InjectAsync`
→ `ResolveContextRefs` → `ResolveComputedFields`. Копии отличаются тем, что делают после.

| Где | Проверки после шагов | Что останавливает | Штамп `_type` / `params` |
|---|---|---|---|
| `GenerateDocumentHandler.cs:72–115` | `ScanLeftoverRefs`, `ScanMissingRequired`, `ValueTypeScanner`, `QualityLinkScanner` | любая ошибка | штамп один раз, `params` на каждый шаблон |
| `PreviewDocument.cs:80–101` (реквизиты — несохранённые, из запроса) | только `ScanLeftoverRefs` | ошибка шагов или висящей ссылки; полнота и типы значений — нет | так же |
| `GetGenerationDebugBundle.cs:67–80` | нет; диагностика наборов не собирается (`null`) | ничего | `params`, потом штамп |
| `InstanceResolutionValidator.cs:64–86` (снимок схем `SchemaCatalog` — для пакетной сверки) | все четыре | — (возвращает диагностику) | нет |

`DomainSnapshotService.cs:307` — пятый вариант, но другой по смыслу: `keepRefProvenance`, без наборов
данных. Его этот change не трогает.

**Каталог компиляции** пишут два места:

| | `TypstGenerator.cs:28–135` | `GenerationEndpoints.cs:128–261` (пакет) |
|---|---|---|
| картинки | `MaterializeAsync(data)`, нечитаемые → `UnreadableImagesException` | `MaterializeJsonAsync(json)`, нечитаемые не собираются |
| вложения | `TypstFileMaterializer`, `att_N`, предел 100 МБ | то же (тот же класс) |
| ассеты шаблона | предел 100 МБ, отмена пробрасывается | без предела, `catch { }` глушит и отмену |
| шрифты | `--font-path`, только если скачался хоть один | README, если шрифты объявлены |
| `data.json` | компактный | с отступами (значения те же) |
| `template.typ`, `systemlib.typ`, блоки типов, библиотека | `TypeBlocksMaterializer`, `UserLibMaterializer` | свои `WriteEntry` в zip «той же раскладкой» |

Ещё одна копия — сборка `GenerationRequest`: блоки типов, снимок библиотеки, ассеты шаблона, `params`.
Её повторяют генерация, предпросмотр и пакет.

Тестов у генерации, предпросмотра и пакета нет: в `BHS.CRG.Tests` нет ни одного вызова
`/api/generate/*` и ни одного теста обработчиков. Юнит-тесты есть у отдельных кирпичей — материализаторов,
сканеров, штампа.

## Goals / Non-Goals

**Goals:**
- у каждого из двух этапов — сборка контекста и запись каталога — одна реализация;
- пакет архивирует каталог, записанный тем же кодом, каким пишет генерация;
- поведение генерации, предпросмотра и проверки документа не меняется;
- тест, который краснеет при расхождении пакета с генерацией.

**Non-Goals:**
- выбор шаблона — это `id-debug-bundle-template-choice` (#1401). Новые функции получают шаблон готовым;
- `DomainSnapshotService` — у него другая задача;
- новые параметры пакета (`?templateId=`, пакет на несколько шаблонов) — пакет по-прежнему про первый
  шаблон экземпляра;
- переход генерации в фоновую задачу и любые правки маршрутов.

## Decisions

### D1. `GenerationContextBuilder` — семь шагов и все проверки [CORE-21]

`Application/Generation/GenerationContextBuilder.cs`. На вход: `DocumentView`, `DataAccess` и снимок схем
(`SchemaCatalog`: типы, примитивы, все типы для `QualityLinkScanner`). На выход:
`(GenerationContext Context, Diagnostics Resolution, Diagnostics Checks)`.

- `Resolution` — диагностика семи шагов и `ScanLeftoverRefs`; это «контекст не собрался».
- `Checks` — `ScanMissingRequired`, `ValueTypeScanner`, `QualityLinkScanner`; это «собрался, но выпускать
  нельзя / есть предупреждения».

Почему две корзины, а не одна: предпросмотр сегодня останавливается только на первой. Одна корзина
заставила бы его либо начать отказывать на незаполненных полях (сломали бы живой предпросмотр
незаконченного документа), либо отфильтровывать коды — и правило «что останавливает предпросмотр» опять
жило бы в вызывающем по кодам. Так оно выражается выбором корзины.

Вызывающие:
- генерация — отказ при ошибке в любой корзине (как сейчас);
- предпросмотр — при ошибке в `Resolution`; `Checks` не смотрит (как сейчас); `DocumentView` с
  реквизитами запроса — как сейчас;
- проверка документа — возвращает обе (как сейчас); пакетная сверка (`QualitySetAudit`) передаёт свой
  снимок схем, как сейчас передаёт в `ValidateAsync`;
- пакет — обе корзины в README (D5), ничего не останавливает.

Альтернатива — общий базовый класс обработчиков: связывает четыре обработчика наследованием ради одного
метода, а `InstanceResolutionValidator` вообще не обработчик. Отклонена.

### D2. `GenerationRequestBuilder` — запрос на шаблон [CORE-21]

`Application/Generation/GenerationRequestBuilder.cs`: штамп `_type` (один раз на контекст) и на каждый
шаблон — `params`, блоки типов, снимок библиотеки, ассеты шаблона → `GenerationRequest`. Его зовут
генерация (в цикле по шаблонам), предпросмотр и пакет. Порядок «штамп, потом `params`» берём у генерации;
у пакета он обратный, но штамп `params` не трогает — содержимое не меняется.

### D3. `TypstCompileDirectory` — одна запись каталога [CORE-21] [CORE-22]

`Infrastructure/Generation/TypstCompileDirectory.cs`: `WriteAsync(GenerationRequest, dir, JsonLayout,
ct) → CompileLayout(FontsDir?, UnreadableImages)`. Пишет всё из таблицы выше, с пределом 100 МБ и для
ассетов, и для вложений, с проброшенной отменой. `FontsDir` есть, только если записан хотя бы один шрифт.

- `TypstGenerator.GenerateAsync`: `WriteAsync(…, Compact)` → нечитаемые картинки → отказ (как сейчас) →
  компиляция с `--font-path`, если есть `FontsDir`.
- Новый `TypstGenerator.DebugBundleAsync(GenerationRequest, BundleNotes, ct)`: `WriteAsync(…, Indented)`
  → `README.txt` (D5) → zip каталога как есть. Метод добавляется в `IDocumentGenerator`: каталог и его
  архив — забота одного объекта, и Api больше не знает про материализаторы.

`JsonLayout.Indented` у пакета оставлен: человек читает `data.json` глазами, а Typst значения
форматирования не видит. Сторож (D6) сравнивает разобранный JSON, а не байты.

Альтернатива — генератор оставляет каталог на диске по флагу, а пакет его подхватывает. Отклонена:
появляется флаг «не убирать за собой» в рабочем пути генерации ради отладки, и двойная запись при
предпросмотре.

### D4. Пакет — обработчик, а не эндпоинт

`GetGenerationDebugBundleHandler` возвращает готовые байты zip: строит контекст (D1), запрос (D2) и зовёт
`DebugBundleAsync` (D3). Эндпоинт только отдаёт файл. Из `GenerationEndpoints.cs` уходят ~130 строк, и
файл перестаёт быть кандидатом в храповик размера. Ответ «экземпляра нет» (404) — как сейчас.

### D5. README называет отказ [CORE-21] [CORE-22]

`BundleNotes` — ошибки обеих корзин D1 (код, путь, текст) и нечитаемые картинки из `CompileLayout`.
`README.txt` пишется, если есть что сказать: команда компиляции (с `--font-path fonts`, когда есть
`FontsDir`) и перечень «генерация откажет: …». Предупреждения в перечень не входят — они выпуск не
останавливают. Пакет без шрифтов и без отказов README не получает, как сейчас.

### D6. Сторож — интеграционные тесты на настоящем Typst [CORE-21] [CORE-22]

Новый класс `Integration/GenerationDebugBundleParityTests` (Typst CLI в CI есть, тест кодировки уже на
него опирается). Сид: тип с картинкой, вложением-PDF, шаблоном с ассетом-картинкой и шрифтом, экземпляр.

- Выпуск через `POST /api/generate/{id}`, затем пакет того же экземпляра: набор путей zip совпадает с
  каталогом генерации. Каталог генерации снимается шпионом `IBlobStorage`/временного каталога в тесте, без
  флага в рабочем коде; разобранный `data.json` совпадает; PDF, скомпилированный из распакованного пакета,
  совпадает с выпущенным по тексту (PdfPig) и числу листов.
- Ассет больше предела (подменённое хранилище отдаёт поток длиннее предела) — нет ни там, ни там.
- Шрифт объявлен, хранилище его не отдало — README без `--font-path`, генерация компилирует.
- Отмена — `CancellationToken` отменён на загрузке ассета — `OperationCanceledException`, не zip.
- `missing-required` и нечитаемая картинка — пакет 200, README называет код/путь и поле; генерация — 422.
- Регрессия поведения: предпросмотр незаполненного документа по-прежнему рисуется; проверка документа
  возвращает тот же набор диагностики, что до перехода (снимок на сиде).

## Risks / Trade-offs

- [Поменять поведение предпросмотра или проверки, сводя их на общий код] → корзины D1 повторяют нынешние
  правила остановки; отдельные регрессионные тесты D6 на предпросмотр и проверку.
- [Пакет теряет ассеты больше 100 МБ, которые раньше в нём были] → так и задумано: генерация их тоже не
  видит, отлаживать по ним нечего. Сказано в описании PR.
- [Тесты на настоящем Typst медленные] → один сид на класс, компиляция — два раза на тест-класс.
- [Пересечение с `id-debug-bundle-template-choice` по `GetGenerationDebugBundle.cs` и
  `GenerateDocumentHandler.cs`] → правки разных строк: тот change меняет выбор шаблона, этот — всё после
  него. Кто сливается вторым, обновляет ветку от master; одна сессия — один change.
- [`plan-15-record-print` начнут раньше] → его дизайн уже говорит «тем же кодом, что документы»; при
  старте он опирается на D2 и D3. Если plan-15 стартует первым — сначала этот change, по правилу «одна
  сессия — один change».
