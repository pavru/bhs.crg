# Design: экраны коммерческих предложений и прайс-листа

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D2, D4, D5, D17,
D18). Здесь только решения этого change.

## Context

Сервер — `plan-13` (КП, наценки, статусы, версии), `plan-14` (прайс-лист, КП без сметы), `plan-15`
(печать), `plan-16` (расхождение, обновление, производные). Навигация модуля и панели карточки стройки —
`plan-02`; карточка сметы — `plan-09`. Готовые компоненты `shared/ui`: `DataGrid`, `EditGrid`, `Modal`,
`ConfirmDialog`, `RowActionsMenu`, `StatusBadge`, `EmptyState`, `DateField`, `NumberInput`, `Tabs`,
`ListDetailShell`. Образец НДС «в том числе / сверху» на клиенте — `features/costs/invoiceVat.ts`.
Слово «план» в клиенте занято планом документов (#796) — папка `features/planning` (D1).

## Goals / Non-Goals

**Goals:** менеджер делает КП из редакции и по прайс-листу, наценивает, печатает, отмечает отправку и итог;
видит, что смета ушла вперёд, и обновляет КП после показа разницы.

**Non-Goals:** печать вне шаблона (шаблон правится в редакторе шаблонов, `plan-15`); телефонная раскладка
сверх правил оболочки; графики — `plan-20`.

## Decisions

- **Макеты:** раунд П3 в локальном каталоге на компонентах `shared/ui`. Код — после выбора владельца
  (`docs/UI.md` «Новый экран: порядок»). См. [разбор вариантов](#раунд-п3).
- **PR 1.**
  - `features/planning/offers/OffersPage.tsx` — глобальный список на `DataGrid`: номер, стройка, источник
    («смета ред. N» | «прайс-лист»), статус, дата отправки, итог (колонка цены — только из ответа сервера).
  - `OfferCard.tsx` — строки на `EditGrid` в черновике и `DataGrid` после «отправлено»; наценки — поле КП,
    раздела и строки; итог и НДС — числа сервера, клиент их не пересчитывает (как `invoiceVat` —
    только показ режима).
  - Колонки себестоимости нет в разметке вовсе, если сервер её не отдал (`hidden` в ответе, D4); строка над
    таблицей называет право.
  - `OfferStatusActions.tsx` — «Отметить отправленным» (дата, `ConfirmDialog`: «после отправки правка —
    только новой версией»), итог. Кнопок нет без `plan.offer.send` — по доступу из `/api/account/access`.
  - `OfferVersions.tsx` — история версий: номер, статус, дата отправки.
  - `OfferDriftBanner.tsx` и `OfferRebaseDialog.tsx` (`Modal wide`) — разница из `rebase-preview`. Оба
    адреса требуют `plan.offer.read` и `plan.offer.edit`. При 409 с новым `preview` заменить показанную
    разницу и получить новое подтверждение. Обычный 409 версии требует перечитывания КП.
    Интерфейс называет цель явно: другая действующая редакция, иначе последняя редакция, отличная от
    исходной. Если доступны обе цели, пользователь выбирает между ними. Без `revisionId` сервер берёт
    действующую, которая может совпадать с исходной даже после появления новой редакции.
  - «Сделать КП» в карточке сметы — `CreateOfferDialog.tsx` (`Modal` 512 px).
  - 409 по `If-Match` везде — «КП тем временем изменили — перечитайте», набранное сохраняется.
- **PR 2.**
  - `features/planning/pricelist/PriceListPage.tsx` — `DataGrid`: вид работы, единица, действующая цена,
    «с даты»; правка — `Modal` с `DateField` и `NumberInput`; история — раскрытие строки.
  - `PriceListOfferDialog.tsx` — КП по прайс-листу; после создания окно показывает строки и итог из ответа
    сервера, включая `no-price` и «неполный итог». В черновике по прайс-листу ручной пересчёт сначала
    показывает изменения сервера. Подтверждение передаёт `previewToken` и `If-Match`. После 409 нужен новый
    предпросмотр.
  - `features/planning/estimates/EstimateDerivatives.tsx` — блок производных под сметой. Прошлые
    отправленные версии остаются под исходными редакциями. `hidden` называет право, блок без чисел.
    Графики используют предусмотренный ответ, данные появятся с Plan-19.
- **Живой прогон** `e2e/plan-offers-smoke.mjs`: «Менеджер проекта» делает КП из посеянной редакции,
  отмечает отправленным, правка недоступна, «Новая версия» доступна; «Сметчик» не видит раздела КП.
- **Сторож.** vitest: без `cost` в ответе колонки себестоимости нет в разметке; отправленное КП не даёт
  ячеек правки; 409 при обновлении перечитывает предпросмотр. Живой прогон под ролями.
- **Чем ломается.** Клиент считает итог сам — расходится с печатью; колонка себестоимости с пустыми
  ячейками — читается как «ноль».

## Раунд П3

Во всех вариантах один набор синтетических данных. Переключатели «Права в макете» и «Сценарий»
показывают доступ и поведение при отказах. В каталоге можно выбрать ширину 390 или 1440 px.

| Вариант | Реестр и карточка | Работа с наценками | Производные |
|---|---|---|---|
| [А · Карточка на всю страницу](http://127.0.0.1:5200/?section=mockups&project=plan-17-offers-ui&page=page) | Табличный реестр и отдельный адрес карточки | Строки, итог, наценки и история на одной странице | Все редакции под строками сметы |
| [Б · Реестр и карточка рядом](http://127.0.0.1:5200/?section=mockups&project=plan-17-offers-ui&page=split) | Список рядом с карточкой на широком экране. На узком экране открываются по очереди | Наценки и версии в боковых панелях | Отдельная вкладка сметы |
| [В · Карточка по разделам](http://127.0.0.1:5200/?section=mockups&project=plan-17-offers-ui&page=sections) | Табличный реестр и отдельная карточка | Вкладки «Строки и итог», «Наценки», «Версии» | Внутри выбранной редакции |

Разбор исполнителя для владельца. Для КП с большим числом строк предлагаю **В**: таблица получает
всю ширину, шапка сохраняет статус и действия при переходах между вкладками. А позволяет видеть
редактирование и историю на одной странице, ценой длинной прокрутки. Б ускоряет просмотр нескольких КП,
при этом реестр занимает часть ширины таблицы. Место производных в В привязывает их к выбранной
редакции. В А и Б проще одновременно сравнить производные разных редакций.

**Выбор владельца от 23.11.2026:** [В · Карточка по разделам](http://127.0.0.1:5200/?section=mockups&project=plan-17-offers-ui&page=sections).
Табличный реестр ведёт на отдельную карточку с вкладками «Строки и итог», «Наценки», «Версии».
Производные показываются внутри выбранной редакции сметы.

## Сверка серверных носителей

Сверено с источниками `BHS.CRG.Modules.Plan/Endpoints`, `Estimates/RevisionDerivatives.cs`,
`Printing/OfferPrintContext.cs`, общей печатью и клиентской карточкой сметы на `6e54eb57`.

| Что показано | Контракт |
|---|---|
| Реестр и карточка КП | `GET /api/plan/offers` с `constructionId`, `estimateId` и `cursor`; `GET /api/plan/offers/{id}` с `source`, `revision`, `constructionId`, `status`, `currentVersion`, `sentOn` и версией `version` для `If-Match`. Чтение требует `plan.offer.read`. История — `GET /{id}/versions`, в её `content` сохранены строки и ID редакции снимка. |
| Наценки и НДС | `markup`, `sections[].markup`, `lines[].ownMarkup` и действующая `lines[].markup.{value,level}` — последнее поле соответствует названному в плане `markupSource`. `lines[].{volume,unit,price,amount}` — снимки сервера. `vat.{mode,rate}` и `money.{linesTotal,vat,total,incomplete}` приходят готовыми. В-8 — итог ЛСР с НР и СП для КП из сметы. В-9 — режим НДС и ставка из КП. |
| Доступ к себестоимости и марже | `cost.{total,margin}` у карточки и строк при `plan.estimate.cost`; `hidden[]` называет код `cost`, право и описание. Суммы в истории и производных берутся только из предназначенных для этого ответов. |
| Статусы и запись | `PUT /{id}`, `PUT /{id}/markups`, `POST /{id}/send`, `POST /{id}/outcome` и `POST /{id}/versions` принимают `If-Match`. Отправка и итог — `plan.offer.send`, новая версия — `plan.offer.edit`. Сервер отдаёт обновлённый снимок. Новое КП получает `revisionId` выбранной вкладки сметы. |
| Расхождение и обновление | `drift.{code,text,source,current,latest}`. `rebase-preview` отдаёт `version`, `source`, `target`, `fingerprint`, `added`, `removed`, `changed`, `unmatched`, `unmatchedSectionMarkups`, `hidden`. Сопоставление и перенос наценок выполняет сервер. `rebase` принимает `If-Match`, `fingerprint` и при явном выборе `revisionId`. 409 с `preview` требует нового подтверждения. |
| Прайс-лист и КП без сметы | `GET /api/plan/pricelist?date=…` отдаёт `effective`, `history` с `unit` и `version` по записи. `PUT /{workTypeId}` и `DELETE /entries/{id}` требуют `plan.pricelist.edit`, для существующей цены нужен `If-Match`. `POST /api/plan/offers/from-pricelist` принимает `constructionId` и пары `workTypeId` / `volume`. В ответе `lines[].marks` содержит `no-price`, `priceSource.kind` равен `none`, `money.incomplete` показывает неполный итог. `reprice-from-pricelist` поддерживает серверный предпросмотр и `previewToken`. |
| Производные | `GET /api/plan/estimates/{id}/derivatives` по `plan.estimate.read`. У каждого блока `state`, при `hidden` — `permission`, при `ok` — `items`. У КП `currentVersion`, `status`, `date`, `sentOn`, `coverage.{covered,total,percent}`, `outdated` и `historical`. Есть отдельный блок `schedules`. |
| Печать | `POST /api/print/КоммерческоеПредложение/{id}` и `…/preview` работают с `plan.offer.read`, включая поставку без `id`. Серверный контекст содержит цены продажи и итог. Редактирование шаблонов уже работает через `core.print.edit`. |

**Печать, решение владельца от 23.11.2026.** Plan-17 открывает предпросмотр PDF по активному шаблону
по умолчанию и скачивает построенный PDF. Создание КП принимает дату, режим НДС и наценку.
Администратор настраивает форму в редакторе шаблонов Plan-15 по `core.print.edit`, включая поставку
без `id`. Доступ к предпросмотру и скачиванию определяется `plan.offer.read`.

Прайс-лист перечисляет виды работ с историей цен. В PR 2 выбор из всего классификатора использует
`GET /api/work-types?purpose=choice` только при фактическом `core.catalog.read`. У штатного Менеджера
проекта это право есть. У пользовательской роли без него остаются разрешённые действия с видами
работ из прайс-листа. При праве изменять цены интерфейс называет право, нужное для добавления нового
вида. Проверки покрывают оба состава прав и отсутствие запроса к классификатору у роли без доступа.
