# Формирование параметра доступа HTTP и MCP

## Context

`DataAccessResolver.ForAsync` вычисляет `DataAccess` по принципалу и `IUserPermissions`.
`ModuleTableService` переносит этот параметр в `ModuleReader` через `ModuleReadersPort.From`.
Поэтому подмена регистрации `IModuleReaders` не меняет читателя в таблицах и системных источниках
на этих таблицах. `JobBackgroundService` запрашивает доступ автора через
`IDataAccessResolver.ForUserAsync` по идентификатору автора.

## Goals / Non-Goals

Точка подмены относится к общему пути таблиц, их источников и снимков. Запись в DI тестового хоста
должна менять вход настоящей службы чтения и позволять сравнить её результаты при том же JWT.

Граница change проходит по адаптерам ядра. Маршруты собственных отчётов, где сотрудник определяется
через `IModuleEmployees`, и менеджерские охваты Work требуют своих контрольных подмен в Work-25.

## Decisions

### D1. Интерфейс запроса в API

Добавить `IRequestDataAccessResolver` в `BHS.CRG.Api.Auth` с одним методом
`Task<DataAccess> ForAsync(ClaimsPrincipal principal, CancellationToken ct)`. Сохранить
`DataAccessResolver` закрытым для наследования и зарегистрировать оба интерфейса как singleton-алиасы
его существующего singleton. Запросный резолвер использует принципал вызова и существующий
`IUserPermissions`. Фоновый вход использует свой scope, актуальные права автора из БД и прежние
причины системного доступа. Вариант с расширением `IDataAccessResolver` связал бы исполнителя
заданий с контрактом запроса.

Для MCP использовать общий адаптер `ForRequestAsync` над интерфейсом. Он извлекает
`HttpContext.User` из `IHttpContextAccessor` и передаёт его в `ForAsync`. Сохранить
`InvalidOperationException` при отсутствии запроса и штатный результат при отсутствии
идентификатора в принципале. Перенести логику адаптера из concrete-метода, сохранив вызовы
остальных потребителей. Правила формирования ключей и преобразование в `ModuleReader` остаются
в существующих реализациях.

### D2. Адаптеры на общем пути чтения

| Точка входа | Изменение зависимости |
|---|---|
| `TableEndpoints` | Заменить concrete во всех текущих вызовах `ForAsync`. Сюда входят каталог, колонки, быстрые отборы, GET с `row`, POST `query`, XLSX-выгрузка, `dataset` и сохранённые представления. |
| `DataSetEndpoints`, `DataSetBindingEndpoints` | Перевести существующие вызовы `ForAsync`, включая список файлов и источников, создание источника, просмотр, выгрузку, обработку и предпросмотр привязок. Маршруты, которые работают только с метаданными, продолжают использовать свой текущий вызов сервиса. |
| `DataSnapshotTools`, `DataSnapshotResources` | Перевести `get_dataset`, `get_source`, `get_rows` и чтение ресурсов `bhs://dataset/{datasetId}`, `bhs://source/{sourceId}`. Вызов `list_datasets` остаётся каталогом метаданных под текущим правом MCP. |

Выбранные адаптеры получают один и тот же запросный интерфейс. Ворота HTTP/MCP, проверка ключа
объявления таблицы, сборка `ModuleReader`, отбор строк и подписи границ продолжают работать в
своих слоях ([AUTH-6], [AUTH-8], [AUTH-9], [AUTH-12.1], [CORE-24.1], [WORK-40]).
Прямые потребители конкретного резолвера вне этой цепочки сохраняют штатную регистрацию.

### D3. Проверка на тестовом хосте

Использовать инфраструктуру `IntegrationTestFixture` и `McpTestClient` с включённым `work`,
отдельной тестовой БД и двумя различимыми синтетическими отчётами. Поднять штатный хост и отдельную
фабрику с заменой только `IRequestDataAccessResolver` через `ConfigureTestServices`. Посев и вход
производить штатным путём. Для сравнения использовать тот же JWT и те же данные, предварительно
проверив одинаковые настройки подписи обоих хостов.

Подмену объявить в сборке тестов. Вызвать штатный резолвер и сузить в возвращаемом
`DataAccess` охват до собственных строк того же читателя. Для этого у читателя должны быть права на оба
охвата и свой отчёт. Сверить идентификаторы строк и границу выдачи у HTTP `query` и MCP `get_rows`.
Штатный хост показывает оба отчёта, хост с подменой показывает свой отчёт и соответствующую границу,
после снятия подмены снова видны оба. Роли, аутентификация, ворота и реальные читатели во всех
вариантах совпадают. Дополнительно проверить отказ обычных ворот MCP пользователю без права чтения
наборов. Эта проверка подтверждает проводку интерфейса. Контроль «все», обход всех путей и
красный прогон относятся к 1.1, 1.5 и 1.6 Work-25 ([STG-6], [WORK-39], [WORK-40]).

## Risks / Trade-offs

- Ошибка регистрации может проявиться только при построении Minimal API или вызове MCP. Поднять
  оба хоста, вызвать реальные маршруты и сравнить выдачу при штатном и подменённом доступе.
- Хосты могут разойтись по стартовым настройкам или данным. Сверять статусы и положительную
  выдачу на одном синтетическом посеве. В тесте ограничить замену собственной фабрикой и освободить
  её после проверки, а локальные тестовые ресурсы перечислить перед их очисткой.
