# Design: контракт «Плановые работы»

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D10 — контракты,
D11 — право контракта, D12 — права с первым адресом, D3 — действующая редакция, D4 — деньги правом).
Здесь только решения этого change.

## Context

- Механизм контракта и `ModuleReader` — `plan-22`; признак «право контракта» — `plan-21`.
- Редакции, строки, ресурсы и метод чтения плана «по действующим» — `plan-06` (D3 зонтика: прямое
  чтение строк для сумм ловит перепись); сопоставление шифра и коэффициент пересчёта — `plan-08`;
  слой распределения — `plan-10`.
- Составы ролей уже несут коды (`plan-01`, `Api/Auth/SystemRoles.cs`); без объявления синхронизатор их
  пропускает.

## Goals / Non-Goals

**Goals:** один контракт с частями по правам; три права контракта объявлены и действуют у ролей;
потребитель при выключенном `plan` получает «не подключено».

**Non-Goals:**
- потребители — заявки (`plan-26`), «план против факта» (`plan-27`), «Ход работ» (`plan-25`), этап 4;
- опубликованный набор «Плановые работы» — `plan-28` строит его поверх этого контракта (`CORE-24`).

## Decisions

- **Интерфейс.** `IPlannedWorks.ReadAsync(ModuleReader reader, PlannedWorksQuery query, ct)`;
  `query` — стройка (обязательна), раздел стройки (необязателен), список позиций перечня
  (необязателен). Ответ `PlannedWorksAnswer`:
  - `Items`: позиция перечня, единица (классификатора), объём, распределение
    `[{sectionId | null, volume}]` — часть `volumes`;
  - `Cost`: стоимость позиции и сметная стоимость её материалов по номенклатуре
    `[{planItemId, total, materials: [{nomenclatureId, amount | not-in-estimate}]}]` — часть `cost`;
    `not-in-estimate` — смета стоимости ресурса не несёт (так бывает у базисно-индексного расчёта), и это
    не ноль. Стоимость материалов нужна «плану против факта» `costs` (`plan-27`);
  - `Materials`: `[{planItemId, nomenclatureId, quantity, unit}]` — часть `materials`;
  - `Labor`: `[{planItemId, hoursPerUnit}]` — часть `labor`;
  - `Hint`: `[{planItemId, nomenclatureIds}]` — часть `hint`;
  - `Basis`: по каким сметам и редакциям посчитано (`estimateId`, `revision`) — часть `volumes`;
  - `Unmapped`: число несопоставленных строк действующих редакций — всегда, без денег и наименований.
  Часть без права — `Hidden(permission)` из `plan-22`, а не `null` и не пустой список.
- **Право → часть.** `plan.estimate.read` открывает `volumes`, `materials`, `labor` и `hint` — всё, кроме
  денег; `plan.estimate.cost` — `cost`. Узкие права открывают по одной части: `plan.estimate.materials` →
  `materials`, `plan.labor.read` → `labor`, `plan.estimate.hint` → `hint`. Права складываются; узкие
  нужны тем, у кого `plan.estimate.read` нет.
- **Нормы трудозатрат.** `hoursPerUnit` — чел.-ч строки на её объём, пересчитанные в единицу
  классификатора коэффициентом сопоставления (D8 зонтика); строки одной позиции из разных смет —
  взвешенным средним по объёму. Иначе «по смете — фактически» завышалось бы в 100 раз (`PLAN-6.1`).
- **Только действующие.** Провайдер читает план единственным методом `plan-06` — по действующим
  редакциям; отдельного пути к строкам у него нет.
- **Объявление прав.** В `PlanModule.Permissions` три права с признаком контракта (`plan-21`):
  - `plan.estimate.materials` — «материалы позиций сметы без цен — для заявок на закупку; модуль
    „Планирование“ не открывает» (решение В-2);
  - `plan.labor.read` — «нормы чел.-ч позиций сметы без денег — для „по смете — фактически“»;
  - `plan.estimate.hint` — «наименования материалов позиций сметы стройки, без цен и количеств, —
    подсказка монтажнику».
  Всем — `ReadAllMark.Out("выдача другим модулям")`.
- **If-Match и ворота.** Нового HTTP-адреса и пишущего API нет: контракт — вызов в процессе. Ворота
  модуля `plan` правами контракта не открываются — сторож в тесте состава доступа.
- **Сторож.** `PlannedWorksContractTests`: две сметы стройки, у одной действующая редакция 2 — в ответе
  только она; несопоставленная строка — в `Unmapped`, не в `Items`; «100 м» с коэффициентом 100 даёт
  `hoursPerUnit` на «м»; только `plan.estimate.hint` — нет количеств, остальные части `Hidden`; без прав —
  все части `Hidden`; система — отказ. Тест состава `/api/account/access`: у «Монтажника» и «Снабженца»
  модуля `plan` нет. Живой хост `costs` без `plan` — «не подключено».
- **Чем ломается.** Провайдер читает строки всех редакций — план удваивается после повторного импорта.
  Право объявлено обычным — у «Монтажника» появляется пустое «Планирование».

## Сверка с master перед реализацией (16.11.2026)

Change написан до `plan-31` и до слияния `plan-10`…`plan-22`. Сверено с кодом; решения ниже дополняют
«Decisions» и там, где расходятся, заменяют их.

- **Форма ответа.** `ReadAsync` отдаёт `ContractAnswer<PlannedWorksAnswer>`: система получает
  `SystemRefused` целиком, человек — `Shown` с частями (`ContractAnswer.Refusal` из `plan-22`). Части —
  `ContractAnswer<…>` каждая; `Unmapped` — числом рядом с частями, и без прав тоже (как сказано выше).
- **«Скрыто» называет узкое право.** Часть, которую открывает и `plan.estimate.read`, и узкое право,
  называет в `Hidden` узкое: `materials` — `plan.estimate.materials`, `labor` — `plan.labor.read`,
  `hint` — `plan.estimate.hint`. Этого кода ждут потребители: `plan-26` («нужно право
  plan.estimate.materials»), `work-28` (`hidden` с `plan.labor.read`), `work-26`.
- **Строки-материалы (`plan-31`, D2).** Позиция ЛСР без работы (материал по КА, ФССЦ, ТЦ) в план не входит
  и позиции перечня не имеет, а таких строк в сметах до 60 % (ЭОМ — 145 из 238). Выпади они из контракта,
  заявка «из сметы» (`plan-26`) молча потеряла бы большую часть материалов. Поэтому их материалы и
  стоимость входят в части `materials`, `cost` и `hint` с `planItemId: null` — «материалы сметы вне
  позиций перечня»; в `volumes` и `labor` их нет. Отбор по списку позиций перечня их не берёт.
- **Несопоставленные ресурсы названы числом.** Часть `materials` — `{lines, unmatched}`: `unmatched` —
  материалов строк ответа без позиции номенклатуры. Без числа заявка не отличила бы «в смете нет» от
  «не сопоставлено».
- **Распределение.** Правило одно с `plan-10` (`DistributionLines.Evaluate`): части строки, иначе правило её
  раздела ЛСР, иначе «не распределено». Смета, составленная на раздел (`Estimate.SectionId`), уходит в
  этот раздел целиком — распределения у неё нет (`plan-10`, задача 1.9). У позиции —
  `distribution: [{sectionId | null, volume}]` в единице плана (`null` — «стройка в целом»: явное решение,
  остаток частей и нераспределённое) и `undistributed` — сколько из «стройки в целом» решения ещё не имеет:
  его показывает полосой «не распределено» `plan-25`.
- **Отбор по разделу.** Каждое число ответа — доля раздела: строка входит долей своего объёма на разделе
  (части — их количеством, правило и смета на разделе — целиком), и с той же долей — её материалы,
  стоимость и чел.-ч. Норма `hoursPerUnit` — отношение долей, то есть та же норма. Строки без доли на
  разделе в ответ не входят; `undistributed` при отборе — 0: нераспределённое не лежит ни на одном разделе.
  Зато ответ называет числом `undecided` строки (работ и материалов) без решения о разделе, которых отбор не
  взял: без него заявка по разделу не отличила бы «на разделе нет» от «ещё не распределено». Число не зависит
  от прав (строки, а не то, что из них видно); без отбора — 0. Сметы, составленные на другие разделы, при
  отборе не читаются и в `basis` не входят.
- **Доли частей не больше единицы.** Доля части — её количество на объём строки, а если части больше объёма
  или объёма в смете нет — на сумму частей. Пути записи частей больше объёма не пускают; знаменатель держит
  ответ и без них: «стройка в целом» не уходит в минус, а строка с частями не становится «нераспределённой».
- **Объём без объёма — числом.** Строка позиции без объёма в смете в `volume` не входит, а `withoutVolume`
  позиции называет, сколько таких строк: неизвестное — не ноль, как у денег.
- **Нормы.** `hoursPerUnit` — `Σ чел.-ч / Σ объём` по строкам позиции, у которых трудозатраты есть и объём
  больше нуля (это и есть взвешенное среднее по объёму). Нет таких строк — `null`, «смета норм не несёт»,
  а не ноль.
- **Деньги не нулями.** `total` позиции и `amount` материала — `null`, если хоть одна строка или ресурс
  своей стоимости не несёт (`not-in-estimate`): частичная сумма читалась бы как полная.
- **Чтение строк — только `PlanRows`.** Число несопоставленных и строки-материалы читаются новыми методами
  `PlanRows` (`Unmatched`, `CurrentMaterialRows`) тем же правилом действующих редакций; перепись
  `PlanRowsInventoryTests` нового места не получает.
- **Единица позиции** — `UnitId` строки: ключ позиции перечня включает единицу (`PlanItemKey`), поэтому у
  строк одной позиции она одна. Единица материала — как в файле (`SourceUnit`), материалы складываются в
  пределах одной единицы.
- **Сторожа на хосте «только планирование».** Тест состава доступа по ролям — это
  `PlanOnlyHostTests.System_roles_get_exactly_their_plan_permissions`: после объявления у «Монтажника»,
  «Снабженца» и «Менеджера проекта» в наборе появляются их права контракта, а признак модуля у первых двух
  остаётся `false`. Права контракта двери не открывают — в `Module_permissions_open_a_door_or_are_named_as_doorless`
  они названы с причиной. «Не подключено» — на хосте `costs` (`CostsOnlyHostTests`).
- **Требование «права первой двери»** (`plan-01`) говорит «не раньше первого адреса»; у права контракта
  адреса нет, его «дверь» — контракт. Требование уточняется дельтой: «адреса или контракта».

## Risks / Trade-offs

- [Узкое право выдаст больше, чем нужно] → каждая часть — отдельный тип ответа; тест сравнивает ответ
  под узким правом с ожидаемой формой целиком.
- [Крупная стройка — сотни тысяч строк] → строки читаются проекцией нужных колонок, материалы и
  трудозатраты — соединением в базе и только для открытых частей; отбор по позициям сужает чтение, части
  распределения читаются только для загруженных строк, отбор по разделу не читает сметы чужих разделов. Если
  этого не хватит, суммы уйдут в базу, а распределение — в ту же арифметику по группам.
