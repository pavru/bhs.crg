# Design

## Context

Зачем это нужно — см. proposal.md, раздел Why. Что есть сейчас:

- **Дверь видов работ.** Классификатор заводится кодом при запуске и только при справочнике единиц:
  `ModuleTypeSpec` `ВидРаботы` ссылается на тип единиц кодом цели, и без цели наполнение его пропускает.
  Без типа `ВидРаботы` ветка списка возвращает `Results.Ok(Array.Empty<…>())`. Ветка заведения
  возвращает `Conflict(new { error })` с текстом «нет справочника единиц… появится при следующем
  запуске», без `code`. Вторую причину — единицы есть, классификатора ещё нет — текст описывает
  правильно, но кодом её не отличить.
- **Образец — дверь сотрудников.** Там `EmployeeEndpoints.DirectoryMissingResult(all)` отвечает
  `409 { code: "directory-missing", reason, error }`, и причина зависит от того, что на экземпляре есть.
  Клиент разбирает отказ в `shared/api/employees.ts` функцией `directoryMissingOf`: отказ приходит
  значением запроса, а не исключением, и экран рисует его как состояние.
- **Читатели в клиенте:**
  - `useWorkTypeChoices` (`planningMatches.ts`) — поле выбора в `RateChoiceFields.tsx`. Сейчас при ошибке
    поле пишет красное «не прочитался» словами сервера, а при пустом списке — «Классификатор пуст».
  - `useWorkTypeNames` (`planningEstimates.ts`) — названия в `RevisionLines`, `MatchDialog` и
    `MakeCurrentDialog`; если названия нет, показывается «…».
  - У клиента запросов `retry: 1`.

## Goals / Non-Goals

**Goals**
- Одно тело отказа «справочник не заведён» у двух дверей ядра: сотрудников и видов работ.
- Чтение и заведение двери видов работ отказывают одинаково.

**Non-Goals**
- Кнопка «Завести классификатор». Классификатор заводится запуском, как и был. Выход — справочник
  единиц и перезапуск; это говорят слова отказа.
- `GET /api/work-types/{id}` — остаётся 404.
- Порт `IModuleWorkTypes` — уже отвечает `null`; модуль `work` переводит это в отказ своего адреса
  в `work-11`.
- Общий адрес `/api/common-data` — у него свой отказ с адресом двери.

## Decisions

**D1. Тело отказа — как у сотрудников, код — одной константой.**
`{ code: "directory-missing", reason, error }`. Строку `"directory-missing"` берём у
`EmployeeAccountReads.DirectoryMissing`, своей не заводим: две константы одного кода однажды
разошлись бы, и клиент перестал бы узнавать один из отказов.

Ответ строит один метод двери, например `WorkTypeEndpoints.DirectoryMissingResult(all)`, и зовут его
обе ветки — список и заведение. Причина:
- `unit-missing` — у экземпляра нет типа с кодом `CoreRecordTypes.UnitCode`;
- иначе `not-created`.

*Отвергнуто:* общий метод «справочник не заведён» для любых справочников ядра. Причины у каждого свои
(«нет физлица», «нет единиц»), и выходы тоже свои: у сотрудников кнопка, у видов работ перезапуск.
Общим остаётся только код.

**D2. Порядок отказов: право → назначение → справочник.**
Ворота права стоят на группе, поэтому без `core.catalog.read` ответ 403 приходит раньше. Затем
проверяется назначение: без `purpose` — 400, как сейчас. Справочник проверяется последним. Тот, кто
справочник не видит, о его состоянии не узнаёт. Неправильный запрос получает 400, даже если
справочника нет: ошибка в запросе и есть ошибка в запросе.

**D3. В клиенте отказ — значение запроса, а не исключение, как у сотрудников.**
`useWorkTypeChoices` и `useWorkTypeNames` ловят `directory-missing` и возвращают его данными:
`{ items, missing }` и `{ names, missing }`. Так отказ не повторяется по `retry: 1` и не рисуется
веткой `isError` как поломка.

Разбор отказа выносится из `employees.ts` в общий
`shared/api/directoryMissing.ts`: `directoryMissingOf(e) → { reason: string; error: string } | null`.
Сотрудники сужают `reason` до своих двух значений поверх него. Второй разборщик того же кода был бы
копией.

*Отвергнуто:* оставить исключение и смотреть `directoryMissingOf(types.error)` в поле. Тогда
отказ дважды ходит в сервер (повтор), а каждый экран-читатель обязан помнить, что эта ошибка — не
ошибка.

**D4. Поле «Вид работы»:**
- при `missing` поле недоступно и показывает слова сервера обычным текстом подсказки, без роли `alert`;
- «Классификатор пуст» остаётся только для `items.length === 0` без `missing`;
- действие «Новый вид работы» в `MatchDialog` скрыто при `missing`, как сейчас без права: шаг всё
  равно получил бы 409.

Названия видов работ при `missing` — пустая карта. Строк с видом работы у такого экземпляра нет,
поэтому «…» не показывается.

## Risks / Trade-offs

- [Внешний читатель ждал 200 и пустой список] → Читателей вне репозитория у двери нет: MCP и модули
  читают виды работ портом. Смена кода ответа записана в DEV_NOTES у адреса.
- [Экран, который мы не нашли, рисует 409 как поломку] → Читатели найдены поиском по `'/work-types'`
  в клиенте: их два хука. Тест поля закрывает видимое состояние.
- [Причина `not-created` устаревает: классификатор заведён другим запуском] → Причина считается
  на каждый запрос по типам экземпляра и не кэшируется сервером. Клиентский `staleTime` — 60 с, после
  перезапуска экран берёт новый ответ.

## Migration Plan

Миграций нет. Откат — возврат PR. Код ответа меняется только у экземпляров без классификатора.
