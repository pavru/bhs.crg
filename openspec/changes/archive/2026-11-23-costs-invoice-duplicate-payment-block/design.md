# Design

## Context

[Proposal](proposal.md) фиксирует решения по #2011, [дельта `costs`](specs/costs/spec.md) задаёт наблюдаемое поведение.

`InvoiceEndpoints.DuplicatesAsync` ищет по индексу `(SupplierId, Number, IssuedOn)` и возвращает подсказку для карточки. `InvoiceSameFiles` отдельно сравнивает доверенные отпечатки, а `twinsOf` сводит эти две подсказки для отображения. `PaymentRefusal` сейчас знает только отклонение, отсутствие суммы и расхождение. `PaymentEndpoints.PostingAsync` обслуживает предпросмотр, запись и чтение записанного расклада. `InvoiceDesk` запирает строку изменяемого счёта и проверяет её `If-Match`. Версия строки и `stamp` расклада способны остаться прежними, когда рядом появляется двойник.

## Goals / Non-Goals

**Goals**

- Одно правило запрета для карточки, предпросмотра и записи с защитой от параллельного появления двойника.
- Подтверждение по увиденным данным двух счетов с сохранением истории решения.
- Переиспользование текущей формы, индикатора и ворот прав модуля.

**Non-Goals**

- Новый алгоритм поиска похожих счетов или перемена правил загрузки повторного файла.
- Отмена уже записанных оплат и изменение исторических раскладов.
- Новый пишущий инструмент MCP. В зарегистрированном MCP приложения внесения оплаты сейчас нет. Будущий вход в оплату должен пользоваться серверной проверкой.

## Decisions

### D1. Сервер определяет блокирующие пары [COST-4] [COST-6.2] [COST-6.4]

Вынести общий запрос кандидатов по существующему индексу и применять к ним состояние и действующие подтверждения. Для решения об оплате учитывать всех кандидатов. Отклонённых исключать, оплаченных учитывать. На чтении отдельно отдать в `payment.duplicateBlockers` идентификатор и данные для узнавания каждого блокирующего второго счёта, его состояние оплаты и непрозрачную отметку актуальности данных для подтверждения. `duplicates` и `sameFile` сохраняют роль сведений о найденных совпадениях. У записей `duplicates` сервер называет действующее подтверждение, чтобы клиент снял замечание о проверенной паре и после нового чтения. Ограниченный перечень `sameFile` для решения об оплате не подходит.

Приоритет одного рода отказа для неоплаченного счёта — `rejected`, затем `duplicate`, затем действующие проверки суммы и сверки. Готовность к «Разобран» рассчитывается существующим правилом. Денежный пробел сохраняется как самостоятельный пункт, когда он есть. Исторический `GET …/paid` строит записанный расклад без применения нового запрета.

Встроить проверку в путь записи до записи денег и после `If-Match`, а также в предпросмотр. Для дубля использовать 409 при записи. Клиент уже запрашивает свежий расклад и карточку после 409, поэтому сможет показать новый отказ и убрать входы в оплату. Для прежних причин оплаты сохранить действующий контракт. Валидация только в карточке оставила бы окно между открытием диалога и записью.

### D2. Транзакция упорядочивает оплату и изменения совпадений [COST-4] [COST-6.2]

Использовать транзакционный advisory lock уровня схемы `costs` с выделенным ключом. Внесения оплаты берут его в разделяемом режиме. Записи, меняющие состав блокирующих пар или подтверждения, берут исключительный режим. Одновременные оплаты разных счетов могут читать актуальные пары параллельно. Блокировка по тройке реквизитов потребовала бы согласовывать прежний и новый ключ при каждой правке, в том числе при заполнении пустых полей распознаванием.

Порядок в `InvoiceDesk` и путях исправления — замок периода, затем замок проверки дублей, затем замок строки. Создание, если ему не нужен замок периода, берёт замок проверки в своей транзакции записи. Под замком повторно читаются счёт и кандидаты. Провести через этот порядок запись реквизитов в обычной правке, исправлении и фоновом распознавании, создание, замену файла, отклонение, возврат отклонённого в черновик, удаление, оплату, отмену и подтверждение пары. Ввод с файла создаёт пустой по реквизитам черновик, а присоединение к группе происходит при записи распознанных полей. Выгрузка файла и само распознавание идут вне замка.

Транзакция записи либо видит уже зафиксированного двойника и отказывает, либо фиксирует оплату раньше изменения соседнего счёта. Во втором случае последующая попытка оплатить соседа уже видит оплаченный экземпляр. Замок строки текущего счёта сам по себе не упорядочивает запись другого счёта. При восстановлении копии модуль берёт тот же исключительный замок в транзакции импорта до записи своих таблиц.

### D3. Подтверждение хранится для двух редакций счетов [COST-6.2]

Хранить запись подтверждения в схеме `costs` с упорядоченной парой идентификаторов и редакцией данных каждой стороны. Уникальность пары редакций делает повтор и встречное подтверждение безопасными. В записи сохраняются идентификатор события, автор, время и короткая причина. История решений переживает потерю силы отметки. Поиск применяет запись только к актуальным редакциям. Общий `xmin` нужен для защиты записи из формы, а отдельная редакция подтверждения меняется только при затронутых данных. Снимок трёх значений без редакции оживил бы старое согласие после возврата прежнего номера или даты.

Смена поставщика, номера, даты, появление файла или замена его содержимого выпускает новую редакцию. Редакция не меняется при равном доверенном SHA-256, смене имени и правках других полей. Если прежний файл без доверенного отпечатка, при замене прочитать старые байты через `IModuleBlobs.OpenAsync` и сравнить SHA-256. Вычисление старого отпечатка сделать до транзакции, внутри проверить, что прочитан именно текущий файл. Если старый файл утрачен и равенство содержимого доказать невозможно, замена выпускает новую редакцию. Отказ хранилища при чтении и отсутствие файла обрабатываются отдельно.

Отклонение исключает счёт из расчёта. Возврат в черновик восстанавливает участие в расчёте по текущей редакции. Сам переход редакцию не меняет. Устаревшей отметке это не возвращает силу.

Учесть, что восстановление старой копии делает прямой upsert известных колонок и оставляет новые колонки существующей строки. В защите от такого обхода использовать проверку редакции на границе обновления строки: SQL-сторож в миграции меняет редакцию при изменении реквизитов или ссылки на файл с недоказанно тем же содержимым, если запись не передала новую редакцию. Для обычного пути с теми же байтами подтверждением равенства служат доверенные отпечатки прежнего и нового пути. Старый отпечаток, вычисленный при замене, записывается для прежнего пути внутри той же транзакции до смены пути. При импорте современной копии восстановленные счета получают свежие редакции. На них переносятся только решения из этой же копии, соответствующие редакциям обеих её сторон. История остаётся в журнале, а живое решение, отсутствовавшее в копии, после возврата реквизитов силы не получает.

### D4. Адрес подтверждения и журнал [COST-6.2] [CORE-28] [AUTH-8] [AUTH-9]

`POST /api/costs/invoices/{id}/duplicate-confirmations` принимает `If-Match` счёта, `otherInvoiceId`, непрозрачный `otherRevision` из карточки и `reason`. В интерфейсе действие начинается с блокируемого неоплаченного счёта, а подтверждение применяется симметрично. За воротами `costs` и `costs.invoice.pay` сервер проверяет версию открытого счёта, свежесть второй стороны и наличие допустимой пары под замком D2. Причину очистить от краевых пробелов, пустую отклонить. Успешный ответ возвращает свежую карточку. При повторе уже записанного решения с актуальными данными использовать прежнее событие.

Объявить отдельный несворачиваемый вид журнала через `InvoiceActions`. Журнал получает идентификаторы и подписи обоих счетов и снимок автора, времени и причины. Действие доступно для просмотра по существующим правилам журнала модуля. Сначала фиксируется подтверждение в своём контексте, затем запись доставляется через порт журнала ядра. У этих контекстов разные транзакции, поэтому сведения для записи остаются в модуле до подтверждения доставки. При сбое доставить событие повторно с тем же идентификатором. Для повторной доставки нужен идемпотентный вход через порт журнала с исходными автором и временем. Это закрывает случай, когда процесс прервался после записи подтверждения или ответа журнала, и сохраняет одно событие при параллельном повторе.

### D5. Состояние счёта и действие проверки пары [COST-6.4] [COST-6.7]

`mayMarkPaid` использует серверный `refusalKind` для обоих входов. В `invoiceStatus.ts` блокирующие пары формируют пункт «Мешает оплате». Один и тот же двойник появляется в нём один раз, в том числе при совпадении файла. Для других совпадений файла действует текущая подача. После подтверждения перечитать затронутые карточки с учётом кэша React Query и убрать предупреждение о дубле у проверенной пары. При конфликте во время оплаты открытый диалог показывает свежую причину и блокирует отправку.

До реализации подготовить три макета на компонентах живой дизайн-системы по [порядку UI](../../../docs/UI.md#новый-экран-порядок):

1. Пункт «Мешает оплате» в перечне ведёт в компактное окно выбранной пары с причиной.
2. Боковая панель показывает все блокирующие совпадения. Сотрудник выбирает одну пару и подтверждает её в панели.
3. Диалог сверки показывает две карточки рядом, с реквизитами, ссылками на файлы и полем причины для выбранной пары.

Каждый вариант показывает одного и нескольких двойников, уже оплаченного двойника, право только на чтение и состояние после подтверждения одной пары. Владелец выбирает вариант до реализации интерфейса.

доступно после ввода причины. При подтверждении А–Б в сценарии с тремя счетами можно открыть Б

## Risks / Trade-offs

- Замок модуля расширяет конкуренцию на коротких записях. Под ним остаются чтение актуального состояния и запись в БД. Запросы к файловому хранилищу выполняются до входа в транзакцию.
- Некоторые клиенты читают только прежние значения `payment.refusalKind`. Добавить `duplicate` в типы клиента и покрыть случай одновременных отказов по дублю и сумме.
- Прямое чтение прежней карточки из кэша может показывать устаревшее действие. Клиент обновляет затронутые карточки, а транзакционная проверка остаётся обязательной при каждом внесении оплаты.

## Migration Plan

Миграция `CostsDbContext` добавляет редакции и таблицу подтверждений без заполнения разрешениями существующих совпадений. Старые счета сразу участвуют в расчёте. Уже записанные оплаты, денежные даты и книги проводок остаются в базе. Свежая копия переносит подтверждения и редакции. Восстановление старой копии может аннулировать действующие отметки по D3. При откате приложения расширенную схему можно оставить до следующего выпуска. Старый сервер снова разрешает отмечать оплату по прежнему правилу.
