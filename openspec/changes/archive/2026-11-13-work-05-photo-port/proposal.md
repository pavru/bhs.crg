# Proposal: порт обработки фото для модулей, лимиты и учёт места

Дочерний change зонтика `work-00-epic`, общая архитектура — `../work-00-epic/design.md` (D13, D15).

## Why

Фото строки работы (`WORK-33`) приходят и с телефона, и из браузера. Если сжимать их только на клиенте,
веб-загрузка положит в хранилище оригинал на 8–15 МБ: это и есть «чем ломается».

Своего уменьшения у модуля нет и быть не должно: модуль ссылается только на контракты. В ядре есть
`ImageDownscaler` (`Infrastructure/Generation/ImageDownscaler.cs`), но для фото он не годится как есть:
- поворот по EXIF не применяет (`:75`, `SKBitmap.Decode`), и снимок с телефона ляжет набок;
- при перекодировании теряет все метаданные (`:103-104`), а с ними геометку, которую владелец решил
  хранить как доказательство места съёмки (Р-10, `WORK-55`).

Change ранний (Р-5): первый потребитель — `work-17`.

## What Changes

- Порт модуля «подготовить фото» в контрактах:
  - на входе файл и лимиты, на выходе JPEG, превью, размеры, геометка и время съёмки — либо отказ с
    причиной;
  - поворот по EXIF применяется;
  - геометка возвращается данными. Модуль хранит её колонками (`work-17`), а не метаданными файла;
  - прочие метаданные снимка (модель и серийный номер устройства) в сохраняемый файл не переносятся.
- Защита от разжатия в гигапиксели: размер в пикселях проверяется по заголовку до декодирования.
  Размер в байтах проверяется до чтения файла целиком.
- Лимиты передаёт модуль. Значения он читает из своих настроек через `IModuleSettings`, объявления
  настроек `work` заводит `work-17`. Файл сверх лимита отвергается до записи в хранилище: порт в
  хранилище не пишет вовсе.
- Учёт места (`WORK-35`): оценка веса копии уже собирает файлы модулей, но отвечает одной суммой.
  `GET /api/backup/size` получает разбивку `modules: [{ code, title, bytes, count }]`, а строка веса в
  настройках называет долю файлов модулей.
