# Design: веб-ввод отчёта

Общая архитектура — [зонтик Work](../2026-11-27-work-00-epic/design.md) (D7, D8, D15, D17). Здесь только решения этого change.

## Context

Действующие контракты на `master` (`4c185f77`, 2.135.1):
- «мои стройки» с `today` и `boundary` — `GET /api/work/sites/mine` (`work-11`);
- модель, свои отчёты, `If-Match`, конфликт четвёрки, `assignedOnDate` — `work-13`;
- автор ввода отдельно от исполнителя — `work-14`;
- окно подачи, момент автоподачи, обязательность места и материалов на переходе «подан» — `work-15`;
- `POST /api/work/entry/reports`, `GET` и `PUT /api/work/entry/reports/{id}`, `POST …/{id}/submit` — право
  `work.report.review`, охват `ManagerSites`, автор `enteredBy` из учётной записи, исполнитель из `employeeId`;
- фото: `PUT /api/work/reports/{id}/lines/{lineId}/photos/{photoId}` без версии, `DELETE` с версией,
  `GET /api/work/photos/{photoId}` и `/preview`, `photosPending` — `work-17`;
- вид работы с признаками и варианты — `work-06`, общие адреса требуют `core.catalog.read`;
- участники бригады — `GET /api/work/constructions/{id}/crew-candidates?date=…` (`work-18`);
- закрытие и досылка — `work-19`; таблица и карточка приёмки — `work-20` и `work-21`.

«Сегодня» в клиенте сейчас одно — день компании: `companyToday()` в
`src/client/src/shared/ui/Calendar.tsx:55`. Его же зовут стрелки года в
`src/client/src/shared/ui/dateSegmentModel.ts:60`.

## Goals / Non-Goals

**Goals:** монтажник вводит и подаёт отчёт в вебе по тем же правилам, что у будущего приложения;
менеджер вводит отчёт за сотрудника; ночная смена после полуночи не путается с днём.

**Non-Goals:**
- ярусы подсказки материалов — `work-26` (после этапа 3);
- поля заказчика «нужно к приёмке» — `work-24`;
- отчёт «объекта нет в списке» — этап 5 (`WORK-58`);
- сверка бригад — `work-18`.

## Decisions

23.11.2026: общую `src/client/src/shared/ui/PhotoGallery.tsx` строит Work-21. Work-22 использует её
с `fullScreen` и передаёт фото черновика или сохранённого отчёта. Загрузкой и состояниями досылки
управляет экран ввода Work-22.

- **Макеты:** 23.11.2026 владелец выбрал [А · Реестр и сетка](#раунд-р3). Строки — `EditGrid`
  с подробностями выбранной строки под сеткой.
- **Состав PR.**
  - **PR 1 — список и шапка.**
    - `src/client/src/shared/api/workReports.ts` — свои отчёты, черновик, правка и подача с `If-Match`.
    - `features/work/entry/MyReportsPage.tsx` — `PageHeader`, `DataGrid`, «Новый отчёт» —
      `PrimaryActionButton` и запись в `PALETTE_ACTIONS` с приёмом `usePaletteIntent`.
    - `features/work/entry/ReportForm.tsx` — страница отчёта со своим адресом. Общий `LeaveGuard`
      держит переходы между страницами, историю браузера и закрытие вкладки.
    - `src/client/src/shared/ui/SitePicker.tsx` — выбор стройки из назначенных.
    - `src/client/src/shared/ui/ShiftDateHeader.tsx` — `DateField` и «День | Ночь» на `Tabs segmented`,
      знак ☾.
    - «Ввести за сотрудника» — `EmployeePicker` (`work-12`).
    - Пункт «Мои отчёты» — в `navConfig.ts`, раздел и ранг входа — из `work-03`.
  - **PR 2 — строки, вид работы, материалы.**
    - `features/work/entry/ReportLines.tsx` — по форме Р3.
    - `src/client/src/shared/ui/WorkTypePicker.tsx` — вид работы с признаками `requires*` и вариантами.
    - `src/client/src/shared/ui/MaterialPicker.tsx` — выбор материала. Ярус пока один: справочник
      номенклатуры. Место под ярусы `work-26` закладывается. `NomenclaturePicker` счётов
      (`features/costs/NomenclaturePicker.tsx`) не берётся: он привязан к строке счёта.
    - Участники бригады — выбор из адреса `work-18`; до его слияния есть только признак бригады.
  - **PR 3 — фото и галерея.**
    - `features/work/entry/LinePhotos.tsx` — загрузка с `crypto.randomUUID()` как `photoId`, повтор
      тем же идентификатором.
    - Сохранение строки объявляет идентификаторы новых фото вместе с уже сохранёнными. Файлы
      отправляются отдельной очередью после объявления, в том числе после перехода с нового
      черновика на адрес отчёта. Имя исходного файла сохраняется при объявлении и помогает выбрать
      его для того же ожидающего фото после открытия отчёта. При уходе можно сохранить отчёт и
      объявления без ожидания доставки. Удаление сохранённого фото использует версию отчёта и
      возвращает новую. После повтора создания локальное снятие фото остаётся правкой состава.
    - `src/client/src/shared/ui/PhotoGallery.tsx` из Work-21 — `fullScreen`, превью и оригинал
      адресами модуля.
- **«Сегодня» стройки — проп календаря.** `Calendar` получает необязательный `today` (ISO).
  `DateInput` и `DateField` передают его насквозь. Нет пропа — `companyToday()`, как сейчас: прочие
  поля даты не меняются.
  - Значение берётся из `today` стройки в ответе `work-11`. Клиент пояса стройки не считает.
  - Стрелки года в `dateSegmentModel.ts:60` получают то же значение через `useSegmentField`.
  - Сторож — тест `Calendar.test.tsx`: Владивосток в 20:00 по Москве подсвечивает завтрашний день, а
    без пропа подсветка прежняя.
- **Пара «дата · смена» нового отчёта — с сервера (D8).** `sites/mine` уже отдаёт
  `suggested: { date, shift, label }` вместе с `today`. Ввод за сотрудника использует то же правило
  `SubmissionWindow.Suggested` с отчётами выбранного сотрудника и поясом его стройки.
- **Галерея.** Решение о переиспользовании записано в
  [архиве Work-21](../2026-11-23-work-21-review-ui/design.md). Как в просмотрщике эпика #1489,
  снимок вписывается в область просмотра. Стрелки и Esc действуют в активном окне галереи. Состав
  открытой галереи фиксируется, чтобы догрузка превью не переключала выбранный снимок.
- **Носители (D15).**
  - `sites/mine`: у стройки `today`, `timeZoneId`, `suggested: { date, shift, label }`; над выдачей
    `boundary: { text, count, reason }`. Для ввода за сотрудника эти же поля отдаёт новый контракт.
  - `ReportDto`: `version`, `autoSubmitAt`, `assignedOnDate`, `enteredBy`, `note`, `photosPending` и
    `lines[].photos[].state`. Чтение доступного отчёта дополнит ответ подписями стройки и сотрудника,
    поясом и датой `today` стройки, комментарием возврата из журнала и состоянием закрытия периода.
  - Конфликт ключа — 409 с `existingId`; отказ подачи — 422 с `requiredMissing: [{ line, lineId, field }]`.
  - Выбор вида работы получает `requiresLocation` и `requiresMaterials` от Work.
  - `GET /api/work/photos/limits` под `work.report.own` или `work.report.review` отдаёт текущие пределы
    `WorkSettings` и их подписи. Отказ 413 или отказ по числу передаёт актуальный текст сервера.

  Пометка «нужно для ИД» — сочетание признака вида из ответа и пустого поля формы. Это состояние
  черновика на экране; окончательно решает отказ сервера на подаче.
- **Правка строк.** Ключ поданного отчёта (стройка, дата, смена) остаётся заперт, строки и часы до
  приёмки редактируются тем же сохранением с `If-Match`. При перечитывании локальные правки полей
  накладываются на свежие строки по их идентификаторам. Если у строки, выбранной для удаления, появились
  новые связанные записи, удаление надо подтвердить заново. После потерянного ответа повтор создания
  использует исходное тело, а поздние правки остаются в форме для сохранения. Из 422 берутся номера строк
  и коды полей. Первая ошибка раскрывает подробности строки и ставит фокус на соответствующее поле.
- **Ввод за сотрудника.** PR 1 добавляет `GET /api/work/entry/reports/candidates` и
  `GET /api/work/entry/reports/candidates/{employeeId}/sites` под
  `work.report.review`: кандидаты и стройки по назначению выбранного сотрудника на запрошенную дату
  в пересечении с действующим охватом `ManagerSites`. `work.sites.all` расширяет охват менеджера,
  условие назначения сотрудника сохраняется. Отсутствие даты означает «сегодня» по каждой стройке.
  Менеджер может указать дату смены до выбора сотрудника. Эта дата задаёт выдачу кандидатов и начальную
  выдачу строек выбранного сотрудника, затем переносится в шапку отчёта.
  `sites/mine` читает назначения спрашивающего. `assignments/candidates` требует
  `work.assignment.edit`; `crew-candidates` предназначен для участников строки известной стройки.
  При вводе за сотрудника `GET /api/work/entry/sites/{id}/crew-candidates` требует `work.report.review`
  и проверяет тот же охват менеджера, что и ввод отчёта. Подбор участников использует дату отчёта.
  Протокол записи, включая `If-Match`, остаётся у `work-13`, `work-15` и `work-17`.
- **Справочники ввода.** До снятия `ReferenceReads` PR 1 даёт необходимые данные через
  `GET /api/work/entry/sites/{siteId}/catalog/{kind}`. Доступны `work-types` с вариантами, `units`,
  `materials` и `sections`. Чтение связано с
  правом ввода и доступной стройкой или уже доступным отчётом. На выборе доступны действующие
  записи. Параметр `reportId` разрешает чтение по уже доступному отчёту той же стройки и добавляет
  ранее выбранные записи. Разделы ограничены заданной стройкой. Потребителя в редакторе строк добавляет PR 2.
- **Закрытый период.** Возвращённые отчёты блокируют закрытие. Для закрытого отчёта доступна только
  досылка фото, заявленного до этого закрытия. Форма читает `canDeliver` у ожидающего фото. Сервер
  определяет этот признак тем же правилом, что и при загрузке. Состав отчёта и снимок `at-closing` сохраняются.
- **Сторож.**
  - vitest: без `reason` кнопка «Новый отчёт» есть, с `not-assigned` — нет; «Ночная смена 16.09» — из
    ответа; вариант исчезает у вида без вариантов; 413 показан у фото.
  - Живой прогон `work-entry-smoke.mjs`: монтажник заводит и подаёт отчёт; повтор той же четвёрки даёт
    «Открыть»; менеджер вводит за сотрудника.
- **Чем ломается.**
  - «Сегодня» из `companyToday()` — у стройки во Владивостоке вечером по Москве отчёт заводится
    вчерашним днём.
  - Окно ночной смены считает клиент — веб и телефон расходятся в сутках.
  - Фото ждут загрузки до подачи — отчёт висит на медленной сети.
- **Зависимости:** `work-11`, `work-13`, `work-14`, `work-15`, `work-03`, `work-12` (`EmployeePicker`);
  PR 2 — `work-06`; PR 3 — `work-17`, `work-05`. Этап 3 не нужен (ярусы — `work-26`).

## Risks / Trade-offs

- [Проп `today` у общего календаря забудут передать в новом поле отчёта] → поле даты отчёта одно,
  `ShiftDateHeader`, и тест на нём проверяет подсветку по стройке.
- [Форма строк по Р3 окажется карточками, а не сеткой] → `EditGrid` не берётся, `ui:ratchet` это не
  трогает; клавиатурный переход по полям тогда — забота карточки, тест на него — в PR 2.

- [В · Ввод по шагам](http://127.0.0.1:5200/work22.html?page=c). Активные отчёты и история
  разделены. Ввод идёт через «Смена», «Работы» с раскрытием карточки и итог перед подачей.

Рекомендация для Р3 — А. На компьютере монтажник может править несколько объёмов подряд с клавиатуры,
а подробности строки занимают место по запросу. Б удобен при одной–двух строках и на узком экране,
но на длинном отчёте растёт прокрутка. В делает этапы явными, но для быстрой правки добавляет переходы.
Архитектурный разбор: календарю нужен сквозной необязательный `today`; для карточек и сетки
подходят текущие компоненты и галерея. Раскрытие строки может стоять под `EditGrid` без смены его API.
