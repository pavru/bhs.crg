# Design: канал действия в журнале — интерфейс или агент через MCP

## Context

- Журнал — одна служба `IActivityLog` (`Application/Activity/IActivityLog.cs`). Автора и время она
  берёт сама: автора даёт `IActivityActor` — синглтон `HttpContextActivityActor`
  (`Api/Activity/HttpContextActivityActor.cs`, регистрация — `ServiceRegistration.Workers.cs:238`).
  Без `HttpContext` автор — `SystemActivityScope.Actor` («Система — <что>», такт модуля, work-08) или
  `ActivityActor.System`.
- Модули пишут журнал портом `IModuleActivityLog` → `ModuleActivityLogPort` → тот же `IActivityLog`.
- Журнал читается рядами серий (`core-journal-series`, CORE-28.2): сессию правки решает при записи
  `ActivitySession.Continues` по предыдущей записи цели (`ActivitySessionTail`), страница идёт по
  головам серий (`ActivityRow`), записи ряда раскрывает `SeriesAsync`.
- MCP — `app.MapMcp("/mcp").RequireAuthorization()` (`EndpointMap.cs:56`), транспорт без сессий. Инструменты выполняются
  внутри HTTP-запроса и берут пользователя из `IHttpContextAccessor` (`JobTools.RequireUserId`).
- Фоновые задачи (`Domain/Jobs/Job.cs`) хранят `UserId` заказчика. `JobBackgroundService` выполняет
  их в своей области, вне запроса. Журнал, записанный внутри задачи, сегодня получает автора
  «Система» — даже если задачу поставил человек. Окружение `AsyncLocal` для автора вне запроса уже
  есть: `SystemActivityScope` (work-08) подписывает записи такта «Система — <такт>».

### Что выяснилось сверкой (master 2.17.11; пересверено на 2.128.3, 16.11.2026)

- Писатели журнала:
  - ядро: роли, пользователи, схемы и владельцы типов, состав модулей, периоды, архив и удаление
    записей, настройки модулей, валюта, номенклатура, представления и выгрузка таблиц;
  - модули `costs`, `plan` и `work` портом (в `work` — и задача такта `AutoSubmitJob`).
- **Ни один из них не достижим из MCP.** Все 26 инструментов сверены: меняющие семь ведут в генерацию,
  сборку комплекта, распознавание, замечания и алиасы, а там журнала нет. Отсюда два следствия:
  - колонка канала сама по себе ничего агентского сегодня не покажет — нужно решение, что писать о
    действиях агента (В1);
  - старые записи достоверно сделаны интерфейсом или системой (D5).
- Меняющих инструментов семь, а не шесть, как в #1337 (см. архив `core-mcp-gate-inventory`). На 2.128.3
  их по-прежнему семь из 26, и журнала из `Api/Mcp/` по-прежнему не пишет никто.

## Goals / Non-Goals

**Goals:** канал у каждой записи без участия писателя; действие агента видно в журнале; канал
доезжает до фоновых задач; отбор по каналу; копия переносит канал.

**Non-Goals:**
- канал «мобильный клиент»: мобильный клиент (этап 5) ходит тем же API, это интерфейс. Отдельное
  значение — по решению при его проектировании;
- канал «ассистент»: заводится вместе с ИИ-ассистентом (отложен). Значения хранятся строкой, новое
  добавляется без миграции существующих;
- журналирование выпуска PDF и распознавания из интерфейса — это вариант Б в В1, не рекомендуемый.

## Decisions

- **D1. Канал — часть автора, его определяет `IActivityActor`.** `ActivityActor(Id, Name, Channel)`.
  `IActivityLog.RecordAsync` сигнатуру не меняет: писатель канал не передаёт и подделать его не может.
  Это то же правило, по которому служба не принимает автора («иначе автор стал бы параметром, который
  можно передать чужой»).
  - Отклонено: **параметр каждого вызова** — новый писатель забыл бы его, о чём issue и
    предупреждает.
  - Отклонено: **разбор пути `/mcp` строкой** — адрес переименуют, и канал молча станет `ui`.
- **D2. Канал запроса — по метаданным адреса.** На `MapMcp("/mcp").RequireAuthorization()` вешается
  `.WithMetadata(ActivityChannel.Mcp)`. `HttpContextActivityActor` читает
  `HttpContext.GetEndpoint()?.Metadata.GetMetadata<ActivityChannel>()`; нет метаданных — `ui`, нет
  запроса — `system`. Будущий адрес ассистента получит свою метку тем же приёмом.
- **D3. Канал и автор едут в фоновую задачу.**
  - `Job` получает колонку `Channel`. `JobService.EnqueueAsync` заполняет её из
    `IActivityActor.Current` в момент постановки — то есть в запросе.
  - `JobBackgroundService`, выполняя задачу, открывает окружающий источник автора `JobActivityScope`:
    `AsyncLocal`, тем же приёмом, что `SystemActivityScope` (work-08). Источник несёт `UserId` задачи,
    имя (одно чтение учётной записи на задачу) с пометкой задачи — «Петрова — задача «…»»,
    `ActivityActor.ForJob` — и канал.
  - Источник читает **только журнал** (`ActivityLog.RecordAsync`: автор задачи, иначе
    `IActivityActor.Current`). `HttpContextActivityActor` его не смотрит: вне запроса он «кто действует»
    и для портов модулей (`IModuleUser`, владелец задачи в `ModuleJobsPort`), а их договор вне запроса —
    «никого». Подставь туда заказчика — и работа модуля сочла бы себя запросом без прав, а дочерняя задача
    ушла бы в его колокольчик (ревью PR #1997). `SystemActivityScope` называет систему без
    идентификатора и этот договор не нарушает, поэтому остаётся у `IActivityActor`.
  - Задача без заказчика (`UserId == Guid.Empty`: плановая копия, такт модуля) — `system`; подпись
    «Система — <такт>» по-прежнему даёт `SystemActivityScope`.
  - Синглтон `IActivityActor` остаётся синглтоном: `AsyncLocal` не требует переводить его в область.
- **D4. Действие агента — одна запись на удавшийся вызов меняющего инструмента** (вариант А из В1).
  - Пишет её **фильтр вызовов MCP-сервера** — `WithRequestFilters(f => f.AddCallToolFilter(…))`
    в `ModelContextProtocol.AspNetCore` 1.4.1, рядом с `AddAuthorizationFilters()`
    (`ServiceRegistration.Domain.cs`) — одно место на все инструменты. Новый инструмент не может «забыть журнал».
  - Признак «меняющий» — `ReadOnly == false` у `[McpServerTool]`, тот же, по которому клиент решает,
    спрашивать ли подтверждение (`McpToolContractTests`).
  - Действие каталога — `core.mcp.tool.called` «Агент вызвал инструмент MCP»; цель — первый
    ОБЪЯВЛЕННЫЙ схемой инструмента аргумент-идентификатор (комплект, документ, набор) в порядке
    параметров, не длиннее колонки; лишний аргумент клиента цель не подменяет. «Стало» — название
    инструмента.
    Аргументы целиком не пишутся: в них бывают данные модулей, а журнал читают по праву ядра.
  - Запись делается после удавшегося вызова. Отказ прав, исключение и ответ `IsError` записи не
    оставляют — правило журнала «после того, как действие удалось».
  - Сбой самой записи вызов не роняет и отмену запроса не слушает: действие уже совершено, и ошибка,
    ушедшая агенту, толкнула бы его повторить неидемпотентный вызов. Сбой — в лог сервера; это та же
    плата, что названа у `IActivityLog`: тихая потеря следа лучше ложного отказа.
- **D5. Старые записи — по автору, миграцией.**
  - `ALTER TABLE activity_log ADD "Channel" text NOT NULL DEFAULT 'ui'`, затем
    `UPDATE … SET "Channel" = 'system' WHERE "ActorId" IS NULL`, умолчание снимается.
  - Это правка схемы и разовое заполнение, а не правка записей службой, и `SaveChanges` журнала её не
    видит.
  - Правило не догадка: до этого change журнал из MCP не писался ни разу (см. сверку). «Неизвестно»
    отклонено — оно утверждало бы незнание там, где ответ известен.
- **D6. Копия.** `BackupActivityRecord` получает `string? Channel = null` — необязательным, как
  `SessionId` и `SeriesHead` из `core-journal-series`. При импорте отсутствующий канал
  выводится тем же правилом, что в D5. Незнакомый код (копия более новой версии) ложится как есть
  (`ActivityChannel.FromStored`): подмена известным записала бы ложь в журнал, который не правится; в отбор
  он не попадает, в «все каналы» виден. `ImportAsync` остаётся единственным путём, где канал приходит
  снаружи.
- **D7. Отбор.**
  - `ReadAsync` и `CountAsync` получают `channel` и отбирают ряды по каналу головы — у серии он один
    (D9). Адрес — параметр `channel`.
  - Канал несут ряд (`ActivityRow.Channel`) и каждая запись серии (`SeriesAsync`).
  - Неизвестное значение — 400 с перечнем: пустой ответ на опечатку был бы отказом, переодетым в
    результат.
  - Частичный индекс `(Channel, OccurredAt DESC, Id DESC) WHERE SeriesHead` (миграция
    `ActivityChannelIndex`): без него редкий канал читался бы обходом всех голов, а число страницы —
    подсчётом по всем головам, на каждой странице (ревью PR #1997).
  - Перечень каналов с названиями отдаёт `GET /api/activity/channels`; клиент своего списка не держит.
- **D8. Экран `/activity`** — второй отбор `Select variant="chip"` рядом с отбором по действию
  (`emptyItem` «Все каналы»; «Интерфейс / Агент (MCP) / Система») и пометка `StatusText` «через агента
  (MCP)» в колонке «Кто» (бывший `StatusBadge`, [UI-74]).
  - Это перенос готового элемента по готовым правилам `docs/UI.md`, без нового взаимодействия, поэтому
    без трёх макетов.
  - Если Дизайнер при ревью сочтёт пометку новым элементом — макет до кода.
- **D9. Канал рвёт сессию правки.** `ActivitySessionTail` получает канал предыдущей записи цели, и
  `ActivitySession.Continues` продолжает сессию только при том же канале.
  - Иначе серия смешала бы каналы, а ряд несёт поля головы: отбор `channel=mcp` спрятал бы запись
    агента внутри ряда, начатого в интерфейсе. Это отказ, переодетый в результат.
  - Прежние записи не меняются (CORE-28.2): граница решается при записи новой.
  - Автор сессии — снимок записи: идентификатор И имя. Запись задачи (имя с пометкой, D3) и ручная правка
    того же человека сессию друг другу не продолжают: иначе автоматическое изменение пряталось бы в ряд
    ручных (ревью PR #1997).
- **Сторож.**
  - Тест фильтра: для каждого меняющего инструмента из описи (`McpInventory.FromHost`,
    `BHS.CRG.Tests/Mcp/McpInventory.cs`, из `core-mcp-gate-inventory`; признак — `Tool.ReadOnly == false`)
    удавшийся вызов через фильтр даёт запись `mcp` с его названием, а читающий — ни одной.
  - Сквозной тест через `/mcp` (`report_observation`): запись `mcp`, автор — владелец токена.
  - Тест задачи: поставленная через `/mcp` несёт `mcp`, запись журнала из неё — заказчик с пометкой
    задачи и `mcp`, а `IActivityActor.Current` и `IModuleUser.Id` в её области — по-прежнему система.
  - Тест миграции: старые записи с автором и без получают `ui` и `system`.
  - Тест сессии: тот же автор, та же цель и группа, другой канал — новая сессия.
  - `BackupManifestCoverageTests`: канал переживает копию, старая копия без поля читается по правилу.

## Risks / Trade-offs

- [`AsyncLocal` утечёт за пределы задачи] → источник открывается `using`-областью вокруг одной
  задачи и закрывается в `finally`. Тест: следующая задача без заказчика пишет журнал от `System`.
- [Запись на каждый вызов меняющего инструмента раздует журнал] → меняющих инструментов семь, и они
  дорогие (выпуск, сборка, распознавание). Агент, выпускающий сотни PDF, — как раз то, что журнал
  обязан показать.
- [Фильтр вызовов — API SDK `ModelContextProtocol.AspNetCore` 1.4.1] → сверено 16.11.2026: в 1.4.1
  есть `WithRequestFilters` с `AddCallToolFilter`. При реализации проверить порядок относительно
  `AddAuthorizationFilters()`: отказ прав до вызова записи не оставляет (D4).

## Открытые вопросы

**В1. Что журнал записывает о действии агента** — **решено владельцем 22.10.2026: вариант А**
(рекомендация принята; дельта спецификации написана под него, D4 действует).

- **А (рекомендация)** — одна запись «Агент вызвал инструмент MCP» на удавшийся вызов меняющего
  инструмента: название инструмента и цель, только канал `mcp`. Одно место в коде, новый инструмент
  покрыт сам, из интерфейса журнал не растёт.
- **Б** — завести в каталоге действия самих операций — «Выпущен документ», «Собран комплект»,
  «Запущено распознавание», «Записано/отозвано замечание», «Предложен алиас» — и писать их по обоим
  каналам. Это расширение перечня `CORE-28`: журнал начинает фиксировать и выпуск PDF из интерфейса —
  частую операцию, — и семь писателей в разных местах.
- **В** — только колонка канала и отбор. Действия агента в журнале не появятся, пока он не дойдёт до
  писателя, который уже есть. «Готово» из issue («действие через MCP видно в журнале») не выполняется.
