# Design: канал действия в журнале — интерфейс или агент через MCP

## Context

- Журнал — одна служба `IActivityLog` (`Application/Activity/IActivityLog.cs`). Автора и время она
  берёт сама: автора даёт `IActivityActor` — синглтон `HttpContextActivityActor`
  (`Api/Activity/HttpContextActivityActor.cs`, регистрация — `ServiceRegistration.Workers.cs:233`).
  Без `HttpContext` автор — `ActivityActor.System`.
- Модули пишут журнал портом `IModuleActivityLog` → `ModuleActivityLogPort` → тот же `IActivityLog`.
- MCP — `app.MapMcp("/mcp")` (`EndpointMap.cs:55`), транспорт без сессий. Инструменты выполняются
  внутри HTTP-запроса и берут пользователя из `IHttpContextAccessor` (`JobTools.RequireUserId`).
- Фоновые задачи (`Domain/Jobs/Job.cs`) хранят `UserId` заказчика. `JobBackgroundService` выполняет
  их в своей области, вне запроса. Журнал, записанный внутри задачи, сегодня получает автора
  «Система» — даже если задачу поставил человек.

### Что выяснилось сверкой (master 2.17.11)

- Писатели журнала:
  - ядро: роли, пользователи, схемы и владельцы типов, состав модулей, периоды, архив и удаление
    записей, настройки модулей, валюта, номенклатура, представления и выгрузка таблиц;
  - модуль `costs` портом.
- **Ни один из них не достижим из MCP.** Все 26 инструментов сверены: меняющие семь ведут в генерацию,
  сборку комплекта, распознавание, замечания и алиасы, а там журнала нет. Отсюда два следствия:
  - колонка канала сама по себе ничего агентского сегодня не покажет — нужно решение, что писать о
    действиях агента (В1);
  - старые записи достоверно сделаны интерфейсом или системой (D5).
- Меняющих инструментов семь, а не шесть, как в #1337 (см. `core-mcp-gate-inventory`).

## Goals / Non-Goals

**Goals:** канал у каждой записи без участия писателя; действие агента видно в журнале; канал
доезжает до фоновых задач; отбор по каналу; копия переносит канал.

**Non-Goals:**
- канал «мобильный клиент»: мобильный клиент (этап 5) ходит тем же API, это интерфейс. Отдельное
  значение — по решению при его проектировании;
- канал «ассистент»: заводится вместе с ИИ-ассистентом (отложен). Значения хранятся строкой, новое
  добавляется без миграции существующих;
- журналирование выпуска PDF и распознавания из интерфейса — это вариант Б в В1, не рекомендуемый.

## Decisions

- **D1. Канал — часть автора, его определяет `IActivityActor`.** `ActivityActor(Id, Name, Channel)`.
  `IActivityLog.RecordAsync` сигнатуру не меняет: писатель канал не передаёт и подделать его не может.
  Это то же правило, по которому служба не принимает автора («иначе автор стал бы параметром, который
  можно передать чужой»).
  - Отклонено: **параметр каждого вызова** — новый писатель забыл бы его, о чём issue и
    предупреждает.
  - Отклонено: **разбор пути `/mcp` строкой** — адрес переименуют, и канал молча станет `ui`.
- **D2. Канал запроса — по метаданным адреса.** На `MapMcp("/mcp")` вешается
  `.WithMetadata(ActivityChannel.Mcp)`. `HttpContextActivityActor` читает
  `HttpContext.GetEndpoint()?.Metadata.GetMetadata<ActivityChannel>()`; нет метаданных — `ui`, нет
  запроса — `system`. Будущий адрес ассистента получит свою метку тем же приёмом.
- **D3. Канал и автор едут в фоновую задачу.**
  - `Job` получает колонку `Channel`. `JobService.EnqueueAsync` заполняет её из
    `IActivityActor.Current` в момент постановки — то есть в запросе.
  - `JobBackgroundService`, выполняя задачу, открывает окружающий источник автора: `AsyncLocal`,
    тем же приёмом, что `IHttpContextAccessor`. Источник несёт `UserId` задачи, имя (одно чтение
    учётной записи на задачу) и канал.
  - `HttpContextActivityActor` смотрит его, когда запроса нет.
  - Задача без заказчика (`UserId == Guid.Empty`, плановая копия) — `system`.
  - Синглтон `IActivityActor` остаётся синглтоном: `AsyncLocal` не требует переводить его в область.
- **D4. Действие агента — одна запись на удавшийся вызов меняющего инструмента** (вариант А из В1).
  - Пишет её **фильтр вызовов MCP-сервера**, зарегистрированный рядом с `AddAuthorizationFilters()`,
    — одно место на все инструменты. Новый инструмент не может «забыть журнал».
  - Признак «меняющий» — `ReadOnly == false` у `[McpServerTool]`, тот же, по которому клиент решает,
    спрашивать ли подтверждение (`McpToolContractTests`).
  - Действие каталога — `core.mcp.tool.called` «Агент вызвал инструмент MCP»; цель — первый
    идентификатор из аргументов (комплект, документ, набор); «стало» — название инструмента.
    Аргументы целиком не пишутся: в них бывают данные модулей, а журнал читают по праву ядра.
  - Запись делается после удавшегося вызова. Отказ прав, исключение и ответ `IsError` записи не
    оставляют — правило журнала «после того, как действие удалось».
- **D5. Старые записи — по автору, миграцией.**
  - `ALTER TABLE activity_log ADD "Channel" text NOT NULL DEFAULT 'ui'`, затем
    `UPDATE … SET "Channel" = 'system' WHERE "ActorId" IS NULL`, умолчание снимается.
  - Это правка схемы и разовое заполнение, а не правка записей службой, и `SaveChanges` журнала её не
    видит.
  - Правило не догадка: до этого change журнал из MCP не писался ни разу (см. сверку). «Неизвестно»
    отклонено — оно утверждало бы незнание там, где ответ известен.
- **D6. Копия.** `BackupActivityRecord` получает `string? Channel`. При импорте отсутствующий канал
  выводится тем же правилом, что в D5. `ImportAsync` остаётся единственным путём, где канал приходит
  снаружи.
- **D7. Отбор.**
  - `ReadAsync` и `CountAsync` получают `channel`, адрес — параметр `channel`.
  - Неизвестное значение — 400 с перечнем: пустой ответ на опечатку был бы отказом, переодетым в
    результат.
  - Индекс `(Channel, OccurredAt)` не заводится: журнал мал, отбор идёт вместе с постраничным чтением
    по времени. Решение пересматривается по замеру.
- **D8. Экран `/activity`** — второй `Select` рядом с отбором по действию («Все каналы / Интерфейс /
  Агент (MCP) / Система») и пометка `StatusBadge` «через агента (MCP)» в колонке «Кто».
  - Это перенос готового элемента по готовым правилам `docs/UI.md`, без нового взаимодействия, поэтому
    без трёх макетов.
  - Если Дизайнер при ревью сочтёт пометку новым элементом — макет до кода.
- **Сторож.**
  - Тест фильтра: для каждого меняющего инструмента из описи `core-mcp-gate-inventory` удавшийся вызов
    через фильтр даёт запись `mcp` с его названием, а читающий — ни одной.
  - Сквозной тест через `/mcp` (`report_observation`): запись `mcp`, автор — владелец токена.
  - Тест задачи: поставленная через `/mcp` несёт `mcp`, и в её области `IActivityActor.Current` —
    заказчик с `mcp`.
  - Тест миграции: старые записи с автором и без получают `ui` и `system`.
  - `BackupManifestCoverageTests`: канал переживает копию, старая копия без поля читается по правилу.

## Risks / Trade-offs

- [`AsyncLocal` утечёт за пределы задачи] → источник открывается `using`-областью вокруг одной
  задачи и закрывается в `finally`. Тест: после задачи `IActivityActor.Current` вне запроса снова
  `System`.
- [Запись на каждый вызов меняющего инструмента раздует журнал] → меняющих инструментов семь, и они
  дорогие (выпуск, сборка, распознавание). Агент, выпускающий сотни PDF, — как раз то, что журнал
  обязан показать.
- [Фильтр вызовов — API SDK `ModelContextProtocol.AspNetCore` 1.4.1] → при реализации свериться с
  тем, как сделан `AddAuthorizationFilters()`. Если фильтра вызова в версии нет — обёртка на уровне
  `McpServerOptions.Handlers` с тем же свойством «одно место» и записью в D4 до кода.

## Открытые вопросы

**В1. Что журнал записывает о действии агента** — **решено владельцем 22.10.2026: вариант А**
(рекомендация принята; дельта спецификации написана под него, D4 действует).

- **А (рекомендация)** — одна запись «Агент вызвал инструмент MCP» на удавшийся вызов меняющего
  инструмента: название инструмента и цель, только канал `mcp`. Одно место в коде, новый инструмент
  покрыт сам, из интерфейса журнал не растёт.
- **Б** — завести в каталоге действия самих операций — «Выпущен документ», «Собран комплект»,
  «Запущено распознавание», «Записано/отозвано замечание», «Предложен алиас» — и писать их по обоим
  каналам. Это расширение перечня `CORE-28`: журнал начинает фиксировать и выпуск PDF из интерфейса —
  частую операцию, — и семь писателей в разных местах.
- **В** — только колонка канала и отбор. Действия агента в журнале не появятся, пока он не дойдёт до
  писателя, который уже есть. «Готово» из issue («действие через MCP видно в журнале») не выполняется.
