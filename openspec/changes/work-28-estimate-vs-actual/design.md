# Design: «по смете — фактически» и выработка

Общая архитектура — `../work-00-epic/design.md`. Здесь только решения этого change.

## Context

- **Часы** указаны на отчёт целиком (`WORK-7`), а не на работу. Поэтому сравнение честно только по
  стройке или разделу за период (`WORK-42`), а выработка по виду работ — только по отчётам с одним
  видом (`WORK-Q6`).
- **Нормы** — чел.-ч на единицу позиции сметы (`PLAN-9.1`) — приходят контрактом «Плановые работы»
  этапа 3 (`CORE-34`, D13). Ответ идёт в правах спрашивающего, узким правом `plan.labor.read` без денег
  (Е3).
- **Принятые объёмы и связь строки с позицией перечня** — свои данные модуля (`work-13`, `work-16`).
  Бригадная работа считается итогом группы (`work-18`), а не суммой строк участников.
- **Экран «Ход работ»** (`PLAN-21`) — свёрстанный экран стройки, его строит этап 3. Собирает ядро,
  каждый модуль даёт свою часть: строка «Колонка „Хода работ“» в таблице контрактов `CORE-34`
  (`docs/tz/10-ядро.md:743`). Полоса трудозатрат — вклад `work`.

## Goals / Non-Goals

**Goals:** два адреса чтения с состояниями и изоляцией; контракт «Выработка» для графика; полоса в «Ходе
работ».

**Non-Goals:**
- сравнение по отдельной работе — его нет по построению (`WORK-42`);
- свои нормы у вида работы (`WORK-Q4`, В), деньги и ставки (`WORK-26`);
- бригада как измерение (`WORK-Q7`);
- показ выработки в графике — экран `plan` (`PLAN-16`); здесь только поставщик;
- выгрузка часов — этап 6.

## Decisions

- **Состав PR.**
  - **PR 1, сервер.**
    - Модуль `work`: `Labor/EstimateVsActual.cs` — сравнение и разнесение по разделу;
      `Labor/Productivity.cs` — выработка, порог, отброшенное, процент к норме;
      `Endpoints/LaborEndpoints.cs` — адреса `GET /api/work/labor/estimate-vs-actual` и
      `GET /api/work/labor/productivity`.
    - Контракт: интерфейс `BHS.CRG.Modules/Exchange/IWorkProductivity.cs`, реализация в
      `RegisterServices` модуля `work`.
    - Тест состава `/api/account/access` по ролям, если `plan.labor.read` уже объявлено этапом 3 (D2).
  - **PR 2, клиент.**
    - Полоса `src/client/src/features/work/labor/EstimateVsActualStrip.tsx` и хук в `shared/api`.
    - Вклад в «Ход работ» — механизмом вклада модулей, который заведёт этап 3. Его нет — заводится по
      образцу панелей карточки стройки `work-03`.
    - Документы: `docs/USER_GUIDE.md`, раздел «Ход работ», и `npm run toc` в `docs/tools`.
- **Разнесение по разделу.** Часы отчёта делятся только между его сметными строками, пропорционально
  «объём × норма». Строки без нормы уходят в `offEstimate` и в деление не входят: делить им «остаток
  поровну» (`WORK-Q5`, Б) значило бы выдать за факт число без основания. Сумма разнесённых часов по
  разделам равна часам отчётов — это сторож.
- **Выработка.**
  - Отчёт входит, только если все его строки — один вид работ в одной единице: метры со штуками не
    складываются.
  - Порог `minSample` — настройка модуля через `IModuleSettings`, отдаётся в ответе: клиент его не
    знает.
  - Отброшенное — счётчиками `discarded.mixedReports` и `discarded.otherUnit`, отдельно
    `notAccepted` — чтобы «данных мало» объяснялось.
- **Изоляция.** Стройки разрешаются тем же параметром доступа, что отчёты (D4, `work-11`). Чужая
  стройка — 404. Процент по сотруднику считается только внутри доступных строек: часы сотрудника на
  чужой стройке не входят даже в его собственный процент.
- **Контракт «Выработка»** отдаёт только производное — объём на час и выборку (Е4, `WORK-57`).
  - Право — `work.facts.read`, право контракта (`work-27`, D3).
  - Почему без построчной изоляции: это не отчёт, а агрегат прошлых строек. Порог выборки не даёт
    восстановить часы одного человека.
  - Граница — решение этого change; на ревью его сверяет Архитектор.
- **Пишущих адресов нет** — If-Match не нужен. Ворота — модуль и составная политика «любое из»
  (`work.report.review`, `work.report.read.all`) из `work-03`.
- **Макеты:** раунд Р6 (полоса «по смете — фактически»), выбор владельца — вписать сюда ссылку.
- **Сторож.**
  - Разнесение: сумма по разделам равна часам отчётов.
  - Бригадная группа из трёх строк даёт один объём, как в `work-27`.
  - Смешанный отчёт в выработку не входит и назван.
  - Каждое состояние получено настоящим путём: `plan` выключен, нет права, нет принятых, ниже порога.
  - `ModuleBoundaryTests` — `work` не ссылается на `plan`.
- **Чем ломается.**
  - Часы делятся «остаток поровну»: выработка по виду работ превращается в смету, выданную за факт
    (`WORK-Q6`).
  - Нет права на нормы — приходит ноль сметных чел.-ч, и стройка выглядит провальной.
- **Зависит от:**
  - этапа 3 — контракт «Плановые работы» с чел.-ч на единицу, право `plan.labor.read`, экран «Ход работ»
    и механизм вклада модулей;
  - `work-09` — механизм межмодульного контракта;
  - `work-13`, `work-16`, `work-18` — принятые объёмы, итог бригады;
  - `work-27` — право контракта `work.facts.read`.

## Risks / Trade-offs

- [`plan.labor.read` в ТЗ не записано] → в таблице `PLAN-23` (`docs/tz/50-планирование.md:189`) его
  нет, есть только решение сессии Е3 и `WORK-57`. Требование к этапу 3 вносится в ТЗ до его нарезки,
  иначе «Менеджер проекта» получит `hidden` всегда.
- [Экран «Ход работ» и механизм вклада модулей строит этап 3] → PR 2 стартует после них. Если этап 3
  сделал «Ход работ» без точки вклада, она заводится первым коммитом PR 2.
- [Порог выборки — компромисс точности и приватности] → значение по умолчанию — 10 отчётов на 2
  стройках. Менять его — настройка модуля, а не код.
