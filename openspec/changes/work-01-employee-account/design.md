# Design: связь «учётная запись → сотрудник» и экран сотрудников

Общая архитектура — `../work-00-epic/design.md` (D6 — связь, D15 — носители, D17 — макеты). Здесь
только решения этого change.

## Context

Сверено по коду master `f8a8b222`.

- Сотрудник — объект общего типа «Сотрудник» (`Application/Documents/CoreRecordTypes.cs:65-92`),
  производного от «Персоны». Дверь — `Api/Endpoints/Core/EmployeeEndpoints.cs`. Своих команд у неё нет:
  она зовёт команды `CommonData`, версия — `xmin` объекта через `Endpoints/Documents/RecordIfMatch.cs`.
- Поле `УчётнаяЗапись` объявлено строкой с `Locked: true` (`CoreRecordTypes.cs:82-83`). Действия
  «связать» нет, и поле заполнить некому.
- Права `core.employees.read` и `core.employees.edit` объявлены (`Api/Auth/CorePermissions.cs:60-63`).
  Чтение есть у «Менеджера проекта» и «Бухгалтера» (`Api/Auth/SystemRoles.cs:69,106`). Правку
  получает только «Администратор»: его состав равен справочнику.
- Удаление учётной записи — `Api/Endpoints/Users/UserEndpoints.cs:186`. Образец «связь переживает
  удаление автора» — `SavedTableViewConfiguration.cs:40` (`DeleteBehavior.SetNull`).
- `GET /api/employees` при незаведённом типе отвечает пустым списком (`EmployeeEndpoints.cs:47`), а
  `POST` — отказом `DirectoryMissing`. Экран различать «не заведён» и «пусто» по такому ответу не может.
- Экрана сотрудников в клиенте нет, раздела ядра `employees` в `BHS.CRG.Modules/CoreSections.cs` нет.

## Goals / Non-Goals

**Goals:** уникальная связь с журналом; носители `account` и `employee`; экран, где администратор
связывает сотрудника.

**Non-Goals:**
- типизированный порт сотрудника для модулей — `work-11`;
- выбор сотрудника как общий компонент с причинами от сервера — `work-12` (D17);
- устройства сотрудника — этап 5 (`WORK-58`).

## Decisions

### Состав PR

- **PR 1 — связь (сервер).**
  - Сущность `EmployeeAccount` в `BHS.CRG.Domain/Catalog/`: `EmployeeId` (ключ), `UserId` (уникальный,
    допускает `null`), `AccountName` — имя снимком на момент связывания.
  - Конфигурация в `Infrastructure/Persistence/Configurations/EmployeeAccountConfiguration.cs`:
    - внешний ключ на `AspNetUsers` с `SetNull`;
    - внешний ключ на объект сотрудника без каскада;
    - частичный уникальный индекс по `UserId`.
  - Миграция ядра `EmployeeAccounts` (`--context AppDbContext`).
  - Адреса `PUT` и `DELETE /api/employees/{id}/account` и `GET /api/employees/account-candidates` в
    `EmployeeEndpoints.cs` — группа `edit` уже стоит под `core.employees.edit`.
  - Поле `account` в выдаче сотрудника.
  - `employee` и `employeeReason` в `/access` (`Api/Endpoints/Account/AccountEndpoints.cs:33-74`).
  - Коды `core.employee.account.linked` и `core.employee.account.unlinked` в `Application/Activity/ActivityActions.cs`.
  - Исключение `EmployeeAccount` в `BackupManifestCoverageTests.cs:40` с причиной «связь адресует учётную
    запись, а их копия не переносит» — рядом с `ApplicationUser` и `UserSetting`.
- **PR 2 — экран (клиент).** Код — после выбора макета Р1.
  - `features/employees/EmployeesPage.tsx` — list-detail на `ListDetailShell`.
  - Блок «Учётная запись» и диалог выбора кандидата.
  - Пункт `/employees` в `shared/ui/navConfig.ts`: `permission: 'core.employees.read'`, `rail: 'data'`,
    `section: 'employees'`.
  - Код `employees` в `CoreSections.All` (сторож `CoreSectionsTests`).
  - `GET /api/employees` при незаведённом типе отвечает 409 `directory-missing` вместо пустого списка.
    Потребителей у адреса в клиенте нет, поэтому правка безопасна. Проверяется это `grep` по
    `src/client/src` и `src/server/BHS.CRG.Api/Mcp` в том же PR.

### Почему таблица, а не поле карточки

`CORE-15`: на связь опираются уникальность и доступ («свои» отчёты). В JSON дубль прошёл бы молча, и
это «чем ломается» change. Поле `УчётнаяЗапись` остаётся запертым и связью не заполняется. Зеркало
дало бы два источника, которые разойдутся при первом восстановлении копии. Убрать поле из схемы
заказчика — не задача этого change: схему правит человек (`CORE-20.2`).

### Версия связывания — версия карточки

Связывание и отвязывание пишут таблицу ядра и трогают `UpdatedAt` объекта сотрудника одной
транзакцией `AppDbContext`, поэтому `xmin` карточки сдвигается. `If-Match` берёт уже существующее
`version` карточки (`RecordIfMatch`). Отдельная версия у связи потребовала бы «версии отсутствующей
строки» для состояния `none`. Побочное следствие честное: форма карточки, открытая до связывания,
получит 409, потому что карточка показывает связь. Ворота модуля здесь неприменимы: это адрес ядра, а
не модуля. Ворота — право `core.employees.edit` (`AUTH-8`), перепись — `EndpointGateInventoryTests`.

### Состояние `deleted`

Строка связи переживает удаление учётной записи: `UserId` становится `null` по `SetNull`, `AccountName`
остаётся. Состояние вычисляется так:
- строки нет — `none`;
- строка с `UserId` — `linked`;
- строка без `UserId` — `deleted`.

Код удаления пользователя не трогается: правило держит внешний ключ, и забыть его негде.

### Носитель в `/api/account/access`

Адрес зовут каждые полминуты. Связь читается одним запросом по `UserId` вместе с именем и признаком
архива объекта. `employeeReason: directory-missing` идёт, когда тип «Сотрудник» не заведён
(`SkipWhenBlocked`). Без этой причины монтажник на чистой установке видел бы «вас не связали», хотя
связывать не с чем.

### Сторож и «чем ломается»

- `EmployeeAccountLinkTests` (интеграционный): вторая связь той же учётной записи — 409 с именем
  занятого сотрудника; без `If-Match` — 400, устаревший — 409; без права — 403; удаление учётной записи
  даёт `deleted`.
- Ломается так: уникальный индекс снят или связь хранится строкой в JSON — тест «вторая связь» краснеет.
- `AccountAccessTests` дополняется полями `employee` и `employeeReason`.

(порт сотрудника), `work-13` («свои» отчёты), `work-18` (бригада).

## Risks / Trade-offs

- [Восстановление копии теряет связи] → это следствие `CORE-7`, а не потеря. ADMIN_GUIDE говорит:
  после восстановления на новый экземпляр связи заводятся заново.
- [409 у формы карточки после связывания] → форма перечитывает карточку тем же путём, что при любом
  конфликте версии.
- [Имя учётной записи снимком устаревает после её переименования] → имя обновляется при связывании.
  Живое имя `linked` берётся из учётной записи, снимок нужен только `deleted`.

## Migration Plan

`УчётнаяЗапись` заполнить было нечем. Откат PR — удаление таблицы.
