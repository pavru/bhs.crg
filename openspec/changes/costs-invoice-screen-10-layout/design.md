# Design: экран счёта — одна прокрутка, липкая сводка, место по контейнеру

Общая архитектура — `../costs-invoice-screen-00-epic/design.md`: D1 (раскладка), D2 (место), D5 (запасной
путь «одна кнопка»), D8 (компоненты MD3), D10.1–2 (как доказывается). Требования — `specs/costs/spec.md`.
Здесь только то, чего нет в зонтике.

## Context

- **Вариант Г**, выбранный владельцем 27.10.2026. Макет «Экран счёта · критический пересмотр»
  (`ee2cb716-f2c0-415c-95bd-95f139b5e4a5`), файлы `mock/var-c.js` (раскладка, `LIST_MIN_FORM = 940`,
  `scanW`), `mock/core.js` (колонки таблицы строк), `mock/sheet0.js` (лист 0, разделы 2–3).

  - 6 — список сворачивается только когда форме не хватает места, правило ≥ 940 px;
  - 7 — 1024 px (1280 при масштабе 125 %) — рабочая ширина.

  Ответы 1, 2, 4, 5 сюда не входят: 1 — ребёнок 01, 2 — ребёнок 12, а 4 и 5 оставляют поведение как есть.
- **Как сейчас** (разбор Дизайнера §1–2):

## Goals / Non-Goals

**Goals:** раскладка Г на всех четырёх размерах из D10. Ни одного нового пути потери ввода: «‹ ›» не
теряет набранного.

**Non-Goals:**
- индикатор и уход плашек с формы — 11 (здесь плашки только переезжают в прокрутку);
- автосохранение, режим «Изменить», явный режим НДС — 12;
- отмена вместо подтверждения — 13;
- бросок файла, окно повтора, «Приложить файл…» — 14 (здесь «Счёт из файла» только встаёт в сводку,
  поведение прежнее);
- рестайл общих компонентов — эпик MD3;
- телефон: узкая раскладка ([COST-6.2] «Узкий экран» до порога) — как сейчас.

## Decisions

### D-10.1. Части — экранная обёртка `InvoicePart` поверх `Card`

Части — компонент экрана `features/costs/InvoicePart.tsx`:
- шапка: номер шага, заголовок, строка-итог, действия справа, «Свернуть»/«Развернуть»;
- тело.

Каркас — `Card` (outlined) из `sharedui-md3-13`, если он слит к началу кода. Если нет — нынешняя
outlined-поверхность на ролях MD3 (`sharedui-md3-01`), и пункт «перевести `InvoicePart` на `Card`»
вписывается в перечень потребителей `sharedui-md3-13`. Общего компонента свёртки экран не заводит (D8
зонтика).

**Альтернатива** — `<details>`/`<summary>`. Отвергнута: строке-итогу нужны свои действия справа
(«Всё верно (5)», «Отметить оплату…»), а `summary` целиком — одна кнопка.

### D-10.2. Что значит «заполнена»

Решает чистая функция `partFilled(view, draft)` в `invoiceParts.ts` (unit-тест):

| Часть | Заполнена, когда |
|---|---|
| Кто и сколько | поставщик, плательщик, номер, дата, сумма к оплате заданы; нет меток «со скана, не проверено» и ошибок значения у полей части |
| Строки | строки есть, у каждой позиция; нет несохранённых |
| Разноска | разноска сходится (`allocation`) |
| Сроки и оплата | срок определён |
| Ещё, История | всегда свёрнуты при открытии |

Решение «свернуть или раскрыть» принимается при открытии счёта. Дальше части сворачивает только человек:
запись не схлопывает часть у него под руками. Состояние живёт, пока открыт этот счёт.

### D-10.3. Правило места — одна чистая функция по ширине рабочей области

```
placeOf(workWidth, fileWanted) → { list: boolean, file: 'beside' | 'over' | 'closed', fileWidth }
fileWidth  = clamp(round(workWidth × 0.38), 420, 520)
file       = !fileWanted ? 'closed' : (workWidth − fileWidth ≥ 720 ? 'beside' : 'over')
list       = file !== 'beside' && workWidth − 320 ≥ 940
```

- **Рабочая область** — ширина под рейлом (подпанель при открытом счёте скрыта, D-10.5). Её меряет
  `ResizeObserver` на контейнере страницы, а не `window.innerWidth`.
- **720 px рядом с файлом.** Число выведено из решения владельца 28.09.2026 («файл рядом — от 1280»)
  при новых размерах. Окно 1280 без подпанели даёт 1200 px рабочей области: файл 456, форма 744 —
  рядом. 1024 даёт 944: файл 420, форма 524 — поверх. Порог встаёт между ними, и проходит его то же окно
  1280, что и раньше. Формулировку «по окну» сменяет «по месту формы».
- **Файл открыт — списка нет**, как в макете (`!s.scan`). Решения «список ИЛИ файл» на 1366 владелец
  принял ответом 6.
- **Узкий экран** (`@container` сплита < 672 px, телефон) — как сейчас: список и форма по очереди.
- Таблица значений — unit-тест: 1366/1280/1024 × файл открыт/закрыт.

### D-10.4. «‹ N из M ›» — по отбору списка

- N и M считаются по тем же элементам, которые список показал бы при текущих отборе, поиске и чипе
  очереди: этот перечень страница уже держит.
- Подпись под числом — имя отбора («Разобрать», «Все»).
- Стрелки идут через ту же функцию смены счёта, что щелчок по строке списка (D-10.7). Щелчок по «N из M»
  закрывает счёт и показывает список (как «Назад» у `ListDetailShell`).
- Счёт, открытый адресом и скрытый отбором, показывает «— из M» и ведущий к списку `NotInRailNotice`.
  Прежнее поведение, только новое место.

### D-10.5. Подпанель — подавление, а не настройка

`AppShell` получает «временно скрыть подпанель» от страницы — хук `useSuppressSectionPanel(active)`
рядом с `SectionRail`. Предпочтение `RAIL_KEY` при этом не пишется: человек закрывает счёт, и подпанель
возвращается такой, какой была. Кнопка «Показать панель» (`ShowPanelButton`) открывает её поверх, не
меняя раскладки.

**Альтернатива** — `setRail('collapsed')` при открытии. Отвергнута: настройка человека переписывалась
бы экраном.

Это правка оболочки, поэтому каждый PR гоняет весь список e2e (`npm run -s test:e2e:ci`).

### D-10.6. Сводка — `InvoiceSummary.tsx`

Порядок слева направо, как в `mock/var-c.js`:
1. «‹ N из M ›»;
2. номер (`title-medium`) и пометки `StatusText` — из `sharedui-md3-12`, если слит, иначе нынешний
   `StatusBadge`;
3. вторая строка — поставщик · дата · сумма;
4. слот индикатора (пуст до 11);
5. носитель записи («Сохранить» или «Сохранено · 12:04», D-10.7);
6. справа — «Счёт из файла» (outlined), «Файл» (tonal, когда открыт), основное действие (filled), «⋮».

- **Высота** — 64 px. Подписи не переносятся, лишнее режется многоточием с полным текстом в `title`
  (правило #1394: нативный `title` — только полным текстом обрезанного).
- **На 1024** вторая строка (метаданные) прячется, когда не помещается: она дублирует первую часть.
  «Счёт из файла» уходит в «⋮», если не помещается и она.
- **«⋮» сводки:** «Заменить файл…», «Распознать», «Вернуть в черновик», «Отклонить…», «Удалить…»,
  «Исправить» — по тем же условиям, что сегодня у `InvoiceMoreMenu` и панели действий. Где списка нет —
  ещё группа справочников (D-10.8).
- **Режим исправления** (`CorrectionBar`) остаётся полосой — первой в прокрутке. Основное действие
  сводки в нём — «Проверить исправление…», «Выйти из исправления» — в «⋮».
- **«Разобран» неактивна** по `readiness.gaps` сервера и по несохранённому. Подсказка `Tooltip` называет
  первые пункты готовности тем же текстом, что `InvoiceReadinessLine`. Сама строка готовности до 11
  остаётся под таблицей, у сверки.

### D-10.7. Одна кнопка «Сохранить» и смена счёта

- **Очередь записи** — `useInvoiceSave` рядом с формой. Шаги — `PUT …/invoices/{id}` (если шапка
  грязная), затем `PUT …/lines` (если строки грязные). Второй шаг идёт с версией из ответа первого.
  Отказ первого шага второй не запускает.
  - Свой повтор при чужой части, как у `useDraftBase`, сохраняется.
  - Так закрывается порядок «шапка раньше строк» (#1657, вариант «строки после шапки»). Если
    `costs-invoice-lines-unsaved-supplier` слит раньше и выбрал другое, его правило встраивается в шаг
    строк и не дублируется.
- **Признак несохранённого один** — `unsaved = headerDirty || linesDirty`. Он идёт в кнопку, в
  `InvoicePayment` (вместо `dirty` шапки, Архитектор §7.3), в «Разобран» и в `useLeaveGuard`. Если
  `costs-invoice-lines-leave-guard` (#1653) уже слит, берётся его признак: своего второго не заводим.
- **Смена счёта** — одна функция `switchTo(id)` для строки списка, «‹ ›» и перехода очереди. При
  `unsaved` она показывает тот же `LeaveGuardDialog`, что уход по ссылке. Так дефект «щелчок по другому
  счёту теряет правки» (Дизайнер §4.3 п. 1) закрывается вопросом уже здесь. Ребёнок 12 заменит вопрос
  дописыванием.
- **Ничего не пишет само сверх сегодняшнего:** «Объект» той же стройки, «Всё верно», «По правилу»
  остаются немедленными.

### D-10.8. Действия страницы при открытом счёте

| Действие | Счёт не открыт | Счёт открыт, список виден | Счёт открыт, списка нет |
|---|---|---|---|
| «Счёт из файла» | шапка страницы | шапка списка (tonal) и сводка | сводка |
| «Новый счёт» | шапка страницы | «⋮» списка | «⋮» сводки |
| «Статьи вне строек», «Соответствия», «Условия поставщиков» | шапка страницы | «⋮» списка | «⋮» сводки |

При открытом счёте шапки страницы (`PageHeader`) нет. Заголовок «Счета на оплату» — в шапке списка.

### D-10.9. Сообщения до индикатора

До 11 плашки остаются, но уходят из неподвижной части:
- **над частями** — только однострочные плашки страницы: «Счёт удалён», «Счёт не перечитался», «Скрыт
  отбором»;
- **между «Кто и сколько» и «Строками»** — все остальные: сбой распознавания, двойники, удалённые записи,
  «изменили», замок, справочник не прочитан, причина «оплатить нельзя». Так требование «первый этап без
  прокрутки» держится при любом их числе. Неудобство временное, и 11 снимает его вместе с плашками;
- **«Замечания распознавания» и «не положенное»** ([COST-8]) — в конце части «Кто и сколько»;
- **`ScanTooNarrow`** исчезает: причину называет подсказка «Файл»;
- **сноска «Весь счёт на один объект…»** исчезает: объект теперь в «Разноске», где она и объясняла.

### D-10.10. Таблица строк

Колонки (по `mock/core.js`): №, позиция, наименование (подпись — артикул), кол-во, ед., цена, сумма,
разноска, удалить.
- Фиксированные колонки — 492 px, две текстовые делят остаток. В плотном виде (список слева) «Разноска» —
  96 px вместо 116.
- `min-w-[70rem]` уходит.
- Сумма НДС строки — не колонкой. В режиме «без НДС, НДС сверху» ставка строки нужна (пункт готовности
  `rate`), поэтому в этом режиме появляется узкая колонка «Ставка» (64 px), а «Разноска» сужается.
  Проверка — в обоих режимах (`invoice-vat-on-top-checks`).
- Сетка правки — нынешний `EditGrid`. Высоты строк 48 / поле 40 придут с `sharedui-md3-14`; тот же PR
  правит проверки высот в `invoice-layout-checks` (сказано в 14 MD3).

### D-10.11. Проверка раскладки — новый живой прогон

`e2e/invoice-screen-layout-checks.mjs` едет внутри `invoices-smoke` (тот у предела размера), как
`invoice-layout-checks`. Счёт СЧ-104 из посева доводится до «всех сообщений сразу»: сбой распознавания,
двойник, три метки, удалённые записи, шесть строк с расхождением. На 1366×768, 1280×720, 1366×650 и
1024×768, с открытой подпанелью у пользователя, прогон проверяет:
- высоту сводки ≤ 64;
- `scrollHeight > clientHeight` у области прокрутки;
- что колесом и Tab доходим до последней строки, сверки и «Разобран» (`boundingBox` внутри окна после
  прокрутки);
- пять полей первого этапа в окне на 1366×650;
- что таблица без прокрутки вбок, где обещано;
- список и файл по `placeOf`;
- подпанель скрыта при открытом счёте и вернулась после закрытия.

Прогон обязан краснеть на нынешнем master — это проверка проверки.

## Risks / Trade-offs

- [Плашки между первой частью и строками выглядят странно до 11] → временно, и только так держится
  «первый этап без прокрутки». В описании PR сказано, что их снимает 11.
- [Подавление подпанели ломает соседние экраны] → весь список e2e в каждом PR. Хук действует только пока
  смонтирован открытый счёт.
- [Старые e2e ищут «Сохранить строки», `ScanTooNarrow`, «Разобран» под таблицей] → правка тех же
  прогонов тем же PR. Перечень — поиском по `e2e/` в задаче 1.1.
- [Число 720 окажется неудобным на реальных ноутбуках] → одна константа в `placeOf`. Снимки на четырёх
  размерах — в PR, а меняется число `/opsx:update`.
- [Владелец выберет по Э1 «объект в первой части»] → меняется только порядок полей в `InvoicePart`
  «Кто и сколько» и требование «"Объект" — в части "Разноска"» через `/opsx:update` до кода.

## Migration Plan

Два PR, оба `version:minor`:
1. **Форма** — сводка, части, одна «Сохранить», «Разобран» в сводке, «Удалить» у книги, таблица, ТЗ
   [COST-6.2], новый прогон (без проверок места).
2. **Место** — `placeOf`, файл и список по месту, «‹ N из M ›», 1024, подпанель и справочники,
   [COST-6.3] в ТЗ, проверки места в прогоне.

Откат — revert PR. Сервер не меняется, данных нет.
