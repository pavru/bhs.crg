# Design: вкладки MD3 primary в `shared/ui/Tabs`

## Context

Мотив — proposal.md. Что есть сегодня (master `67f1e034`, 2.92.0):

- `src/client/src/shared/ui/Tabs.tsx` — `Tabs` и `TabPanel`; `variant: 'underline' | 'segmented'`. `underline` —
  это MD3 *secondary*: индикатор 2 px на всю ширину вкладки (`border-b-2`), ряд с разделителем, прокрутка вбок без
  полосы прокрутки, подписи в одну строку (#1384). `segmented` рисуется `segmentClass` и на телефоне
  (`useMedia(NARROW)`) становится `underline`. Клавиатура — `useRoving` с ручной активацией, `onChange` — просьба.
- Вызовов `Tabs` — семь (`CostViewsBand`, редактор документа, `LinkPickerModal`, `EstimateCard`, `ImportDialog`,
  `RateMatchesPage`, `PrimitiveTypesPage`, `TemplatesPage`); `segmented` — у пяти.
- Правило храповика `tabs` (`scripts/ui-ratchet-lib.mjs`) считает свои `role="tab"` / `tablist` / `tabpanel`
  мимо `Tabs`; его подсказка `instead` называет `underline` и `segmented`.
- Макет П11, вариант 1 (`https://claude.ai/artifact/XabqQ7TwPQagXTT2gcuzyw`, лист `A`), рисует переключатель
  «Редакции 3 | Приложения 3» **сегментами** (`.seg`); класс `.tab` в `mock.css` холста подписан «Tabs, primary»
  (48, `label-large`, индикатор 3 px с радиусом 3 px сверху, отступ 12 px от краёв вкладки), но на листе
  варианта 1 не использован. То есть облик primary-вкладок в этом ряду владелец ещё не видел: выбран вариант с
  сегментами, а замену на primary предложил Архитектор после выбора.
- Дизайн-система «BHS.CRG UI» заморожена на 2.74.0 (`docs/UI.md`, «Новый экран: порядок»).

## Goals / Non-Goals

**Goals:**
- Вид `primary` у `Tabs` по MD3 primary tabs: облик, раскладка, телефон — [UI-90].
- Правило вложенности primary над secondary — записано в `docs/UI.md` и спецификации ([UI-91]).
- Тесты вида: роли, клавиатура и Tab между двумя рядами, индикатор по содержимому, равная ширина на телефоне.

**Non-Goals:**
- Экран сметы: `EstimateCard`, `RevisionTabs`, `TabPanel` вокруг строк редакции, `?view=attachments` —
  `plan-11-conjuncture`.
- «Ещё N» внутри `Tabs` (ни у одного вида): переполнение второго ряда остаётся у потребителя.
- Переименование `underline` в `secondary`, перевод существующих вызовов, сторож вложенности в храповике.
- `/design-sync` — владелец, когда синхронизация в Claude заработает.

## Decisions

### D1. API — третье значение `variant`, `underline` не трогаем

`variant?: 'primary' | 'underline' | 'segmented'`; по умолчанию по-прежнему `underline`. `TabItem` не меняется:
`icon`, `badge`, `disabled`, `title` работают и у `primary`.

Отвергнуто: (а) переименовать `underline` → `secondary` ради имён MD3 — семь вызовов и снимки без изменения
поведения, и тот же PR смешал бы правку API с новым видом; в комментарии и `docs/UI.md` прямо сказано
«`underline` — MD3 secondary». (б) Отдельный компонент `PrimaryTabs` — повторил бы `useRoving`, `TabPanel` и
связку `id`, а разница — только классы и раскладка. (в) `level="primary" | "secondary"` вместо вида — три вида
одного переключателя уже живут в `variant`, вторая ось ничего не добавляет.

### D2. Облик — MD3 primary буквально

- Вкладка: высота 48 px, поля 16 px по горизонтали, `label-large` (14/20, 500), `state-layer`, кольцо фокуса
  внутрь (`focus-ring-inset`, как у `underline`: прокручиваемый ряд срезал бы наружное).
- Выбранная: подпись и значок `text-primary`; индикатор — отдельный элемент внутри содержимого вкладки
  (абсолютно, снизу), высота 3 px, верхние углы `rounded-t-xs` (см. ниже), ширина = ширине
  содержимого (значок + подпись + счётчик), не меньше 24 px. Рамка вкладки (`border-b-2`) у `primary` не
  используется — она даёт ширину во всю вкладку, это вид secondary.
- Остальные: `text-on-surface-variant`, без индикатора.
- Со значком (`icon`): значок 24 над подписью, высота вкладки 64 px; без значка — 48. Высота ряда — по наличию
  значка у любой вкладки; вкладка без значка в таком ряду держит пустое место 24 под него, чтобы подписи ряда
  стояли на одной высоте (ревью PR #1840).
- Ряд: разделитель снизу `border-b border-outline-variant`, прокрутка вбок без полосы — как у `underline`.
- Счётчик («Приложения 3») — `badge` вкладки, туда кладётся `CountText` ([UI-45]); у выбранной цвет счётчика
  остаётся его собственным (`on-surface-variant`). Между подписью и счётчиком — пробельный текст: в строке flex
  он не рисуется, а имя вкладки для диктора выходит «Приложения 3», а не «Приложения3». Касается всех видов
  (ревью PR #1840).
- `aria-controls` — только у выбранной вкладки: `TabPanel` рисуется для текущего значения, и ссылка у остальных
  вела бы на несуществующий элемент. Касается всех видов (ревью PR #1840).

Радиус индикатора у MD3 — 3 dp, а в шкале формы проекта такой ступени нет (`--radius-*` сброшены,
`src/theme/md3-tailwind.css`; свой радиус в скобках отказывает `theme-classes.test.mjs` и `legacy-radius`).
Индикатор берёт `rounded-t-xs` — extra-small, 4 px, ближайшая ступень; на полосе высотой 3 px разница не видна.
Нового исключения в храповике нет.

Отвергнуто: индикатор шириной во всю вкладку (как в `mock.css` холста: отступ 12 px от краёв при полях 16) —
по MD3 у primary индикатор по содержимому; разница с макетом — 4 px с каждой стороны, называется в PR.

### D3. Раскладка — по содержимому на рабочем столе, поровну на телефоне

- От `md` и шире: вкладки по ширине содержимого, от начала ряда (MD3 scrollable/left-aligned). Карточка сметы —
  824 px, вкладок две: растянутые на 412 px каждая читались бы как сегменты.
- Ниже `md` (`useMedia(NARROW)`, тот же порог, что у `segmented`): вкладки делят ряд поровну (MD3 fixed tabs) и
  не сжимаются меньше содержимого — если поровну не влезает, ряд прокручивается.
- Индикатор и на телефоне — по содержимому, а не по половине ряда.

Отвергнуто: «поровну» везде (на рабочем столе две короткие вкладки на всю карточку); «по содержимому» везде (на
телефоне MD3 советует fixed, а большие цели касания лучше для пальца).

### D4. Без «ещё N»

Верхний уровень — 2–4 раздела; не влезает — прокрутка, как у `underline` (#1384). Меню переполнения
`RevisionTabs` (чип «ещё N» рядом с рядом редакций) остаётся во втором ряду у потребителя. Перенос «ещё N» в
`Tabs` — отдельная задача для всех видов, если понадобится (сегодня он нужен одному экрану).

### D5. Вложенность primary над secondary

- Порядок: ряд `primary` → его `TabPanel` → внутри ряд `underline` → его `TabPanel`. У рядов разные `id`
  (`useId()` или префикс от сущности).
- Между рядами нет зазора: разделитель первого ряда — верхняя граница второго (MD3: secondary стоит в
  содержимом под primary). Отступ содержимого — внутри панели второго ряда.
- Ряд `primary` внутри `underline` (и внутри `segmented`) — запрещён в `docs/UI.md` и [UI-91]; сторожа храповика
  нет (вложенность через компоненты не видна разбору текста одного файла) — ловит ревью.
- Tab: каждый `tablist` — одна остановка (выбранная вкладка), поэтому Tab идёт «выбранная primary → выбранная
  underline → содержимое» без нового кода; проверяется тестом.

### D6. Документы, храповик, дизайн-система

- `docs/UI.md`, «Язык формы», строка «Вкладки»: три вида и когда какой, правило вложенности; оговорка о
  дизайн-системе — компонент новее 2.74.0.
- `ui-ratchet-lib.mjs`: текст `instead` правила `tabs` называет `primary`; уровни и счёт не меняются.
- `.d.ts` и витрина дизайн-системы — генерирует `/design-sync`, руками не правятся; синхронизация — владелец.
  В этом change — только упоминание в PR, что дизайн-система отстаёт на этот вид.

### D7. Макеты — вопрос владельцу (В1)

`docs/UI.md`, «Новый экран: порядок»: новый вариант компонента идёт через три макета и выбор владельца; «макеты не
нужны» — только когда правка сводится к пункту готовых правил и не меняет, что видит пользователь. Primary tabs —
новый облик, которого в проекте нет, поэтому под исключение буквально **не подпадает**. Довод за исключение: место
и смысл ряда выбраны в П11 (вариант 1), а облик primary tabs полностью задан спецификацией MD3 — варианты макета
различались бы только раскладкой (D3) и шириной индикатора (D2). Исполнитель сам не решает — вопрос В1 ниже;
от ответа зависит раздел 0 `tasks.md` (0.3).

### D8. Зонтик

`sharedui-md3-00-epic` не закрыт (4.3 открыта, ждёт экран счёта) и уже принимал поздних детей (4.1a md3-19,
4.1b md3-21). Этот change — шаг 4.1c; условие 4.3 дополняется его архивом. Зонтик закроется не раньше
`plan-11`-зависимого архива этого change — это задержка на дни, а не на этап.

## Вопросы владельцу до кода

- **В1. Макеты.** (а) Без раунда: облик — MD3 primary буквально (D2–D5), к PR — снимки ряда «Редакции |
  Приложения 3» на 1366 и 375 px в обеих темах (на витрине теста, не на экране сметы); (б) раунд из трёх
  макетов в Claude (Design) на «BHS.CRG UI»: например А «MD3 буквально» (D2–D3), Б «поровну везде», В «по
  содержимому везде, индикатор во всю вкладку как в `mock.css`».
- **В2. API** — `variant="primary"`, `underline` остаётся именем secondary (D1).
- **В3. Раскладка** — по содержимому на рабочем столе, поровну на телефоне (D3).
- **В4. «Ещё N»** — у `primary` нет, переполнение второго ряда — у потребителя (D4).
- **В5. Вложенность** — primary только над underline, без зазора между рядами (D5).
- **В6. Зонтик** — шаг 4.1c `sharedui-md3-00-epic` (D8).

## Risks / Trade-offs

- [Ширина индикатора считается по содержимому, а у вкладки поля 16 px] → индикатор — элемент внутри обёртки
  содержимого (`relative inline-flex`), а не рамка кнопки; тест сверяет, что он внутри содержимого, а не у кнопки.
- [Равная ширина на телефоне при длинной подписи сжала бы соседку] → `flex-1` с `min-w-max`: не уже содержимого,
  иначе — прокрутка; сценарий «Ряд не влезает».
- [jsdom не считает раскладку] → тесты проверяют классы и структуру (ширина индикатора — по месту элемента,
  поровну — по классу при `matchMedia` узкого экрана, `shared/testing/matchMedia.ts`); облик — снимками к PR.
- [Дизайн-система не знает `primary`] → макеты `plan-11` опираются на код и `.d.ts` (оговорка `docs/UI.md`);
  `/design-sync` — владелец.
- [Радиус 3 dp вне шкалы] → `rounded-t-xs` (4 px), без исключения в храповике (D2).

## Migration Plan

Один PR: `Tabs.tsx`, тесты, `ui-ratchet-lib.mjs` (подсказка), `docs/UI.md`, задачи зонтика. Существующие вызовы не
меняются, поведение `underline` и `segmented` — тоже. Откат — revert PR (потребителей `primary` до `plan-11` нет).
Архив change — отдельным PR после слияния, по слову владельца.
