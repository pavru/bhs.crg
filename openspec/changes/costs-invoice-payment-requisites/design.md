# Design

## Context

Мотивация — в [proposal.md](proposal.md), контракт — в [дельте costs](specs/costs/spec.md). План подготовлен от `master` `abf2defe`, версия 2.134.15.

С владельцем согласованы четыре условия оплаты: поставщик, номер, дата и сумма к оплате; плательщик исключён. Оплата до разбора строк остаётся. Архивный поставщик допустим, удалённый блокирует. Новые попытки оплаты проверяются и для старых счетов, а ранее записанные оплаты сохраняются.

Сейчас `InvoiceReadiness.Required` берёт пять обязательных полей из `CostsRecordTypes.Invoice`; `InvoiceRequisites.MissingFields` использует тот же перечень для «Разобран». Оплата пользуется отдельным `PaymentRefusal`: отклонение, блокирующие дубли, отсутствие суммы и расхождение. `InvoiceDesk.PaymentAsync` формирует факты карточки, `PaymentEndpoints.PostingAsync` обслуживает предпросмотр, запись и чтение записанного расклада. Проверки реквизитов в оплате пока нет.

Состояния ссылок уже читаются пакетно через `IModuleReferenceTargets`: `Present`, `Archived`, `Lost`. `ModuleReferenceTargetsPort` различает архив и отсутствие одним запросом. При чтении `InvoiceSnapshots` имеет эти состояния, поэтому дополнительный запрос на каждый счёт не нужен. Создание/смена стороны уже проверяют допустимость ссылки организацией; этот change не меняет механизм выбора типов справочника.

## Goals / Non-Goals

**Goals:**

- Одно правило готовности реквизитов для чтения, предпросмотра и записи, самостоятельное относительно полного разбора.
- Полный список проблем с ключами полей, включая старый `Parsed`, и повторная проверка при записи.
- Совместимость истории оплат, исправлений и существующего запрета дублей.

**Non-Goals:**

- Требование `Parsed`, строк, номенклатуры, плательщика, скана или подтверждения каждой метки распознавания перед оплатой.
- Положительность суммы вместо ненулевого значения; новые ограничения даты счёта относительно даты платежа; нормализация номеров и иной алгоритм дублей.
- Изменение схемы данных, новые адреса API, права, настройки экземпляра или модули этапов 3–4.

## Decisions

### D1. Отдельное чистое правило реквизитов оплаты [COST-4] [COST-9]

Добавить небольшое правило в модуль `costs` (например, `InvoicePaymentRequisites`), получающее сохранённый счёт и уже установленное состояние поставщика. Оно возвращает упорядоченный список препятствий. Ключи и названия берутся из существующих ключей реквизитов и объявления модуля, а не из словаря клиента.

| Поле | Условие | Причина препятствия |
|---|---|---|
| `Поставщик` | идентификатор не пуст, состояние `Present` или `Archived` | `missing` при отсутствии выбора, `lost` при удалённой записи |
| `Номер` | не пустой и не состоит только из пробелов | `missing` |
| `Дата` | есть корректная сохранённая дата | `missing` при отсутствии |
| `Итого` | не `null` и не ноль | `missing` по текущему `InvoiceRequisites.NoTotal` |

Порядок списка: поставщик, номер, дата, сумма. Проверка пробелов не переписывает номер в базе и не меняет сопоставление дублей. Некорректный формат даты уже отказывает при записи реквизитов; дополнительных календарных ограничений не вводится. Отрицательные суммы предусмотрены существующими тестами корректировок и допустимы.

Не использовать все `InvoiceRequisites.MissingFields` как запрет оплаты: он потребовал бы плательщика и связал две разные готовности. Дополнительные поля пользовательского типа также не становятся условиями оплаты автоматически. Новый перечень не меняет требования к «Разобран» и существующие звёздочки обязательности полей для разбора.

### D2. Один результат и существующие порты на трёх входах [COST-4] [COST-6.4]

- **Чтение карточки.** Из `InvoiceSnapshot.Records` получить состояние поставщика и тем же чистым правилом построить препятствия для `InvoiceDesk.PaymentAsync`. Передать этот результат и в расчёт `blocks` готовности. Использовать общий снимок, сохранив пакетный характер чтения списка.
- **Предпросмотр.** `PaymentEndpoints` читает состояние сохранённого поставщика через существующий порт и получает тот же список. Пустой идентификатор не требует запроса к ядру. Ошибку порта не заменять пустым списком или разрешением оплаты.
- **Запись.** Повторить проверку реквизитов и актуального состояния поставщика внутри callback `InvoiceDesk.WriteAsync` после текущей проверки `If-Match`/захвата строки и до `invoice.Pay`. Не переиспользовать результат запроса предпросмотра или снятое до ожидания блокировки состояние поставщика.

Сохранить текущую блокировку оплаты против изменений дублей (`InvoiceDuplicateWrite.Payment`), проверку `stamp` расклада, границы периодов и права. Новый отказ не должен менять оплату, учётные даты, книгу проводок и журнал. При актуальной версии отказ реквизитов даёт 400; устаревший `If-Match` продолжает давать 409 до проверки содержимого. Предпросмотр возвращает 200 с отказом, списком и пустыми `rows`/`stamp`.

Проверка поставщика покрывает удаление до повторного чтения при записи. Общей транзакции схемы ядра и модуля и новой распределённой блокировки не вводится: не заявляется гарантия против удаления прямым SQL уже после этой проверки. Штатное удаление занятой записи по-прежнему защищено текущими правилами ядра.

### D3. Контракт препятствий и приоритеты [COST-6.4]

Расширить `PaymentView` и `PaymentPostingView` полем `requisiteGaps`: массив `{ field, kind, label }`, где `field` — существующий ключ реквизита, `kind` — `missing`/`lost`, `label` — подпись проблемы словами сервера. У допустимой будущей оплаты и у уже оплаченного счёта массив пуст. Клиент не восстанавливает обязательный перечень по пяти полям `readiness.required` и не разбирает текст отказа.

`PaymentRefusal` остаётся единственным местом определения основного рода отказа:

1. `rejected`;
2. `duplicate`;
3. `requisites`, если проблема есть у поставщика, номера или даты;
4. прежние `amount` и `discrepancy`.

Если отсутствует только сумма, остаётся `amount`. Если нет номера и суммы, основной род — `requisites`, но список содержит оба поля. При дубле информация о реквизитах остаётся доступна; разрешение дубля не снимает требование реквизитов. `moneyRefusal`/`moneyRefusalKind` сохраняют нынешний смысл денежной причины под запретом дубля, не переименовываются и не превращаются в самостоятельную вторую проверку реквизитов.

Оба ответа используют одинаковые `requisiteGaps` и текст сводного отказа. Для совместимости клиентских фикстур отсутствие нового массива принимается как `[]`, но актуальный сервер всегда отдаёт его. Поля DTO добавляются, существующие имена и значения сохраняются. Обновить типы и комментарии контракта в C# и TypeScript.

`InvoiceReadiness` помечает `payment` только у тех `field`/`reference`-пунктов, которые совпали с отдельным списком реквизитов оплаты; плательщик остаётся только `parsed`. Расхождение продолжает получать свою пометку. Список оплаты доступен независимо от `readiness.gaps`, который у `Parsed` может быть `null`. UI объединяет совпадающие пункты по полю/причине и не добавляет поверх них общий дубликат текста отказа.

### D4. UI через текущие компоненты с выбором владельца [COST-6.2] [COST-6.4]

Бизнес-правило согласовано, визуальный вариант нового ограничения ещё не выбран. Перед изменением представления подготовить три варианта в живом каталоге на реальных компонентах: отдельные пункты готовности, сгруппированное препятствие с полным перечнем полей и размещение полного перечня рядом с первой частью. Все варианты показывают все проблемы, переходы к полям и различие между оплатой и разбором. Рекомендация — первый вариант как продолжение существующего индикатора.

Макеты сохранить в `src/client/design-system/`, показать владельцу и записать выбранный вариант и ссылки в этот раздел до UI-кода. Варианты отличаются компоновкой, не только цветом. Согласование данного плана не является выбором макета. Разбор интерфейса и архитектуры здесь: новый серверный факт расширяет уже существующие пункты готовности, не требует нового глобального компонента, а основной риск — дублирование причин и ошибочное требование плательщика.

Два входа в оплату и текущее окно оплаты остаются. Для `requisites` использовать текущую модель блокировки из-за исправляемых реквизитов: действие неактивно с причиной сервера; после сохранения и перечитывания становится доступно, если других запретов нет. Для `duplicate` сохраняется существующее скрытие входов. `payHold`, `primaryOf` и индикатор используют серверные факты и не получают второй перечень обязательных полей.

Обрабатывать 400 реквизитов и 409 устаревших данных из уже открытого окна: оплата не записана, карточка/предпросмотр обновляются и показывают актуальные препятствия. Отсутствие прав правки не превращает запрет в разрешение: объяснение видно, изменение поля доступно по существующим правам.

### D5. История не проверяется как будущая оплата [COST-4]

Новую проверку вызывать только для возможности внести новую оплату. Не помещать её в общий guard любой записи счёта: иначе нельзя будет заполнить реквизиты, отменить старую оплату или выполнить разрешённое исправление.

Ветка `Paid` в `InvoiceDesk.PaymentAsync` возвращает историю без нового отказа и с пустыми `requisiteGaps`. `GET …/paid`, использующий общий расчёт расклада, не должен применять новый guard будущей оплаты к записанной оплате. Отмена оплаты и правка платёжного документа сохраняют свои права, причины и протоколы; после отмены счёт `Unpaid` получает актуальный список проблем, а повторная оплата проходит все новые проверки.

Нет миграции или массового изменения строк: старый `Unpaid` проверяется наравне с новым, старый `Paid` сохраняет факт и учётные даты. У старого `Parsed` не менять статус автоматически при чтении; обычные правила возврата в черновик при правке остаются.

### D6. Проверки и документация [COST-4] [COST-6.4] [COST-9]

- Чистое правило: все четыре поля по отдельности и одновременно; пробельный номер, `null`/ноль/отрицательная сумма; поставщик `Present`/`Archived`/`Lost`; отсутствие плательщика, строк и метки распознавания не дают нового запрета.
- Integration: одинаковый список в карточке/preview, прямой POST в обход UI, старый `Parsed` без реквизита, удаление поставщика после preview при прежней версии счёта, очистка номера с отказом по `If-Match`, архивирование после preview без нового запрета, ошибка проверки ядра без записи оплаты.
- Совместимость: приоритет дубля и отклонения, сохранение денежного отказа, номенклатура не нужна оплате, старый `Paid` читается/отменяется и разрешённо правится, повторная оплата без реквизитов отказывает. Суммы, даты периодов, книга и журнал до/после отказа неизменны.
- Клиент: объединение пунктов без повторов, плательщик только `parsed`, отсутствие `readiness.gaps`, права, оба входа в оплату, обновление после 400/409. Живой `invoice-payment` smoke проверяет видимый список и переходы, затем разрешение после сохранения четырёх полей при пустом плательщике и неразобранных строках.
- Существующим тестам/посеву, где проверяется другая причина оплаты, дать четыре допустимых реквизита. Не менять общий смысл неполного черновика ради массового озеленения тестов; намеренно неполные фикстуры должны продолжать проверять новый отказ.
- Обновить REST-листинг и пояснения в `docs/DEV_NOTES.md`, руководство пользователя и `docs/tz/55-счета-и-накладные.md`. При изменении заголовков пользовательского руководства перестроить содержание штатным инструментом.

## Risks / Trade-offs

- Прежде допустимые неполные счета после обновления не оплачиваются → полный список проблем, переходы к полям, сохранение черновиков и истории, явное описание изменения.
- Пять полей готовности к разбору ошибочно становятся условиями оплаты → отдельное правило из четырёх полей и положительные тесты без плательщика/строк.
- Новый guard случайно блокирует историю, отмену и исправление → отдельные тесты старого `Paid`, не размещать проверку в общей связке записи.
- Дополнительный запрос на каждый счёт замедляет список → переиспользовать пакетные состояния `InvoiceSnapshots`, отдельный запрос нужен лишь операции оплаты/preview.
- Список реквизитов и главный отказ расходятся → общий результат правила для трёх входов и тест смешанных причин, включая дубли.
- Параллельно меняется геометрия секций по `sharedui-section-field-spacing` → пользоваться текущими компонентами, не копировать их разметку и отступы; перед обновлением ветки учитывать коммит повышения версии соответствующего слияния.

## Migration Plan

Миграции данных нет. Поставляется обычным обновлением сервера и клиента с добавленным полем ответа и новым родом отказа. Выпуск документирует, что для новых попыток оплаты старых неоплаченных счетов теперь нужны четыре реквизита. Версия в PR не меняется вручную. Откат возвращает сервер/клиент к прежнему поведению без отмены уже записанных операций.
