# Design: печать записи модуля шаблоном Typst и форма КП

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D4, D13).
Здесь только решения этого change.

## Context

Сверено по коду master `6b81e51e`.

- Генерация знает только экземпляр документа: `GenerateDocumentCommand(InstanceId, …)`
  (`Application/Generation/GenerateDocumentCommand.cs:7`), обработчик ищет шаблоны по
  `DocumentTypeId == instance.CompositeTypeId` (`GenerateDocumentHandler.cs:51`).
- Сам генератор от экземпляра не зависит: `IDocumentGenerator.GenerateAsync(GenerationRequest)` принимает
  содержимое шаблона, контекст, блоки типов, библиотеку и ассеты (`Application/Generation/IDocumentGenerator.cs:6-21`);
  реализация — `Infrastructure/Generation/TypstGenerator.cs:21`.
- Шаблон привязан к типу (`Domain/Templates/Template.cs:7`), а тип записи модуля ядро уже проецирует в
  схему типа при старте (`BHS.CRG.Modules/ModuleRecordType.cs:143`) — значит шаблон к типу КП
  привязывается без новой сущности.
- В `IAppModule` членов печати нет (`BHS.CRG.Modules/IAppModule.cs`: права, адреса, типы, таблицы,
  настройки…). Счёт `costs` не печатается (M4, `Modules.Costs/CostsRecordTypes.cs:132-141`).
- Шаблоны, ассеты и библиотека закрыты правами `id`: `/api/templates` —
  `id.document.read` / `id.config.edit` (`Api/Endpoints/Templates/TemplateEndpoints.cs:22-23`),
  `/api/template-assets` и `/api/typst-userlib` — `id.config.edit` (`TemplateAssetEndpoints.cs:34`,
  `TypstUserLibEndpoints.cs:13`).

## Goals / Non-Goals

**Goals:** любой модуль объявляет печатную форму своей записи; печать идёт общим генератором; закрытое
правами не попадает в контекст; печать КП работает на установке без `id`.

**Non-Goals:**
- печать счёта и накладной (M4 в силе);
- печать отчёта монтажника (`TYPE-7`, вопрос раунда Р4 этапа 4);
- метаданные генерации и «Сделать источником» для печати записей — печать записи не создаёт
  `GeneratedFile` комплекта, она отдаёт PDF (повторная печать — снова);
- печать графика — `plan-20` (ждёт решения В-10).

## Decisions

- **Контракт печатной формы** (`BHS.CRG.Modules/Printing/`):
  - `ModulePrintForm(TypeCode, Title, ReadPermission)` в новом члене `IAppModule.PrintForms`
    (умолчание — пусто);
  - `IModulePrintContext` — служба модуля: `BuildAsync(recordId, IModuleUser, ct)` → JSON контекста или
    «нет записи» / «нет права»; регистрирует её модуль в `RegisterServices` с ключом `TypeCode`.
- **Проверка при старте.** У каждой формы — тип из `RecordTypes` того же модуля и ровно одна реализация
  контекста; иначе отказ с названием формы. Сторож — `ModulePrintFormCatalogTests` на пробном модуле.
- **Адреса ядра** `Api/Endpoints/Generation/RecordPrintEndpoints.cs`:
  - `POST /api/print/{typeCode}/{recordId}?templateId=` → PDF; `POST /api/print/{typeCode}/{recordId}/preview`;
  - ворота: модуль-владелец типа включён (иначе 501 выключенного модуля) и `ReadPermission` формы;
  - запись не пишется — адрес `WritesNothing`, `If-Match` не нужен (названное исключение).
  - Шаблон — выбранный, иначе по умолчанию, иначе первый активный, как у документов; шаблона нет — 409 с
    причиной «у типа нет шаблона печати», а не пустой PDF.
- **Генерация.** Команда `PrintRecordCommand` собирает `GenerationRequest` тем же кодом, что документы:
  блоки типов, библиотека, ассеты шаблона. Общая часть выносится из `GenerateDocumentHandler`, чтобы
  блоки и библиотека не собирались двумя разными путями (FileSizeRatchet держит обработчик в пределах).
- **Право на шаблоны типов модулей** — новое право ядра `core.print.edit` («шаблоны печатных форм записей
  модулей и библиотека Typst»), по умолчанию — «Администратор» (`AllPermissions`). Ворота `/api/templates`
  для шаблона типа модуля — `core.print.edit`, для типа `id` — прежние `id.config.edit`. Библиотеку и
  ассеты открывает любое из двух прав («любое из» — механизм `plan-02`). **Предложено, ждёт решения
  В-13** (в зонтике его нет — вопрос добавляется к списку владельцу). Альтернатива — своё право у каждой
  печатной формы — дала бы три разных права на одну библиотеку.
- **Форма КП (PR 2).** `Modules.Plan/Printing/OfferPrintContext.cs`: шапка, стройка, заказчик
  (организация), строки с ценой продажи и итогом, НДС по режиму КП (ждёт решения В-9), номер и дата
  версии, условия по схеме `КоммерческоеПредложение`. **Себестоимость и наценка в контекст не входят
  никогда** — даже у держателя `plan.estimate.cost`: печать уходит заказчику. Право формы —
  `plan.offer.read`. Шаблон по умолчанию заводит `PlanModule.InitializeAsync`, если у типа шаблона нет.
- **Сторож.**
  - PR 1: пробный модуль с формой без контекста — отказ старта; печать без права — 403; модуль-владелец
    выключен — 501; поле, закрытое правами, в `data.json` отсутствует (тест читает отладочный контекст).
  - PR 2: `PlanOnlyHostTests` печатает КП без `id` и без настоящего Typst — генератор подменён, проверяется
    контекст; `OfferPrintTests`: в контексте нет ни `cost`, ни `markup`.
- **Чем ломается.** Контекст печати собирает ядро из таблицы модуля — ядро знает модуль, тест границ
  краснеет; контекст отдаёт все поля записи — себестоимость уходит заказчику на бумаге.

## Risks / Trade-offs

- [В-13 решится «шаблоны — под правом модуля»] → меняются только ворота `/api/templates` и состав
  «Администратора»; контракт печатной формы не меняется.
- [Отладка шаблона записи] → тот же отладочный архив, что у документов: `GET /api/print/{typeCode}/{recordId}/debug-bundle`
  под `core.print.edit`.
- [Шаблон под конкретную форму КП заказчика не совпадёт с шаблоном по умолчанию] → шаблон по умолчанию —
  образец, а не обещание; заказчик правит его в редакторе (`PLAN-14`).
