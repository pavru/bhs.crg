# Design: роли модуля в посеве, живой прогон и проверка нарушением

Общая архитектура — `../work-00-epic/design.md`. Здесь только решения этого change.

## Context

Образцы этапа 2:
- **Место хранения.** `BHS.CRG.Tests/Configuration/ModuleMoneyStorageTests.cs` (H1, issue #1104):
  закрытость сумм следует из места хранения, а не из полноты перечня путей. Тест прямо называет, чего
  сторожа не видят.
- **Обход путей.** Проверка `outsider-finds-no-invoice-by-any-stage-path` в
  `src/client/e2e/routing-smoke.mjs:408`: каждый путь отвечает отказом, а не пустым списком.
- **Прогон под ролью.** `src/client/e2e/limited-smoke.mjs`: список экранов роли записан руками, главная
  проверка — «ни одного 403 за проход».
- **Посев.** `src/client/e2e/seed.mjs` и `seed-invoices.mjs`: роли через `ensureUser`, строки `SMOKE_*`.

Чего у `costs` не было: изоляции **внутри** модуля. Там граница — «есть модуль или нет». Здесь
монтажник А и монтажник Б оба в модуле, и разделяет их только параметр доступа (D4). Поэтому
поверхностного «отказ, а не пусто» мало: у А путь открыт, и ответ обязан быть полным для его отчётов
и пустым для чужих.

## Goals / Non-Goals

**Goals:** сиденья посева; живой прогон под ролями; проверка нарушением по месту хранения со сплошным
обходом и положительным контролем; первый красный прогон.

**Non-Goals:**
- новые адреса и правки приложения — change только проверяет построенное;
- путь `/api/field` и устройства — этап 5;
- набор «Выполненные работы» без изоляции — этап 6.

## Decisions

- **Состав PR (один).** Тест сервера, посев, прогон, вписка в `test:e2e:ci`, `Modules__Enabled` в
  `ci.yml`, раздел в `e2e/README.md`. Кода приложения PR не меняет. Найденная утечка чинится отдельным
  PR в change, который её допустил, и только после этого слияние.
- **Проверка нарушением — три слоя в `Integration/WorkIsolationViolationTests.cs`.**
  - *Место хранения.*
    - Перепись: `WorkDbContext.Model.GetEntityTypes()` — каждая сущность либо заполняется меткой,
      либо стоит в списке «не несёт отчёта» с причиной (назначения, настройки).
    - После посева метки — поиск её по всем текстовым и `jsonb` колонкам базы вне схемы `work`, по
      метаданным вложений и по тексту уведомлений и журнала действий. Найдена — красный с названием
      таблицы и колонки.
  - *Сплошной обход.*
    - Адреса `GET` группы `/api/work` берутся из `EndpointDataSource` живого хоста, как в
      `EndpointGateInventoryTests.cs:28`; параметры пути подставляются из идентификаторов отчёта Б.
      Неизвестный параметр — красный с адресом, а не пропуск.
    - К ним — таблицы (`/api/tables/{address}`, `/query` с поиском, `/export`, `/dataset`), системные
      наборы и источник на них, MCP (`DataSnapshotTools`: `list_datasets`, `get_dataset`, `get_source`,
      `get_rows`), фото (`work-17`), `/api/notifications`, `/api/activity`.
    - Обход идёт под А и под менеджером без назначений.
  - *Положительный контроль.*
    - Второй хост подменяет разрешение параметра доступа (D4) на «все». Тот же обход обязан найти метку
      на каждом пути, иначе путь назван немым.
    - Под руководителем — на каждом пути, открытом его правам.
    - Без контроля проверка «не нашёл» проходила бы и на пустом ответе: так у этапа 2 не ловили
      поломку три первые редакции маршрутного прогона (`e2e/README.md`, раздел маршрутного smoke).
- **«Сначала упасть».** Первый коммит PR — тест плюс временная подмена доступа в основном хосте. Прогон CI
  красный, ссылка на него — в описании PR. Второй коммит подмену убирает. Положительный контроль держит
  то же свойство постоянно: падение проверено не один раз при слиянии, а в каждом прогоне.
- **Фото.** Обход проверяет только «404 и метки нет». Условие безопасности — локальный отчёт аудита,
  раздел 2.
- **Посев — `e2e/seed-work.mjs`**, вызов из `seed.mjs` рядом с `seedInvoices` (`seed.mjs:805`).
  - Отдельный файл потому, что `seed.mjs` стоит в `src/file-size-baseline.json:4` с числом 568 и расти
    не может.
  - Учётные записи — через `ensureUser` с ролями `Installer`, `ProjectManager`, `Executive`, `User`
    (`Api/Auth/SystemRoles.cs:62,66,89,51`).
  - Связь с сотрудником — адресом `work-01`, назначения — `work-11`.
  - Отчёты заводит сам их автор, своим входом: заведённый администратором «за сотрудника» отчёт
    проверял бы другой путь (`WORK-31`).
  - Пояс стройки — `Construction.SetTimeZone` (`Domain/Documents/Construction.cs:51`) адресом стройки,
    например `Asia/Novosibirsk` против пояса компании `Europe/Moscow`.
- **Живой прогон `e2e/work-smoke.mjs`.**
  - Обвязка `harness.mjs`; список экранов каждой роли записан руками, как в `limited-smoke.mjs`: выведенный
    из `/api/account/access`, он подстроился бы под потерю права.
  - Проверки: монтажник А, монтажник без связи, менеджер без назначений, руководитель без кнопок,
    инженер ИД без раздела.
  - Последняя проверка — ни одного 403 на видимое действие за весь проход.
  - Если `work-27` ещё не слит и `work.facts.read` не объявлено, сиденье инженера ИД проверяет то же
    самое: строка состава роли просто не находит объявления (`SystemRoles.cs:57-59`).
- **CI.** В `.github/workflows/ci.yml:550` и `:602` `Modules__Enabled: id,costs` становится
  `id,costs,work`. Имена работ — договор с правилом слияния (CLAUDE.md, раздел CI), их не трогаем.
  Правка затрагивает все живые прогоны, поэтому идёт весь их список.
- **Сторож.** `suites.test.mjs` — прогон `work` вписан в `test:e2e:ci`. Перепись сущностей и немого
  пути — в самом тесте.
- **Чем ломается.**
  - Проверка по перечню путей: новый путь идёт мимо неё молча.
  - Утверждение «метки нет» без положительного контроля проходит на пустом ответе.
- **Зависит от:** `work-07` (параметр доступа и его подмена в хосте), `work-11`, `work-13`, `work-16`,
  `work-17`, `work-20` (пути), `work-21`–`work-23` (экраны прогона), `work-01` (связь).

## Risks / Trade-offs

- [Поиск метки по всей базе медленный] → метка — одна строка; поиск идёт по колонкам текстовых типов
  из `information_schema` одним запросом на таблицу, на своей тестовой базе.
- [Подставить параметры пути удаётся не всем адресам] → такой адрес красный с названием. Таблица
  подстановок растёт осознанно, а не пропуском.
- [Прогон под семью сиденьями удлиняет работу живых прогонов] → входы идут одним браузером со
  сменой контекста, как в `routing-smoke.mjs` с `userPage`.
