# Design: периодический такт модульных заданий

Общая архитектура — `../work-00-epic/design.md` (D12). Здесь только решения этого change.

## Context

Сверено по коду master `f8a8b222`.

- `Infrastructure/Backup/BackupScheduleService.cs` — образец: `PeriodicTimer` раз в минуту, пауза на
  старте, `TimeProvider`, правило «прошёл ли срок и не ставили ли после него», работу делает задачей
  той же очереди, что и кнопка.
- `Api/Modules/Ports/ModuleJobsPort.cs` — постановка задачи модуля: `ModuleWork.EnsureHandled` отказывает
  сразу, если обработчика нет; владелец вне запроса — `Guid.Empty`, отказ — общесистемным
  уведомлением. Дубль по цели ловит частичный уникальный индекс «одна активная задача на цель»
  (issue #900, сырым SQL — `Persistence/Configurations/JobConfiguration.cs:22`).
- Автор журнала вне запроса — `ActivityActor.System` («Система», `Application/Activity/IActivityActor.cs:10`),
  без указания, чем система занята.
- `IAppModule` (`BHS.CRG.Modules/IAppModule.cs`) — объявления модулем (таблицы, настройки, файлы); такта
  среди них нет.

## Goals / Non-Goals

**Goals:** модуль объявляет такт, ядро ставит одну задачу на цель; догон — запросом модуля; задача
такта подписана в журнале.

**Non-Goals:** автоподача и её запрос (`work-15`); сводка уведомлений за такт (`work-16`); серверные
«напоминания» (`WORK-41`, вынесены в `WORK-58`); расписание «в определённый час» — такт периодический.

## Decisions

- **Состав PR — один.**
  - `BHS.CRG.Modules/Ports/ModuleTick.cs` — `ModuleTick(Code, Title, Operation, Period)`;
    `IAppModule.Ticks => []`.
  - Проверка объявлений при старте — рядом со сборкой реестра модулей: операция обязана иметь
    `IModuleJobHandler` (тот же `ModuleWork.EnsureHandled`), код уникален в модуле, `Period` не меньше
    минуты (шаг службы).
  - `Api/Modules/ModuleTickService.cs` — `BackgroundService` по образцу `BackupScheduleService`: шаг
    минута, пауза на старте, `TimeProvider`. Живёт в `Api`, рядом с `ModuleWorkRunner`: инфраструктура о
    модулях не знает.
  - Цель задачи такта — постоянный идентификатор из `модуль:код` (UUID v5): по нему индекс «одна активная
    задача на цель» не даёт второй, а «когда ставили последнюю» читается из той же таблицы задач. Своей
    таблицы состояния такта нет: второе место правды разошлось бы с очередью.
  - «Уже выполняется» от индекса — штатный исход такта, не ошибка: в журнал сервера не пишется.
  - `ModuleWorkRunner.cs`: у задачи с целью такта автор журнала — `ActivityActor(null, "Система — <Title>")`;
    параметр доступа — `DataAccess.OfSystem(Title)`, поэтому опубликованные наборы и `PerUser`-таблицы
    отвечают отказом с названием такта (`work-07`).
- **Догон — у модуля.** Такт не помнит пропущенных сроков: задача модуля выбирает по состоянию («все
  черновики, чьё окно истекло», `work-15`). Поэтому неделя простоя — одна задача.
- **Нового пишущего API нет** — If-Match и ворота модуля не применимы.
- **Сторож.** `ModuleTickDeclarationTests` — такт без обработчика, повтор кода, период короче минуты не
  стартуют. `ModuleTickServiceTests` на пробном модуле с поддельным `TimeProvider`: срок прошёл — одна
  задача; задача идёт — вторая не ставится; сдвиг часов на неделю — одна задача; модуль выключен — ни
  одной; запись журнала из задачи — «Система — …».
- **Чем ломается.** Такт ставит задачу на каждом шаге без оглядки на прежнюю: после простоя очередь
  забита дублями (индекс спасает только от одновременных, а не от последовательных). Догон в такте:
  неделя простоя — две тысячи задач.
- **Зависимости.** Нет входящих; `work-07` даёт отказ системы у `PerUser`-таблиц. Потребитель — `work-15`.

## Risks / Trade-offs

- [Шаг такта — минута, период короче минуты невозможен] → для автоподачи достаточно; ограничение
  названо в объявлении (`Period` не меньше минуты — отказ старта).
- [Задача такта упала — следующая поставится через период, а не сразу] → это и есть «по состоянию»:
  следующий прогон заберёт то же; отказ виден общесистемным уведомлением.
