# Design: палитра находит записи

Общая архитектура — `../shell-00-epic/design.md` (D1 — макет, D6 — живые прогоны). Здесь только решения
этого change. Макет — артборд «A · Открыт поиск (Ctrl K)» канваса варианта B (палитра одна для обоих
вариантов); выбор сделан решением эпика, новых макетов не нужно.

## Context

Сверено по коду ветки от master `c9586405`; пересверено 11.11.2026 по `6dec4de6`.

**Что выяснилось сверкой** (issue писался 17.10, до PR #1478):
- Часть 1 сделана (#1478): действия `PALETTE_ACTIONS` («Новый счёт», «Счёт из файла», «Новая накладная»,
  «Новая стройка»), тема, «Выйти», разделы; чипы «Везде / Действия / Разделы»; подвал «↑ ↓ выбрать»,
  «Enter открыть», «Подсказка: напишите „тёмная тема“ или „…“»; поиск по словам с подсветкой и
  ранжированием (`paletteSearch.ts`). Подпись поля — «Найти раздел или действие…», а не «Перейти к
  разделу…», как в issue.
- **Не сделано из «Действий и разделов»:** Tab (в `onKey` его нет, в подвале нет строки «Tab искать
  только в …»). Tab сужает до группы ДАННЫХ раздела, поэтому едет здесь, с чипами данных; комментарий у
  `SCOPES` (`CommandPalette.tsx:36`) так и говорит. С 03.11.2026 палитра — search view MD3
  (`sharedui-md3-15-shell`); её состав и клавиши от этого не менялись.
- Серверного поиска записей нет. Список счетов ищет по загруженному (`InvoicesPage.tsx:185`).
  `GET /api/document-sets/search` (`IDocumentSearch`) ищет документы комплектов `id` — группы палитры не
  кормит.
- **Архив.** `purpose=choice` есть у общих данных (`CommonDataEndpoints.cs`), организаций `costs`
  (`OrganizationEndpoints.cs`) и видов работ (`WorkTypeEndpoints.cs`). У строек (`Construction : Entity`), наборов данных и счетов
  архивного состояния нет — для трёх групп правило сегодня пусто. Оно записано как правило поиска и
  связывает поставщиков, которые появятся (общие данные, `plan`, `work`).
- **Пример issue «Создать накладную от ООО …» модели не соответствует:** у накладной нет организации,
  есть стройка (`Waybill.ConstructionId`, `Data/Waybill.cs:57`). Действие с найденным — В-2.
- **Переход к записи.** Экран записи по коду типа — `RECORD_ROUTES` (`shared/ui/recordRoutes.ts`): там
  только `СчётНаОплату`; рядом — `CATALOG_RECORD` (запись общих данных, `/common-data?entry=`, #1517), но
  не по коду типа. Стройка открывается адресом `/document-sets/<id>`; у наборов данных параметра
  записи в адресе нет вовсе (`DataSetsPage.tsx` не читает `useSearchParams`) — его придётся завести.
- **ТЗ.** `AUTH-16.1`: «поиск ищет везде и помечает найденное „вне пространства“»; `CORE-34`: контракт
  отвечает в правах спрашивающего, «тем же правилом работают поиск по всем модулям». Механизм
  межмодульного контракта с «многими поставщиками» и `ModuleReader` **построен** `plan-22-module-exchange`
  (#1858, 10.11.2026): `[ModuleContract("…", Many = true)]` в `BHS.CRG.Modules/Exchange`,
  `IModuleContracts.GetAll<T>()` — реализации включённых модулей (выключенный просто не отвечает),
  `ModuleReader` — права спрашивающего, общие ответы `ContractAnswer.Hidden` («скрыто правами») и
  `SystemRefused`. Рабочих контрактов ещё нет — поиск был бы первым; сторожа проверены пробными модулями. Таблицы `CORE-33` (`BHS.CRG.Modules/Tables/ModuleTable.cs`) уже несут ключ доступа
  `Requires`, вид отбора строк `Isolation` и код типа записи `RecordType`.

## Goals / Non-Goals

**Goals:** счёт, стройка, набор данных находятся из любого экрана за Ctrl K — Enter; закрытое правами не
видно ни записью, ни числом; Tab сужает до раздела; один пример действия с найденным.

**Non-Goals:**
- полнотекстовый поиск по реквизитам и строкам (поиск — по названию, номеру, поставщику);
- группы документов `id`, общих данных, накладных — добавляются тем же механизмом позже;
- поиск в списках экранов (там свой поиск, его не трогаем).

## Decisions

### Состав PR
- **PR 1 — сервер.** Адрес поиска `GET /api/search` (В-1 — Б), контракт «Поиск записей» и поставщики трёх групп, тесты прав, архива,
  выключенного модуля, перепись ворот. Клиент не меняется.
- **PR 2 — клиент.** `shared/api/recordSearch.ts` (React Query, ключ — запрос и область; задержка ввода
  ~200 мс; ответ на устаревший запрос отбрасывается), группы и чипы в `CommandPalette.tsx`, Tab, действие с
  найденным, `RECORD_ROUTES` для стройки и набора данных, параметр записи у экрана наборов данных.

### Сверка макета с кодом (12.11.2026) и решения владельца
Артборд «A · Открыт поиск» нарисован 17.10, до перехода на чистый MD3 (`sharedui-md3-00`, закрыт 10.11).
Вывод сверки — **годен с правками**, новых макетов не нужно (М-1). Где макет и код расходятся:
- место и форма — по коду: docked search view на месте строки поиска, на телефоне full-screen (`md3-15`), а
  не окно 680 по центру; цвета — ролями MD3, не hex макета;
- чип «Разделы» есть (UI-31), в макете его нет; подвал — «Tab искать только в счетах» (спека);
- «Создать накладную от ООО …» устарело (В-2) — действие с найденной стройкой;
- нет в макете — группа «Стройки», «вне пространства», «ещё в разделе», отказ, пусто, телефон: решает этот
  design и спека.

Решения владельца 12.11.2026:
- **М-1.** Вывод «годен с правками» принят, трёх новых макетов нет.
- **М-2.** Все строки палитры — действия, разделы и записи — рисует `ListOption` (вариант под полем поиска,
  `aria-activedescendant`), а не своя кнопка. Цветная плитка действия уходит: действие от раздела отличает
  группа. Это выходит за «действия и разделы не меняются» proposal — по слову владельца, в PR 2.
- **М-3.** «Новая накладная на стройку „…“» — пунктом в начале группы «Действия», как в макете, а не
  кнопкой у строки стройки.
- **М-4.** Счёт показывается как в макете: «№ 418 · ООО „КабельТорг“» и сумма у замыкающего края. В ответе —
  `amount`; у набора данных замыкающий текст — место (стройка), у стройки — внешний код (`detail`).

### Что не зависит от формы адреса
- **Ответ** — группы `{ code, title, module, recordType, items: [{ id, title, detail?, place?, amount? }],
  more, refused? }` (М-4: `detail` — внешний код стройки, назначение счёта; `place` — стройка набора данных;
  `amount` — сумма счёта; форматирует клиент).
  Сервер называет код типа записи и идентификатор; адрес экрана знает только клиент (`RECORD_ROUTES`,
  `openTo`) — сервер адресов клиента не знает, как и у таблиц (`recordRoutes.ts`).
- **Права** — ключ доступа группы тот же, что у списка записей: `costs.invoice.read`,
  `core.constructions.read`, `core.datasets.read`. Клиент дополнительно не показывает группу, экран
  которой закрыт `openTo` — второй пояс, а не единственный.
- **Что ищется:** счёт — номер, название поставщика, назначение (то же, что поиск списка счетов);
  стройка — название и внешний код (`Construction.ExternalCode`); набор данных — название. Сравнение без
  учёта регистра и «ё», по словам в любом порядке — как `paletteSearch.ts` на клиенте.
- **Порог и предел:** запрос короче двух знаков сервер не спрашивают; на группу не больше пяти записей и
  `more` — «ещё в разделе», ведущее в раздел с тем же запросом там, где экран его принимает.
- **Пространство** не передаётся (`AUTH-16.2`: пространство не граница); пометку «вне пространства»
  ставит клиент тем же `inside()`, что у разделов.
- **Порядок групп** в палитре: «Действия» → «Счета», «Стройки», «Наборы данных» → разделы. Enter
  исполняет первый пункт, и «счета» по-прежнему ведёт в раздел, а не в найденный счёт: совпадение
  подписью раздела выше совпадения в данных (правило ранжирования `docs/UI.md`, «Палитра»).
- **Отказ ≠ пусто.** Отказ группы приходит `refused` с причиной и показывается строкой у группы.

### Tab
Tab в поле палитры перехватывается (как стрелки) и выбирает чип группы раздела, где стоит человек, —
по `activeRail`/`ownerItem` и таблице «раздел → группа» рядом с `SCOPES`. Повторный Tab возвращает
«Везде». Фокус из поля не уходит: палитра — модальное окно, ловушка фокуса в нём законна, а Esc
закрывает её. Shift+Tab не перехватывается.

### Действие с найденным (по рекомендации В-2)
Запись `PALETTE_ACTIONS` получает необязательный признак «с записью типа X» (`withRecord: 'Стройка'`).
Палитра ведёт адресом `?do=<действие>&record=<id>`; `usePaletteIntent` отдаёт экрану `record`, и экран
заводит черновик своей кнопкой с подставленной записью. Перепись `paletteActions.test.ts` проверяет, что
экран принимает и `record`.

### Сторож и «чем ломается»
- Сервер: `RecordSearchTests` — право только на счета; без права ни записи, ни числа; выключенный
  `costs` — 200 без группы; отказ поставщика назван у группы; пять записей и `more`; адрес в
  `EndpointGateInventoryTests`. Перепись поставщиков поиска: каждый называет ключ доступа (объявление без
  ключа — отказ старта, как у `ModuleTable`).
- Клиент: vitest `CommandPalette.test.tsx` — группа без права не показана, отказ сказан словами, Tab
  выбирает чип раздела, устаревший ответ отброшен; `paletteActions.test.ts` — приём `record`.
- Живой прогон: Ctrl K → номер счёта → Enter открывает счёт (`e2e/keyboard-smoke.mjs` или
  `invoices-smoke.mjs`); `limited-smoke.mjs` — под ролью без счетов группы «Счета» нет. Плюс весь список
  живых прогонов (зонтик, D6).
- Ломается так: палитра показывает номер счёта бухгалтеру без права; поиск, отказавший целиком из-за
  одного поставщика; «Ничего не найдено» при упавшем сервере.

## Risks / Trade-offs

- [Поиск подстроки медленный на больших таблицах: индекса под него нет, `ix_invoices_duplicate` —
  составной и подстроку не ускоряет] → счетов сотни в год (реестр 2025 года — 99), предел пять на группу,
  порог два знака; триграммный индекс — только по замеру.
- [Поиск — первый рабочий контракт «со многими поставщиками»] → механизм проверен пробными модулями
  (`ModuleContractCatalogTests`); общие ответы — `ContractAnswer`, свой «нет права» поиск не заводит.
- [Tab в поле непривычен] → подвал называет его, и на экране без группы Tab ничего не делает.

## Open Questions

### В-1. Форма адреса поиска — решение Архитектора, до кода PR 1 (решено 11.11.2026)
- **А. Адрес на модуль.** `GET /api/costs/search?q=`, ядро — `GET /api/search?q=`; клиент спрашивает
  каждый доступный модуль параллельно и сливает. «+» ворота модуля и права — те же, что у остальных
  адресов модуля, перепись ворот уже умеет; не ждёт `plan-22`. «−» N запросов на каждое нажатие;
  ранжирование и предел — на клиенте; новый модуль — правка клиентского реестра источников; отказ
  выключенного модуля (501) клиент обязан понимать как «группы нет».
- **Б. Один адрес ядра и контракт «со многими поставщиками».** `GET /api/search?q=`; каждый модуль
  реализует контракт «Поиск записей» — `[ModuleContract("Поиск записей", Many = true)]`, адрес берёт их
  `IModuleContracts.GetAll<T>()` (механизм `plan-22`, построен) и зовёт с `ModuleReader` спрашивающего;
  группы ядра (стройки, наборы данных) адрес ищет сам, не через порт. Закрытая правами группа — ответ
  `ContractAnswer.Hidden`, которого клиент не показывает. «+» один запрос, одно ранжирование; выключенный
  модуль просто не отвечает; ровно то, что пишет ТЗ («тем же правилом работают поиск по всем модулям»);
  изоляция строк `work-07` приходит в поиск даром (расширяет `ModuleReader`). «−» права проверяет
  поставщик — нужна перепись, что каждый называет ключ доступа; медленный поставщик держит весь ответ —
  нужен предел времени на поставщика, превысивший отвечает `refused` (как таймаут подсказок поля, #1530).
- **В. Один адрес ядра поверх таблиц `CORE-33`.** Таблица объявляет «колонки поиска»; ядро ищет фильтром
  `contains` по таблицам, которые человек может читать (`Requires`, `Isolation`), и ведёт к записи по
  `RecordType`. «+» права, изоляция и код записи уже есть, не ждёт `plan-22`. «−» стройки и наборы данных
  — не таблицы модулей, им нужен свой путь; запрос таблицы тяжелее поиска; таблица становится второй
  обязанностью «быть поиском».

**Рекомендация — Б** (пересмотрено 11.11.2026: условие «если `plan-22` сливается раньше PR 1» выполнено —
механизм слит 10.11.2026). А больше не нужна как обход ожидания: она заводит N запросов и клиентский реестр
источников там, где механизм уже есть. В не рекомендуется: делает таблицы обязанными поиску. Спецификация от
выбора не зависит.

**✅ Решено владельцем 11.11.2026 — вариант Б.** Один адрес ядра `GET /api/search`; модули — контракт
«Поиск записей» `[ModuleContract("Поиск записей", Many = true)]`, адрес зовёт `GetAll<T>()` с `ModuleReader`
спрашивающего; группы ядра ищет сам адрес; предел времени на поставщика, превысивший — `refused` у своей
группы. Тот же контракт отдаёт карточки записей по идентификатору для «Недавних» `shell-08` (В-3 там —
Б): одно объявление «найти» и «показать по id», а не два.

### В-2. Действие с найденной записью — решение владельца (решено 11.11.2026)
Пример issue («Создать накладную от ООО …») модели не соответствует: у накладной стройка, а не
организация. Варианты: (1) «Новая накладная на стройку „…“» у найденной стройки — **рекомендуется**: обе
стороны есть, действие частое; (2) «Новый счёт от „…“» у найденной организации — требует группы
«Организации», которой в issue нет; (3) без действий с найденным в этом change. Спецификация (`UI-32`)
написана по варианту 1; при другом ответе правится она и задача 3.3.

**✅ Решено владельцем 11.11.2026 — вариант 1**: «Новая накладная на стройку „…“». `UI-32` и задача 3.3 —
без изменений.
