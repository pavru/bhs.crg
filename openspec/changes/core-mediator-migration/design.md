# Design: переход с MediatR 12.5 на Mediator

## Context

- Регистрация: `ServiceRegistration.Domain.cs:35` —
  `AddMediatR(cfg => cfg.RegisterServicesFromAssembly(typeof(CatalogHandlers).Assembly))`, вызов из
  `Program.cs:21` (`AddMediatRAndRepositories`).
- Версия прибита диапазоном `[12.5.0,13.0)` в `BHS.CRG.Application.csproj:12`. Сторож —
  `Tests/Configuration/MediatRLicenseTests.cs`: читает версию загруженной сборки. Обоснование —
  `docs/DEV_NOTES.md:336–346`, исключение для бота — `.github/dependabot.yml:34–37`.
- Обработчики — классы с несколькими `IRequestHandler<…>` сразу (`Catalog/Handlers.cs` и т. п.);
  некоторые сами берут `IMediator` (`Documents/PlanHandlers.cs`,
  `Reconciliation/ProblemSummaryHandler.cs`, `RelatedProblemsHandler.cs`).
- Тесты зовут обработчики и напрямую — 34 места `new …Handler(` — и через `IMediator` хоста
  (`fixture.Services.CreateScope()`).
- `IMediator` берут и вне запросов: `ModuleTypeProjector` при старте, `DomainSnapshotService`,
  `DocumentSetAssemblyService`, `OperationLauncher`, службы приёма (`CatalogIntakeService`,
  `NomenclatureIntakeService`).

### Что выяснилось сверкой (против цифр issue на 17.10.2026)

| Что | Issue | Сейчас |
|---|---|---|
| Обработчики | 151 | 152 |
| `using MediatR`: Application / Api / Infrastructure / тесты | 45 / 26 / 5 / 91 | 46 / 26 / 6 / 95 |
| Обращения к `IMediator` / `ISender` / `IPublisher` | ≈340 | 378 (175 код + 203 тесты) |
| `.Send(` | ≈200 | 205 в коде; в тестах ещё 984 — issue их не считал |
| Уведомления, behaviors, потоковые и обобщённые запросы | нет | нет |

Объём вырос мало; труднопереносимых частей по-прежнему нет. Главная механическая работа — тесты: 984
вызовов `.Send(` компилируются без правки, правится только `using`.

## Goals / Non-Goals

**Goals:** в решении нет `MediatR`; поведение и ответы не меняются; две главные ловушки — время жизни
и пропущенный генератором обработчик — закрыты сторожами.

**Non-Goals:**
- уведомления и pipeline behaviors — их нет и с переходом не появляется;
- MediatR в модулях — контракты модулей от медиатора свободны и такими остаются (`ModuleBoundaryTests`).

## Decisions

- **D1. Генератор — только в `BHS.CRG.Api`.** Во все проекты с сообщениями и обработчиками —
  `Mediator.Abstractions`. Генератор в двух слоях одной поставки даёт ошибки сборки (заметки миграции
  библиотеки). Тестовый хост собирается из `BHS.CRG.Api` и получает сгенерированный `IMediator`
  оттуда. Тестам, создающим обработчик через `new`, генератор не нужен — проверить первым шагом на
  одном классе.
- **D2. `ServiceLifetime.Scoped` обязательно.** У Mediator по умолчанию Singleton: обработчик-синглтон
  захватил бы `DbContext` первого запроса. Заметят это не сборка и не юнит-тесты, а два одновременных
  запроса. Места, где `IMediator` берёт синглтон или фоновая служба, обязаны брать его из созданной
  области. Проверка области при сборке контейнера (`ValidateScopes` / `ValidateOnBuild` тестового
  хоста) ловит захват на старте.
- **D3. `Task<T>` → `ValueTask<T>` механически**, кроме мест, где результат `Send` сохраняют и ждут
  потом или ждут дважды. `ValueTask` второй раз ждать нельзя. Сверка 22.10.2026: присваиваний
  `= ….Send(` без `await` в коде нет, `Task.WhenAll` по `Send` нет. При переходе — повторить поиск и в
  тестах. Найденное — `.AsTask()` с комментарием.
- **D4. Обработчики без ответа** (20 штук, `IRequestHandler<TCommand>`) переходят на форму Mediator
  для команд без результата (`IRequest` → `ValueTask<Unit>`). Вызывающие `await m.Send(cmd)` не
  меняются.
- **D5. Сторожа.**
  - `MediatRLicenseTests` → «пакета `MediatR` в решении нет»: ни в одном `csproj`, ни среди
    загруженных сборок.
  - **Время жизни:** два одновременных запроса к адресу, обработчик которого пишет через `DbContext`,
    получают разные контексты. Тест краснеет, если убрать `ServiceLifetime = Scoped`.
  - **Генератор нашёл все обработчики:** отражением собрать все реализации `IRequestHandler<,>` и
    `IRequestHandler<>` в сборках решения и сверить с тем, что зарегистрировал генератор. Обработчик,
    которого генератор не увидел (сборка не названа в `Assemblies`), — красный тест, а не 500 в
    продукте.
- **D6. Один PR, без промежуточного состояния «два медиатора».** Смешанное состояние удвоило бы
  регистрацию, и половина обработчиков зависела бы от того, какой `IMediator` пришёл в конструктор.
  Объём механический, ревью идёт по дифу `using` и сигнатур.

## Risks / Trade-offs

- [Singleton по умолчанию прошёл незамеченным] → сторож времени жизни (D5) и проверка областей
  контейнера (D2).
- [Генератор не видит обработчик из второй сборки] → сторож «все обработчики» (D5). Сегодня все
  обработчики в одной сборке, но это свойство, а не закон.
- [`ValueTask` ждут дважды] → поиск по D3 перед слиянием и анализатор `CA2012` (использование
  `ValueTask`) уровнем warning в затронутых проектах на время перехода.
- [Живые прогоны ловят то, что не ловят тесты] → полный backend и все живые прогоны CI зелёные до
  слияния (условие «Готово» из issue).
