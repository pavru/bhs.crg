# Design: факты для индикатора состояния счёта

## Context

Общая архитектура — `../costs-invoice-screen-00-epic/design.md` (D3, D4). Мотивация — `proposal.md`.

Как устроено сегодня:
- **Вид счёта собирает `InvoiceDesk.ViewAsync` → `InvoiceViews.Of`.** Тот же вид возвращают чтение и
  каждая запись. Готовность — `InvoiceReadiness.Of`, одна функция для перечня и для отказа перехода.
  `null` у разобранного, отклонённого и запертого ставит `InvoiceViews.Of`.
- **Срок в реестре** — `InvoiceDue.DaysLeftOf` и `InvoiceDue.OverdueOf` от `clock.TodayAsync` (пояс
  компании). Колонки таблицы счетов считают тем же правилом (`InvoiceTable`). Срок в виде счёта —
  `InvoiceDueView(Manual, ByRule, SupplierDeferral)`, без «осталось».
- **Отказ оплаты** — `PaymentPosting.Refusal` (нет суммы; расхождение сверх допуска, если строки есть) и
  `InvoiceDesk.Unpayable` (отклонён). Причина приходит строкой `payment.refusal`.
- **Версия** — `db.VersionOf(invoice)`, отметка строки базы. `UpdatedAt` двигает `Touch()` в каждом
  методе сущности. Автора записи у счёта нет. `CreatedBy` есть, но наружу не отдаётся.
- **Прецедент снимка имени** в модуле: `SupplierMatch.UpdatedByName`, `SupplierTerms.UpdatedByName`,
  `InvoiceBookEntry` (`author_name`), версии накладной.

## Goals / Non-Goals

**Goals:**
- Индикатор получает всё нужное одним ответом счёта, без правил на клиенте.
- Одно расхождение — один пункт (D3 зонтика).

**Non-Goals:**
- Уровни индикатора и тексты пунктов — ребёнок 11.
- «Кто завёл» и пометка сознательного повтора — ребёнок 03.
- Готовность у разобранного счёта («разобран до разноски»). Её нет нарочно: «Разобран» — утверждение
  человека.

## Decisions

### D1. Срок — расширение `InvoiceDueView`

`InvoiceDueView(Manual, ByRule, SupplierDeferral, DaysLeft, Overdue)`. Функции и «сегодня» — те же, что
у `InvoiceViews.Item`. `clock.TodayAsync` зовётся один раз на сборку вида. Без неё «сегодня» вида и
реестра расходилось бы на полночи в поясе компании.

*Отвергнуто:* считать на клиенте по поясу из `/account/access`. Получилось бы второе место правила
«дата отгрузки + отсрочка − 1».

### D2. «Чему мешает» — из правила оплаты, а не списком видов

- `InvoiceReadinessGap.Blocks: IReadOnlyList<string>` — `parsed` и, при условии, `payment`.
- Пометку ставит сборка готовности. Она спрашивает правило оплаты, какой род отказа у счёта:
  `PaymentPosting.RefusalKind(invoice, balance)` возвращает `amount`, `discrepancy` или `null`.
  `Refusal` строит текст по тому же роду, так что правило одно.
- `payment` получает пункт, который чинит ту же причину:
  - `amount` → пункт поля `Итого` (после ребёнка 01);
  - `discrepancy` → пункт `total`.
- Оплаченному счёту `payment` не ставится: вопрос об оплате не стоит.
- `PaymentView.RefusalKind` — тот же род, плюс `rejected` из `InvoiceDesk.Unpayable`.
- Договор для индикатора: если у причины отказа есть пункт с `payment` в `blocks`, это один пункт.
  Иначе причина — отдельный пункт (у разобранного счёта, у отклонённого).

*Отвергнуто:*
- «`total` мешает оплате» списком видов на клиенте или в готовности. Правило оплаты меняется (01 добавил
  нуль), а список молча отстаёт.
- Один общий перечень «готовность + оплата». Он ломает договор «переход прошёл ⇔ перечень пуст».

⚠️ Пункт `field` с полем `Итого` появляется только после ребёнка 01. До слияния 01 род `amount` пунктом
готовности не покрыт, и индикатор покажет причину отдельно. Это правда, не дефект. Порядок слияния
01 → 02 желателен, но не обязателен.

### D3. Только чтение — `If-Match` не нужен

Новых пишущих адресов нет. Все поля — в ответе чтения и в ответах существующих записей, а записи уже
требуют `If-Match` (`InvoiceStaleFormTests`). Чтение `GET /api/costs/invoices/{id}` стоит под
`costs.invoice.read` в группе модуля (AUTH-8, AUTH-9), и это не меняется. Автор последней записи (D4)
ставится внутри существующих записей и версии не добавляет: столбцы меняются только вместе с изменением
счёта.

### D4. «Кто и когда изменил» (Э4) — форма снимка

Нужен индикатору для пункта «изменили, пока вы правили»: «Изменил Петров · 12:04» или «Дописало
распознавание · 12:04». Время уже есть (`updatedAt`), автора нет.

| Вариант | Как | За | Против |
|---|---|---|---|
| **А. Снимок в строке счёта** (рекомендую) | колонки `updated_by` (uuid), `updated_by_name` (снимок, предел длины — `SupplierMatch.ByNameLength`), `updated_via` (`user` / `recognition` / `system`). Ставятся одним местом — при сохранении изменённого счёта контекстом модуля, по автору текущей записи: пользователь запроса, род `recognition` у `InvoiceDesk.MergeAsync`, `system` у прочих фоновых записей | одно чтение, атомарно с версией; прецедент модуля (`SupplierMatch`, `SupplierTerms`, книга); «это вы» — сравнением `updated_by` | миграция; при копии старше колонок автора нет (честно — пусто) |
| **Б. Последняя запись журнала** | новый порт чтения `IModuleActivityLog.LastAsync(target)` в `BHS.CRG.Modules` | без миграции | расширение контракта модулей ради одного поля; запись журнала может не лечь (`from-scan` это терпит), а свёртка серий (`core-journal-series`) — не граница записи строки; второй запрос в ядро на каждое чтение счёта |
| **В. Только в ответе 409** | тело отказа «изменили» называет автора | без миграции и без поля в виде | «изменили» клиент узнаёт и без 409 — сравнением при перечитывании (`useDraftBase`); там автора не было бы |

**Рекомендация — А.** Ограничение реализации: автор ставится только тогда, когда у счёта есть
изменённые столбцы. Иначе пустая запись (`POST …/draft` у черновика) двигала бы версию и давала соседу
ложное «изменили». Удобнее всего перехват сохранения в `CostsDbContext`: состояние строки `Modified`, не
считая собственных столбцов автора. Выбирает Архитектор — задача 0.2.

У счетов, записанных до миграции, `updatedBy` пуст. Экран тогда говорит только время. Дозаполнения из
журнала нет: его запись не равна записи строки (см. Б).

## Risks / Trade-offs

- [Перехват сохранения поставит автора записи, сделанной не через связку] → все записи счёта идут через
  `InvoiceDesk` (spec: «адрес MUST NOT мочь её забыть»). Фоновая без пользователя получает `system`, а не
  чужое имя.
- [`blocks` разойдётся с отказом оплаты] → род берётся из той же функции. Тест сверяет `blocks`,
  `refusalKind` и фактический отказ `POST …/paid` на одних счетах.
- [Лишний вызов часов компании на каждое чтение счёта] → часы читают настройку один раз на запрос; на
  чтение счёта это один вызов.

## Migration Plan

- Миграция схемы `costs` (вариант А): `dotnet ef migrations add InvoiceUpdatedBy --project
  src/server/BHS.CRG.Modules.Costs --context CostsDbContext`. Колонки допускают `NULL`, умолчаний нет:
  `NULL` значит «неизвестно».
- **Откат** — новые поля ответа необязательны, клиент без 11 их не читает. Миграция обратима (`Down`
  удаляет колонки).

## Open Questions

- Подпись рода `system` для человека («система», «смена допуска») решает ребёнок 11 по месту. Ответ
  сервера от неё не зависит.
