# Design: источник подсказок для вложенных полей и строк массивов

Общая архитектура — `../suggest-00-epic/design.md` (D1, D2, D10, D12); слои и форма запроса верхнего
уровня — `../archive/2026-10-23-suggest-02-endpoint/design.md`. Здесь только решения этого change. **Приоритет понижен**
(proposal, Why).

## Context

- После `suggest-02` есть: план источников `SuggestionSources.For`, порт `IFieldSuggestionReader`,
  индекс `IX_domain_objects_CompositeTypeId_UpdatedAt_Live`, окно по объёму, таймаут 503, ранжирование.
  Тип строки массива там отвечает 200 и пустым списком.
- Схема поля: `complex` / `array` с `typeId` (`shared/api/schema.ts`, `SchemaFieldInfo.TypeId`);
  составной тип-«выбор» (`type.union`) — вложенное составное с одним заполненным подполем.
- Цена массива по замеру #1528 — разбор строк (~5 мкс на строку), а не объём: 1000 документов по 40 строк
  укладываются в 8 МБ и стоят p95 300 мс; 250 документов (10 000 строк) — 63 мс.

## Goals / Non-Goals

**Goals:** значения из строк массивов и встроенных составных по точным путям из схем; цена запроса в
пределах D2 с дополнительным пределом строк.

**Non-Goals:** изменение контракта адреса и клиента; ссылки на записи каталога как источник;
рекурсивный `$.**`; производная таблица (условие перехода — p95 > 150 мс при пределах).

## Decisions

- **Пути — из схем, при запросе.** `SuggestionSources.For` обходит типы, в схемах которых тип-владелец
  встречается полем `complex` или `array` (с учётом наследования схем этих типов), до глубины 6, и
  собирает пары «тип записи-владельца → путь JSON до поля» (`Работы[*].Наименование`,
  `Адрес.Регион`). Путь строится по ключам схемы, а не поиском ключа в данных — поэтому «Организация.
  Наименование» и «Работа.Наименование» не смешиваются. Тип-«выбор» (`type.union`) — обычное составное.
- **Чтение.** По каждому типу записи-владельца — то же окно подзапросом над индексом, но с двумя
  нарастающими суммами: `pg_column_size("Data")` ≤ 8 МБ и длина читаемых массивов ≤ ~10 000; значения
  разворачиваются (`jsonb_path_query` по выведенному пути) только у записей окна. Частота — по разным
  записям-владельцам, а не по строкам.
  *Как сделано:* длина — `jsonpath` `.size()` последнего массива пути (у вложенных массивов — сумма по
  вхождениям), а не `jsonb_array_length`: путь бывает с массивом внутри массива. Считается только у
  записей, прошедших предел объёма. Запись отдаёт значение однажды (`DISTINCT` в подзапросе), разные
  записи считает ранжирование — как у верхнего уровня. Верхний уровень и вложенные пути — одним
  запросом (`UNION ALL`) под одним пределом времени, окна у них свои, а бюджет общий: при обеих частях
  пределы записей и объёма у каждой — половина (замер: тип с 50 000 своими записями и строками 2000
  журналов — p95 144–154 мс с полными окнами, 65 мс пополам; дороже всего счётчик строк у всего окна по
  объёму). Число путей за запрос — не больше 32, от мелких к глубоким: тип, вложенный в себя
  несколькими полями, иначе давал бы больше тысячи путей к глубине 6.
- **Ссылка на запись каталога** (значение вида `{ $ref }`) путём не порождается: путь идёт только во
  встроенные значения.
- **Чем ломается.** Рекурсивный поиск ключа — красный сценарий «тот же ключ в другом составном типе».
  Частота по строкам — красный сценарий «повтор в одном журнале». Окно без предела строк — замер на
  синтетике 2 000 × 40 выходит за 150 мс.

## Risks / Trade-offs

- [Предел строк не удержит цель 150 мс] → сказать в PR: это условие перехода на производную таблицу
  (зонтик, Non-Goals); контракт адреса при переходе не меняется.
- [Сценарий «тип строки массива — 200 и пусто» требования `suggest-02` становится ложным] → при
  архивации этого change после `suggest-02` дельта переписывается на MODIFIED требования «Подсказки по
  ранее введённому — адрес и форма ответа» с новым сценарием.
