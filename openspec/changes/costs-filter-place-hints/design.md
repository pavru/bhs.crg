# Design

## Context

Зачем — proposal.md, «Why». Здесь только то, что определяет устройство.

- **Поле значения условия** — `RowFilterValue` (`shared/filter`): по виду колонки `<select>`, `DateInput`
  или голый `<input>`. Его рисует `ConditionEditor`, общий для окошка чипа (`FilterChips`) и строки
  расширенного диалога (`RowFilterDialog`). Колонки отбора — `FilterColumn` (`name`, `kind`,
  `operators`, `options`, `unavailable`); для таблиц модулей их строит `tableFilterColumns` из ответа
  `/api/tables/{адрес}/columns`.
- **Как сервер сверяет «Объект» и «Раздел».** Колонки-перечни (`TableSql.List`): названия по ссылкам
  берутся из `InvoiceShares` — стройки и статьи (`AllocationPlaces.LoadAsync`: `IModuleConstructions` и
  справочник статей с архивными), разделы — подписью `SectionLabel` «стройка / раздел» плюс «стройка /
  без раздела»; потерянная ссылка называется «объект удалён» / «раздел удалён». Сверка — правило ядра
  `TableConditions.Compile`: `Upper` (`ToUpperInvariant`), сравнение `Ordinal`, строка целиком; ё и е
  различаются, пробелы значимы.
- **Что уже есть на клиенте.** `/costs/constructions` (`useCostsConstructions`) отдаёт
  `IModuleConstructions.ListAsync` — тот же порт и в том же составе, со стройками и разделами;
  `/costs/articles` (`useCostsArticles`) — статьи с признаком `archived`. Оба уже грузит экран реестра
  (`SitesChip`, разноска). Избранное и состояние фильтра — `useSiteFilterState()`.
- **`SuggestField`** (`shared/ui`, требования UI-1…UI-8) связан с адресом подсказок: источник — только
  `SuggestSource`, список строится из ответа `useFieldSuggestions`, разделитель — по признаку `here`.
- **Плохое условие уже показывается**: `conditionProblem` / `chipProblem` — красным, `role="alert"`,
  смысл «сервер не выполнит». Наш случай — «выполнит, но не найдёт»: другой смысл и другой тон.
- **Сторож-реестр строек** (`siteFilterRegistry.test.ts`): файл, взявший `useCostsConstructions` (или
  обёртку, названную в `carries`), обязан быть вписан — «фильтрует» или «не фильтрует, потому что…».

## Goals / Non-Goals

**Goals:**
- Перечень подсказки и перечень сверки совпадают по построению (один порт, одни справочники), а слова
  и формат подписей, живущие в двух местах, сверяет общий набор случаев.
- `shared/filter` и `shared/ui` не знают про стройки и статьи: перечень колонки приходит снаружи.
- Одно поведение подсказки на оба источника (адрес и перечень) — без второго комбобокса рядом.

**Non-Goals:**
- Адрес значений колонки таблицы и подсказки в прочих текстовых колонках.
- Нечёткий поиск («Комарова36» → «Комарова 36» по расстоянию правки): мягкое совпадение — только
  перечисленная в UI-56 нормализация.
- Правка сохранённых отборов: пометка ничего не переписывает сама, замена — действие человека.

## Decisions

### D1. Перечень собирает клиент из `/costs/constructions` и `/costs/articles`

Источник — тот же порт, что у сервера, поэтому состав совпадает без копии правила «кто входит».

Отвергнуто:
- **Справочник фильтра** (`/constructions/directory` через `useSiteFilterState().sites`). Разделов в
  нём нет, а это другой адрес с другой проекцией — совпадение с сервером было бы случайным.
- **Значения в объявлении колонки** (`options` у `TableColumnDto`). Объявление таблицы статично
  (`ModuleTable` в коде модуля); чтобы отдавать живые названия, модулю понадобился бы новый контракт
  «значения колонки на момент чтения» в `BHS.CRG.Modules` — по сути адрес значений, вынесенный за
  рамки (вариант 2).
- **Новый адрес** — исключён решением владельца.

Избранное берётся из `useSiteFilterState()` только для порядка и только при `active`: выключенный
фильтр — «без любимчиков», алфавит.

### D2. Перечень приходит в отбор полем `FilterColumn.known`

```
features/tables                      shared/filter                     shared/ui
---------------                      -------------                     ---------
useTableKnown(decl.columns)  --->    FilterColumn.known  --->  RowFilterValue --> SuggestField(options)
  sites    -> стройки+статьи+lost      { items, complete }       conditionNotice --> пометка/замена
  sections -> подписи разделов+lost                              FilterChips  --> значок на чипе
```

`known: { items: KnownItem[]; complete: boolean } | undefined`, где `KnownItem` — `value`, подпись
(если отличается), группа и приписка. `undefined` — перечня у колонки нет (поле прежнее);
`complete: false` — подсказка работает, пометка молчит (UI-56: «ещё не знаем»). Сборку держит
`features/tables` (новый файл рядом с `tableSites.ts`): только он знает, что у таблицы со `sites`
объекты — это стройки и статьи модуля `costs`. Связка общей страницы таблиц с `costs` уже есть
(`SitesChip` берёт `useCostsArticles`) — см. риски.

Отвергнуто: флажок `sites` в `FilterColumn` и сборка внутри `shared/filter` — общий отбор узнал бы
про справочники модуля, а наборы данных получили бы пустой хвост чужого понятия.

### D3. `SuggestField` делится на список и источник

Слой, клавиатура, `aria-*`, живая область и выделение совпадения выносятся из `SuggestingField` в
общую часть; источников два — адрес (`source`, как сейчас) и перечень (`options`). Публичный
компонент один: `SuggestField` принимает `source` **или** `options` (взаимоисключающие пропсы на уровне
типа). Разделитель `here` у адреса и подписи групп у перечня — один механизм «подпись над первым
пунктом группы»: «С других строек» становится подписью группы чужих пунктов.

Отвергнуто: отдельный компонент «подсказка из перечня» — два комбобокса с одним поведением
расходились бы при каждой правке UI-1…UI-8. Раскладку частей утверждает «Архитектор» (затронут
`shared/ui`, порядок #1545).

Перечень сопоставляется с набранным на клиенте тем же правилом выделения, что `suggestMatch`
(начало слова, без регистра, ё = е), и обрезается до 10 пунктов; задержки нет — нечего ждать.

### D4. Правило сверки — одна функция, зеркало `TableConditions`

`shared/filter` получает функцию «подходит ли значение под условие оператора» по правилу сервера:
`toUpperCase()` и сравнение строк целиком / `includes` / `startsWith` / `endsWith`. Отличия
`toUpperCase()` от `ToUpperInvariant()` есть только у символов вроде «ß» и турецкой «ı», которых в
названиях строек и статей нет; это записывается рядом с функцией, а тест держит русские случаи из
UI-56 (регистр, ё ≠ е, хвостовой пробел).

Мягкое совпадение для замены — отдельная функция: ё → е, обрезка краёв, схлопывание пробелов, без
пробелов вокруг «/». Замена предлагается, только когда мягко совпало ровно одно значение перечня.

### D5. Пометка — `conditionNotice`, отдельно от `conditionProblem`

Проблема («не выполнится») и пометка («не найдёт») — разные функции, разный тон (`danger` против
`warning`) и разные места в доступности (`role="alert"` только у проблемы). Если у условия есть
проблема, пометки нет: сначала то, что сервер отвергнет. Пометка возвращает, что сказать и по каким
значениям, плюс предложение замены; рисуют её `RowFilterValue` (под полем и на значении списка),
строка диалога и `FilterChips` (значок с подсказкой на чипе, без действия).

### D6. Флажок `Sections` рядом с `Sites`

`ModuleTableColumn` → `TableColumnDto` → клиентский `TableColumn.sections?`. Не перечисление вместо
двух флажков: на `Sites` завязан `SitesChip` («избранные стройки» к разделам не относится), а
переименование поля контракта задело бы клиент и сервер, обновляемые порознь. Флажок необязателен в
ответе: старый сервер его не пришлёт, и «Раздел» останется без перечня — как сегодня.

### D7. Общий набор случаев для слов и подписей

Формат подписи раздела и слова «без раздела», «объект удалён», «раздел удалён» живут в
`InvoiceShares` и в копии на клиенте. Пример — `invoiceLineCases.json`: JSON рядом с клиентским
кодом, его читают тест vitest и тест xUnit (`RepoPaths.File(...)`). Отставший краснеет.

## Risks / Trade-offs

- [Вторая таблица со стройками в другом модуле (этап 3, `plan`) получит `sites`, но статей `costs` у
  неё нет, а модуль `costs` может быть выключен] → сборка перечня в `features/tables` ветвится по
  таблице, а не по одному флажку; пока таблица одна, это записано здесь и в комментарии к сборке.
  Когда появится вторая — решать, не пора ли перечню приходить от модуля.
- [Клиентская копия правила сверки разойдётся с сервером] → тест на случаи UI-56; правило сервера
  меняется редко и только вместе с семантикой отбора (тогда же меняется и пометка).
- [Справочник строек большой — сотни строек × разделы] → перечень строится один раз на смену
  данных (memo), список показывает не больше 10 пунктов; запросов не прибавляется.
- [Пометка выглядит обвинением при законном старом значении] → тон предупреждения, без запрета;
  формулировка говорит о справочнике, а не об ошибке человека.
- [Права: читателю реестра закрыт `/costs/constructions` или `/costs/articles`] → часть перечня не
  пришла = `complete: false`, пометка молчит (UI-56); подсказка предлагает пришедшее.

## Migration Plan

Миграций базы нет. Флажок `sections` — необязательное поле ответа: сервер и клиент можно выкатывать в
любом порядке. Откат — откат PR; сохранённые отборы не меняются.

## Open Questions

- Размер поля с подсказкой в строке условия (сейчас `text-xs`-поле, `DateInput size="sm"`) и вид
  пометки в трёх местах — по выбранному владельцем макету; на требования не влияет.
