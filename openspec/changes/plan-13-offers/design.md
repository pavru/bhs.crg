# Design: коммерческое предложение из редакции

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D3, D4, D5, D12,
D17). Здесь только решения этого change.

## Context

Сверено по коду master `6b81e51e`.

- Образец записи модуля с суммами, версиями и `If-Match` — счёт `costs`: `Modules.Costs/Data/Invoice.cs`
  (режим НДС `VatMode`, стр. 109; смена режима — стр. 426), `Data/InvoiceVersion.cs`, тип записи с запертыми
  системными полями — `CostsRecordTypes.cs` (`Locked: true`, стр. 128-129).
- `VatMode` живёт в модуле `costs` (`Modules.Costs/Data/VatMode.cs:18`) и знает два режима: «в том числе»
  и «сверху». Модуль `plan` на `costs` сослаться не может (`ModuleBoundaryTests`).
- Документы с суммами объявляются `IAppModule.AccountingDocuments`
  (`BHS.CRG.Modules/Data/ModuleAccountingDocument.cs`): пока они есть, валюту учёта не сменить.
- Базовый тип версии — `plan-12` (`BHS.CRG.Modules/Data/ModuleRecordVersion.cs`).
- Заказчик — организация ядра: `IModuleCatalog` по роли `role.organization`, модуль объявляет её в `Needs`.

## Goals / Non-Goals

**Goals:** КП из редакции одним действием; наценки трёх уровней; деньги по правам; отправленная версия
неизменна.

**Non-Goals:** КП без сметы и прайс-лист (`plan-14`); печать (`plan-15`); «смета изменилась» и обновление
(`plan-16`); экраны (`plan-17`).

## Decisions

- **Хранение.** `Offer` (номер, дата, стройка, заказчик, `RevisionId` или `null` для КП по прайс-листу,
  статус, `CurrentVersion`, дата отправки, режим и ставка НДС, наценка предложения, итог, данные по схеме
  типа, `xmin`), `OfferLine` (строка редакции — `RevisionLineId`, вид работы, наименование, объём, единица,
  порядок, раздел ЛСР, наценка строки, цена продажи за единицу и сумма), наценки разделов —
  `OfferSectionMarkup`. Себестоимости в таблицах КП нет.
- **Номер** — сквозной по экземпляру, «КП-<год>-<NNN>», выдаётся при создании и не меняется между версиями.
- **Наценка.** Строка → раздел ЛСР → предложение: действует самая частная. Цена продажи = база ×
  (1 + наценка); база — итог строки ЛСР в текущих ценах с НР и СП, делённый на объём (ждёт решения В-8).
  Базу код читает из редакции при создании и при правке наценки; редакция зафиксирована, поэтому база не
  плывёт. Округление — до копейки на единицу, сумма строки — цена × объём, итог — сумма строк.
- **НДС** (ждёт решения В-9, рекомендация (а)): режим у КП — «в том числе», «сверху», «без НДС», ставка у
  КП. Своё перечисление в модуле `plan`: ссылаться на `costs` нельзя, а третьего режима у счёта нет.
  Правило расчёта — то же, что у счёта (`COST-7.2`): сумма НДС считается с итога, а не по строкам.
- **Деньги по правам** (D4). Цены продажи, наценки, итоги — только с `plan.offer.read`. Себестоимость строки
  и маржа — полями ответа только с `plan.estimate.cost`, иначе `hidden: ["cost"]`. Ни пустых, ни нулевых
  полей вместо скрытых.
- **Тип `КоммерческоеПредложение`** — открытый документ модуля (`TYPE-17`): системные поля «Наценка»
  (тэг `offer.markup`, объявлен модулем в `Tags`) и «Итого» — `Locked`; поля заказчика добавляет
  администратор. Охрана записи по схеме (`CORE-20`) — как у счёта.
- **Статусы и версии (PR 2).**
  - `draft` → `sent` (`POST …/send` с датой, право `plan.offer.send`) → `accepted` | `rejected` |
    `no-answer` (`POST …/outcome`, то же право).
  - Правка в `sent` и после — 409 «отправлено: правка — новой версией». `POST …/versions` снимок текущей
    версии (шапка, строки, деньги, статус, дата отправки) кладёт в `OfferVersion`, текущая становится
    черновиком версии N+1 с теми же строками.
  - `GET …/versions` — список версий с номером, статусом, датой отправки и итогом (итог — по
    `plan.offer.read`).
  - Удалить можно только черновик версии 1, ни разу не отправлявшийся; иначе 409.
- **Фиксация редакции.** Создание КП вызывает фиксацию редакции `plan-06` в той же транзакции модуля;
  удаление последнего черновика фиксацию не снимает (редакция видела производную).
- **Адреса** (ворота модуля `plan`): `GET /api/plan/offers`, `GET /api/plan/offers/{id}` —
  `plan.offer.read`; `POST /api/plan/offers` (из редакции), `PUT /api/plan/offers/{id}`,
  `PUT …/markups`, `POST …/versions`, `DELETE …` — `plan.offer.edit`; `POST …/send`, `POST …/outcome` —
  `plan.offer.send`. Все, кроме создания, требуют `If-Match`: без заголовка — 400, устаревший — 409.
- **Права** с объяснениями и `ReadAllMark`: `plan.offer.read` — `In`; `.edit`, `.send` — `Out` с причиной.
  Тест состава доступа по ролям: «Менеджер проекта» получает все три, «Сметчик» — ни одного.

## Risks / Trade-offs

- [Себестоимость утекает через КП] → её нет в таблицах КП вовсе; проверка нарушением `plan-29`.
- [Наценка на раздел и на строку путают] → ответ несёт у строки действующую наценку и её уровень.
- [В-8 или В-9 решатся иначе] → база и режим НДС заперты в `OfferPricing`; правка одного места и тестов.
