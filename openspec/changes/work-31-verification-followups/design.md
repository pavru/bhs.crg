# Design: исправления по итоговой проверке Work

## Context

Опора — [отчёт #2120](../work-00-epic/verification.md) и [архитектура Work](../work-00-epic/design.md). Автоподача уже сохраняет `required_missing` с идентификаторами строк. Очередь строит свои пометки через `ReviewMarks`. Карточка получает действия с сервера и уже читает версии. `ReportCorrection` сохраняет снимок и новую версию одной транзакцией. Редактор ролей показывает объяснения прав из каталога.

## Goals / Non-Goals

- Использовать существующий протокол приёмки и исправления, историю отчёта и справочники.
- Дать менеджеру законченный сценарий от признака проблемы до записи исправления там, где эта запись разрешена.
- Печать, мобильная доставка, карта этапов и расширение доступа к фото остаются за рамками change. Архивация зонтика остаётся решением владельца после повторной проверки 7.6.

## Decisions

### D1. Пометка опирается на текущую строку и перечень автоподачи

Отдельный код `required-missing` включается только при действующей автоподаче с сохранённым перечнем. Сервер сопоставляет его со строками по `lineId`. Пустое место определяется тем же правилом, что в `RequiredFields`, пустые материалы — отсутствием записей. Если строку удалили либо реквизит заполнили, соответствующий пропуск больше не участвует в пометке. Номер строки и наличие полей заказчика на это правило не влияют. Журнал и исходный перечень остаются историей автоподачи. Смена справочника сама по себе не создаёт новых пропусков задним числом.

В `ReportReads.QueueAsync` применять правило к доступным поданным отчётам с обычными фильтрами. Использовать одну проекцию для пометки, счётчика отчётов и фильтра до пагинации. Чтение должно быть пакетным и ограниченным уже отобранными кандидатами. Показ клиенту — код и сообщение в существующем `marks`; поля и значения отдельных строк в список не добавляются. Отчёт, у которого остался один из нескольких пропусков, считается один раз.

- Прямой показ сохранённого перечня оставляет предупреждение на уже заполненном отчёте.
- Повторная оценка справочника при каждом чтении добавляет проблемы, которых не было при автоподаче, и зависит от доступности справочника. Выбранный вариант отвечает на вопрос, остался ли пропуск из зафиксированной автоподачи.

### D2. Веб-форма опирается на имеющийся контракт исправления

Сервер карточки добавляет отдельное действие `correct` для видимой действующей версии в закрытом периоде. Разрешение вычисляется по праву `work.report.review` и охвату `ManagerSites.ReachAsync`, как у пишущего адреса. Широкое чтение карточки само по себе действие не даёт. У прошлых версий доступен обычный просмотр. Использовать существующие действия `accept`, `return` и `edit` в их текущих состояниях. При отправке сервер повторно решает вопрос доступа, закрытия и версии.

Для формы использовать текущую карточку, элементы редактирования отчётов и `ReportCustomerFields`. Обязательный сценарий — исправить объём, место, материалы или поле заказчика существующей строки, а также часы либо примечание отчёта. Шапка идентичности только для чтения. Остальные строки и значения передаются в полном снимке, поля сведений, участники и существующие ссылки на фото сохраняются. Для фото существующей строки переиспользовать контракт пропуска свойства `photos`, если форма их не меняет. Управление фотографиями и изменение состава строк в этой форме не требуется для закрытия 7.6. Этот объём формы принят для плана из проверенного сценария Work-24 и текущей карточки. Любое расширение состава операций фиксируется при выборе макета.

Перед сохранением форма проверяет причину по правилам сервера (значение после `Trim`, до 1000 символов), защищает несохранённый ввод и блокирует повторное нажатие, пока запрос идёт. Клиент формирует полезную нагрузку существующего `ReportRequest` без подстановки нового номера версии. При 409 объясняет, изменён ли отчёт или открыт период, и предлагает перечитать карточку без автоматической отправки. При неопределённом результате сети сначала перечитывается серверная версия по явному действию пользователя. При успехе показать новую действующую версию и обновить карточку, журнал и затронутые представления через существующий механизм обновления данных после записи.

- Использование обычного PUT не даёт снимка закрытия. Существующий POST уже выполняет версионирование, журнал и пересчёт связанного факта.
- Варианты взаимодействия для макетов: панель редактирования внутри карточки, диалог с предварительным просмотром и отдельный экран исправления. Выбор делает владелец до кода по [правилам UI](../../../docs/UI.md#новый-экран-порядок).

### D3. Объяснение берётся из каталога прав Work

Дополнить пояснения `WorkModule.Permissions` для `work.report.own`, `work.report.review` и `work.report.read`. Сохранить действующие подписи и описание охвата. Указать, что при наличии геометки в исходном фото координаты сохраняются отдельно от изображения. Изменение текста в каталоге покажется через существующую карточку права. Вариант с отдельной подсказкой в редакторе ролей дублировал бы серверное объяснение и оставил бы без текста остальные потребители каталога.

## Risks / Trade-offs

- Счётчик и строка очереди могут разойтись при расчёте после пагинации. Проверка с несколькими страницами и разными охватами подтверждает единое правило.
- Полная замена строк при исправлении может потерять не показанные в форме сведения. Проверить сериализацию всех строк, сохранение полей и фото, чтение прежнего снимка и журнала.
- У менеджера мог измениться охват или граница периода между чтением и сохранением. Пишущий адрес остаётся источником истины, форма показывает отказ и сохраняет ввод.

## Migration Plan

Пометка строится из существующего `required_missing` и текущих строк. При старом отчёте без перечня пометка отсутствует. Миграция базы не требуется. Сервер добавляет код пометки и действие карточки, затем их использует клиент той же поставки. При откате записанные исправления остаются читаемыми по действующему контракту версий.
