# Design: носители экранов смет

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D4, D7, D8, D9,
D17). Вход — `../plan-09-estimate-ui/design.md`, разделы «Макеты П1» и «Носители макета» (строки «нет»).

## Context

Сверено по коду master `43e08494`.

- Разбор знает больше, чем пишет: `GrandSmeta/ParsedLocalEstimate.cs`, `LocalEstimatePosition` несёт
  `Number` (сквозной, «13», «1.1»), `IsInactive`, `IsSubordinate`, `MarketAnalysis`; строку будущей
  редакции собирает `Import/EstimateImportRows.cs` и берёт из позиции только номер в разделе, шифр, объём,
  единицу, цены, материалы и трудозатраты.
- Строка без вида работы помечается `unmatched` (`EstimateViews`), счётчик редакции `unmatched` считает
  такие строки.
- Импорт помнит созданную редакцию (`EstimateImport.RevisionId`), редакция импорта не помнит; адреса
  импорта — под `plan.estimate.edit`.
- Смета уже привязывается к разделу стройки (`Estimate.SectionId`, `EstimateDto.sectionId`): для пункта
  «Сметы» в разделе серверу ничего не нужно.
- Сопоставление: строка (`PUT …/lines/{lineId}/match`) и один раздел (`POST …/sections/match`), версия —
  редакции, `If-Match`; коэффициент предлагается единицами внутри `RowMatching` и виден только в ответе
  правки. Материал — ресурс одной строки (`PUT …/resources/{resourceId}/match`).

## Goals / Non-Goals

**Goals:** каждый носитель «нет» из сверки `plan-09` — поле или адрес сервера; клиент не досчитывает.

**Non-Goals:** экраны (`plan-09`); новые права — всё под `plan.estimate.read` / `edit` / `cost`;
перечитывание прежних редакций.

## Decisions

- **D1. Поля строки.** `EstimateRowDto` получает `number` (строка файла как есть, `null` у редакций до
  этого change), `subordinate` и `kind`: `work` | `material`. Ключ переноса распределения
  остаётся номером в разделе (D9): `number` — только показ, он сдвигается при вставке позиции.
- **D2. Строка-материал** (решение владельца 26.10.2026, вопрос 14 П1). Вид `material` — позиция, у
  которой разбор не видит работы: ссылка на КА (`MarketAnalysis`) или шифр сборника цен материалов
  (ФССЦ, ТЦ_). Точное правило — по образцам `TestData/GrandSmeta` (задача 1.1). Строка-материал:
  - не помечается `unmatched` и не входит в счётчик `unmatched`, в план, «Ход работ» и график;
  - несёт свой материал в `materials[]` (если разбор не дал ресурса — один, из наименования, шифра,
    единицы и объёма позиции) и сопоставляется с номенклатурой адресами материалов;
  - сопоставление с видом работы для неё отвергается: «это материал, а не работа».
- **D3. Неактивная позиция не импортируется** (решение владельца 26.10.2026). Строки редакции для неё нет;
  отчёт импорта называет её в `skipped[]` {`place`, `reason: inactive`, `text`: «неактивна в файле —
  пропущена»} — отдельно от не разобранного: «разобрано N из M» её не уменьшает, и согласия на частичный
  импорт (`acceptPartial`) она не требует. Сводка будущей редакции её не считает. Это меняет решение
  `plan-07` («неактивные позиции тоже ложатся строками», `Import/EstimateImportRows.cs`).
- **D4. Счётчики и связь редакции.** `EstimateRevisionDto` получает `materialsUnmatched` (материалы без
  номенклатуры, с материалами строк-материалов), `unitChanged` (строки с пометкой `unit-changed`),
  `importId` и `partial` {`parsed`, `inFile`} — `null`, если редакция создана из полного разбора.
  `importId` отдаётся всем с `plan.estimate.read`; сам отчёт по-прежнему под `plan.estimate.edit`.
- **D5. Разделы ЛСР.** `GET /api/plan/revisions/{id}/sections` (`plan.estimate.read`) → `items[]` {`code`,
  `name`, `rows`, `unmatched`, `materialsUnmatched`, `units[]` {`sourceUnit`, `rows`}} в порядке файла.
  Читается одним запросом: таблица рисует свёрнутые разделы со счётчиками, не листая 300 строк.
- **D6. Общий список.** `GET /api/plan/estimates` без `constructionId` — сметы всех строек страницами
  (`cursor`, `limit`, как у строк), строка несёт `constructionId`, `sectionId` и счётчики действующей
  редакции; `hidden` — как у списка стройки. Название стройки клиент берёт справочником строек.
- **D7. Предпросмотр смены действующей.** `GET /api/plan/estimates/{id}/current-revision/preview?revisionId=`
  (`plan.estimate.edit`, только чтение) → `changes[]` {`workTypeId`, `unitId`, `was`, `becomes`} только по
  изменившимся видам работ, `unmatched` новой редакции, `version` сметы для следующего `POST` и
  `cost` {`was`, `becomes`} только с `plan.estimate.cost`. Смена по-прежнему одна — `POST …/current-revision`
  с `If-Match`; предпросмотр по устаревшей версии получает 409 там.
- **D8. Коэффициент до записи.** `GET /api/plan/unit-factor?sourceUnit=&unitId=` (`plan.estimate.read`) →
  `factor` и обе единицы — тем же правилом, что `RowMatching`; не выводится — `factor: null` с причиной,
  а не 1.
- **D9. Массовое сопоставление** (решение владельца, вопрос 16). `POST /api/plan/revisions/{id}/lines/match`
  (`plan.estimate.edit`, `If-Match` редакции): тело — `lineIds[]` или `sections[]`, вид работы, единица,
  коэффициент, `remember`. Одна фиксация: строки и версия редакции — вместе; ответ как у раздела —
  `matched`, `skipped[]` с причиной, `units`, `memory`, новая `version`. Строки-материалы пропускаются с
  причиной `material`.
- **D10. Материалы по материалу.** `GET /api/plan/revisions/{id}/materials` (`plan.estimate.read`) →
  группы по ключу «шифр + наименование + единица» файла: `key`, `sourceName`, `sourceCode`, `sourceUnit`,
  `rows`, `quantity` (сумма), `nomenclatureId` (если у всех одна), `marks`. `PUT
  /api/plan/revisions/{id}/materials/match` (`plan.estimate.edit`, `If-Match` редакции) сопоставляет все
  ресурсы группы одной фиксацией, «запомнить» — как у ресурса строки. Цена — только с
  `plan.estimate.cost`.

## Risks / Trade-offs

- [Миграция строк] → новые колонки строки с пустым значением у прежних редакций; экран показывает номер
  в разделе, если `number` пуст. Перечитывать старые файлы не требуется.
- [Правило «материал» ошибётся] → правило проверяется на всех образцах ЛСР в `TestData/GrandSmeta`; спорная
  позиция остаётся `work` — лишнее «не сопоставлено» видно, а пропавшая из плана работа нет.
- [Массовая правка большой редакции] → одна фиксация на запрос; лимит строк в запросе — как у страницы
  строк (1000), сверх — 400 с числом.
