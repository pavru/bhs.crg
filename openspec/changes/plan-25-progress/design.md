# Design: «Ход работ» стройки и факт в графике

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D16 — «Ход
работ», D10 — контракты, D17 — носители, D18 — макеты, D2 — интерфейс «Фактических работ» приходит
из Work-27). Здесь только решения этого change.

## Context

Сверено по коду master `bee4584fd`, версия `2.142.0`. Work-27 поставлен в #2103 (`085f43ffe`),
фактический бамп `d1bcc389a`, архив #2105. 26.11.2026 владелец отдельной командой возобновил Plan-25.

- Адреса справочника строек читаются под `core.constructions.read` (`ConstructionEndpoints`).
  У отдельного адреса «Хода работ» свои ворота из прав поставщиков.
- Позиция перечня — ключ «вид работы, стройка, раздел, единица» (`WorkPlanItem`);
  чтение позиций по списку — порт `plan-04`.
- Механизм контракта, контракт со многими поставщиками и `ModuleReader` — `plan-22`; «Плановые работы» —
  `plan-23`; «Фактические затраты» — `plan-24`; «любое из прав» и панели карточки стройки — `plan-02`.
- Работы графика с позицией перечня и частью распределения — `plan-19`.
- Каталог проверяет обязательную реализацию именованного контракта при старте. Поэтому Work-27
  объявляет `IActualWorks` вместе с настоящим поставщиком; здесь интерфейс повторно не создаётся.

## Goals / Non-Goals

**Goals:** экран, собранный из вкладов, с честными состояниями; потребление готового Work-27;
действующий факт в графике с видимыми исключениями; проверки на настоящем и синтетическом факте.

**Non-Goals:**
- поставщик «Фактических работ» — `work-27`;
- полоса «по смете — фактически» трудозатрат (`WORK-42`) — вклад `work-28`;
- колонка «закрыто актом» — модуль `id`, этап 6 (`ID-12`); до тех пор колонки нет, полосы о ней нет;
- сохранённые представления `CORE-33` — «Ход работ» свёрстанный экран, а не представление (`PLAN-21`).
- ручная разноска бригадного итога и исторический агрегат «на момент закрытия»; текущий контракт их не обещает.

## Decisions

- **«Фактические работы» — готовая предпосылка.** Полная форма, настоящий поставщик и право ответа
  поставляются атомарно Work-27. Чтение принимает стройку, раздел/позиции и период; возвращает текущие
  принятые объёмы и безопасные счётчики исключений с охватом. Ни часов, людей, авторов, ни ID отчётов
  в форме нет (`WORK-57`). Каталог и штатный `NotConnected` не меняются.
- **Неполный факт.** Work-27 включает бригаду один раз, когда итог актуален, все текущие отчёты
  группы приняты и ключ позиции/раздела/единицы единственен. Неподанные участники не блокируют это;
  их поздняя подача делает итог устаревшим. Сборщик не распределяет исключённый объём и не суммирует
  строки участников. При исключениях сервер отдаёт `partial`, сохраняет включённые объёмы и причины.
  Отсутствие включённого объёма при исключениях не означает достоверный ноль.
- **Охват предупреждений.** Классификацию целой группы выполняет Work-27 до отбора по позициям/разделу.
  Диагностика относится ко всей стройке и запрошенному периоду; её охват явно подписан даже на экране
  раздела. Отчёты, группы и строки имеют разные единицы счётчиков; причины не складываются в ложный
  общий итог. Для держателя одного `work.facts.read` нет имён, ID отчётов и ссылок в закрытые карточки.
  `GET /api/constructions/{id}/progress` фильтруется по разделу и показывает текущий факт за весь период.
  В `factDiagnostics.scope` обе даты `null`. Закрытый или выключенный факт не отдаёт `factDiagnostics`.
- **«Колонка Хода работ».** `[ModuleContract("Колонка Хода работ", Many = true)]`
  `IProgressContribution.ReadAsync(ModuleReader, constructionId, sectionId?, ct)` →
  `columns: [{code, title, kind, values: [{planItemId, value}] | Hidden | NotAvailable(reason)}]`,
  `strips: [{code, text, link?, state}]`, `planItemIds: [ids]` — позиции, доступные читателю.
  Код колонки уникален внутри вклада. В `columns[].code` и `rows[].cells` ядро добавляет к нему код
  поставщика (`plan:estimate`), а встроенная колонка сохраняет код `fact`. Совпадение локальных кодов
  у разных поставщиков даёт отдельные колонки. Повтор кода внутри вклада отвергается.
  Числовые объёмы позиций одной строки суммируются. Если чисел нет, объём остаётся `null`.
  Даты объединяются по крайним границам.
- **Сборка ядром.** Строки — объединение позиций перечня всех вкладов и фактов, сгруппированных по виду
  работы и единице: строка без пары остаётся. Колонка факта — ядро само спрашивает «Фактические работы»;
  полоса затрат — «Фактические затраты». `NotConnected` даёт строку «учёт работ не подключён» вместо
  колонки факта (`PLAN-21`) и «затраты: модуль „Счета и накладные“ не подключён» — словами из ответа
  контракта, ядро имён модулей не знает.
  `CoreDirectoryRoutesTests` учитывает этот конкретный адрес чтения по стройке. Адресами модулей и
  операциями над их записями маршрут не распоряжается.
- **Отбор по разделу.** Ядро сверяет принадлежность раздела стройке. Факт отбирается по разделу строки
  факта, план — по долям распределения (`plan-23`, `plan-10`). План может ссылаться на позицию всей
  стройки, поэтому ядро проверяет принадлежность позиции стройке и сохраняет отобранную поставщиком долю.
  Нераспределённое — полосой `plan`, а не строками раздела (`PLAN-5.1`).
- **Вклад `plan`.** Колонка «план по смете» — объём из «Плановых работ» тем же провайдером, в правах
  читающего (`plan.estimate.read`); «срок по графику» — самое раннее начало и самое позднее окончание
  работ всех графиков стройки по позиции (`plan.schedule.read`). Полосы: «план по: смета „…“ ред. N» по
  каждой смете (`PLAN-5.2`), «строк сметы не сопоставлено: N ▸» (`PLAN-6.1`), «не распределено по
  разделам: N м по K работам — план всей стройки ▸» при отборе по разделу. Долю раздела
  и предупреждение по стройке читаем в одном снимке. Разные единицы показываем отдельными полосами.
  Ссылка на редакцию использует существующую карточку сметы с параметром `revision`.
  Счётчик несопоставленных относится ко всей стройке. Из полосы есть переход к каждой действующей
  редакции, вошедшей в него, с отбором `queue=unmatched`. Счётчик и ссылки читаются в одном снимке.
  Дополнительный признак `PlannedItem.HasVolume` различает отсутствующий объём и явный ноль.
  Существующие `Volume` и `WithoutVolume` сохраняют семантику контракта.
- **Факт в графике (`PLAN-18`).** Ответ графика (`plan-19`) получает у работы `fact: {volume, state}`:
  по позиции работы и её разделу, без часов. `state`: `ok` | `partial` | `not-connected` | `hidden`.
  Чтение в `GET /api/plan/schedules/{id}` вызывает Work один раз для всех позиций и учитывает точный
  раздел, включая `null` для стройки в целом. При `hidden` `fact.permission` называет право. При
  `partial` возвращается включённый объём, если есть. `factDiagnostics` один на график и явно называет
  охват стройки за весь период. У работ без включённых записей `fact.volume` остаётся `null`.
  После записи графика клиент обновляет его через `GET` и сохраняет прочитанный факт до ответа.
- **Ворота.** `GET /api/constructions/{id}/progress` — «любое из» (`plan-02`), но список в ядре литералом
  не пишется: ядро собирает его при сопоставлении адресов из вкладов включённых модулей (П0, Архитектор).
  - Каждый поставщик называет права, под которыми отдаёт данные: `IProgressContribution` — права своих
    колонок и полос (`plan` — `plan.estimate.read`, `plan.schedule.read`); поставщик «Фактических работ» —
    `work.facts.read` (`work-27`); поставщик «Фактических затрат» — `costs.totals.read` и
    `costs.report.read` (`plan-24`).
  - Почему не литерал: `Declared()` (`PermissionPolicies.cs:72`) сверяет код со справочником ядра и
    включённых модулей. Work теперь уже реализован, но может быть выключен на отдельной установке.
    Литеральное требование его права сломало бы такой состав. Так в ядре нет чужих кодов и развилки
    «выключенный модуль или опечатка».
  - Пустой список (нет ни одного вклада) — адрес закрыт всем (403), а не отказ при старте.
  - Пункт «Ход работ» в карточке — литеральный список всех пяти прав: на клиенте невыданное право просто
    не засчитывается, а `missingFor` не называет коды модулей, которых нет на экземпляре (`plan-02`).
  - Адрес только читает: `If-Match` не нужен.
- **Раздел ядра `progress`.** `CoreSections.Progress = "progress"` и `All` — здесь, первым потребителем.
  Панель «Ход работ» называет `section: 'progress'` (реестр панелей `plan-02`, блок «Работы»). Раздел
  объявляет модуль, который вкладывает в «Ход работ»: `plan`, `costs` и `work` — здесь одновременно с
  появлением раздела и с сохранением существующих разделов, включая `employees`. Work-27 не зависит от
  этого экрана. Модуль `id` не объявляет: «Инженер ИД» видит «Ход работ»
  во «Всех модулях», а в пространстве «ИД» — нет. Отбор «виден, если пространство включает модуль любого
  из прав» отвергнут: второй механизм рядом с `section`, смешение доступа и пространства (`AUTH-16.2`), и
  право контракта `costs.totals.read` модуль `costs` не открывает (`plan-21`), а такой отбор его засчитал
  бы.
- **Синтетический факт (`STG-6.1`).** В тестах — пробный модуль с кодом `work`, регистрирующий
  `IActualWorks` с засеянными фактами, в отдельном составе без production Work. Дополнительно обязателен
  настоящий Work с принятыми отчётами и сверенной бригадой; две реализации одновременно не регистрируются.
  Живой прогон проверяет и настоящий факт, и отдельный режим без Work с «учёт работ не подключён».
- **Экран (PR 3).** Макеты П5: три варианта на живой локальной дизайн-системе, выбор владельца,
  ссылка — здесь. Во всех вариантах есть неполный факт, причины и охват счётчиков, несметная работа,
  чтение только с контрактным правом, узкий экран и обе темы. Таблица — `DataGrid`;
  полосы — общий компонент состояния (`hidden`, `not-connected`, `not-tracked`) из `shared/ui`; минимальная
  ширина 1280.
- **Сторож.** `ConstructionProgressTests`: пробный `work` с фактом по позиции без плана — строка есть,
  план пуст; позиция плана без факта — строка есть; `work` выключен — полоса «не подключено», колонки
  факта нет; без `plan.estimate.read` — колонка плана «скрыто правами»; отбор по разделу — полоса
  нераспределённого и предупреждения Work-27 с широким охватом. На настоящем Work: 120/120/100 → 120,
  частичная приёмка → исключение, разные позиции → исключение, поздняя подача → stale, исправление
  заменяет текущий факт; несметная позиция сохраняется. `PlanProgressContributionTests` — действующая
  редакция в полосе и число несопоставленных.
- **Последовательность PR.** Каждый следующий PR начинается только после слияния предыдущего,
  подтверждённого коммита повышения версии и обновления базы. Локальный WIP прежнего Plan-25
  пересматривается по этому плану, а не переносится вслепую.
- **Чем ломается.** Строки — только позиции плана: факт без плана пропадает. Колонка факта без
  поставщика — нули.

## Risks / Trade-offs

- [Часть бригадных итогов нельзя отнести к позиции] → согласованный минимальный Work-27 исключает их
  с причинами. Экран показывает неполноту, а не обещает все фактические объёмы; ручная разноска вне change.
- [Экран тяжёлый на большой стройке] → вклады читают агрегаты по позиции, а не строки; адрес без
  пагинации, потому что строк — виды работ стройки, а не документы.
