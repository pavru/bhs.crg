# Design: правило `Suggestable` и тэг `input.noSuggest`

Общая архитектура — `../suggest-00-epic/design.md` (D3, D4, D11). Здесь только решения этого change.

## Context

- Поле схемы на сервере — `SchemaFieldInfo` (`Application/Schema/DocumentTypeSchemaReader.cs:26`): вид,
  `Computed`, `Locked` — но **без тэгов**; тэги поля читает `SchemaTags` (`Application/Schema/
  SchemaTags.cs`), у `identity` с номером компонента (`identity:1`) — сравнивать по коду тэга, без
  номера (`tagCode` в `shared/api/tags.ts:31`).
- Реестр тэгов — `TagRegistry.cs` (запись: код, подпись, описание, `TagScope`, допустимые виды,
  `Multiple`, группа); `GET /api/tags` отдаёт `TagCatalog.All` (`Api/Endpoints/Schema/TagsEndpoints.cs:14`).
- Образец общего файла случаев — `features/costs/invoiceLineCases.json`: поле `about`, массив `cases`;
  сервер читает его через `RepoPaths.File(...)` (`Tests/Costs/InvoiceLineCasesTests.cs:17`), клиент —
  импортом JSON.
- Сторож круга схемы — `shared/api/schemaRoundTrip.test.ts`: тэги поля там уже в
  `FIELD_WITH_EVERYTHING` (`tags: ['doc.total']`), то есть круг их переносит; нужен случай именно с
  `input.noSuggest`, потому что флажок `suggest-05` будет прятать тэг из списка чипов.
- Что выяснилось сверкой: `work.producesId` объявлен только для `boolean`
  (`TagRegistry.cs:181-184`) — код причины ему не нужен (`type`). Строковые `nomenclature.article` и
  `org.name` появились после согласования; по В-4 (решено 22.10.2026, вариант (а)) оба — тэги
  однозначности с кодами `article` и `orgName`.

## Goals / Non-Goals

**Goals:** одно правило с кодами причин на обеих сторонах; тэг в реестре; расхождение реализаций и
потеря тэга на круге схемы краснеют тестом.

**Non-Goals:** адрес и источники (`suggest-02`); флажок в редакторе типа и скрытие чипа (`suggest-05`);
переопределение тэга в наследнике — не заводится.

## Decisions

- **Где живёт.** `Application/Objects/FieldSuggestions/Suggestable.cs` — чистая статическая функция
  `Reason(string type, bool computed, bool locked, IReadOnlyCollection<string> tags)` → код; рядом с
  будущим запросом адреса (D11 зонтика). Клиент — `shared/api/suggestable.ts`, функция по `SchemaField`.
  Отдельный вход «по полю схемы и тэгам» нужен потому, что `SchemaFieldInfo` тэгов не несёт, а
  расширять широкий тип ради одного читателя — та ловушка, от которой ушли в D4.
- **Порядок проверок — фиксированный и в общем файле.** `type` → `computed` → `locked` → тэги
  однозначности → `manual`. Код — первый сработавший; случай «строка с `identity` и `input.noSuggest`» в
  наборе есть, чтобы порядок нельзя было поменять на одной стороне.
- **Коды — строковые константы, а не числа перечисления.** Их показывает клиент (текст причины по коду в
  `suggest-05`) и сверяет общий файл; число молча сдвинулось бы при вставке.
- **Тэг.** `FunctionalTag.InputNoSuggest = "input.noSuggest"`; в реестре: подпись «Не подсказывать
  введённое ранее», описание — что тэг выключает подсказки поля и что в редакторе он виден флажком, а не
  чипом; `TagScope.Field`, виды `["string"]`, `Multiple: true`, владелец — ядро (выключить ядро нельзя,
  тэг не пропадёт из редактора), группа «Ввод».
- **Общий файл случаев** — `src/client/src/shared/api/suggestableCases.json`: `about`, `cases[]` с полями
  `name`, `field` (`type`, `computed`, `locked`, `tags`), `expect` (код). Случай на каждый код плюс
  порядок и `identity:N` с номером.
- **Итог В-4** (решено 22.10.2026, (а)): `nomenclature.article` → `article`, `org.name` → `orgName` — кодами
  в оба правила и в общий файл, по случаю на каждый.
- **Вид поля под тэгом сервер при сохранении не сверяет** (выяснилось реализацией): `AppliesTo` у
  тэгов поля читает только редактор (`fieldTags` в `shared/api/tags.ts`) — так у ВСЕХ тэгов, см.
  `RoleResolution.cs` у `UnfitBearerProblems`. Заводить общую сверку ради одного тэга — правка для
  каждой схемы заказчика, где тэг уже стоит не на том виде; отдельную только для `input.noSuggest` —
  исключение из общего порядка. Ни то, ни другое не нужно: `input.noSuggest` на `text` безвреден,
  правило отвечает `type` раньше, чем смотрит тэги, — это случай общего файла. Поэтому проверка 1.1
  «сохранение с тэгом на `text` отклоняется» заменена этим случаем.
- **`employee.account` не однозначный в правиле**, хотя значение у каждого сотрудника своё: поле
  `УчётнаяЗапись` заперто ядром (`CoreRecordTypes`, `Locked: true`), его отсекает `locked`. Решение
  записано в переписи с причиной.
- **Чем ломается.** Код причины, добавленный в C# без зеркала, — красный клиентский тест на общем файле,
  и наоборот. Пропуск тэга при разборе схемы — красный `schemaRoundTrip.test.ts`. Тэг, объявленный без
  записи в реестре, — отказ старта (`TYPE-2`, неизвестный тэг).

## Risks / Trade-offs

- [Новый тэг однозначности объявят, а в правило не впишут — поле станет подсказываемым молча] → в
  описании `FunctionalTag` у раздела однозначности — ссылка на правило; тест перечисляет строковые тэги
  ядра поимённо и требует для каждого решения «однозначный / нет» (перепись по образцу инвентарных).
