# Spec Delta: core

## ADDED Requirements

### Requirement: [CORE-24.1] [CORE-24.2] Метаданные изолированного источника без содержимого
Системный источник с изоляцией по пользователю SHALL сохранять описание колонок без примеров значений, строк и количества строк конкретного читающего. Создание, мост таблицы и обновление метаданных MUST соблюдать это правило. Данные и актуальное число строк SHALL вычисляться при чтении с параметром доступа.

#### Scenario: Прямое создание и мост
- **WHEN** пользователь создаёт изолированный источник из кандидата или экрана таблицы с уникальной меткой в значении строки
- **THEN** сохранённые метаданные не содержат метки, примеров и снимка числа его строк
- **AND** разрешённое чтение получает актуальные строки того же поставщика

#### Scenario: Обновление и другой читающий
- **WHEN** источник обновляют и затем читает пользователь с другим охватом
- **THEN** обновление не сохраняет примеры, а второй пользователь получает только свою выдачу и её число

#### Scenario: Обычный источник
- **WHEN** обновляют обычный файловый источник без изоляции
- **THEN** его прежнее поведение кэширования сохраняется

### Requirement: [CORE-24.2] [WORK-39] Очистка прежних метаданных Work
Обновление экземпляра и восстановление копии SHALL очищать автоматически сохранённые значения и пользовательские счётчики источников таблиц Work до открытия доступа к ним. Операция MUST быть повторяемой и сохранять идентичность источника, выбранные колонки, пользовательские настройки обработки и связи.

#### Scenario: Источник до исправления
- **WHEN** обновляют экземпляр с источниками work.reports и work.lines, содержащими примеры строк
- **THEN** примеры и прежние пользовательские счётчики очищены, фильтры, сортировка, идентификаторы и связи сохранены

#### Scenario: Восстановление и выключенный модуль
- **WHEN** восстанавливают старую копию с такими источниками, в том числе при выключенном Work
- **THEN** до выдачи метаданных копии содержимого очищены; повтор процедуры не меняет уже очищенные данные

### Requirement: [CORE-28] Очистка прежних копий содержимого Work
Только адресная процедура обновления или восстановления SHALL заменять свободные тексты возврата и исправления Work в общем аудите безопасными метаданными. Она MUST сохранять записи, авторов, время, цели, каналы и серии; другие события не изменять. Обычные API и операции записи MUST NOT получать возможность менять аудит.

#### Scenario: Прежний аудит
- **WHEN** процедура обрабатывает события work.report.returned и work.report.corrected с прежним свободным текстом
- **THEN** текст удалён из общей записи, её идентичность и метаданные сохранены, оригинал в журнале или версии Work не изменён

#### Scenario: Повтор и посторонняя запись
- **WHEN** процедуру повторяют рядом с событием другого модуля
- **THEN** очищенные записи не меняются и постороннее событие остаётся побайтово прежним

#### Scenario: Запрет обычной правки
- **WHEN** обычный код пытается изменить или удалить запись аудита
- **THEN** прежний запрет и проверка неизменяемости продолжают действовать

## MODIFIED Requirements

### Requirement: [CORE-28] [CORE-28.1] Журнал действий
Журнал действий SHALL быть одной службой ядра (`activity`, адреса `/api/activity` под правом
`core.audit.read`). Запись несёт время, код действия из каталога, автора и цель снимком имени, прежнее
и новое значение и канал: `ui` (интерфейс и API), `mcp` (агент через MCP) или `system` (сам экземпляр).
Канал служба берёт из контекста действия, а не у вызывающего; записи MUST только дописываться, кроме адресной очистки прежних копий содержимого Work по правилу ниже.

#### Scenario: Попытка правки записи
- **WHEN** код пытается изменить или удалить запись журнала
- **THEN** `SaveChanges` отвергает это, а обращения к набору перечисляет `ActivityLogInventoryTests`

#### Scenario: Смена ролей
- **WHEN** администратор меняет роли пользователя
- **THEN** после удавшегося действия журнал получает запись с прежним составом ролей

#### Scenario: Действие в интерфейсе
- **WHEN** сотрудник меняет роль пользователя в интерфейсе
- **THEN** запись журнала несёт канал `ui` и его имя автором

#### Scenario: Действие системы
- **WHEN** при старте замечена смена состава модулей
- **THEN** запись журнала несёт канал `system` и автора «Система»

#### Scenario: Фоновая задача
- **WHEN** фоновая задача, поставленная запросом через MCP, пишет журнал
- **THEN** запись несёт канал `mcp` и автором — сотрудника, от имени которого задачу поставили, с
  пометкой задачи в имени

#### Scenario: Записи до появления канала
- **WHEN** экземпляр обновляется до версии с каналом, или восстанавливается копия, снятая до неё
- **THEN** записи без автора получают канал `system`, остальные — `ui`
