# Design: сопоставление видов работ и материалов

Дочерний change зонтика `plan-00-epic`, общая архитектура — `../plan-00-epic/design.md` (D7, D8, D17).
Здесь только решения этого change.

## Context

Сверено по коду master `6b81e51e`.

- Образец запоминания — `Modules.Costs/Data/SupplierMatch.cs`: своя таблица модуля, ключ — отпечаток
  SHA-256 приведённого текста (`KeyHashLength`, стр. 45), вид ключа «код старше наименования»
  (`SupplierMatchKind`, стр. 8-15). Запоминание — `Endpoints/SupplierMatching.cs:251`
  (`RememberAsync`, с повтором при гонке), подстановка — `RecallAsync` (стр. 152), список и «забыть» —
  `Endpoints/SupplierMatchListEndpoints.cs:39-59`, правка с `If-Match` (стр. 256).
- В `SupplierMatch` коэффициента пересчёта нет нарочно (комментарий стр. 30-32). Здесь он обязателен:
  расценка и классификатор считают в разных единицах.
- `ВидРаботы` несёт обязательную единицу по умолчанию (`Application/Documents/CoreRecordTypes.cs:117-150`);
  `ЕдиницаИзмерения` кратности не несёт (`CoreRecordTypes.cs:42`).
- Похожие позиции номенклатуры — `IModuleCatalog.SimilarAsync` (`BHS.CRG.Modules/Ports/IModuleCatalog.cs:248`)
  по роли `role.nomenclature`; модуль объявляет роль в `IAppModule.Needs`.

## Goals / Non-Goals

**Goals:** запомненное сопоставление шифра и ресурса; коэффициент пересчёта; позиция перечня в единице
классификатора; массовое сопоставление по разделу ЛСР.

**Non-Goals:** экран (`plan-09`, макеты П1); перенос распределения (`plan-10`); заявки на материалы
(`plan-26`).

## Decisions

- **Ключ сопоставления шифра** — приведённый шифр расценки (верхний регистр, без пробелов и
  неразрывных пробелов) плюс нормативная база, если файл её называет: «ГЭСН08-02-001-01» в ФЕР и в ФСНБ —
  одна работа, но единицы сборников могут различаться. Отпечаток — как у `SupplierMatch`. Ключ без
  поставщика: шифр — общий язык сборника, а не отдельной сметы.
- **Нормативная база в ключе** (решение владельца 25.10.2026, вариант А) — `RegionInfo/@RegionName` файла
  до первой скобки: «ГЭСН-2020, ФЕР-2020 (с Изм. 1-9) …» → «ГЭСН-2020, ФЕР-2020», «ФСНБ-2022 (с Изм. 1-18.1)»
  → «ФСНБ-2022». Номер изменений в ключ не входит. Значение как в файле хранит редакция
  (`estimate_revisions.normative_base`, читает `LocalEstimateReader`), приведение — одно место,
  `RateMatchKey.BaseOf`. Другого поля, называющего базу, в образцах нет: `FRSN_Info/@BaseType` у всех — GSN.
  Почему не другие варианты:
  - **Б** (`RegionName` целиком, с изменениями) — каждое выпущенное изменение базы стирало бы всю память,
    хотя шифры и единицы между изменениями почти всегда те же; редкую смену единицы и так ловит
    `unit-changed`.
  - **В** (`Position/@DBComment`, приказ сборника) — это реквизит сборника, а не базы: в одной смете
    позиции разных приказов (876/пр, 747/пр, 696/пр), ключ дробился бы по ним, а новый приказ на сборник
    терял бы память.
  - **Г** (без базы, только шифр) — ФЕР и ФСНБ делили бы одну запись: выбор в одной базе перезаписывал бы
    выбор в другой, а `unit-changed` ловит лишь смену единицы, не различие самих норм.
- **Значение** — вид работы, единица классификатора (по умолчанию — единица вида работы, можно другую:
  «прокладка кабеля, м» и «…, шт» — разные позиции, `CORE-10`), коэффициент (десятичный, > 0) и единица
  расценки, от которой он считался. Расхождение единицы расценки в новом файле с записанной — запомненное
  не подставляется, строка получает пометку `unit-changed` (D17).
- **Объём позиции** = объём строки × коэффициент. Объём строки сметы хранится как в файле: смета остаётся
  свидетельством ЛСР; пересчитанный объём — поле сопоставления строки, его читают контракт и «Ход работ».
- **Подстановка при импорте** — реализация точки `IEstimateRowMatcher`, которую `plan-07` оставил пустой:
  запомненное по шифру и по наименованию ресурса подставляется в строки редакции до её записи.
- **Позиция перечня** заводится портом `plan-04` при сопоставлении — до записи сопоставления; повтор
  безопасен. Строка без раздела стройки даёт позицию «стройка в целом»; позиции по разделам распределения
  — `plan-10` и график (D7).
- **Зафиксированная редакция** (решение В-6 (а)): сопоставить несопоставленную — можно,
  это не меняет ни объёмов, ни цен производных; пересопоставить — 409 «редакция зафиксирована: <КП/график>,
  пересопоставление — новой редакцией».
- **Массовое действие** «сопоставить раздел ЛСР» — одним запросом, ответ — сколько строк сопоставлено,
  сколько пропущено и почему (`differentUnit`, `alreadyMatched`).
- **Материалы.** Ключ — код ресурса из файла (если есть) старше наименования, как `SupplierMatchKind`.
  Значение — номенклатура. Новая позиция номенклатуры — только явным действием после показа похожих
  (`COST-7.1`); запомненное — с пометкой и отменой.
- **Адреса** (`/api/plan/…`, ворота модуля и `plan.estimate.edit`; чтение списков — `plan.estimate.read`):
  - `PUT /api/plan/revisions/{id}/lines/{lineId}/match`, `POST /api/plan/revisions/{id}/sections/match`;
  - `PUT /api/plan/revisions/{id}/resources/{resourceId}/match`;
  - `GET/PUT/DELETE /api/plan/rate-matches[/{id}]`, `GET/PUT/DELETE /api/plan/resource-matches[/{id}]`.
  Правка строки — `If-Match` версии редакции; правка запомненного — `If-Match` версии записи
  сопоставления. Без заголовка — 400, устаревший — 409.
- **Запоминание** — после записи сопоставления строки, вне её транзакции, с повтором при гонке
  (`RememberSafelyAsync`): сбой запоминания не отменяет сопоставления, ответ называет его (`memory.failed`).

## Risks / Trade-offs

- [Коэффициент введён неверно — план в 100 раз больше факта] → коэффициент предлагается из единиц
  («100 м» → «м» = 100), ответ несёт обе единицы; сторож на «100 м → м».
- [Один шифр в разных сметах — разные виды работ] → запомненное только предлагается, с пометкой и
  отменой; «перенацелить» в списке.
- [Пересопоставление ломает график] → в зафиксированной редакции запрещено (В-6).
