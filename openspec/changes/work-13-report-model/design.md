# Design: отчёт монтажника — модель, строки и протокол на будущее

Общая архитектура — `../work-00-epic/design.md` (D1, D4, D7, D9). Здесь только решения этого change.

## Context

- Схема `work`, назначения и порты ядра — `work-10` и `work-11`. Параметр доступа и перепись
  изолированных таблиц — `work-07`. Варианты вида работ — `work-06`.
- Позиция перечня уже есть таблицей ядра, но без правила «найди или создай»: оно ждёт первого
  вызывающего (`src/server/BHS.CRG.Domain/Documents/WorkPlanItem.cs`, комментарий о `CORE-12`;
  `src/server/BHS.CRG.Application/Documents/WorkPlanItems.cs` — только удаление). Правило строит этап 3
  с импортом смет. `ReferenceTarget.WorkPlanItem` в контрактах уже объявлен
  (`src/server/BHS.CRG.Modules/Data/ModuleReference.cs:17`).
- Закрытого типа живьём ещё нет: `costs` объявляет только `Extendable` и `Open`
  (`src/server/BHS.CRG.Modules.Costs/CostsRecordTypes.cs:100,173`). Проекция уровня —
  `src/server/BHS.CRG.Api/Modules/ModuleTypeProjector.cs:148-150`.
- Клиентских идентификаторов, повтора и курсора в системе нет нигде. Это первый протокол для этапа 5.

## Goals / Non-Goals

**Goals:**
- Модель отчёта и строки, которую этап 5 не мигрирует.
- Свои отчёты с изоляцией.
- Позиция перечня из строки.
- Первый закрытый тип живьём.

**Non-Goals:**
- Статусы кроме «черновика», подача, окно, автоподача — `work-15`.
- Журнал отчёта — `work-14`: здесь только протокол изменений.
- Чтение чужих отчётов менеджером и руководителем (очередь, карточка), приёмка — `work-16`. Здесь
  менеджер видит только отчёты, введённые адресами ввода за сотрудника на своих стройках.
- Правила участников бригады («назначен на ту же стройку на ту же дату») — `work-18`.
- Фото — `work-17`.
- Экран — `work-22`.
- Подсказка материалов — `work-26`.

## Decisions

### Состав PR

**PR 1 — «модель».**
- Таблицы:
  - `work.reports`: `id` (от клиента), `employee_id`, `construction_id`, `date`, `shift`, `hours`, `status`
    (пока только `draft`), `note`, `seq`, `xmin`; уникальный индекс `(employee_id, construction_id, date,
    shift)`;
  - `work.report_lines`: `id` от клиента, `report_id`, `work_type_id`, `variant_id`, `volume`, `unit_id`,
    `section_id`, `location`, `comment`, `is_crew`, `work_plan_item_id`, `details` JSONB;
  - `work.report_line_materials`: `line_id`, `nomenclature_id`, `note`;
  - `work.report_line_participants`: `line_id`, `employee_id`;
  - `work.report_changes`: `report_id`, `change_id`, `seq`, `device_time`, `server_time`, `kind`, `version`
    после правки, `IAppendOnly`.
- Миграция `Reports`.
- `WorkRecordTypes.cs`: `ОтчётМонтажника` (`ModuleSchemaLevel.Closed`) и `СтрокаРаботы.Сведения`
  (`Extendable`) с системными полями.
- `WorkReferences.cs`: все колонки-ссылки; JSON `details` объявлен держащим с `Target: null`.
- `Data/ReportRules.cs` — проверки строки (вариант своего вида, раздел своей стройки, материал по
  номенклатуре, участники только у бригадной строки, архив). Это чистые функции, тесты без хоста.
- `Data/WorkPlanItemLink.cs` — позиция перечня через порт этапа 3.

**PR 2 — «адреса и протокол».**
- `Endpoints/ReportEndpoints.cs`:
  - `GET /api/work/reports?since=&limit=`;
  - `GET`, `PUT`, `DELETE /api/work/reports/{id}`;
  - `POST /api/work/reports`.
- Повтор по `id` и `changeId`, курсор `since`, `deviceTime`, `assignedOnDate`, изоляция через параметр
  доступа (`work-07`, вид «свои»).
- `Endpoints/EntryReportEndpoints.cs` — ввод за сотрудника (`WORK-31`):
  - `POST /api/work/entry/reports`;
  - `GET` и `PUT /api/work/entry/reports/{id}`.

  Адреса стоят под `work.report.review`. Параметр доступа — вид «стройки» (`work-11`, `ManagerSites`); с
  `work.sites.all` — все стройки. Сотрудник берётся из тела, автор ввода — из учётной записи. Поле
  `enteredBy` хранится колонкой `reports.entered_by_user_id` с именем снимком, журнал `work-14` пишет
  `enteredFor`.
- Отдельная группа адресов, а не флаг в `/api/work/reports`: право и вид доступа у них разные. Перепись
  ворот видит каждую группу со своим правом. Один адрес с двумя ветками прав спрятал бы ветку «чужой
  сотрудник» от переписи.
- Стройка вне своих — 404 и на заведении. По запросу экрана `work-22` ответ различим с отсутствием
  стройки только текстом причины.

### Позиция перечня — порт этапа 3 с безопасным повтором (D9)
- Порядок: сначала позиция в ядре («найди или создай» по уникальному ключу), потом строка в схеме модуля.
  Общей транзакции нет (`CORE-4`). Упавшее сохранение строки оставляет позицию без ссылок — это
  допустимое состояние перечня: повтор найдёт её же.
- Имя порта — каким его заведёт этап 3; рабочее — `IModuleWorkPlanItems.FindOrCreateAsync(workTypeId,
  constructionId, sectionId, unitId)`.
- Сторож — тест «две параллельные строки одного ключа — одна позиция» и тест сбоя между ядром и модулем.
- **Условие.** Если этап 3 порт не завёл, перед PR 1 идёт отдельный PR ядра с этим портом и дельтой
  `core` к `CORE-10`/`CORE-12`. Тогда этот change сначала дополняется (`design.md`, `tasks.md`), потом
  пишется код (`config.yaml`, `operations.apply`).

### Протокол повтора (MOB-15, MOB-16, MOB-17)
- **Заведение** — `POST` с `id` в теле. Тот же `id` того же сотрудника — 200 с лежащим отчётом и признаком
  `replayed: true`. `id` чужого отчёта — 409 «идентификатор занят» без полей. Идентификатор — UUID от
  клиента, подобрать чужой нельзя. Ответ «занят» говорит лишь, что значение использовано, а 404 на
  заведение читался бы как «адрес не найден».
- **Правка** — `PUT` с `If-Match` и `changeId`. `changeId` уже есть в `report_changes` этого отчёта — ответ
  строится по текущему состоянию с версией из той записи. Повтор не применяется и не получает 409.
- **Последовательность** — sequence `work.report_seq`. Номер получает каждое изменение, и он же пишется в
  `reports.seq`. `since` читает `report_changes` по `seq`; удалённые черновики берутся оттуда же (`kind =
  deleted`).
- **Время** — `deviceTime` из тела. В вебе это время браузера. Нет поля — время сервера с пометкой
  «устройство не назвало». Отказа нет.

### Свои отчёты и изоляция (D4)
- Сотрудник отчёта — из связи учётной записи (`work-01`) через `IModuleEmployees`. Тело его не задаёт.
- Чтение — только методом с параметром доступа (`work-07`): `DbSet<Report>` не выставлен, перепись
  `work-07` ловит `Set<Report>()`.
- Чужой и несуществующий отчёт дают один ответ 404 одним путём кода (`ReportAccess.FindOwnAsync`), чтобы
  ответы не разошлись.

### Архив и ссылки (CORE-34.1, CORE-34.4)
- Новые ссылки сверяются через `IModuleReferenceTargets.StatesAsync`, как у счёта
  (`src/server/BHS.CRG.Modules.Costs/Endpoints/InvoiceDesk.cs:352-377`). «Новая» — значение, которого не
  было в этой колонке этой строки до правки.
- Сведения строки идут через `IModuleWriteGuard`. Сторож — `RecordWriteGuardCoverageTests`.

### `assignedOnDate` (MOB-21)
Считается на чтении по назначениям `work-11` и не хранится: назначение могут поправить задним числом.
В веб-форме выбор стройки ограничен назначенными (`work-22`), сервер не отказывает.

### If-Match
Через `SeenVersion`, как `src/server/BHS.CRG.Modules.Costs/Endpoints/InvoiceDesk.cs:242`. Исключение — `POST`
заведения: прежней версии нет, от дубля защищает клиентский `id`.

### Сторож и «чем ломается»
- **Сторож:** повтор `POST` и `PUT` не дублирует; чужой отчёт по `id` — 404; закрытый тип отклоняет новое
  поле.
- **Чем ломается:**
  - ключ без смены — ночная смена затирает дневную, тест двух смен краснеет;
  - `HasQueryFilter` вместо параметра — фоновое чтение `work-15` видит ноль строк.

### Зависимости
- `work-11` (сотрудник, назначения, `assignedOnDate`).
- `work-06` (варианты).
- `work-07` (параметр доступа и перепись).
- Этап 3 (порт позиций).

## Risks / Trade-offs

- [Закрытый тип впервые живьём (`CORE-19.2`)] → PR 1 проверяет уровни правки на `ОтчётМонтажника`
  тестами `SchemaEditLevelTests`, а не только на поддельном типе.
- [`report_changes` растёт с каждой правкой] → строка узкая, без содержимого. Содержимое правки пишет
  журнал `work-14`. Чистка — вопрос этапа 5, когда появится настоящий объём.
- [Удаление черновика — потеря для журнала] → удаление пишется в `report_changes` и журнал ядра. Запись
  журнала `work-14` за удалённый отчёт остаётся: она только дописывается.
