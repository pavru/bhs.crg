# Design: приёмка отчётов и очередь с пометками

Общая архитектура — `../work-00-epic/design.md`. Здесь только решения этого change.

## Context

- Отчёт, его строки, адреса правки и `version` — `work-13`; журнал отчёта на дописывание — `work-14`;
  статусы `WORK-9`, окно подачи и такт автоподачи — `work-15` поверх `work-08`.
- Параметр доступа (D4, `work-07`) и «стройки менеджера» из назначений (D5, `work-11`) уже есть: этот
  change их только применяет.
- Порт уведомлений `IModuleNotifications` (`src/server/BHS.CRG.Modules/Ports/IModuleNotifications.cs`)
  принимает либо `audience`, либо `userId`; потребителей у порта пока нет — этот change первый.
  Переходник — `src/server/BHS.CRG.Api/Modules/Ports/ModuleNotificationsPort.cs`.
- Проверка версии — образец `src/server/BHS.CRG.Modules.Costs/Endpoints/InvoiceDesk.cs:242`
  (`EnsureSeen`): заголовок читает общее место, `*` — отказ.

## Goals / Non-Goals

**Goals:** серверная приёмка и очередь, на которых `work-21` строит экраны без единого вычисления на
клиенте.

**Non-Goals:**
- экраны очереди и карточки — `work-21` (макеты Р4);
- коды `crew-mismatch`, `accepted-changed`, `fields-missing` — `work-18`, `work-19`, `work-24`;
- настоящая «поздняя доставка» — этап 5 (`WORK-58`); код заведён, счётчик в вебе всегда 0;
- напоминания `WORK-41` — вынесены.

## Decisions

### Состав PR
- **PR 1 — действия.**
  - `Review/ReportReviewEndpoints.cs`: `accept`, `return` под `perm:work.report.review` в группе `/api/work`.
  - Правка строк менеджером — тот же адрес строки, что у `work-13`. Ветка прав выбирается по виду
    доступа: свой отчёт или отчёт своей стройки.
  - `acceptWouldMark` считается в одном месте: `enteredBy == viewer`, автор ввода — поле `work-14`.
  - `Review/SubmittedDigest.cs` — сводка о поданных; `Review/ReturnNotice.cs` — личное уведомление.
  - Записи «принят», «возвращён», «правка менеджером», «ввёл и принял один человек» — в журнал отчёта
    одним `SaveChanges` с отчётом (D10). Дубль в журнал ядра — через `IModuleActivityLog`, коды — в
    `IModuleActivityActions` модуля.
- **PR 2 — очередь.**
  - `Review/ReviewQueue.cs`: `GET /api/work/review/queue`; чтение — только методом с параметром
    доступа (D4).
  - `Review/ReviewMarks.cs` — каталог кодов: код, текст, источник.
  - Типы и `WORK_MARK_CODES` — в `src/client/src/shared/api/work.ts`.

### Каталог пометок — открытый перечень на сервере
Код пометки — постоянная строка, текст — для человека. Каждая пометка в каталоге объявляет, из каких
данных она считается. Счётчики `counts` считаются запросом по всему отбору, а не по странице. Приходят
все коды каталога, и нулевые тоже: отсутствие кода иначе читалось бы как «не знаем».

`photos-pending` заводится здесь, хотя данные для него приносит `work-17`. До `work-17` фото нет вовсе,
поэтому ноль честен — догружать нечего. `late-delivery` в вебе всегда 0 до этапа 5.

Альтернатива — пометки строкой в ответе без каталога — отклонена: отбор по пометке и счётчик требовали
бы от клиента знать тексты.

### Права действия — по стройке, а не по праву
Право `work.report.review` проверяют ворота. Принадлежность стройки проверяет чтение отчёта с
параметром доступа: отчёт не своей стройки не находится, ответ — 404 (`WORK-39`). Отдельной ветки
«есть право, но не та стройка → 403» нет, поэтому через отказ не узнать, существует ли отчёт.
`work.report.read.all` открывает чтение, но не действия: `actions` у строки пуст, адреса действий — 403.

### Отказ по статусу — 409 со статусом
Приёмка черновика или уже принятого отчёта — 409 с телом `{ status }` и текстом «отчёт в статусе
„черновик“». От конфликта версии он отличается кодом причины в теле. Иначе экран сказал бы
«обновите страницу» там, где обновление ничего не изменит.

### Уведомления (D16, `WORK-56`)
- **Возврат.** Личное, `userId` учётной записи сотрудника-исполнителя (связь `work-01`). Нет связи —
  нет уведомления; журнал отчёта говорит «уведомить некого», а не молчит.
- **Сводка о поданных.**
  - Задача той же цели, что такт автоподачи (`work-15`), — второй шаг после подачи.
  - Отбирает отчёты, у которых `review_digest_at` пуст, и группирует их по менеджерам с действующим
    назначением «менеджер» на стройку.
  - Публикует одно личное уведомление на менеджера, затем ставит `review_digest_at`.
  - Повтор безопасен: одна задача на цель (D12). Сбой между публикацией и отметкой даёт повтор сводки,
    а не её потерю — так и задумано.
- Держатели `work.sites.all` без назначения сводку не получают: у администратора было бы уведомление
  о каждой стройке компании.

### Сторожа
- `NotificationAudienceInventoryTests` (`src/server/BHS.CRG.Tests/Configuration/`) уже ловит
  публикацию без адресата. Новых записей «всем вошедшим» модуль `work` не вносит.
- `Work/ReviewDigestTests`: две стройки, менеджер каждой видит только свою сводку. Два прогона такта
  подряд дают одну сводку.
- `Work/ReviewMarkCatalogTests`: коды сервера равны `WORK_MARK_CODES` клиента. Пустой список клиента —
  отказ, а не «расхождений нет» (приём `RecordRoutesTests`).
- `Work/ReviewGateTests`: 403 монтажнику и руководителю, 404 менеджеру чужой стройки, 400 и 409 по
  `If-Match`, 501 при выключенном модуле.

### Чем ломается
- Пометка вычисляется на клиенте — пропадает на странице, где нет журнала.
- Сводка аудиторией `work.report.review` — менеджер стройки Б получает имена монтажников стройки А.
- Проверка стройки после проверки права с ответом 403 — существование чужого отчёта узнаётся
  перебором идентификаторов.

### Зависимости
- `work-13`, `work-14`, `work-15` — обязательно до PR 1.
- `work-11` — стройки менеджера; `work-01` — адресат возврата.
- Этап 3 — не нужен.

## Risks / Trade-offs

- [Сводка за такт у стройки с поясом, отличным от пояса компании, приходит не в полночь компании] →
  так и задумано: такт один, а окна подачи у строек свои. В сводке названы стройки.
- [Каталог кодов дописывают три других change] → код без источника данных не регистрируется. Сторож
  каталога сравнивает и с клиентом, поэтому забытый код клиента виден сразу.
- [Повтор сводки при сбое между публикацией и отметкой] → принят: лишнее уведомление лучше
  потерянного.
