# Design: владелец у файла хранилища

Самостоятельный change ядра. Связь с этапом 4 — `../work-00-epic/design.md` (Risks: фото отчёта
подчиняются изоляции отчёта). Условие безопасности — локальный отчёт аудита, раздел 2.

## Context

- Реестр файлов — `blob_registry` (`Domain/Storage/BlobRegistryEntry.cs`). Наполняет его обёртка
  `Infrastructure/Storage/RegisteredBlobStorage.cs` на каждой записи, читает — на каждом
  `DownloadAsync`. Это одна дверь для всех читателей хранилища (выдача вложения, материализация
  картинок, отладочный ZIP, наборы данных, письма), и её надо сохранить.
- Владельца в реестре нет сознательно (доккомментарий `BlobRegistryEntry`): пользователи — сотрудники
  с равным допуском (#675). Условие пересмотра там же: изоляция появится «целиком и осознанно». Модуль
  `work` и есть этот случай — для файлов модулей, а не для данных ядра.
- Порт модуля `IModuleBlobs` (`Modules/Ports/IModuleBlobs.cs`) — один scoped-сервис на всех
  (`Api/Modules/Ports/ModulePorts.cs:42`, `ModuleBlobsPort.cs`), кода модуля он не знает.
- Скан счёта клиент уже читает адресом модуля (`src/client/src/shared/api/invoices.ts`,
  `loadInvoiceScan`), а не общим адресом. Закрыть общий адрес для файлов `costs` экраны не ломает.
- Читаемый образ офисного файла (`Api/Renditions/RenditionStore.cs:153,235`) — служба ядра, которая
  читает файл `costs` через `IBlobStorage` напрямую.

## Goals / Non-Goals

**Goals:** владелец «ядро | код модуля» у каждой записи реестра; общий адрес и генерация не выдают
файлы модулей; модуль не читает чужие файлы; разовый сбор владельцев.

**Non-Goals:**
- разграничение файлов ядра между пользователями (решение #675 остаётся в силе);
- выдача файлов модуля по построчной изоляции — это дело адреса модуля (`work-17`);
- вставка фото отчёта в документы ИД — через контракт модуля (этап 6), а не путём в реквизитах.

## Decisions

- **Владелец — колонка `Owner` в `blob_registry`**, `core` или код модуля, обязательная. Не отдельная
  таблица: вопрос «чей файл» задаётся на том же чтении, что «наш ли файл», одним индексированным
  запросом.
- **Порт модуля знает свой код по построению.** `IModuleBlobs` регистрируется keyed-сервисом на каждый
  включённый модуль (`AddKeyedScoped<IModuleBlobs>(module.Code, …)`); модуль берёт его как
  `[FromKeyedServices("costs")]`. Без ключа `IModuleBlobs` в контейнере нет — забытая метка даёт отказ
  на старте, а не файл ядра. Альтернатива — код параметром метода — отклонена: модуль мог бы назвать
  чужой.
- **Одна дверь остаётся одной.** `IBlobStorage.DownloadAsync(path)` читает только файлы ядра;
  перегрузка `DownloadAsync(path, owner)` — для порта модуля и служб ядра, читающих от имени модуля;
  резервная копия читает внутренним путём без проверки владельца (она переносит всё). Отказ на чужом —
  то же исключение «нет файла», что сейчас у незнакомого пути.
- **`RenditionStore`** читает оригинал от имени `costs`. Владелец берётся из записи образа, а не
  подставляется строкой в коде службы.
  - *Уточнено при реализации.* Владельца службе называет порт `IModuleRenditions`, и он тоже
    keyed-сервис на модуль — тем же построением, что `IModuleBlobs`: иначе службе неоткуда узнать,
    от чьего имени читать, а порт без кода модуля дал бы модулю `work` образ скана `costs`. Образ
    ложится с владельцем оригинала (модуль открывает его своим портом), запись образа служба
    показывает, только если оригинал принадлежит спрашивающему.
- **Удаление тоже по владельцу** (*уточнено при реализации*). `DeleteAsync(path)` удаляет только
  файл ядра: пути в реквизитах пишет клиент, и удаление документа с вписанным путём скана `costs`
  иначе удалило бы скан. Файл другого владельца остаётся на месте, отказ — в журнал. Порт модуля
  удаляет `DeleteAsync(path, owner)`; уборка осиротевших — от имени владельца из записи реестра.
  Путь вне реестра ядро удаляет, как прежде, а модуль — нет: его файлы значатся в реестре всегда.
  «Любой» на удалении — отказ (ревью PR #1568).
- **Перегрузки с владельцем — без умолчания интерфейса** (*ревью PR #1568*). Умолчание «передать без
  владельца» досталось бы и обёрткам: обёртка, не переопределившая его, молча делала бы владельца
  ядром, и копия теряла бы файлы модулей как «отсутствующие». Владельца отбрасывает только само
  хранилище и его подделки — явно, базовым классом `OwnerBlindBlobStorage`.
- **Свой маркер у резервной копии** — `BlobOwner.Any`: копия читает, измеряет и проверяет файлы
  всех владельцев. Перепись (`BlobReaderInventoryTests`) пускает его только в чтение копии; она же
  следит за удалением и записью с владельцем, не только за чтением (ревью PR #1568).
- **Сбор раздаёт образам владельца оригинала** (*уточнено при реализации*): путь образа лежит в
  таблице ядра `renditions`, и без этого шага образ скана счёта достался бы ядру — модуль перестал
  бы его открывать.
- **«Генерация называет поле»** (*уточнено при реализации*). Канала предупреждений у генерации нет,
  а прежнее решение «одна картинка не роняет документ» остаётся. Материализация собирает адреса
  полей, чей файл не прочитан; отказ компиляции называет их в своём тексте, удачная генерация — в
  журнале. Файл модуля и отсутствующий файл называются одинаково.
- **Разовый сбор владельцев — EF-миграцией ядра**, как `BlobRegistryBackfill`: путь, найденный в
  колонке схемы модуля (`information_schema.columns.table_schema`), получает код этого модуля,
  остальные — `core`. Схема модуля — та, где лежит история миграций EF под стандартным именем
  (*ревью PR #1568*): списка модулей у статичной миграции нет, а любая непубличная схема (расширение,
  оставленная руками) отдала бы своему имени вложения ядра безвозвратно. Стандартное имя истории
  модулю теперь обязательно — `ModuleSchemaMigrator.EnsureHistoryStaysInSchema`. Разово по той же причине, что и сбор реестра: повторный проход по данным, которые
  пишет клиент, позволил бы присвоить чужой файл.
- **Восстановление копии** возвращает владельца из архива; запись копии несёт владельца рядом с путём
  (`BackupManifestCoverageTests`).
- **Право `core.files.use`** остаётся воротами общего адреса и списка профилей печати. Текст
  `CORE-37.2` в ТЗ описывает новое устройство.
- **Сторож.**
  - `BlobOwnerTests`: файл модуля общим адресом — 404; путь файла модуля в реквизитах — генерация
    называет поле; порт `work` не открывает файл `costs`; скан счёта адресом модуля читается.
  - `BlobRegistryOwnerBackfillTests`: сбор на базе с файлами ядра и `costs` раздаёт владельцев верно;
    второй прогон ничего не меняет.
  - Перепись: каждый вызов `DownloadAsync` вне `Storage/` либо без владельца (ядро), либо с владельцем
    из записи — `BlobReaderInventoryTests`.
- **Чем ломается.** Порт без ключа модуля — старт отказывает. Код модуля, негодный владельцем
  (`core`, «любой», пустой, длиннее 64), — тоже старт, а не первая загрузка. Служба ядра, читающая файл модуля без
  владельца, — `BlobReaderInventoryTests` красный. Сбор, запускающийся на каждом старте, — второй
  прогон теста меняет строки.
- **Файлы кода:** `Domain/Storage/BlobRegistryEntry.cs`,
  `Infrastructure/Persistence/Configurations/BlobRegistryConfiguration.cs`,
  `Infrastructure/Storage/RegisteredBlobStorage.cs`, `Application/Common/IBlobStorage.cs`,
  `Api/Modules/Ports/ModuleBlobsPort.cs`, `Api/Modules/Ports/ModulePorts.cs`,
  `Api/Renditions/RenditionStore.cs`, `Infrastructure/Backup/BackupService*.cs`,
  `Infrastructure/Maintenance/BlobRegistryBackfill.cs` (образец сбора),
  `Modules.Costs/*` — места, берущие `IModuleBlobs`.
- **Зависимости.** Ни от этапа 3, ни от других change не зависит. `work-17-photos` не сливается без
  него; `work-05-photo-port` может идти параллельно.

## Risks / Trade-offs

- [Сбор назначит владельцем ядро файлу модуля, путь которого лежит вне колонок схемы модуля] → после
  сбора тест сверяет: каждый путь из колонок `IAppModule.Files` получил владельцем свой модуль.
- [Документы ИД, куда уже вписан путь скана из `costs`] → генерация называет поле; на живой копии базы
  заказчика проверить, что таких реквизитов нет, до слияния.
