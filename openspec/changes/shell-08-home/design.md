# Design: Главная «Продолжить работу»

Общая архитектура — `../shell-00-epic/design.md` (D1 — макет, D2 — решения владельца, D5 — пересечение с
`plan-02`, D6 — живые прогоны). Макет — артборд «B · Главная „Продолжить работу“» канваса варианта B;
выбран решением владельца 17.10.2026. Раздел «Главная» — новый раздел рейла в `shared/ui`: по `docs/UI.md`
(«Новый экран: порядок», шаг 1) до кода — разбор с Архитектором (новый вид раздела без подпанели) и
Дизайнером (что не покрывает макет: телефон, пустые состояния).

## Context

Сверено по коду ветки от master `c9586405`.

- **Маршрут.** Индекс — `<Navigate to="/document-sets" replace />` (`App.tsx:122`; в issue — `:115`).
- **Рейл.** `RailId = 'constructions' | 'data' | 'costs' | 'system'` (`navConfig.ts:42`); раздел без
  страниц не показывается (`buildRail`, `railSections.ts:25`), «куда ведёт раздел» — первая страница
  (`home`). Раздела без подпанели вовсе нет: есть только `panelOnlyAt` (подпанель лишь на одной странице).
  Пункта «Главная» нет — #1429 его не завёл.
- **Очереди счетов** (`features/costs/invoiceQueues.ts`, `shared/api/invoiceQueues.ts`):
  - «Разобрать» — `GET /api/costs/invoices/queues/parsing` (`useParsingCount`), спрашивается у каждого,
    кто видит список (`costs.invoice.read`);
  - «Не распознано», «Удалённые записи», «В архиве» — одним ответом `GET /api/costs/invoices/queues`
    (`useInvoiceQueues`); сервер закрывает его чтением, а клиент спрашивает только при
    `costs.invoice.edit` (`InvoicesPage.tsx:96`): «число без выхода было бы упрёком»;
  - у чисел есть оговорка «проверено не всё» (`doubt`) и «число не пришло» ≠ ноль (`queueChip`).
- **Что выяснилось сверкой:** отбор очереди живёт только в состоянии страницы
  (`useState<InvoiceQueue | 'upload' | null>`, `InvoicesPage.tsx:83`) — адресом очередь не открыть, и
  карточке Главной вести некуда. Нужен параметр `queue` (дельта `costs`).
- **Фоновые задачи** — `useActiveJobs()` (`shared/api/jobs.ts:29`) и строка `JobRow`
  (`features/jobs/JobRow`) — тот же источник у `ActivityCenter` (#1431).
- **Личные настройки** — `UserSettingKeys` (`Application/Settings/UserSettingKeys.cs`), ключи с
  проверкой формы; длинные значения бывают (`workspaces` — 16 000). Зеркало в браузере —
  `useSyncedPreference`, загрузка ничего не отправляет (`CORE-25.3`).
- **Экран записи по коду типа** — `RECORD_ROUTES` (`shared/ui/recordRoutes.ts`): там только счёт.
- **История открытий** не хранится нигде.
- **Пересечение:** `plan-02-navigation` (PR 2) и `work-03-navigation` планируют страницу входа по рангу
  пункта (`entryPage.ts`) на том же индекс-маршруте.

## Goals / Non-Goals

**Goals:** человек после входа видит свои очереди, недавние записи, идущие задачи и три неочевидных
умения; Главная не знает о счетах; ни одного числа, посчитанного вторым способом.

**Non-Goals:**
- очереди других модулей и ядра (подключаются тем же объявлением, когда появятся);
- «закреплённые» записи и избранное на Главной;
- лента событий и уведомления на Главной (у них место — кнопка активности).

## Decisions

### Состав PR
- **PR 1 — Главная и очереди.** Маршрут `/` (по ответу В-1), раздел рейла «Главная», страница
  `features/home/HomePage.tsx`, блоки «Ждут вас», «Выполняется», «Полезно знать» и ключ настройки
  «скрыто»; параметр `queue` у экрана счетов.
- **PR 2 — «Недавние».** Хранение на сервере (по ответу В-3), отметка «открыто» на экранах записей,
  блок на Главной. Можно отдельно и позже PR 1: без него Главная честно показывает остальные блоки.

### Раздел «Главная» без подпанели
`RailId` += `'home'`, первым в `railSections`, `unscoped: true` (пространство его не сужает), новый признак
`panel: false` — подпанели нет нигде (а не «только на одной странице», как `panelOnlyAt`). Пункт
`{ to: '/', label: 'Главная', rail: 'home' }` без права и модуля — открыт каждому вошедшему. Раскладку
сверяет `railSections.test.ts`; правило «Подпанель есть только у разделов со списками» в `docs/UI.md`
дополняется: «Главная — раздел без подпанели». На телефоне — первый пункт `BottomNav` (пять мест
хватает: Главная, Стройки, Данные, Учёт).

### «Ждут вас» — по рекомендации В-2
Клиентский реестр `shared/ui/homeQueues.ts` рядом с `PALETTE_ACTIONS`: модульная часть объявляет
описатели `{ id, label, hint, href, visible(access), useCount() }`; `features/costs/homeQueues.ts`
объявляет четыре очереди счетов, `useCount` — те же `useParsingCount` и `useInvoiceQueues`. Видимость —
то же правило, что у чипа очереди на экране (один источник: функция в `invoiceQueues.ts`).
Число — через `queueChip`: «?» при `doubt`, «не посчитано» при отказе, карточки с нулём нет. Перепись
`homeQueues.test.ts`: у каждой очереди экран принимает её `href` (параметр `queue` в списке значений
экрана) — как `paletteActions.test.ts` для действий.

### «Недавние» — по рекомендации В-3
- Сервер: своя таблица ядра `user_recent_records` (`UserId`, `RecordType`, `RecordId`, `OpenedAt`, ключ —
  первые три; не больше 20 на пользователя, вытеснение старых при записи). Адреса `POST /api/account/recent`
  (`{ recordType, id }`, ответ 204) и `GET /api/account/recent`. Только свои: идентификатора пользователя
  адрес не принимает.
- Чтение разрешает записи владельцем типа: тип ядра — ядро, тип модуля — модуль через объявление «карточка
  записи по идентификатору в правах спрашивающего» (название, раздел, стройка). Это тот же поставщик, что
  отвечает поиску палитры (`shell-05`, В-1): одно объявление «найти» и «показать по id», а не два.
  Нет записи или нет права — пропускается. Выключенный модуль — его записи пропускаются, в таблице
  остаются (включат — вернутся).
- **Исключение из правила `If-Match`, названное:** `POST /api/account/recent` пишет личную отметку
  пользователя, а не запись модуля или общих данных; потерянного обновления нет (последнее открытие —
  всегда верно), запись модуля не меняется. Так же устроены личные настройки (`PUT /api/account/settings`).
- Клиент: хук `useRecentTouch(recordType, id)` на экранах, у которых есть `RECORD_ROUTES` (счёт; дописать
  стройку, комплект, набор данных, шаблон) — зовётся, когда запись показана, не чаще раза на открытие.
  Перепись: каждый экран из `RECORD_ROUTES` отмечает открытие.

### «Выполняется» и «Полезно знать»
- «Выполняется» — `useActiveJobs()` и `JobRow`, без второго запроса; блок пропадает, когда список пуст.
- «Полезно знать» — три строки по правам (сканы — `costs.invoice.edit`); «Скрыть» пишет новый ключ
  `UserSettingKeys.HomeTips` (`home.tips`, значения `shown`/`hidden`) через `useSyncedPreference`.
  Вернуть блок — тем же ключом в профиле («Показывать подсказки на Главной»), иначе «насовсем» было бы
  без выхода.

### Сторож и «чем ломается»
- Vitest: `HomePage.test.tsx` — без прав на модули блоков модулей нет, «Недавние» и «Полезно знать» есть;
  отказ числа — «не посчитано»; все пусты — «Сейчас ничего не ждёт»; `homeQueues.test.ts` — перепись
  приёма адреса; `railSections.test.ts` — «Главная» первой и без подпанели.
- Сервер: `RecentRecordsTests` — повтор поднимает, 21-я вытесняет, удалённая и закрытая не отдаются,
  выключенный модуль, чужого списка не получить; `EndpointGateInventoryTests` — личные адреса.
- Живой прогон: вход → Главная → «Разобрать» открывает очередь «Разобрать»; `limited-smoke.mjs` — роль
  только с накладными не видит карточек счетов; `rail-checks.mjs` — «Главная» на 375/390 px. Плюс весь
  список живых прогонов (зонтик, D6): индекс `/` меняется у каждого прогона, что на него опирался.
- Ломается так: Главная считает число своим запросом (расходится с чипом); карточка с нулём; удалённый
  счёт в «Недавних»; `/` уводит на «Стройки» пользователя без `core.constructions.read`.

## Risks / Trade-offs

- [Живые прогоны и закладки ждут `/` → «Стройки»] → прогоны, начинавшие с `/`, переводятся на явный
  адрес в том же PR; в `docs/USER_GUIDE.md` — что открывается после входа.
- [Отметка «открыто» на каждом показе — лишняя запись] → не чаще раза на открытие записи, ответ 204, без
  ожидания в интерфейсе.
- [Разрешение «Недавних» через модуль ждёт механизма `shell-05`] → PR 2 идёт после PR 1 `shell-05`; до
  тех пор «Недавние» не показываются, а не показываются без проверки прав.

## Open Questions

### В-1. `/` — Главная или страница входа по рангу — решение владельца и Архитектора, до кода PR 1
`plan-02-navigation` (PR 2) и `work-03-navigation` планируют: `/` открывает видимый пункт с наименьшим
рангом (монтажник — «Мои отчёты»). Решение 17.10.2026: `/` — Главная.
- **А. Главная для всех.** Ранги страницы входа не нужны; отказа после входа не бывает (Главная открыта
  всем). Монтажнику его отчёты — карточкой «Ждут вас», которую объявит `work`. `entryPage.ts` из `plan-02`
  не строится.
- **Б. Главная — пункт со стандартным рангом.** Механизм `plan-02` строится; Главная — пункт с рангом по
  умолчанию, и только пункт модуля с меньшим рангом её перебивает (монтажник — сразу на свои отчёты).
  Кто без таких пунктов — на Главной, как решено 17.10.
- **Рекомендация — Б:** держит оба решения (Главная по умолчанию; монтажник с телефона — сразу к делу) и
  один механизм на индекс-маршрут.
- **✅ Решено владельцем 22.10.2026 — вариант Б.** Главная — пункт ядра с рангом `HOME_ENTRY_RANK`
  (константа шкалы рангов `entryPage.ts` из `plan-02`); индекс-маршрут зовёт `entryPage`, а не открывает
  Главную напрямую. Вписано в `plan-02-navigation` (требование «Страница входа по доступу», D «Вход»,
  задача 2.1) и `work-03-navigation` («Мои отчёты» — меньше `HOME_ENTRY_RANK`). Если `shell-08` идёт
  раньше PR 2 `plan-02`, он сам заводит `entryPage.ts` с этой константой в форме, описанной `plan-02`, и
  `plan-02` её расширяет, а не переписывает.

### В-2. Как модуль объявляет очередь Главной — решение Архитектора, до кода PR 1
- **А. Клиентский реестр** `shared/ui/homeQueues.ts`, описатели в части модуля (см. Decisions). «+» числа
  — буквально те же хуки, что у очереди; адреса экранов знает только клиент (`recordRoutes.ts`: «модуль
  на сервере адресов клиента не знает»); сервер не меняется. «−» новая очередь — правка клиента (как и
  новый экран).
- **Б. Серверное объявление** `IAppModule.Queues` + адрес ядра `GET /api/home/queues`, который зовёт счётчик
  модуля. «+» модуль объявляет себя на сервере, один запрос. «−» числа идут вторым путём, если адрес
  очереди не зовёт тот же счётчик; клиент всё равно сопоставляет очередь с экраном; права — дважды.
- **Рекомендация — А.** Decisions написаны по ней.

### В-3. Где хранить «Недавние» и как проверять удалённые и закрытые — решение Архитектора, до кода PR 2
- **А. Личная настройка** — ключ `recent` в `UserSettingKeys` (JSON до 20 записей). «+» без нового адреса и
  таблицы. «−» сервер настроек значения не читает (как избранное, `FavoritesAreNotApiParameterTests`) —
  удалённые и закрытые отсеять некому, кроме клиента, а он не знает об удалённых.
- **Б. Своя таблица ядра и разрешение через владельца типа** (см. Decisions). «+» удалённые и закрытые
  отсеивает сервер в правах спрашивающего; то же объявление служит поиску палитры. «−» таблица, миграция
  ядра, порт модуля.
- **В. Только браузер.** «+» проще всего. «−» на другом устройстве пусто (issue предпочитает сервер);
  удалённые остаются.
- **Рекомендация — Б.** Decisions и дельта `core` написаны по ней; при ответе А дельта `core` сужается до
  ключа настройки, а сценарий «удалённая и закрытая» уходит на клиент.
