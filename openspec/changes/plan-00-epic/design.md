## Goals / Non-Goals

**Goals:**
- Сметчик импортирует ЛСР, сопоставляет строки с видами работ и материалами, распределяет смету по
  разделам; менеджер делает из редакции КП и график; «Ход работ» стройки показывает план, сроки, факт и
  затраты — под ролями «Сметчик», «Менеджер проекта», «Снабженец», «Руководитель».
- Ни одним путём пользователь без права не видит денег сметы (`plan.estimate.cost`) и цен продажи
  (`plan.offer.read`): проверка нарушением по месту хранения (`plan-29`).
- Этап 4 приходит на готовое: позиции перечня, контракт, право контракта, «Плановые работы» с узкими
  правами, интерфейс «Фактических работ», навигация, базовый тип версии.

**Non-Goals:**
- Ввод сметы вручную и копирование, запись в ГРАНД-Смету, нормативные базы и индексы (`PLAN-6`, `PLAN-7`,
  `PLAN-8`, `STG-14`).
- Автопересчёт сроков, выравнивание ресурсов, связи кроме «окончание → начало» (`PLAN-16.1`, `PLAN-19`).
- Выработка рядом с работой графика (`PLAN-16`) — этап 4, `work-28`.
- Сверка `plan` × `work` (`CORE-32`) — этап 6.
- Перенос графика на новую редакцию сметы (В-17), привязка конъюнктурного анализа к ресурсам строк.
- КС-2, КС-3 (`PLAN-Q3`, `ID-12`).

## Decisions

### D1. Модуль — отдельный проект со своей схемой
`BHS.CRG.Modules.Plan` ссылается только на `BHS.CRG.Modules` и `BHS.CRG.Domain` (`CORE-2`). Контекст
`PlanDbContext : ModuleDbContext`, схема `plan`, миграции в проекте модуля, фабрика для `dotnet ef` по
образцу `CostsDbContextFactory`. Операции «ядро + модуль» (импорт: позиции перечня + строки) проектируются
с безопасным повтором (`CORE-4`, `STG-6.1`). Клиент — `features/planning/*`: имя `plan` в клиенте занято
планом документов (#796).

### D2. Что этап 3 забирает у этапа 4 (`PLAN-24`)
Поддерживающая задача едет с первым потребителем (правило нарезки 6). Этап 4 записал часть задач с
условием «если этап 3 не сделает»; первый потребитель каждой — здесь:

### D3. Смета: смета → редакция → строка, редакция фиксируется производными
- **Смета** — стройка или раздел, название, признак основной/дополнительной. **Редакция** — номер, файл
  источника с версией схемы, дата импорта, признак «зафиксирована». **Действующая** — одна на смету;
  «план» стройки — сумма действующих редакций всех её смет (`PLAN-5.2`). Смена действующей — журнал.
- **Строка** — колонки-скелет (`PLAN-3`, `TYPE-16`): позиция перечня, вид работы, объём, единица, порядок,
  раздел ЛСР, шифр расценки, номер в разделе; остальное — данные по схеме `ПозицияСметы` (открытый тип,
  `CORE-19`). Ресурсы строки — дочерние таблицы: материалы (номенклатура, количество на объём строки) и
  трудозатраты (чел.-ч) (`PLAN-9.1`).
- Редакция фиксируется, когда из неё сделаны КП или график (`PLAN-5`); правка зафиксированной — 409 с
  названием производной. Повторный импорт создаёт новую редакцию, а не правит прежнюю.
- Редакции — не версии `CORE-36`: они сосуществуют и читаются производными. Охрана «план считается по
  действующим» — единственным методом чтения плана; прямое чтение строк для сумм ловит перепись
  (по образцу `InvoiceBookInventoryTests`).

### D4. Деньги сметы закрыты правом, а не экраном (`PLAN-26`)
Стоимость строки, итоги, наценка и себестоимость в КП отдаются только с `plan.estimate.cost`; цены
продажи — только с `plan.offer.read`. Закрытые поля не попадают в ответ вовсе (ни пустыми, ни нулями):
носитель — `hidden: ["cost"]` с кодом права (`CORE-33`, «колонка скрыта правами»). То же правило — в
таблицах, наборах, MCP и печати. Сторож — проверка нарушением `plan-29`.

### D5. КП — запись модуля с версиями базового типа
КП хранится в схеме `plan` (`PLAN-Q8`): шапка, строки (из редакции или из прайс-листа), наценки трёх
уровней и итог — системные поля под замком (`TYPE-17`, `CORE-20.2`); поля заказчика — по схеме
`КоммерческоеПредложение`. Себестоимость в КП не копируется — показывается из сметы (`PLAN-11`).
Статусы: черновик → отправлено → принято / отклонено / без ответа (`PLAN-12`). Отправленная версия
замерзает: правка создаёт новую. Действующая версия — в основной таблице, прежние — записью истории на
базовом типе `CORE-36` (`plan-12`, форма `InvoiceVersion`); запросы сумм историю не читают.

### D6. Импорт — разбор по схемам, решение человека, идемпотентная запись
- Разбор OpenXML ГРАНД-Сметы — чистый C# в модуле (`System.Xml`, без новых пакетов), по XSD; версия схемы
  хранится с файлом (`PLAN-7`, `STG-12`). Неизвестная версия — отказ с названием версии, а не попытка.
- Импорт — двумя шагами: разбор с отчётом «N из M, K не разобраны ▸» (фоновая операция `IModuleJobs`), затем
  решение человека «создать редакцию». Частичный разбор молча редакцию не создаёт.
- Запись: позиции перечня «найди или создай» (`plan-04`) **до** строк; строки редакции — одним
  `SaveChanges` модуля; повтор после сбоя находит те же позиции и не создаёт второй редакции (ключ
  импорта у редакции).

### D7. Позиция перечня — порт ядра «найди или создай»
`IModulePlanItems.FindOrCreateAsync(key)` и чтение по списку; уникальный ключ уже есть, гонка
решается вставкой с повтором чтения при конфликте. Ключ — «вид работы, стройка, раздел, единица
классификатора» (`CORE-10`). Строка сметы без сопоставления позиции не имеет и в «Ход работ» и график не
идёт (`PLAN-4`). Распределённая строка даёт позиции по разделам распределения — в момент построения
графика и в плане «Хода работ», а не в момент импорта (распределение — мнение сметы, `CORE-Q2`).

### D8. Сопоставления запоминаются по образцу `COST-7.1` (`PLAN-25`)
- «Шифр расценки → вид работы + единица классификатора + коэффициент пересчёта» (`PLAN-6.1`): объём
  позиции = объём строки × коэффициент; единица позиции — всегда единица классификатора.
- «Наименование ресурса (+ код, если есть) → номенклатура» (`PLAN-9.1`).
- Подстановка помечена «запомнено» и отменяется одним действием; список запомненного — свой экран с
  «забыть». Новый вид работы — из окна сопоставления через дверь `plan-03`.

### D9. Распределение — изменяемый слой над редакцией
Таблица модуля «строка редакции → раздел стройки → количество» плюс правило «раздел ЛСР → раздел
стройки». Правится и у зафиксированной редакции, пишется в журнал (`PLAN-5.1`). Баланс — как `COST-13`:
сумма частей не больше объёма строки, остаток — «стройка в целом». Перенос при повторном импорте — по
ключу «раздел ЛСР + шифр + номер в разделе»; неоднозначные и не перенесённые — списком в ответе.

### D10. Контракты — интерфейс в контрактах, реализация у поставщика
- Механизм — как спроектировано в `work-09` (D13 этапа 4): `BHS.CRG.Modules/Exchange/*`, атрибут
  поставщика на интерфейсе, регистрация в `RegisterServices` поставщика, ответ `Connected` |
  `NotConnected`, проверка при старте, ссылок модуль → модуль нет.
- Параметр доступа контракта — `ModuleReader`: кто спрашивает, его права, «система с причиной»
  (`plan-22`). Изоляцию строк (`WORK-40`) в него добавит `work-07`; форма заложена расширяемой.
- **Контракты этапа:**

| Контракт | Поставщик | Ответ по праву | Потребитель |
|---|---|---|---|
| Плановые работы | `plan` | `plan.estimate.read` — объёмы, распределение; `.cost` — плюс стоимость; `plan.estimate.materials` — материалы без цен; `plan.labor.read` — чел.-ч на единицу без денег; `plan.estimate.hint` — наименования материалов без количеств | заявки и «план против факта» `costs`; `work-26`, `work-28` |
| Фактические затраты | `costs` | по стройке, разделу, позиции: разнесено и оплачено | «Ход работ» (`PLAN-21.1`) |
| Фактические работы | `work` (`work-27`) | принятые объёмы без часов и людей | «Ход работ», факт графика (`PLAN-18`) |
| Колонка «Хода работ» | каждый модуль | своя часть экрана | ядро собирает экран |

- «Колонка Хода работ» — единственный контракт со многими поставщиками: каталог при старте разрешает
  несколько реализаций, если контракт так объявлен; остальные — строго один поставщик.

### D11. «Право контракта» — вид права

### D13. Печать записи модуля — шаблоном Typst ядра
`IAppModule` получает объявление печатной формы записи модуля: тип записи, поставщик контекста
(JSON записи в правах печатающего, D4), шаблон — обычный `Template` ядра, который заказчик правит в
редакторе. Генерация — общим путём `TypstGenerator`. Первый потребитель — КП (`PLAN-14`), второй — список
работ графика (`PLAN-17`, рекомендация В-10). Решение M4 «счёт не печатается» механизм не трогает.

### D14. Календари и даты графика
Даты графика — календарные даты без времени. Длительность и задержки считаются в рабочих днях календаря
стройки: календарь компании (рабочие дни недели, праздники и переносы на год, загрузка из файла, часов в
смене) плюс исключения стройки и сменность (`PLAN-19.1`). Окончание на выходном — предупреждение.
Пересчёта сроков нет (`PLAN-19`): нарушения зависимостей и выходные — носители с сервера
(`warnings: [{code, text}]`), клиент их не вычисляет.

### D15. График: шапка, работы и связи — записи модуля
Шапка графика по `CORE-20.1` — объект общего типа, но порт `IModuleOwnCatalog` пишет только записи
«по названию», и для шапки понадобился бы новый пишущий порт ядра. Поэтому шапка — тоже запись модуля и
печатается механизмом D13 (ждёт решения В-14). Работы и связи — таблицы схемы `plan`
(`PLAN-Q7`): работа ссылается на позицию перечня (или, если добавлена руками, на вид работы, стройку,
раздел и единицу — позиция заводится тем же портом), сроки, объём, исполнители (сотрудники), часть
распределения. Связь — предшественник, последователь, вид (`FS` — пока единственный разрешённый),
задержка в рабочих днях; допустима на работу другого графика той же стройки. Цикл — отказ с перечнем
работ цикла. Работы строятся по частям распределения; «распределение изменено после построения» —
носитель у графика.

### D16. «Ход работ» — экран ядра, собранный из вкладов
Адрес ядра `GET /api/constructions/{id}/progress` с отбором по разделу. Строка — вид работы (через позицию
перечня), колонки — вклады модулей контрактом «Колонка Хода работ»: `plan` — план по смете, срок по
графику; `work` — факт (поставщик `work-27`, в этапе 3 — синтетический в CI, `STG-6.1`); акты `id` — позже.
Полосы над таблицей — тоже вклады с состоянием: «план по: смета … ред. N», «не сопоставлено строк: N»,
«не распределено по разделам», «учёт работ не подключён», затраты `costs`. Колонка без права — «скрыто
правами», без поставщика — «не подключено» (`CORE-34`). Строки без пары не прячутся.

### D17. Носители пометок и состояний приходят с сервера
Как D15 этапа 4: «не сопоставлено», «запомнено», «редакция зафиксирована (кем)», «смета изменилась
после КП», «распределение изменено после построения», «нарушение зависимости», «окончание на выходном»,
«скрыто правами», «не подключено» — кодом и текстом в ответе. Каталог кодов открыт: change, приносящий

### D19. Решения, принятые в дочерних change
Записаны здесь, чтобы не потеряться в 29 папках:
- КП вписан в `IAppModule.AccountingDocuments` (`plan-13`): пока есть КП, валюту учёта не сменить.
- Номер КП — сквозной, «КП-<год>-<NNN>» (`plan-13`).
- Режим НДС у КП — своё перечисление с тремя значениями (`VatMode` счёта знает два и лежит в `costs`);
  общий тип выносится в контракты, только если В-9 решится «как у счёта» буквально (`plan-13`).
- Количество распределения хранится в единице строки сметы, ответ называет обе единицы (`plan-10`).
- Сметное наполнение строки (`data` по схеме `ПозицияСметы`) отдаётся целиком только с
  `plan.estimate.cost`; тэги `estimate.*` не объявляются (`plan-06`).
- Стоимость ресурса-материала — колонка строки ресурса под `plan.estimate.cost` (`plan-06`); её читают
  `plan-23` и `plan-27`.
- Подстановка запомненных сопоставлений при импорте — точка `IEstimateRowMatcher` из `plan-07`,
  реализует `plan-08`.
- ВОР и КА в редакцию не превращаются: импорт отправляет их приложением к смете (`plan-07` → `plan-11`).
- Колонку факта и полосу затрат «Хода работ» рисует ядро, читая контракты (`plan-25`): вклад колонки от
  `work-27` не нужен.
- Доля затрат «привязано к работам» (`PLAN-21.1`) — состояние `not-tracked`: разноски на позицию перечня
  (`COST-14`) в коде нет (ждёт решения В-15).
- Общий выбор сотрудника `shared/ui/EmployeePicker` первым заводит `plan-20` (исполнители графика);
  `work-12` дополняет его кандидатами и причинами.
- Перенос графика на новую редакцию в ТЗ не описан: в этапе 3 — пометка «устарел» и покрытие (`plan-16`,
  `plan-19`), сам перенос — вне этапа (ждёт решения В-17).
- Привязка предложений конъюнктурного анализа к ресурсам строк — вне этапа (`plan-11`).

## Risks / Trade-offs

- [Формат ГРАНД-Сметы меняется с версиями] → разбор по схемам, версия с файлом, отказ на неизвестной
  (`STG-12`); образцы файлов заказчика — условие `plan-05` (вопрос В-11).
- [Сопоставление 300 строк руками — смета не дойдёт до «Хода работ»] → запоминание по шифру, массовое
  сопоставление по разделу ЛСР, счётчик «не сопоставлено» в «Ходе работ».
- [Коэффициент пересчёта забыт — план в 100 раз больше факта] → сопоставление без единицы классификатора
  не сохраняется; сторож на «100 м → м».
- [Деньги сметы утекают через таблицы, наборы, MCP, печать] → D4, проверка нарушением по месту хранения
  (`plan-29`).
- [Механизмы, забранные у этапа 4, расходятся с его артефактами] → зонтик `work-00-epic` и затронутые
  change получают пометку тем же PR, что и эта нарезка; перед стартом каждого change этапа 4 сверяется
  master.
- [«Ход работ» без единого реального факта] → синтетический поставщик «Фактических работ» в CI
  (`STG-6.1`); форма ответа фиксируется интерфейсом в этапе 3.
- [Счёт PR втрое выше оценки ТЗ] → тот же механизм, что на этапах 1, 2 и 4; плюс работы, забранные у
  этапа 4, — этап 4 на столько же короче.

## Migration Plan

Модуль включается переменной `Modules__Enabled`. Миграции ядра (если понадобятся: печатная форма записи
модуля) применяются всегда, миграции схемы `plan` — только при включённом модуле (`CORE-4`). Выключение
модуля данных не теряет (`AUTH-19`). Перенос данных не нужен: калькулятор и прежние КП не используются
(`PLAN-Q6`). Откат PR — обычный.
