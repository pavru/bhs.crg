# Design: адрес `GET /api/field-suggestions`, источник верхнего уровня

Общая архитектура — `../suggest-00-epic/design.md` (D1, D2, D5–D8, D10, D11). Здесь только решения
этого change.

## Context

- Записи — `domain_objects` (`Domain/Objects/DomainObject.cs`): `CompositeTypeId`, `Data` (JSONB),
  `ScopeLevel`/`ScopeId`, `UpdatedAt`, `ArchivedAt`; документ отличается видом типа
  (`DocumentType.Kind`) и гранью `document_facets` (`IsDocument`).
- Индексы `domain_objects` (`Persistence/Configurations/DomainObjectConfiguration.cs:56-62`):
  `(ScopeLevel, ScopeId)`, `CompositeTypeId`, частичный по архивным. Нужного индекса нет.
- `SET LOCAL statement_timeout` в транзакции уже применяется — `Persistence/ModuleReferenceScan.cs:129`.
- Семья — `DocumentTypeSchemaReader.IsSameOrDescendant` (`:119`); стройка по `scope`/`scopeId` — как у
  `GET /api/common-data/for-scope` (`Api/Endpoints/Documents/CommonDataEndpoints.cs:51`), каскад уровней
  — `Application/Objects/ScopeCascade.cs`.
- Права — `DataAccess` (`Application/DataSets/DataAccess.cs`): `Keys` (права + доступные модули) и
  `EnabledModules` раздельно.
- Перепись адресов: корзина `GatedInside` (`Tests/Integration/EndpointGateInventoryTests.cs:123`)
  требует названного сторожа. Перепись чтений: `ArchiveReadInventoryTests` (ключ «файл|строка кода»,
  `Kind.Choice` и живой тест в `ArchiveReadPurposeTests`).
- Что выяснилось сверкой: шаг «Новая позиция» открыт держателю `core.nomenclature.edit`, а не «читателю
  счетов» (В-1 зонтика); клиент не знает типа-владельца поля (В-2); записи номенклатуры — уровня «вся
  система», своей стройки у них нет (В-3).

## Goals / Non-Goals

**Goals:** контракт D10 на верхнем уровне записей; план запроса, не читающий записи вне окна; права,
архив, `_baseRef`, порог и 503 — тестами.

**Non-Goals:** вложенные поля и строки массивов (`suggest-04`; тип строки массива здесь — 200 и пусто);
клиент (`suggest-03`, `suggest-05`); порт для модулей; производная таблица.

## Decisions

- **Слои (D11).** `Application/Objects/FieldSuggestions/`:
  - `FieldSuggestionsQuery` (MediatR) — разбор параметров, правило `Suggestable` (`suggest-01`), план,
    чтение, ранжирование;
  - `SuggestionSources.For(type, field, types, access)` — **чистая** функция: семья типа, отбор по правам,
    «пусто, потому что …»; тестируется без базы;
  - `SuggestionRanking` — нормализация, склейка, порог, порядок; тоже чистая.
  `IFieldSuggestionReader` — узкий порт «значения поля у окна записей типов X»; реализация —
  `Infrastructure/Persistence/FieldSuggestionReader.cs` на SQL. Не partial `DomainObjectRepository`.
- **Тип в запросе (В-2, рекомендация (а)).** `type` — любой тип семьи, где поле видно; объявивший поле
  тип сервер находит, поднимаясь по цепочке родителей до типа, у которого ключ свой. Семья — потомки
  объявившего, кроме перекрывших ключ своим полем и исключивших его (`excludedFields`). Если решение
  В-2 — (б), шаг подъёма снимается, остальное то же.
- **Форма запроса — часть решения.** Окно отбирается подзапросом: по каждому типу семьи — `ORDER BY
  "UpdatedAt" DESC LIMIT 1000` над новым индексом, нарастающая сумма `pg_column_size("Data")` (размер
  виден без распаковки), отсечение по 8 МБ; поле `"Data" -> @field` читается **только** у записей окна,
  соединением по `Id`. Семья из нескольких типов — `UNION ALL` по типу (Merge Append над Index Scan
  каждого), а не `= ANY(...)`, если EXPLAIN покажет сортировку; выбор фиксирует тест плана. Фильтр по
  полю снаружи окна запрещён: планировщик выполнил его последовательным просмотром всей таблицы до
  соединения (264 мс, замер #1528).
  **Выбрано реализацией (23.10.2026): `UNION ALL`, ветка на тип с типом-параметром.** Первый вариант —
  `unnest(@types)` с `LATERAL` — тест плана отверг: тип из `unnest` планировщику не виден, число записей
  он оценивает по среднему на тип и на большом типе выбирал старый индекс `CompositeTypeId` с
  сортировкой всех записей типа — в зависимости от соседних типов в таблице. Поле читается подзапросом
  в списке выборки (`SubPlan` по первичному ключу), а не соединением: соединение планировщик волен
  исполнить хешем с просмотром всей таблицы. Тест плана кладёт 1000 тяжёлых записей и 9000 лёгких
  старых: при числе записей, равном пределу окна, сортировка всех законно дешевле, и тест проверял бы
  совпадение чисел, а не форму запроса.
- **Индекс** — `IX_domain_objects_CompositeTypeId_UpdatedAt_Live` на `("CompositeTypeId", "UpdatedAt"
  DESC) WHERE "ArchivedAt" IS NULL`, миграцией `AppDbContext`. Он же исполняет D6: архивные в окно не
  попадают по самому индексу. Побочно он — второй путь «по типу» у выбора записей (тот же отбор «не в
  архиве»): тест `ChoiceSearchIndexTests`, принуждающий триграммный путь снятием индекса по типу, теперь
  снимает оба.
- **Таймаут.** Чтение — в транзакции с `SET LOCAL statement_timeout = '300ms'` (приём
  `ModuleReferenceScan`); `PostgresException` с кодом `57014` → 503 с причиной «подсказки сейчас не
  успевают». Никакой другой отказ базы в 503 не переводится: он остаётся 500.
- **Своя стройка.** До чтения сервер собирает множество «своих» областей читателя: стройка, её разделы и
  комплекты (стройка — по цепочке вверх, как `for-scope`; комплекты — общим спуском `IScopeSubtree`,
  которым пользуется и `ScopeCascade`: сам каскад — план удаления и для этого не годится). `here` = область записи в этом множестве. Записи уровня «вся
  система» — свои для любого читателя (В-3, рекомендация (а)); если решение — (б), они уходят в «чужие».
  Без `scope` — своих областей нет, все значения чужие.
- **Ранжирование.** Нормализованный ключ: нижний регистр, ё→е, пробелы схлопнуты и обрезаны. Совпадение
  — `q` (нормализованный) — префикс ключа или префикс слова ключа (граница — пробел). Частота — число
  разных записей с этим ключом, отдельно своих и чужих; порог: свои ≥ 1, чужие ≥ 2. Показываемое
  написание близнецов — самое частое, при равенстве — самой свежей записи. Порядок: свои, затем чужие;
  внутри — по частоте, затем по свежести. Ключ, равный `q`, выбрасывается. Пустой `q` — без отбора по
  совпадению.
- **Права.** `SuggestionSources.For` получает `DataAccess`: тип вида «документ» — только при
  `id.document.read` в `Keys` и `id` в `EnabledModules`; остальные — при `core.catalog.read`. Если в
  семье не осталось ни одного типа из-за прав (а не из-за схемы) — 403. Семья, вся ушедшая с
  выключенным модулем `id`, — 200 и пусто: модуль выключен для всех, это не право читателя. Типы,
  хранимые в таблице модуля (`TypeStorage.ModuleTable`), в семью не входят — их записей в
  `domain_objects` нет. Шаг «Новая позиция» — по решению
  В-1: при (а) у семьи типа с ролью `role.nomenclature` третий ключ — `core.nomenclature.edit`.
- **Ворота адреса.** На адресе — только вход (`RequireAuthorization()`), права — в службе; строка в
  `GatedInside` называет сторожа — интеграционный тест «без обоих прав — 403, без права на документы —
  значения документов нет».
- **Чем ломается.** Фильтр по полю вынесен из окна — красный тест плана (Seq Scan вместо Index Scan
  или прочитанные строки вне окна). Чтение без назначения «выбор» — красная перепись чтений.
  Разрешённый `_baseRef` — красный тест частоты.

## Risks / Trade-offs

- [Тест плана зависит от статистики тестовой базы] → `ANALYZE` типа перед EXPLAIN; проверяется
  наличие `Index Scan using IX_domain_objects_CompositeTypeId_UpdatedAt_Live` под `Limit` и отсутствие
  `Seq Scan on domain_objects`, а не стоимость.
- [Окно из 1000 записей обрежет давние редкие значения] → это решение D2: подсказка про недавнее;
  весь архив — условие перехода на производную таблицу.
- [403 у поля формы] → поле молчит так же, как при пустом ответе (`suggest-03`); причина видна в сети.

## Migration Plan

Миграция `AppDbContext` добавляет индекс; откат — `Down` удаляет его. Данные не меняются. Проверка —
старт на пересозданной базе.
