# Design: навигация этапа 4

Общая архитектура — `../work-00-epic/design.md` (D3 — право контракта, D15 — носители, D17 — макеты Р0
и панели модулей в карточке стройки). Здесь только решения этого change.

## Context

Сверено по коду master `f8a8b222`.

- **Пункт навигации.** `NavItem` (`client/src/shared/ui/navConfig.ts:14-36`) несёт одно `permission?: string`.
  Отбор и причина отказа — `shared/ui/navAccess.ts:15-40` (`allowed`, `missingFor`). Ими же пользуются
  `ProtectedRoute.tsx:51` и палитра команд `CommandPalette.tsx:72`.
- **Разделы рейла.** `RailId` — `'constructions' | 'data' | 'costs' | 'system'` (`navConfig.ts:42`), список —
  `railSections` (`navConfig.ts:68-79`). Раздел без пунктов не строится (`railSections.ts:buildRail`).
  Основной список пунктов называется `workNav` (`navConfig.ts:82`): это «рабочие пункты» против
  `settingsNav`, а не модуль `work`. Имя совпадает с кодом модуля, и путать их легко.
- **Вход.** Индекс-маршрут жёстко ведёт на `/document-sets` (`client/src/App.tsx:122`).
- **Карточка стройки.** Панели — тип `'catalog' | 'datasets' | 'subscribers'`
  (`features/document-sets/ConstructionDetail.tsx:31`) и ручной список пунктов (`:111-118`).
  «Наборы данных» уже отбираются по пространству (`:42`, `useWorkspace().showsSection`).
- **Сервер.** Политики собираются по имени: `perm:<код>` и `module:<код>`
  (`BHS.CRG.Modules/AppPolicies.cs`, `PermissionPolicies.cs:42-56`). Политики «любое из» нет. Атрибут MCP
  принимает один код (`Api/Mcp/McpGates.cs:29`).

## Goals / Non-Goals

**Goals:** «любое из» на пункте и на адресе одним списком; раздел рейла модуля; вход по доступу;
механизм панелей карточки стройки.

**Non-Goals:**
- сами страницы модуля `work` и их ранги входа — `work-12`, `work-21`, `work-22`, `work-23`;
- закрепление разделов — `work-04`;
- пространство как граница безопасности — его нет и не будет (`AUTH-16.2`).

Пишущих адресов change не заводит, правило `If-Match` его не касается.

## Decisions

### Состав PR

- **PR 1 — «любое из» и раздел рейла.**
  - Клиент:
    - `NavItem.permission: string | string[]`;
    - `allowed` — «любое из»;
    - `missingFor` возвращает `{ kind: 'permission', codes: string[] }`;
    - `NoAccessPage.tsx` пишет «нужно одно из прав» при двух и более.
  - `RailId` += `'work'`, строка в `railSections` с подписью по Р0. Если владелец выберет и
    переименование раздела `costs`, меняется только `label`, `id` остаётся.
  - Сервер:
    - `AppPolicies.AnyPermission(params string[] codes)` — имя `perm:<a>|<b>`;
    - провайдер разбирает список, каждый код проходит `Declared()`;
    - требование `AnyPermissionRequirement` и его обработчик;
    - атрибут `McpPermission` принимает тот же список (`AUTH-12.1`: право инструмента = право адреса).
  - Переписи `PermissionGateTests`, `EndpointGateInventoryTests`, `ReadAllWritesNothingTests` читают
    составное имя.
- **PR 2 — вход и панели** (после выбора макета Р0).
  - `NavItem.entry?: number` и `shared/ui/entryPage.ts` — чистая функция «доступ + пространство → адрес
    входа». Индекс-маршрут в `App.tsx` зовёт её вместо `Navigate to="/document-sets"`.
  - `shared/ui/constructionPanels.ts` — реестр панелей `{ id, label, icon, permission | module, section,
    render }`. `ConstructionDetail.tsx` строит пункты и содержимое по реестру. Адреса прежних панелей не
    меняются: адрес карточки и суффиксы `/datasets`, `/subscribers` к нему (`ConstructionDetail.tsx:77`).

### Почему одна политика, а не две двери

Альтернатива — два адреса сводки, под `review` и под `read.all`. Отклонена: экран получил бы два
источника, перепись ворот — две записи, а пункт навигации всё равно называл бы два права. Список в
одном имени политики проверяется тем же `Declared()` и тем же обходом адресов.

### Вход: ранг у пункта, а не карта «роль → страница»

Карта по ролям противоречит `AUTH-14`: навигация не читает названий ролей. Ранг у пункта вычисляется
из того же ответа доступа. Пространство учитывается: вход вне него открывал бы раздел с плашкой сразу
после входа. Конкретные ранги назначают change экранов модуля по макету Р0.

### Сторож и «чем ломается»

- Vitest `navAccess.test.ts`: «любое из» показывает пункт при любом праве списка, `missingFor` называет
  весь список. `entryPage.test.ts`: ранг, пространство, пустая навигация.
- `AnyPermissionPolicyTests` — живой хост с тестовым модулем: адрес под «любым из» открыт носителю
  каждого права и закрыт без обоих; необъявленный код роняет сборку политики.
- Живой прогон `e2e/limited-smoke.mjs`: под каждой системной ролью все видимые пункты открываются без
  отказа и без 403 в сети, а `/` ведёт на видимую страницу. `e2e/rail-checks.mjs` — раздел `work` не
  виден без прав модуля.
- Ломается так: сводка под одним `work.report.review`, и руководитель её не видит. Это ловит тот же
  прогон под «Руководителем», когда `work-23` вписывает пункт сводки. В этом change — тестовым пунктом
  в vitest и тестовым адресом в `AnyPermissionPolicyTests`.
- Правка оболочки, поэтому весь список живых прогонов идёт в каждом PR.

### Зависимости

- После `work-10`: раздел `work` осмыслен только с модулем.
- После `work-02`: модуль, открытый одним правом контракта, не должен давать раздел.
- `work-04` правит те же файлы навигации (`navConfig.ts`, `SectionRail.tsx`). Кто сливается вторым, тот
  перебазируется. Порядок не важен, механизмы не пересекаются.
- От этапа 3 не зависит. Если `plan` заведёт свой раздел рейла раньше, `RailId` уже расширен им, и
  этот PR добавляет одно значение.

### Макеты

Раунд Р0:
- раздел рейла и его подпись, переименование «Учёт» → «Затраты»;
- страницы по ролям и страница входа;
- закрепление (`work-04`);
- панели модулей в карточке стройки.

## Risks / Trade-offs

- [Список в имени политики делает имена длинными] → имена строятся кодом из констант прав, руками их не
  пишут.
- [Ранг входа у двух модулей совпал] → порядок — порядок рейла, тест `entryPage.test.ts` закрепляет его.
- [Переезд панелей карточки ломает адреса закладок] → адреса прежние, проверка — `e2e/routing-smoke.mjs`.
