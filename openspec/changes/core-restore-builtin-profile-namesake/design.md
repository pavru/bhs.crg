# Design: встроенный профиль распознавания из копии заменяет тёзку

## Context

- Восстановление (`BackupService.Import.cs:85–93`) идёт одной транзакцией: примитивы, перечисления,
  **профили распознавания**, затем тёзки типов (`ReplaceTypeNamesakesAsync`, #1400) и сами типы.
- `RestoreRecognitionProfilesAsync` (`BackupService.Restore.cs:66`) пропускает нетронутые встроенные
  (`IsBuiltIn && !IsModified` — их переутверждает сидер) и сличает остальные с базой только по `Id`.
- Уникальность — `IX_recognition_profiles_Code` с фильтром `"Code" IS NOT NULL`
  (`RecognitionProfileConfiguration`). Код есть только у встроенных: свой профиль тёзок не имеет.
- `RecognitionProfileSeeder` заводит встроенный профиль под новым `Id` у каждой установки и апсертит
  по `Code`, пока профиль не правлен.

### Кто ссылается на `RecognitionProfile.Id` (сверено grep'ом)

- `DataSetFile.RecognitionProfiles` — JSON-карта `{вид: id}` набора (issue #412).
- `DataSetFile.Grouping` — JSON групп листов, у группы `ProfileId` (issue #410; `GostGroupingData.cs`).
- Модуль `costs` ссылается на профиль **кодом** (`IAppModule.RecognitionProfiles`,
  `IModuleRecognition`), а не идентификатором. Других держателей в коде нет.
- Ссылка на отсутствующий профиль не роняет распознавание: файл берёт встроенный профиль вида
  (`ProfileForFileAsync`), группа — встроенный по тэгу (`ResolveTableSpecAsync`). Но группа без
  табличного тэга, привязанная только профилем, потеряла бы таблицу — поэтому ссылки переписываются, а
  не оставляются деградации.

### Что выяснилось сверкой

- Код `RestoreRecognitionProfilesAsync` в master тот же, что в issue: дефект не исправлен.
- `BackupService.Restore.cs` стоит в `file-size-baseline.json` (636 строк) — расти ему нельзя, новая
  логика идёт отдельным partial, как у типов.
- Файлы копии пишутся в хранилище ДО транзакции (`BackupService.Import.cs:57–80`), поэтому после
  отката они остаются; повторное восстановление их перезаписывает. Это прежнее поведение, его change
  не трогает.

## Goals / Non-Goals

**Goals:** копия с правленным встроенным профилем восстанавливается на чистый экземпляр и на экземпляр
с другими идентификаторами встроенных профилей; ссылки экземпляра на тёзку не теряются; отказ, если он
нужен, называет профиль и держателя.

**Non-Goals:**
- запись файлов копии внутри транзакции (отдельный вопрос, issue его только упоминает);
- тёзки других сущностей, заводимых при старте, — сверить их перечень можно отдельно; этот change
  закрывает профили распознавания;
- слияние двух правленных редакций одного профиля.

## Decisions

- **D1. Идентификатор — из копии.** Тёзка удаляется, профиль из копии ложится под своим `Id`. Так
  остаются верными все ссылки внутри копии, включая данные модулей, о которых ядро не знает. Обратный
  вариант — «оставить здешний `Id`, переписать ссылки копии в памяти» — отклонён: держателей в копии
  ядро перечислить не может (схемы модулей едут как есть), пропущенный держатель тихо деградировал бы.
  Тот же выбор сделал #1400 у типов.
- **D2. Ссылки экземпляра переписываются.** Известные держатели ядра — `dataset_files."RecognitionProfiles"`
  и `dataset_files."Grouping"` — получают идентификатор из копии заменой строки идентификатора
  (`replace(col::text, old, new)`): GUID уникален, ложного совпадения нет. Строки наборов, которые
  затем приедут из копии с тем же `Id`, всё равно перезапишутся — переписываются только здешние.
- **D3. Неизвестный держатель — отказ с названием.** После переписи — проход по схеме
  (`CoreHolderOfAsync` из #1400, обобщённый: исключается собственная колонка `recognition_profiles.Id`)
  и порт держателей модулей `IRecordHolders`. Нашлось — `ConflictException` «профиль „…“ (код …) есть и
  в копии, и на этой системе под разными идентификаторами, на здешний ссылается схема.таблица.колонка».
  Порт не ответил — тоже отказ: «проверить не удалось» не значит «никто не держит» (правило #1400).
- **D4. Правленный здешний тёзка заменяется с предупреждением.** Альтернатива — отказ — отклонена:
  восстановление на тот же экземпляр уже перезаписывает правку профиля по `Id` молча, а перенос копии
  на чужую систему — тот же акт «привезённое главнее». Предупреждение называет профиль и что правка
  этой системы заменена.
- **D5. Место и порядок.** Новый partial `BackupService.Restore.ProfileNamesakes.cs`, вызов
  `ReplaceProfileNamesakesAsync` в `BackupService.Import.cs` перед `RestoreRecognitionProfilesAsync`, в
  той же транзакции: отказ откатывает всё, как у типов. Тёзками считаются только профили копии, которые
  восстановление действительно положит (`IsBuiltIn && IsModified` или свой), — нетронутый встроенный
  из копии пропускается, и здешний остаётся.
- **D6. Проход по схеме — общий.** `CoreHolderOfAsync(Guid typeId)` становится
  `CoreHolderOfAsync(Guid id, (string Table, string Column) own)`; типы вызывают его со своей колонкой.
  Поведение типов не меняется — проверяется их тестами (`RestoreModuleTypesTests`).

## Risks / Trade-offs

- [Проход по схеме — по всем таблицам] → платится только при тёзке, то есть на чужой для копии
  системе; на чистой таблицы почти пусты (та же цена, что у #1400).
- [В журнале действий (`activity_log`) текст «было/стало» может упоминать идентификатор профиля] →
  для профиля журнал проход держателем не считает: таблица журнала исключается из прохода явно, с
  причиной в доккомментарии (запись неизменяема, переписывать её нельзя, а ссылкой она не является).
  Проход для типов остаётся прежним — его поведение этот change не меняет.
- [Новый держатель профиля появится у модуля] → его найдёт порт `IRecordHolders`, и восстановление
  откажет с названием, а не потеряет ссылку молча.

## Migration Plan

Миграций и смены формата копии нет. Обход из issue (`DELETE FROM recognition_profiles WHERE "Code" =
'invoice'` на свежей установке) после выпуска не нужен.
