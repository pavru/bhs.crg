# MCP-сервер BHS.CRG (issues #415, #419, #421, #423, #425, #427, #429, #440, #448, #590, #591, #592, #593, #594, #595, #596, #597, #598, #599, #600)

Даёт внешнему ИИ-агенту типизированный доступ к данным системы — вместо чтения файлов с диска.
Задуман под сверку документов на непротиворечивость: агент тянет строки источников, а не воюет с
версиями файлов.

Две половины отвечают на разные вопросы, и для сверки нужны обе: **наборы данных** (#415) — «что
лежит в файлах», **домен** (#419) — «что об этом знает сама система».

**Читающий, с тремя исключениями.** Состояние системы меняют `generate_document` (#425),
`report_observation` (#440) и `propose_alias` (#448); все объявлены `readOnly: false`, поэтому клиент может спросить у
пользователя подтверждение. Список записывающих инструментов ведётся явно и закреплён
`McpToolContractTests`: право записи агенту — решение, а не побочный эффект правки.

Распознавание агенту НЕ отдаётся: оно тратит деньги на внешние LLM-вызовы, и открывать его — отдельное
решение, а не побочный эффект.

## Подключение

Эндпоинт: `POST http://<хост>:5000/mcp` (streamable HTTP), та же аутентификация, что у REST —
`Authorization: Bearer <JWT>`. Токен получается обычным входом:

```
POST /api/auth/login  { "email": "...", "password": "..." }  →  { "accessToken": "..." }
```

Агент действует **от имени пользователя**: применяются те же правила доступа, отдельной модели
доступа для MCP нет.

### Без сессий (#599)

Транспорт работает в режиме `Stateless`: заголовок `Mcp-Session-Id` не выдаётся и не требуется,
каждый запрос самодостаточен. Прежде сессия жила в памяти процесса, и первый вызов после паузы
регулярно получал **404 «Session not found»**, а повтор того же вызова проходил: мост лечил это сам
(#438), но любой другой клиент вынужден был закладывать слепой ретрай — для неидемпотентного вызова
небезопасный.

Плата: сервер не может слать клиенту сообщения по своей инициативе (sampling, elicitation, подписки
на ресурсы) и не поднимает legacy `/sse`. Ничем из этого мы не пользуемся — сервер отвечает на
вопросы и не задаёт своих. Появится такая нужда — режим придётся пересматривать вместе с ней.

### Набор инструментов не меняется на ходу (#600)

За одну живую сессию агента набор инструментов рос 10 -> 15 -> 17 -> 21 -> 22, и вдобавок менялась
форма списочных ответов. Каждое изменение инвалидирует кэш модели целиком: около **35 %** контекста
сессии ушло на перечитывание инструкций и списка инструментов вместо работы с данными.

Полный набор объявлен статически и закреплён тестом `ToolSet_MatchesDeclaredList` — добавление
инструмента обязано быть видно в дифе. Организационная часть техникой не закрывается: **пока агент
работает в живой сессии, сервер с изменённым контрактом не выкатывают**; если выкатили — заметить
это клиенту даёт версия контракта.

`serverInfo.version` — версия сборки, а не константа: по ответу видно, с какой именно сборкой
говорит клиент, а разбор жалоб на MCP всегда начинается с этого вопроса.

Общие правила (страничность, `origin`, `stale`) уходят клиенту один раз в `instructions` при
инициализации — вместо повторения в описании каждого инструмента.

## Проверка и выпуск (#425)

| Инструмент | Назначение |
|---|---|
| `validate_document` | Диагностика документа средствами системы (READ) |
| `generate_document` | Выпуск PDF — **единственная запись** |

`validate_document` отдаёт ту же детерминированную проверку, которую выполняет генерация: незаполненные
обязательные поля, битые ссылки, ошибки расчётных полей, циклы. Агенту стоит цитировать её, а не
рассуждать о том, что с документом не так. `Error` блокирует выпуск, `Warning` нет.

**Однотипные проблемы приходят одной записью** (#597): `{severity, code, message, count, paths,
pathsTruncated}`. По реестру материалов вернулось 152 предупреждения, из которых 151 — дословно одна
фраза «Поле „Количество“: ожидается число, а хранится строка» с разными индексами, около 70 КБ; тем
временем потребитель первым делом сворачивал их обратно в одну строку. Адресов по умолчанию три на
группу, `pathsTruncated` говорит, что показаны не все, полный перечень — по `allPaths: true`.

Группируется по тройке (существенность, код, сообщение): один код носят проблемы с разным текстом
(«ожидается число» и «ожидается дата» — обе `value-type`), а разный текст требует разного разбора.

Только по одному документу: проверка прогоняет полный резолв с инъекцией наборов, и на комплекте в
десятки документов это риск таймаута — а частичный ответ был бы той самой тихой неполнотой.

Генерация синхронная (Typst отрабатывает за секунды, отдельного Job здесь нет). Ошибка резолва
возвращается диагностикой, а не голым отказом: агент должен знать, что чинить.

**Признака «PDF устарел» нет и не будет:** правка реквизитов вызывает `ResetToDraft()`, который удаляет
сгенерированные файлы и возвращает статус в `Draft`. Инвариант обеспечен, поле было бы всегда ложным.
Сравнивать `document.UpdatedAt` с `file.CreatedAt` тоже бесполезно — `AddGeneratedFile` дёргает
`TouchUpdatedAt()` после создания файла, так что документ всегда «новее» своего PDF.

Контекст в `get_document_set` не украшение: имена документов между разделами повторяются, и находка
без «чей это комплект» непроверяема.

### Две формы реквизитов (#421)

`get_document` по умолчанию **разворачивает ссылки**: организации и лица приходят данными, а не
идентификаторами, унаследованные через `_baseRef` поля подмешаны, коды перечислений заменены именами,
расчётные поля вычислены. Плюс ключ `уровень` — амбиентные данные стройки/раздела/комплекта. Это те же
реквизиты, что попадают в PDF. Поле `refsResolved` говорит, какую форму держит клиент.

`resolveRefs: false` отдаёт форму хранения со ссылками `{"$ref":"catalog","entryId":"…"}`. Она точнее
для сравнения тождества: сопоставить `entryId` надёжнее, чем строки имён. Оттуда же путь в каталог —
`entryId` есть идентификатор для `get_catalog_entry`.

**Наборы данных и документы качества в `get_document` НЕ подмешиваются.** Они вносят неограниченное
число строк, а форма ответа не выражает `truncated` — вышла бы ровно та тихая неполнота, от которой
защищает страничность `get_rows`. Табличные данные остаются за инструментами наборов.

### Один разворот на сущность (#594, #595)

Каждая запись каталога развёрнута **один раз** — в словаре `entities` ответа, а по месту стоит
`{"$entity":"<id>"}`. В титульном листе ЭОМ-1 карточка ООО «Инвест Строй» (наименование, ИНН/КПП/ОГРН,
СРО, юрадрес) присутствовала трижды побайтово — как заказчик, как организация подписанта и как
эмитент вложенного приказа; объект стройки повторялся там же тоже трижды. Побочная выгода важнее
экономии: тождество проверяется по идентификатору, а не сравнением карточек по значениям.

Реквизиты **других документов** не разворачиваются вовсе: на их месте `{"$document":"<id>",
"displayName":"…"}`. Поле `ОсновнойДокумент` в реестрах-приложениях несло полную копию акта со всеми
его организациями — именно так реестр работ доходил до 16 МБ. Нужна копия — `expandDocumentRefs:
true`.

Идентификатор развёрнутого берётся не из догадки о совпадении значений: резолвер по явной просьбе
(`keepRefProvenance`) помечает развёрнутый объект `_entryId` / `_instanceId`. Просит это только
внешнее чтение — в data.json шаблона и в сохранённых данных служебных ключей по-прежнему нет.

### Табличные поля документа (#591)

Строк в `get_document` нет, но **сами табличные поля видны** — `tableFields`: ключ, заголовок,
`boundToDataset`, `sourceId`, `datasetId`, `rowCount` (после фильтра источника). Раньше ключа
табличного поля в ответе не было вовсе, и «таблицы нет» было неотличимо от «таблица придёт из
набора»: агент прочитал отсутствие ключа «Материалы» как пустой реестр, хотя в нём 151 позиция, и
выпустил ошибочное замечание, а потом потратил контекст на его отзыв.

`boundToDataset: false` означает лишь «источника нет»: табличное поле заполняют и руками, и оно
наследуется от базового документа — тогда строки лежат прямо в реквизитах, и `rowCount` считается по
ним. `rowCount: null` — «сосчитать не удалось» (источник недоступен) либо «значения нет».

Это же поле служит обратной ссылкой **документ → источник**: без неё нечем понять, из какой из трёх
распознанных таблиц кабельного журнала собран документ.

Сломанная привязка чтение не роняет: `rowCount` останется пустым, остальной документ придёт. То же в
`get_source` — недоступный файл даёт `rowsError` вместо отказа, а метаданные и признак устаревания
читаются и без строк.

### Проекция полей (#596)

`get_document(documentId, fields: ["НомерДокумента","Подписи"])` отдаёт реквизиты только с этими
ключами верхнего уровня — почти каждый вызов делается ради двух-трёх полей.

Разбор при этом идёт **полный** и проецируется ответ, а не наоборот: расчётное поле читает соседние,
унаследованное приходит от базового документа, и «считать только запрошенное» вернуло бы другое
значение. Ответ несёт `projectedFields` (ответ неполон по просьбе — иначе тот же документ, прочитанный
дважды с разной проекцией, выглядит изменившимся) и `unknownFields` — запрошенные ключи, которых нет
в схеме: опечатка иначе неотличима от незаполненного поля.

### Повторная проверка без повторной выгрузки (#598)

Работа с комплектом итеративна — «поправил реестр, перепроверь», — и каждый повтор выгружал те же
данные заново: кабельный журнал за сессию выгружался целиком не менее четырёх раз при двух реальных
изменениях; из 113 связок менялась одна, а список запрашивался весь.

- `get_rows` отдаёт `pageHash` — отпечаток ЭТОЙ страницы; его и передают обратно в `ifNoneMatch` при
  повторном чтении той же страницы. Совпал — придёт `unchanged: true` без таблицы, остальные поля
  заполнены как обычно (чтобы «не изменилось» не пришлось отличать от «пусто»).
- `rowsHash` (он же в `get_source`) — сквозной отпечаток всех строк источника, отвечает на вопрос
  «менялись ли данные вообще». В `ifNoneMatch` он не годится: со сквозным отпечатком запрос
  СЛЕДУЮЩЕЙ страницы вернул бы «не изменилось» с пустыми строками, и обход «пока truncated» не
  двигался бы с места.
- `list_material_quality_links` и `list_quality_documents` принимают `changedSince`; каждая запись
  несёт `updatedAt`.

Что здесь **не** экономится: загрузка. Отпечаток без неё не посчитать, и обещать дешевизну, которой
нет, хуже, чем не обещать. Экономится контекст — он тут и есть дефицит.

Чего `changedSince` **не** показывает: удалений. Пропавшая связь не «изменилась», её замечает только
полное чтение — об этом сказано и в описании инструмента.

### Одноимённые наборы (#593)

Два набора «250701-ЭОМ-ЕЦДМ, ДНС-Сити_ИД» различались только уровнем и идентификатором. Уровень в
ответе был и раньше, но выбирают по имени, а не по UUID стройки — поэтому рядом с ним теперь
`scopeName`, наименование стройки/раздела/комплекта. У `System` контейнера нет, там `null`.

Запрещать одинаковые имена не стали: имя набора — дело пользователя, а неразличимость была свойством
ВЫДАЧИ, там её и починили.

### Сколько строк в источнике (#592)

`get_source` отдаёт **два** числа: `rowCount` — после обработки, ровно столько вернёт `get_rows` и
столько попадёт в документ; `rawRowCount` — сколько было до фильтра. Разницу объясняет `filtered`.
Прежде отдавалось одно число (кэш сырых строк), и на «Кабельном журнале (без ГРЩ)» оно показывало 48
против 44 в выборке, ничем о разнице не сообщая.

В сводке набора (`get_dataset`) точного числа нет намеренно: считать его на каждый источник значило
бы скачать и разобрать файл столько раз, сколько в нём листов, ради навигационной выдачи. Там
`rawRowCount` + `filtered` — признак того, что за точным числом надо сходить в `get_source`.

### Связи материалов (#423)

`list_material_quality_links` отдаёт **действующую** карту для комплекта — ту же цепочку
`Set → Section → Construction → System`, где узкий уровень побеждает, что применяет генерация. Сырой
выборки по одному уровню намеренно нет: перебирать четыре уровня и воспроизводить правило приоритета
значило бы просить агента повторить логику системы и рано или поздно разойтись с ней.

Каждая запись несёт **уровень, с которого связь пришла** — связь может быть заведена на System и
неожиданно действовать на конкретном комплекте.

Ключ материала — нормализованный артикул или наименование, тот же, что в строках наборов. Поэтому
расхождение «в реестре указан один сертификат, а привязан другой» находится сопоставлением этой карты
с `get_rows`.

> Список каталога идёт мимо `ListCommonDataEntriesQuery`: тот по пути дёргает `EnsureProfileAsync` и
> **создаёт** объект-профиль уровня. Чтение через MCP писать в БД не имеет права.

## Ресурсы

**Адресация по шаблону** (`resources/templates/list`): `bhs://dataset/{id}`, `bhs://source/{id}`,
`bhs://construction/{id}`, `bhs://document-set/{id}`, `bhs://document/{id}`, `bhs://document-type/{id}`,
`bhs://catalog-entry/{id}` — те же данные по URI.

**Витрина прикрепления** (`resources/list`, #427): реальные объекты под человеческими именами —
стройки, комплекты документов, наборы данных. Только шаблонов было недостаточно: клиент, показывающий
лишь `resources/list`, не видел ничего, и возможность «прикрепить объект к диалогу» в нём не
существовала. Шаблоном её и не покрыть — выбирают «Комплект 250701.ЭОМ-1» из списка, а не подставляют
UUID руками.

Отдельных документов, типов и записей каталога в витрине намеренно нет: документов сотни и они
достижимы из комплекта, типы это конфигурация, а записи каталога — то, на что ссылаются, а не то, что
прикрепляют. Усечения и курсора нет: перечисляемые единицы человек заводит руками, и молча обрезанный
список спрятал бы объекты от пользователя. Отсутствующий объект даёт ошибку, а не пустой JSON.

Внутри витрина дочитывает страничные выдачи до конца (`ReadAllAsync`): списки стали страничными все
без исключения (#590), а полнота витрины — обязательство перед пользователем, а не удобство.

Строки ресурсом не отдаются намеренно: они страничные, а ресурс не выражает «за этой страницей есть
ещё».

> Ресурсная функция обязана возвращать `ResourceContents` (хелпер `McpJsonResource.Json`). Произвольный
> POCO компилируется, но роняет чтение в рантайме — контракт закреплён `McpResourceContractTests`.

## Замечания анализа (#440)

| Инструмент | Назначение |
|---|---|
| `list_observations` | Ранее сообщённые замечания с их разбором |
| `report_observation` | Записать находку анализа в журнал — **запись** |

До этого находки агента жили только в переписке: память не копилась, отчёт не с чем было сравнить.

Замечание попадает в систему как **утверждение, требующее подтверждения человеком**, а не как
результат проверки. Подтвердить или отклонить через MCP нельзя намеренно: агент не подтверждает сам
себя — прямое следствие «предложить → подтвердить → персистить» из #414. Инструмента разбора нет, и
его отсутствие проверяется тестом.

Замечания живут отдельно от находок сверки. Находка — результат арифметики по спеке; замечание —
свободное утверждение. Смешать их значило бы пустить модель в путь сравнения и получить «прыгающий»
от прогона к прогону отчёт.

**Ключ и ссылки обязательны.** Ключ строится из существа утверждения, а не из номера строки: повторный
анализ с тем же ключом обновляет запись, а нестабильный забьёт журнал дублями — тот же урок, что и с
ключом находки сверки. Ссылки нужны, чтобы человек проверил утверждение глазами: без адреса это
мнение, а не находка.

Разбор человека переживает повторный анализ: отклонённое замечание не возвращается в работу, а
`reviewNote` объясняет агенту, почему это не ошибка.

## Сверка (#448)

| Инструмент | Назначение |
|---|---|
| `list_reconciliations` | Настроенные сверки — точка входа |
| `get_reconciliation_findings` | Находки последнего прогона с ключами позиций |
| `list_aliases` | Заведённые соответствия позиций с разбором |
| `propose_alias` | Предложить, что две позиции — одно и то же — **запись** |

Находки — результат **арифметики** системы, а не оценка: их цитируют как есть. Несопоставленные
позиции (`MissingLeft` / `MissingRight`) и есть кандидаты на связывание.

`propose_alias` создаёт **предложение**. На сверку оно не влияет, пока человек не подтвердит, и
подтвердить его агент не может — такого инструмента нет. Неподтверждённый алиас в пути сравнения
означал бы модель внутри арифметики и «прыгающий» от прогона к прогону отчёт (риск P1 в #414).

Ключи берутся **из находок**: они нормализованные, и написанные от руки не совпадут ни с чем.

Отклонённое предложение агент видит в `list_aliases` — это ответ человека, а не повод повторить.

## Промпты (#429)

| Промпт | Параметр | Назначение |
|---|---|---|
| `reconcile_document_set` | комплект | Сверка на внутреннюю непротиворечивость с отчётом |
| `check_set_readiness` | комплект | Что мешает выпуску: обход `validate_document` по документам |

Принцип тот же, что у профилей распознавания (#405): **промпты пишем мы, пользователь задаёт
параметр**. Здесь параметр ровно один — комплект; его имя, раздел и стройка подставляются в текст,
иначе агент начинает с уточняющих вопросов вместо работы.

Содержимое — доменное знание о том, что в исполнительной документации значит «непротиворечивость»
(организации и подписанты, номера и даты, материалы против сертификатов, реестры против состава
комплекта), плюс правила, без которых отчёт становится вредным: проверять `truncated`, различать
`Parsed` и `Recognized`, учитывать `stale`, адресовать каждую находку и не выдавать отсутствие данных
за нарушение.

Правила одинаковы в обоих промптах и закреплены тестом: разойдись они — один отчёт был бы аккуратен,
а другой выдумывал при внешне одинаковой постановке задачи.

## Что в ответах критично для корректности

1. **`truncated`** — выборка страничная. Пока `truncated: true`, данные получены НЕ полностью;
   анализ по неполным данным даст неверный результат (потерянные позиции выглядят как отсутствующие).
   Всегда сверять `totalRows` (у строк) или `total` (у списков) с числом полученных записей.

   Страничны **все** `list_*` и `get_rows` / `get_reconciliation_findings`. Форма одна —
   `items` / `offset` / `limit` / `total` / `truncated`, — чтобы способ листать был один. Состав
   детали (разделы стройки, документы комплекта) оболочки не получает: это поле объекта, а не
   отдельная выдача.
2. **`stale` + `staleReason`** — данные могли устареть относительно текущего содержимого файла
   (файл заменён, границы документа изменились после распознавания таблицы).
3. **`origin`** — `Parsed` (детерминированный разбор XML/CSV/XLSX) против `Recognized` (извлечено
   vision-LLM, вероятностные данные). Существенно, если по правилам проекта первоисточником считается
   XML, а PDF/DOCX — производные.

Плюс `sheet` у табличных источников из PDF — шифр, наименование и номера страниц исходного документа,
чтобы найденное расхождение можно было проверить глазами по чертежу.

## Версия контракта (#590)

Каждая страничная выдача несёт `contractVersion` — целое, сегодня `6`. Клиент сравнивает его с тем,
под который написан: смена формы становится заметной сразу, а не через неверный отчёт.

| Версия | Что изменилось |
|---|---|
| 1 | Единая оболочка списков `{items, offset, limit, total, truncated}` у всех `list_*` |
| 2 | У источника вместо одного `rowCount` — `rawRowCount` / `rowCount` / `filtered` (#592) |
| 3 | `validate_document` отдаёт диагностики группами, у элемента больше нет `path` (#597) |
| 4 | Записи каталога — в словаре `entities`, чужие документы — ссылкой (#594, #595) |
| 5 | `scopeName` у наборов, `rowsHash`/`unchanged` у строк, `updatedAt` у качества (#593, #598) |
| 6 | `ifNoneMatch` сверяется с `pageHash` страницы; `rowCount`/`rowsHash` источника необязательны, рядом `rowsError` |

Номер один на весь контракт, а не на каждую выдачу: возить его в ответе про одну сущность значило бы
платить за поле там, где оно не нужно, а списки агент вызывает в любом сценарии.

Номер поднимается, когда прежний клиент разберёт ответ НЕПРАВИЛЬНО — поле переименовано, убрано или
сменило смысл. Добавление нового поля версию не двигает: читатель прежних полей его не заметит.

Понадобилось это после регрессии #577: часть списков переехала на страницы, часть осталась голыми
массивами. Клиент, написанный под массив, получал объект и молча видел ноль записей — ни ошибки, ни
признака. Поймал это живьём внешний агент, не тест, поэтому теперь единую форму держит
`McpToolContractTests.EveryListTool_ReturnsPage`: правило проверяется по имени инструмента, а не по
списку, который ведут руками, — забытая строчка в списке и была способом внести регрессию.

## Адресация значения

`(sourceId, offset + позиция строки в массиве, имя колонки)`. Порядок строк стабилен, поэтому ссылаться
на конкретную ячейку можно без дополнительных метаданных — их намеренно не добавляли, чтобы не
фиксировать форму находки раньше, чем появится подсистема сверки.

## Архитектура

Тонкий адаптер над `IDataSnapshotService` и `IDomainSnapshotService` — ноль доменной логики в MCP-слое, ровно как в
Minimal-API эндпоинтах. HTTP-API и MCP остаются двумя адаптерами над одним ядром и не расходятся.
Хостится в процессе API (общая аутентификация, DI, scoping DbContext).

### Кодировка ответов (#576)

Кодировщик задаётся явно (`McpSerialization`) и передаётся каждой регистрации инструментов в
`Program.cs`. По умолчанию `System.Text.Json` экранирует всё не-ASCII, то есть каждую букву русского
домена — шесть символов вместо одного. На живом вызове `list_quality_documents` это давало ответ в
139 446 символов при 37 тысячах символов данных: 88 % веса приходилось на `\uXXXX`, и клиент
отказывался его принимать. Взят `UnicodeRanges.All`, а не `UnsafeRelaxedJsonEscaping`: кириллица
проходит как есть, `<`, `>`, `&` остаются экранированными.

Новый инструмент получает это правило только вместе с регистрацией — забытый кодировщик проявится
не ошибкой, а вчетверо распухшим ответом на реальных данных.
